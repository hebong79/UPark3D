## 1. 배경 — 왜 화각을 config로 빼는가

직전 작업(`20260806_221552`)에서 `DefaultHFov`를 58°→56.5°로 정정했지만, `MaxZoom`(배율 상한)은 이미 `config_pmaker.json`의 최상위 `max_zoom` 키로 설정 가능한 반면 화각은 여전히 C++ 상수로 남아 있었다.

문제는 이 두 값이 **모델별로 함께 결정되는 한 쌍**이라는 데 있다 — 휴컴스 HNR-2036LA는 `56.5° + x36`, HNR-2030WA는 `58.9° + x30`이다. 구조가 갈라져 있으면 "config의 `max_zoom: 36`"과 "코드의 `DefaultHFov: 58`"이 서로 다른 모델을 가리키는 상태가 아무 경고 없이 성립할 수 있고, 그것이 바로 직전 작업에서 정정한 `58° + 36x` 불일치 사고의 원인이었다. 이번 변경의 본질은 "화각을 설정 가능하게 한다"가 아니라 **"광학 규격 한 벌을 한 곳에 모은다"**이다.

## 3. 스키마와 파싱 우선순위

### 3.1 확정 스키마

```json
{
    "rpc_port": 13510,
    "preset_file": "001_Preset_office.json",
    "carpos_file": "CarPos_office.json",
    "camerapos_file": "CamPos_office.json",
    "camera": {
        "model": "HNR-2036LA",
        "hfov_wide": 56.5,
        "max_zoom": 36.0
    },
    "cam_port_min": 13601,
    "cam_port_max": 13650
}
```

`hfov_wide`는 **수평** 화각(도)이다. 수직 화각은 별도 키로 두지 않는다 — `USceneCaptureComponent2D::FOVAngle`이 이미 수평이고, 수직은 `2·atan(tan(H/2)·9/16)`로 결정되는 파생값이라 두 개를 따로 저장하면 어긋날 여지만 생긴다. 최상위 `max_zoom`은 하위 호환으로 계속 읽히되 `camera.max_zoom`이 있으면 그것이 우선한다. `camera.model`은 **어떤 계산에도 쓰이지 않는다** — 어느 장비 기준 데이터인지 로그로 추적하기 위한 라벨일 뿐이다.

### 3.2 파싱 우선순위 표 (요구된 5가지 경우)

| # | config 내용 | `MaxZoom` | `CameraHFovWide` | `CameraModel` | 반환 |
|---|---|---|---|---|---|
| ① | `camera`만 있음 | 36.0(camera) | 56.5 | `"HNR-2036LA"` | true |
| ② | 최상위 `max_zoom`만 있음(기존 파일) | 36.0(최상위) | 0(미지정) | `""`(미지정) | true |
| ③ | 둘 다 있음(값이 다름) | **camera 값**(우선) | camera 값 | camera 값 | true |
| ④ | `camera`에 `hfov_wide`만 | 최상위 값 생존 | camera 값 | `""` | true |
| ⑤ | `camera`가 오브젝트가 아님(예: 문자열) | 최상위 규칙만 적용 | 0 | `""` | **true + Warning** |

핵심 규칙: ① `camera` 안 세 키는 서로를 요구하지 않는(독립 적용) 값이다 — `hfov_wide`만 있어도 그것만 적용된다. ② `cam_port_min/max`의 "둘 다 있어야 적용" 규칙은 여기 적용하지 않는다 — 포트 대역은 min·max가 함께 있어야 의미를 갖는 한 쌍이지만, `hfov_wide`와 `max_zoom`은 각자 독립적으로 의미가 완결되는 스칼라다. ③ 잘못된 타입은 파싱 실패가 아니다 — `FromJson`이 `false`를 돌려주는 경우는 지금도 앞으로도 JSON 자체가 깨진 경우뿐이며, `camera` 타입 오류는 "이 항목만 못 읽음"이라 나머지 항목(프리셋·카메라위치·차량배치 자동 로딩)까지 죽여서는 안 된다.

## 4. 검증 규칙

- **채택 범위: `0 < hfov < 180`(배타)**. 벗어나면 적용하지 않고 기존값을 유지하며 Warning을 남긴다.
- **검증 위치: 적용 함수(`SetCameraDefaultHFov`)에서 판정**한다. `FromJson`은 원본 값을 그대로 담아 넘긴다(`max_zoom` 선례를 따름). `rpc_port`처럼 파싱 단계에서 0으로 뭉개면 "왜 무시됐는지"를 로그가 말할 수 없기 때문이다.
- **라이브러리 내부 클램프와 중복이 아니다.** `TanHalfFovDeg`는 입력을 `(0.001°, 179.999°)`로 선클램프해 수학을 유한하게 유지하는 최후 방어선이고, config 단 검증은 사람이 적은 설정을 수용/거부 판정하고 그 판정을 로그로 남기는 별개 계층이다. `hfov_wide: 200`을 라이브러리 클램프에만 맡기면 `179.999`로 조용히 적용돼 화면이 거의 반구를 담는 극단 광각이 되는데, config 단 검증이 있으면 적용을 거부하고 원래 화각을 유지한다.
- 거부 시 되돌아가는 값은 **CDO 기본값이 아니라 직전 유효값**이다(예: 45를 적용한 뒤 200을 적으면 45가 유지된다).

## 5. 적용 경로 — 재적용 3단이 필요한 이유

### 5.1 처리 흐름

```
config_pmaker.json (도)
   └─ FromJson            → FPark3DAppConfig.CameraHFovWide (도, 0=미지정)
        └─ ApplyStartupConfig (>0 게이트, Menu 캐스트 이전)
             └─ ACameraControlManager::SetCameraDefaultHFov ((0,180) 검증)
                  ├─ CameraDefaultHFov 갱신                     ← 이후 AddCamera 가 주입
                  └─ 기존 카메라 루프: GetZoom → DefaultHFov 갱신 → SetZoom
                       └─ APTZCameraActor::SetZoom
                            └─ UCameraControlLibrary::ZoomToHFov(Zoom, MaxZoom, DefaultHFov)
                                 └─ TanHalfFovDeg 클램프 (0.001,179.999)  ← 최후 방어선
                                      └─ Capture->FOVAngle (도)
```

### 5.2 재적용 3단 — 이번 구현의 핵심

```cpp
const float Zoom = Cam->GetZoom();      // ① 필드 대입 '전에' 옛 화각 기준으로 현재 배율을 읽는다
Cam->DefaultHFov = CameraDefaultHFov;   // ②
Cam->SetZoom(Zoom);                     // ③ 새 화각 기준으로 FOVAngle 재계산
```

**왜 필요한가**: `APTZCameraActor::Capture->FOVAngle`은 **생성자에서 한 번**, 그리고 **`SetZoom`이 불릴 때만** 갱신된다. `DefaultHFov` 필드만 바꾸면 화면은 그대로다. 그리고 `Park3DGameMode::BeginPlay`의 순서는 `EnsureDefaultCamera`(카메라 #0 스폰, 옛 화각으로 굳음) → `ShowCameraViewer` → `ApplyStartupConfig`(config를 여기서 처음 읽음) 순이라, config를 읽는 시점에는 이미 카메라 1대가 옛 화각으로 존재한다. 재적용이 없으면:

- `camerapos_file`이 지정된 config → `SyncCamerasToData` → `ApplyDir` → `SetZoom`이 **우연히** 화각을 고쳐준다.
- `camerapos_file`이 **비어 있는** config → 아무도 `SetZoom`을 부르지 않는다 → **화각 설정이 조용히 안 먹는다.**

"어떤 config 조합에서는 먹고 어떤 조합에서는 안 먹는다"는 진단이 가장 어려운 부류의 버그다. 재적용으로 이 의존을 끊었다.

**순서가 중요한 이유**: `GetZoom()`을 새 `DefaultHFov` 대입 **이전에** 읽어야 원래 줌이 보존된다. 순서를 뒤집으면(먼저 `DefaultHFov`를 갱신하고 `GetZoom()`) 새 화각으로 옛 `FOVAngle`을 역산하게 되어 배율이 오염된다.

## 6. 기각한 대안 — 라이브러리 기본 인자는 코드 상수로 유지

`ZoomToHFov(Zoom, MaxZoom=36.f, DefaultHFov=56.5f)`와 `HFovToZoom(...)`의 기본 인자는 config를 반영하도록 바꾸지 **않았다.**

1. **CDO 일치 단정이 무의미해진다.** `CamCdo->DefaultHFov == ZoomToHFov(1.f)` 단정은 "상수 3중 중복 중 한쪽만 고치면 즉시 실패"하도록 봉인한 장치다. 오른쪽이 런타임 config를 따르면 "config와 CDO가 같은가"라는 전혀 다른 명제로 바뀌어 원래 잡으려던 회귀를 못 잡는다.
2. **절대값 테스트 다수가 재현 불가능해진다.** `zoom1→56.500` 같은 단정이 전부 "그 순간 디스크의 config 파일"에 의존하게 된다.
3. **기술적으로 성립하지 않는다.** UFUNCTION 기본 인자는 `.generated.h`에 리터럴로 구워지는 컴파일 타임 상수라 런타임 값을 넣을 수 없다.
4. **순수함수 계약이 곧 테스트 가능성의 근거다.** `UCameraControlLibrary`는 월드·설정에 의존하지 않아 PIE 없이 전량 유닛테스트가 가능하다. 여기에 config 의존을 넣으면 이 성질이 사라진다.

그 결과 **"액터 인스턴스를 경유하는 모든 경로는 config를 따르고, 라이브러리 무인자 호출·CDO·직접 스폰 액터는 코드 상수(56.5)를 따른다"**는 의도된 비대칭이 생긴다. 현재 게임 코드에서 라이브러리를 무인자로 직접 호출하는 지점은 0건(테스트만 사용)이며, Automation `OpticsIsolation`(X-1, X-2)이 이 두 경로가 실제로 갈라지는 것을 실증했다.

그 밖에 기각한 대안:

| 대안 | 판정 | 이유 |
|---|---|---|
| 검증 없이 라이브러리 클램프에만 위임 | 기각 | `200`이 `179.999`로 적용돼 화면이 망가지는데 경고가 없다 |
| `EnsureDefaultCamera()`를 `ApplyStartupConfig()` 뒤로 옮김 | 기각 | 기존 GameMode 순서에 "뷰어보다 먼저 만들어 첫 틱에 RT가 잡히게 한다"는 명시된 이유가 있다. 요청과 무관한 초기화 순서 변경 |
| `APTZCameraActor::DefaultHFov`를 setter로 감싸 자동 재적용 | 기각 | `UPROPERTY` 직접 대입 경로(에디터·블루프린트)가 남아 setter를 우회할 수 있고, 액터 API 확장은 요청 범위 밖 |
| config 파일의 최상위 `max_zoom` 유지(중복) | 기각 | 두 값이 어긋난 채 방치되는 상태를 상시화한다 — 정확히 이번 작업이 없애려는 사고 형태 |

## 8. 이번 작업에서 잡힌 결함 2건의 경위

### F-1 — QA의 첫 E-C가 판별력 없는 값을 써서 잘못된 결론을 냈다

QA가 처음 재적용 검증(E-C)을 할 때 `hfov_wide: 45`를 썼다. 45는 기본값(56.5)보다 **좁은** 값인데, `HFovToZoom(HFov, MaxZoom, DefaultHFov) = tan(DefaultHFov/2)/tan(HFov/2)`(결과는 `[1, MaxZoom]`로 클램프)에서 재적용이 빠진 결함 시나리오의 값은 `tan(22.5°)/tan(28.25°) ≈ 0.771`이 되어 **하한 클램프에 걸려 1.0으로 뭉개진다.** 즉 정상 구현(1.0)과 결함 구현(0.771→클램프 1.0)이 **같은 값**을 낸다 — 이 실측만으로는 재적용 여부를 구분할 수 없었는데도, 원래 QA는 이를 "1.304로 반증했다"고 잘못 기록했다(사후 영향도가 지적: 그 1.304라는 숫자 자체가 다른 시나리오(`DefaultHFov=70`)의 계산값을 45 케이스에 잘못 전용한 계산 오류였다).

사후 영향도가 이 오류를 발견해 F-1로 등급 "높음"(코드 결함이 아니라 **근거 기록의 오류**라서 높음)으로 지정했고, QA가 `hfov_wide: 70`(기본값보다 **넓은** 값)으로 재검증(E-C′)해 확증했다. 70에서는 결함 시나리오 값이 `tan(35°)/tan(28.25°) ≈ 1.3031`로 클램프 범위 안에 들어와 정상값(1.0)과 명확히 구분된다.

**교훈: 클램프가 걸리는 방향으로 검증하면 증거가 지워진다.** 범위 제한(클램프, 상한/하한, 포화)이 있는 함수를 반증 실험으로 검증할 때는 "정상과 결함이 클램프 밖에서 서로 다른 값을 내는" 방향을 골라야 판별력이 생긴다.

### F-2 — 신규 테스트가 스스로 자기 전제를 만들어 결함을 비껴갔다

`ACameraControlManager::AddCamera`는 `Cam->DefaultHFov = CameraDefaultHFov;`로 **필드만 대입**했다. `APTZCameraActor` 생성자가 `Capture->FOVAngle`을 CDO 기본값(56.5)으로 이미 굳혀 놓았으므로, `AddCamera`를 마친 직후 카메라는 `DefaultHFov=신규값`인데 `FOVAngle=56.5`인 스테일 상태가 된다. `AddCamera` 호출부 6곳 중 5곳(`EnsureDefaultCamera`, `SyncCamerasToData`, UI 카메라 추가 3곳)은 직후 `SetZoom`을 다시 호출해 이 스테일이 우연히 씻기지만, **RPC `cam.create` 한 곳만 그렇지 않아** 이 경로로 만든 카메라만 화각이 안 먹었다.

이 결함을 신규 유닛테스트(`ManagerOptics` A-1)가 애초에 놓친 이유는, A-1이 `FOVAngle`을 단정하기 **전에 스스로 `SetZoom(1.f)`을 호출**해 구멍을 정확히 우회했기 때문이다. 사후 영향도가 이를 지적해 `AddCamera`에 `SetZoom(1.f)` 1줄을 추가하고, 그 우회를 제거한 신규 단정(A-1b — `SetZoom` 호출 없이 `FOVAngle`을 바로 확인)으로 재검증했다.

**교훈: 테스트가 자기 전제를 만들면 결함을 가린다.** 어떤 함수의 부작용(여기서는 `FOVAngle` 갱신)을 검증하는 테스트가, 검증 직전에 그 부작용을 유발하는 다른 호출을 자기 손으로 먼저 하면, 실제로 검증하는 것은 그 다른 호출이지 대상 함수가 아니게 된다.

## 9. 잔여 위험과 재패키징 체크리스트

### M-1. 스키마 이원화 — 패키지 config는 의도적 무변경

`Package/Windows/Save/Config/config_pmaker.json`은 이번 작업에서 건드리지 않았다. 패키지 exe는 이번 변경이 없는 구 바이너리라(바이너리 UTF-16 문자열 프로브로 `hfov_wide` 부재를 확정) `camera` 오브젝트를 모른다. 여기서 최상위 `max_zoom`을 지우면 패키지가 배율 설정을 잃는다(미지정 폴백). 아무 이득 없이 산출물을 열화시키는 변경이므로 재패키징 시점의 과제로 넘긴다. 지금은 값이 같아(56.5/36) 무증상이며, `hfov_wide`를 56.5 이외로 바꿔 시연할 때만 "에디터는 바뀌는데 exe는 안 바뀐다"로 드러난다.

### M-2. RPC 13510 = 패키지 exe(PID 27228) — MCP 브리지로 검증하면 조용히 실패한다

현재 13510 포트를 리슨하는 프로세스는 **패키지 exe(PID 27228)**다. `park3d-rpc` MCP 브리지는 `.mcp.json`에서 13510에 고정돼 있다. 다음 작업자가 이 기능을 브리지로 검증하려 하면, 패키지 exe에는 `camera.hfov_wide`를 읽는 코드 자체가 없으므로 **에러 없이 "안 먹는다"만 관측된다.** 검증 전 반드시 `Get-NetTCPConnection -LocalPort 13510`의 `OwningProcess`를 확인할 것(메모리 [인스턴스 2개면 RPC가 엉뚱한 쪽으로]의 실사례).

### R-3. zoom 의미 혼재 — 1회성에서 상시로 바뀌었다

`CamPos_*.json`의 `zoom`은 실장비 PTZ 명령값이고, 같은 zoom 값이 만드는 화각은 `camera.hfov_wide`에 따라 달라진다. 직전 작업(58→56.5 정정)에서 이 위험은 **1회성**이었다 — 정정 시점 전후로 파일을 구분하면 됐다. 이번 변경 이후에는 **`config_pmaker.json`을 편집하는 것만으로 언제든, 누구든, 아무 흔적 없이 기준 화각을 바꿀 수 있는 상시 위험**이 됐다. 시작 로그(`[Config] 카메라 광학 규격: model=... hfov_wide=... max_zoom=...`)가 매 기동 1줄 남지만, 이는 **사후 추적 가능성일 뿐 데이터에 각인되지 않는다** — `CamPos_*.json`은 자기 화각 기준을 여전히 모르고, 로그는 `Saved/Logs/`(순환 삭제 대상)에 남으며 데이터 파일과 연결하는 것은 사람의 규율뿐이다. 근본 해결(`FCameraPosList`에 화각/버전 필드 추가)은 Unity 원본 스키마 권위를 침해해 기각했다(메모리 [Unity 원본이 스키마 권위]).

### 재패키징 체크리스트 요약

재패키징 시 다음을 순서대로 수행할 것(전체 11항목은 `_workspace/camera_config_hfov_impact_post.md` §4-5 참조):

1. 실행 중 패키지 인스턴스 종료, 13510·13601 포트 해제 확인
2. 변경 소스 mtime이 마지막 패키지 exe보다 뒤인지 확인(복사 파일은 mtime이 옛것이라 UBT가 조용히 스킵 — 메모리 [Copy-Item 타임스탬프 보존])
3. `RunUAT BuildCookRun` 실행 — exit 0을 믿지 말고 로그로 실패 판정
4. 산출물 타임스탬프 확인
5. **[필수]** 새 exe에 UTF-16 `hfov_wide` 문자열이 존재하는지 바이너리로 확증
6. 5번이 확인된 뒤에만 패키지 config를 신 스키마로 교체
7. 두 config의 `camera` 키 존재 여부 일치 확인
8. 패키지 `Save/3D/` 데이터 동기화 여부 판단(R-3 두 벌 분화 방지)
9. 기동 후 로그에 광학 규격 1줄이 남는지 확인
10. §3-5(설계 §5.4)의 `hfov_wide: 70` 절차를 패키지에서도 1회 수행
11. RPC 포트 정리 — 재기동 후 13510의 `OwningProcess`를 반드시 확인·기록

## 12. 결론

`config_pmaker.json`에 `camera.hfov_wide` 설정 경로를 새로 만들었다. 이번 작업 자체는 값이 코드 기본값과 동일해 화면에 아무 변화가 없지만(S6, 안전판), 앞으로 `hfov_wide`를 56.5 이외로, 또는 `camera.max_zoom`을 36 이외로 바꾸는 순간부터 M-1(패키지 이원화)·M-2(RPC 오인)·R-3(zoom 의미 혼재 상시화)가 동시에 깨어난다. 이 세 가지는 기능 결함이 아니라 **이 기능을 실제로 쓰기 시작할 때 반드시 마주치게 되는 운영상의 함정**이므로, 다음 작업자는 §9를 먼저 읽을 것을 권한다.

이번 작업에서 F-1(검증 산술 오류)·F-2(스폰 경로 재적용 누락) 두 결함이 발견·수정·재검증됐고, 둘 다 "검증 자체가 대상을 놓치는 방식"이었다는 공통점이 있다(§8). 유사한 재적용/클램프 로직을 검증할 때 참고할 가치가 있다.
