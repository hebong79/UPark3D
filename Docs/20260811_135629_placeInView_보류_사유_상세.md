# `random.placeInView` 를 왜 보류했는가 — 상세

- 작성일: 2026-08-11
- 질문: "`random.placeInView`는 보류(요청대로). 사유 메시지만 정확하게 갱신했습니다: PTZ 뷰포트 배치 게이트 미이식 — 이 부분을 자세히 설명해줘."
- 관련 문서: `Docs/20260811_133654_RPC_미구현_메서드_구현.md` §4.7

---

## 0. 한 줄 요약

`placeInView` 는 "차량을 랜덤 위치에 놓는다"가 아니라 **"번호판이 카메라에 또렷하게 보이는 위치만 골라서 놓는다"** 는 기능이다. 그 판정을 하는 8개의 게이트 중 **2개는 원본 소스가 이 저장소에 없고**, **2개는 UE 포트에 아예 없는 인프라(PTZ 카메라 기준 화면 투영)를 새로 깔아야 하며**, **1개는 현재 맵 설정(바닥 콜리전 없음)에서 그대로 옮기면 전량 실패**한다.

---

## 1. 이 메서드가 하려는 일

`random.slotPlace` 와 목적이 다르다.

| | `random.slotPlace` | `random.placeInView` |
|---|---|---|
| 어디에 놓나 | 프리셋이 정의한 **주차면 위** | 카메라 **화면 안 아무 지면** |
| 위치 결정 | 결정적(슬롯 중심 + 지터) | 탐색적(후보를 뽑아 검사, 실패하면 재시도) |
| 목적 | 주차장 장면 구성 | **번호판 인식 학습/검증 이미지 생성** |
| 실패 개념 | 없음(슬롯 수만큼 배치) | 있음(`maxRetry` 안에 조건 만족 못 하면 그 대수는 포기) |

Unity 원본 `CPtzSpaceVehiclePlacer.PlaceVehicles()` 의 클래스 주석이 조건을 명시한다:

> 배치 조건 (모두 만족해야 스폰):
> (1) 현재 카메라 뷰 안 — ViewportPointToRay 기반 랜덤 샘플링으로 보장
> (2) 주차장 맵 콜라이더 위 — Physics.Raycast 하방 검증
> (3) 기존 차량과 겹치지 않음 — XZ 최소 거리 검사
> (4) 신규 차량 번호판이 카메라에서 보임 — 번호판 면적 다중 지점(코너4+중심) 샘플링 레이캐스트
> (5) 기존 차량 번호판을 가리지 않음 — 동일 다중 지점 샘플링 시선 재검증
> (6) 화면 2D 박스 겹침 방지 — 월드 AABB 8코너 투영 후 Rect 겹침 비율 임계 검사

여기에 코드 본문이 **줌 관련 검사 2개를 더** 얹는다(주석에 ①, ⑥ 으로 표기되어 헷갈린다):

- **거리 상한** — `zoom = DMAX_ZOOM` 이 되는 카메라↔번호판 임계 거리를 역산해, 그보다 먼 후보는 버린다.
- **줌 포화 최종 게이트** — 스폰 후 실제 번호판으로 목표 PTZ 를 계산해, 필요한 zoom 이 `DMAX_ZOOM` 이상이면(= 최대 줌으로도 번호판이 충분히 크게 안 잡히면) 버리고 재샘플.

그리고 샘플링 자체도 균등이 아니다. `SampleDistanceUniformV()` 는 뷰포트 세로 좌표 `v` 를 그냥 랜덤으로 뽑지 않고, **카메라↔지면 거리가 균등 분포하도록** 이분탐색 16회로 역산한다. 원근 때문에 화면 위쪽(원거리)에 후보가 몰리는 편향을 제거하기 위해서다.

즉 이 메서드는 "랜덤 배치"가 아니라 **작은 광학 시뮬레이션**이다.

## 2. 게이트별 이식 가능성 — 실제로 확인한 것

### 2.1 ❌ 거리 상한 + 줌 포화 — **원본 소스가 이 저장소에 없다**

두 검사 모두 `CLicensePlateFocusCapture` 에 의존한다.

```csharp
// CPtzSpaceVehiclePlacer.cs:513-522
private static float CalcPlateZoomThresholdDist(float dmaxZoom, float aspect)
{
    float hFovAtMax   = CObjCamera.ZoomToHFov(dmaxZoom);
    float tanHalfHFov = Mathf.Tan(hFovAtMax * 0.5f * Mathf.Deg2Rad);
    float dist = CLicensePlateFocusCapture.CKoreanPlateStandardWidth
               / (2f * tanHalfHFov * CLicensePlateFocusCapture.CDefaultTargetScreenRatio);
    return dist;
}
```

```csharp
// CPtzSpaceVehiclePlacer.cs:201-216
if (CLicensePlateFocusCapture.CalcTargetPTZ(
        cam, car, useFrontPlate: true, out _, out _, out float fFovActual))
{
    float rawPlateZoom = fFovActual > 0f ? cam.ZoomFromFov(fFovActual) : cam.DMAX_ZOOM;
    if (rawPlateZoom >= cam.DMAX_ZOOM) { /* reject */ }
}
```

필요한 것: 상수 `CKoreanPlateStandardWidth`, `CDefaultTargetScreenRatio` 와 함수 `CalcVerticalFOV`, `CalcTargetPTZ`.

**확인 결과 — `unity/` 폴더에 이 파일이 없다.**

```
$ find unity -iname "*LicensePlate*" -o -iname "*PlateFocus*"
(결과 없음)

$ grep -rl "CLicensePlateFocusCapture" . --include=*.cs
./unity/_MoveTmp/CPtzRandomCameraPlacer.cs
./unity/_MoveTmp/CPtzSpaceVehiclePlacer.cs
./unity/_MoveTmp/CVlaPSImgMakerGameUI.cs
./unity/_MoveTmp/CVlmPSimGameUI.cs
```

**4개 파일이 참조하는데 정작 정의 파일만 없다.** `unity/` 에 있는 C# 은 55개인데 그중 이 클래스는 빠져 있다.

상수는 추측할 수 있다(한국 번호판 표준 폭 520mm 는 공개 규격이고, `ACarActor` 의 번호판 프레임 주석에도 "검정 520×110 비율"이라고 적혀 있다). 하지만 `CDefaultTargetScreenRatio`(번호판이 화면에서 차지해야 할 목표 비율)와 `CalcTargetPTZ` 의 정확한 계산 경로는 **추측하면 배치 결과가 조용히 달라진다.** 거리 상한이 20m 인지 60m 인지에 따라 배치 가능 영역이 완전히 바뀌는데, 결과 이미지만 봐서는 "원본과 다르다"를 알아챌 수 없다.

> 메모리 규약 `unity-source-is-schema-authority` 와 같은 함정이다. 데이터 표본으로 규약을 추론하다 prefabId 회귀를 낸 전례가 있다.

### 2.2 ⚠ 뷰 안 샘플링 + 화면 2D 박스 겹침 — **PTZ 카메라 기준 투영이 UE 포트에 없다**

Unity 는 `Camera` 컴포넌트가 `ViewportPointToRay` / `WorldToScreenPoint` / `CalculateFrustumCorners` 를 전부 제공한다. UE 포트의 PTZ 카메라는 **`USceneCaptureComponent2D`** 라서 그런 API 가 없다.

기존 `view.pick` 은 못 쓴다 — 그건 **메인 뷰포트**용이고 `APlayerController::DeprojectScreenPositionToWorld` 에 의존한다(`ViewRpcModule.cpp:22-35`, `GetViewController`). PTZ 카메라에는 PlayerController 가 붙어 있지 않다.

```
$ grep -rn "WorldToScreen|ProjectWorldToScreen|CalculateFrustum" Park3D/Source/Park3D/
(결과 없음)
```

새로 깔아야 하는 것:

```cpp
FMinimalViewInfo View;
View.Location    = Cam->Capture->GetComponentLocation();
View.Rotation    = Cam->Capture->GetComponentRotation();
View.FOV         = Cam->Capture->FOVAngle;              // 수평 화각
View.AspectRatio = (float)RT->SizeX / (float)RT->SizeY;
FMatrix ViewMat, ProjMat, VPMat;
UGameplayStatics::CalculateViewProjectionMatricesFromMinimalView(View, nullptr, ViewMat, ProjMat, VPMat);
// 월드→화면: FSceneView::ProjectWorldToScreen(P, FIntRect(0,0,W,H), VPMat, OutPixel)
// 화면→월드: VPMat 역행렬로 언프로젝트 → 지면(Z=0) 교점
```

**가능은 하다.** 다만 이건 새 인프라이고, 부호·종횡비·수평/수직 FOV 변환에서 틀리기 쉽다. 이 프로젝트는 이미 화각 규약에서 한 번 데인 이력이 있다(`ZoomToHFov` 주석의 "UE 는 이미 수평 화각이라 aspect 변환 불필요" 경고, 실장비 56.5° vs 코드 58° 정정). 검증 없이 넣으면 조용히 어긋난다.

### 2.3 ❌ 지면 검증 — **현재 맵은 바닥에 콜리전이 없다**

Unity 게이트 (2) 는 후보 지점 위 50m 에서 하방 레이캐스트를 쏴 주차장 콜라이더를 확인한다.

```
$ grep -n "Collision" Park3D/Source/Park3D/Map/MapFloorActor.cpp
46:    FloorMesh->SetCollisionEnabled(ECollisionEnabled::NoCollision);
```

**바닥이 `NoCollision` 이다.** 이 게이트를 그대로 옮기면 `IsOnParkingLot()` 이 항상 false → 후보 전량 reject → **배치 0대**. 로그만 보면 "왜 0대인지" 알기 어렵다(Unity 원본이 진단 카운터를 넣어 둔 이유가 정확히 이것이다).

**단, 이건 우회로가 있다.** Unity 도 콜라이더가 없을 때를 대비해 `boxMin`/`boxMax` 사각 박스 경로를 넣어 뒀다:

```csharp
bool hasBox     = Mathf.Abs(boxMax.x - boxMin.x) > 1e-3f && ...;
bool inBox      = hasBox && IsWithinMapBox(candidate, boxMin, boxMax);
bool onCollider = IsOnParkingLot(candidate, groundY);
if (!inBox && !onCollider) { failGround++; continue; }
```

`map.get` 이 `{sizeX:160, sizeZ:160}` 을 주므로 호출자가 박스를 넘기면 된다. **8개 중 유일하게 깔끔하게 해결되는 게이트다.**

### 2.4 ⚠ 번호판 가시성 / 가림 — **콜리전 설정에 결과가 통째로 달려 있다**

현재 상태를 확인했다:

| 컴포넌트 | 콜리전 | 함의 |
|---|---|---|
| `ACarActor::MeshComp` | `QueryOnly` (`CarActor.cpp:51`) | ✅ 라인트레이스에 잡힌다 — **가림 판정은 원리적으로 가능** |
| `FrontPlateComp` / `BackPlateComp` | `NoCollision` + `SetVisibility(false)` (`ConfigurePlateVisual`) | 번호판 자체는 트레이스에 안 잡힘. Unity 도 자기 자신은 무시하므로 이건 오히려 맞다 |
| `AMapFloorActor::FloorMesh` | `NoCollision` | Unity 의 "지면 충돌(y<0.15)은 무시" 분기가 UE 에선 무의미 |

즉 ④⑤ 는 **막혀 있지는 않다.** 문제는 결과가 차량 메시의 콜리전 형상에 좌우된다는 점이다. glTF 임포트 메시의 단순화된 콜리전(박스 근사인지 per-poly 인지)에 따라 "번호판이 보인다"의 판정이 달라지고, 그건 코드를 읽어서는 알 수 없다 — **차종별로 캡처를 떠서 눈으로 맞춰 봐야 하는 튜닝 사이클**이다.

Unity 원본도 이 부분을 5점 샘플링(코너4+중심)으로 보수적으로 짜고, 부분 가림도 가림으로 판정한다(`IsPlateVisible` 은 하나라도 막히면 false). 임계를 조금만 다르게 잡아도 배치 성공률이 크게 흔들린다.

### 2.5 ✅ 차량 간 최소 간격 — 문제 없음

`IsOverlapping()` 은 XZ 제곱거리 비교뿐이다(기본 4m). 그대로 옮기면 된다.

## 3. 정리 — 8개 게이트 이식 난이도

| # | 게이트 | 상태 | 막는 것 |
|---|---|---|---|
| 1 | 뷰 안 거리균등 샘플링 | ⚠ 신규 인프라 | SceneCapture 뷰-프로젝션 행렬 + 이분탐색 역산 |
| 2 | 지면 검증 | ✅ 우회 가능 | 바닥 `NoCollision` → `boxMin/boxMax` 경로 사용 |
| 3 | 차량 간 최소 간격 4m | ✅ 그대로 | 없음 |
| 4 | 신규 번호판 가시성 | ⚠ 튜닝 필요 | 차량 메시 콜리전 형상 의존 |
| 5 | 기존 번호판 가림 | ⚠ 튜닝 필요 | 동상 |
| 6 | 화면 2D 박스 겹침 | ⚠ 신규 인프라 | ①과 같은 투영 코드 |
| 7 | 거리 상한(줌 역산) | ❌ **원본 없음** | `CLicensePlateFocusCapture` 상수·공식 |
| 8 | 줌 포화 최종 게이트 | ❌ **원본 없음** | `CalcTargetPTZ` |

**✅ 2 / ⚠ 4 / ❌ 2.**

## 4. 왜 "부분 구현"이 아니라 "보류"가 맞았나

⑦⑧ 을 빼고 ①~⑥ 만 넣으면 문법적으로는 동작하는 `placeInView` 가 나온다. 그리고 **그게 함정이다.**

- 이 메서드의 존재 이유는 "번호판이 읽히는 이미지"를 만드는 것이다. ⑦⑧ 이 바로 그 **"읽히는가"** 를 판정하는 게이트다.
- 그 둘을 빼면 카메라에서 80m 떨어진, 최대 줌으로도 번호판이 몇 픽셀밖에 안 되는 자리에도 차를 놓는다. `placedCount: 5` 라는 성공 응답이 오고 화면에도 차가 보이지만, **정작 쓸 수 없는 데이터가 나온다.**
- 실패가 조용하다. 캡처 이미지를 사람이 하나씩 보기 전까지 알 수 없고, 학습 데이터셋으로 쓴 뒤에야 드러난다.

`-32000` 은 시끄럽게 실패한다. 쓸 수 없는 결과를 성공으로 포장하는 것보다 낫다고 판단했다.

같은 이유로 사유 메시지도 "백엔드 없음"(사실이 아님 — 슬롯 백엔드는 이미 있다)에서 다음으로 바꿨다:

```
미구현(random.placeInView): PTZ 뷰포트 배치 게이트 미이식 — 슬롯 배치는 random.slotPlace 사용
```

호출자가 (a) 무엇이 없는지, (b) 대신 무엇을 쓸지 를 응답만 보고 알 수 있게 했다.

## 5. 이식하려면 — 순서

1. **`CLicensePlateFocusCapture.cs` 확보.** 원본 Unity 프로젝트에서 `unity/_MoveTmp/` 로 가져온다. 이게 없으면 ⑦⑧ 은 추측이 되고, 추측하면 이 문서 §2.1 의 회귀를 반복한다. **선행 조건.**
2. **PTZ 투영 유틸 신설.** `UCameraControlLibrary` 에 순수 함수로 추가하는 것이 이 프로젝트 관례에 맞다(설계 §7: 좌표/FOV 계산은 라이브러리 경유). 월드↔화면 왕복 Automation 테스트를 먼저 붙인다 — 화각 규약은 이미 한 번 틀린 전력이 있다.
3. **`boxMin/boxMax` 기본값 결선.** 생략 시 `AMapFloorActor` 의 현재 크기(`map.get` 과 같은 소스)를 쓰도록. 바닥 콜리전을 켤지는 별도 판단(픽·트레이스 동작에 영향).
4. **번호판 가시성 트레이스.** `FrontPlateComp` 의 bounds 5점 → `LineTraceSingleByChannel`, 자기 차량·`ignoreCar` 제외. 차종 3~5종으로 캡처를 떠서 임계 튜닝.
5. **진단 카운터를 응답에 노출.** Unity 원본이 `failRay/failZoom/failGround/failOverlap/failPlate/failOccl/failScreenOverlap` 을 로그로 뱉는 이유가 있다. RPC 에서는 로그를 볼 수 없으므로 **응답 JSON 에 넣어야** 외부에서 "왜 0대인지" 추적할 수 있다.

작업량은 앞서 구현한 9개 전부(약 500줄)와 비슷하거나 더 크다. 특히 2·4 는 코드보다 **검증 왕복**이 비용이다.

## 6. 지금 대신 쓸 수 있는 것

번호판 가시성 보장이 필요 없는 용도라면 조합으로 대체된다.

```jsonc
// ① 프리셋 주차면에 차량 배치 (전면이 카메라를 향하도록 자동 정렬됨)
{"method":"random.slotPlace","params":{"presetId":1,"random":true,"seed":12345}}

// ② 화면 밖 노이즈 차량을 임의 위치에 추가
{"method":"car.create","params":{"pos":{"x":10,"z":10},"prefabId":3}}

// ③ 위치·전후면 흔들기
{"method":"random.randomizeAll","params":{"presetId":1,"seed":999}}

// ④ 카메라를 그 자리로 조준하고 캡처
{"method":"cam.setPTZ","params":{"camId":1,"pan":35,"tilt":20,"zoom":4.0}}
{"method":"cam.captureJPG","params":{"camId":1,"quality":90}}
```

차이: `slotPlace` 는 **주차면 위에만** 놓고, 번호판이 보이는지는 보장하지 않는다. 카메라 조준은 호출자가 한다.
