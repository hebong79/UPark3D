# 차량 번호판 양각(엠보싱) 구현 방안 — 조사·3안 비교·선택

작성 2026-08-26 16:56 / 대상 `Park3D/Source/Park3D/CarActor.*`, `CarPlateNumberWidget.*`

## 1. 요청

> 인터넷을 조사해서 차량 번호판의 번호가 양각으로 되어 있다.
> 1번 이미지 = 현재 번호판(평면), 2·3번 이미지 = 양각(실제 번호판).
> **처음 차량을 로딩할 때 번호판을 양각으로 만들어 붙이는 방법**을 3가지 제시하고 최적안을 선택할 것.

## 2. 조사 결과 — 실제 번호판의 양각 규격

| 항목 | 값 | 근거 |
|------|-----|------|
| 양각 돌출 높이 | **1.3 mm ~ 1.6 mm** | 「자동차 등록번호판 등의 기준에 관한 고시」 — "번호판에 표시하는 관할관청, 용도, 차종 및 일련번호 등 **모든 문자는 1.3㎜∼1.6㎜로 양각**되어야 하며, 문자 획의 너비는 +1㎜ 이내의 허용차를 인정한다" |
| 판 규격(유럽형) | 520 × 110 mm | 2006-11-01 전 자가용 시행. 우리 구현의 52 × 11 cm 와 일치 |
| 제작 방식 | 알루미늄 판을 **압인(press)** 하여 문자를 돌출시키고 돌출면에 도색 | 페인트식 번호판 |
| 반사필름식(2020-07~) | 재귀반사 필름 부착 + 홀로그램. **양각 유무는 이번 조사에서 확정하지 못함** | 정책 자료는 반사·위변조 방지만 다루고 압인 여부를 명시하지 않는다 |

**사용자가 준 2·3번 이미지의 관찰 소견** — 양각이 화면에서 읽히는 단서는 두 가지다.

1. **글자 위/아래 가장자리의 명암 분리** — 위 모서리는 밝고 아래 모서리는 어둡다(광원이 위에 있을 때). 검은 도색면 자체가 아니라 **압인 측벽**이 만드는 것이다.
2. **글자 주변 판 바닥에 지는 짧은 그림자** — 1.5 mm 라 아주 짧지만 사선에서 확실히 보인다.

즉 "양각으로 보인다"의 실체는 **글자 외곽 1.5 mm 측벽에 생기는 명암과 그림자**이며, 색·굵기·서체는 이미 맞다.

### 우리 구현이 평면으로 보이는 진짜 이유

`ACarActor` 는 번호를 `UWidgetComponent`(World space, `UCarPlateNumberWidget`) 로 그린다
([CarActor.cpp:97-111](Park3D/Source/Park3D/CarActor.cpp#L97-L111)).
**WidgetComponent 의 3D 패스스루 머티리얼은 Unlit** 이라 태양·채움광·그림자가 전혀 걸리지 않는다.
따라서 지금 번호는 두께가 없을 뿐 아니라 **애초에 조명을 받지 않는 순수 평면 스티커**다.
1번 이미지가 스티커처럼 보이는 원인이 여기 있다.

## 3. 세 가지 구현 방안

### 1안 — 위젯 안에서 의사(擬似) 양각: 다중 드로우 오프셋

`UCarPlateNumberWidget::RebuildWidget` 의 `UTextBlock` 하나를 세 장으로 늘린다.

```
Overlay
 ├ TextBlock(하이라이트)  색 흰색 70%, 오프셋 (-1.5, -1.5) px   ← 압인 위 모서리
 ├ TextBlock(그림자)      색 검정 60%, 오프셋 (+1.5, +2.5) px   ← 압인 아래 모서리 + 바닥 그림자
 └ TextBlock(본체)        색 검정 100%, 오프셋 0
```

(더 싸게는 `UTextBlock::SetShadowOffset` / `SetShadowColorAndOpacity` 한 쌍으로 그림자만.
DrawSize 520 px = 판 52 cm 이므로 **10 px = 1 cm**, 1.5 mm 양각 = 0.15 px 이지만
눈에 보이게 하려면 규격보다 과장해 1.5~2.5 px 를 쓴다.)

| 항목 | 평가 |
|------|------|
| 작업량 | C++ 약 20줄. 위젯 파일 1개만 수정 |
| 콘텐츠 변경 | 없음 (에셋·머티리얼·플러그인 무관) |
| 성능 | 드로우 3배지만 위젯 하나가 텍스트 8글자 — 무시 가능 |
| 리스크 | 사실상 0. 되돌리기도 1커밋 |
| 진짜 양각인가 | **아니다.** 명암 방향이 코드에 고정돼 있다 |

**결정적 약점**: 이 레벨(`LV_Park_01`)의 조명은 UDS 가 지배하고 `Time of Day` 가 흐른다(CLAUDE.md 2026-08-17).
태양이 서쪽으로 넘어가면 실물 양각의 명암은 뒤집히는데 위젯의 가짜 명암은 그대로다.
아침·저녁 캡처를 나란히 놓으면 **번호판만 조명을 안 따라가는 것이 오히려 눈에 띈다.**
또 사선(우리 CCTV 의 표준 시야)에서 시차(parallax)가 0이라 각도가 깊어질수록 스티커 느낌이 강해진다.

### 2안 — 높이맵 → 노멀맵: 판 머티리얼에 번호를 굽는다

번호 문자열을 **렌더타깃(RT)** 에 흰 글자/검은 배경으로 그리고(위젯을 `EWidgetSpace::Screen` +
`RenderTarget` 모드로 두거나 `FWidgetRenderer::DrawWidget` 로 1회 렌더),
그 RT 를 판 머티리얼의 **높이맵**으로 물려

- `BaseColor` = 글자 마스크로 검정 도색
- `Normal` = 높이맵 기울기(미리 1~2 px 블러 후 `DDX/DDY` 또는 Sobel)로 측벽 법선 생성
- 필요하면 `Bump Offset` / POM 으로 얕은 시차까지

를 한 머티리얼에서 처리한다. 판 컴포넌트에 MID 를 만들어 차량마다 자기 RT 를 물린다.

| 항목 | 평가 |
|------|------|
| 작업량 | C++ 약 100줄 + **머티리얼 에셋 신규 제작** |
| 콘텐츠 변경 | **크다.** 아래 참조 |
| 성능 | 폴리곤 0. 대신 차량 65대 × 앞뒤 2판 = **RT 130장**(256×64 R8 이면 약 2 MB, 감당 가능하나 관리 대상) |
| 리스크 | 중간~높음 |
| 진짜 양각인가 | **조명은 진짜로 받는다.** 실루엣(외곽선)은 여전히 평면 |

**가장 큰 함정** — 판 메시 `SM_Plate_F/B` 의 머티리얼은 **Content 소유**이고, 현재 코드는
`SetMaterial(0/1, nullptr)` 로 **Content 의 흰 바탕·둥근 베젤·파란 KOR 필드를 그대로 쓰고 있다**
([CarActor.cpp:141-144](Park3D/Source/Park3D/CarActor.cpp#L141-L144)).
여기에 우리 MID 를 덮어씌우면 **그 세 가지가 통째로 사라진다** → 새 머티리얼에서 KOR 필드까지 다시 만들어야 한다.
게다가 `Content/` 는 `.gitignore` 대상이라 새 에셋은 커밋되지 않는다
→ WBP 처럼 `Tools/` 재생성 스크립트를 또 하나 떠안는다(2026-08-17 전례).

### 3안 — 실제 압출 지오메트리를 로딩 시 붙인다 (진짜 양각)

글자를 **두께 1.5 mm 짜리 3D 메시**로 만들어 판 표면에 올린다. 두 갈래가 있다.

#### 3-A. `Text3DComponent` 런타임 압출 ★

UE 5.8 에 `Engine/Plugins/VirtualProduction/Text3D` 가 **런타임 모듈로 들어 있다**(설치 확인 완료).
`SetFont(UFont*)` · `SetTypeface(FName)` · `SetExtrude(float)` · `SetBevel(float)` API 를 제공하므로
**지금 위젯이 쓰는 폰트 에셋(`/Game/Widgets/Fonts/Pretendard/Pretendard`, Typeface `Bold`)을 그대로** 물릴 수 있다.

```
FrontPlateComp
 └ FrontPlateText3D (UText3DComponent)
      Font      = Pretendard, Typeface = Bold
      Extrude   = 0.15  (cm = 1.5mm, 고시 규격 중앙값)
      Bevel     = 0.02, BevelType = Convex, Segments = 2   ← 압인 모서리의 둥근 맛
      Front/Extrude/Bevel Material = 검정 (도색면)
```

배치는 기존 `AlignPlateAndText` 의 축 계산을 **그대로 재사용**한다 —
판 메시의 얇은 축/넓은 축을 바운즈에서 읽는 방식이라, 콘텐츠가 바뀌어도 글자가 모서리로 서지 않는다
(코드에 축을 박았다가 2026-08-16 콘텐츠 교체 때 글자가 사라진 전례가 주석에 남아 있다).

| 항목 | 평가 |
|------|------|
| 작업량 | C++ 약 60줄 + `.uproject` 에 플러그인 1줄 |
| 콘텐츠 변경 | **없음** (판 머티리얼·KOR 필드 무손상, 폰트 재사용) |
| 성능 | 차량당 2개 컴포넌트. 로딩 시 글리프 압출 비용 — 아래 참조 |
| 리스크 | 플러그인 의존성(`GeometryProcessing`/`GeometryScripting`/`GeometryMask`)이 **쿡에 붙는다** |
| 진짜 양각인가 | **그렇다.** 조명·그림자·시차 전부 물리적으로 맞다 |

#### 3-B. 사전 제작 글리프 메시 + HISM

문자 집합이 유한하다(숫자 10 + 용도 한글 1글자 30~40종). 에디터에서 한 번 압출해 글리프 메시로 굽고,
런타임에는 `HierarchicalInstancedStaticMeshComponent` 로 인스턴스만 배치한다.

| 항목 | 평가 |
|------|------|
| 작업량 | 3-A 의 배 이상 — **굽기 파이프라인 + 자간/비례폭 배치 코드를 직접** 짜야 한다 |
| 성능 | **최고.** 65대 × 8글자 = 520 인스턴스가 드로우콜 십수 개로 접힌다. 런타임 지오메트리 생성 0 |
| 리스크 | 글리프 에셋이 `Content/`(gitignore) → 재생성 스크립트 필요 |
| 진짜 양각인가 | **그렇다** (3-A 와 동일 결과물) |

## 5. 선택 — **3-A (Text3DComponent 런타임 압출)**

### 근거

1. **요청이 "양각으로 만들어 붙이는" 것이다.** 1안은 눈속임이고 2안은 실루엣이 평면이다.
   3안만이 압인 측벽·그림자·시차를 전부 물리적으로 만족한다.
2. **판 콘텐츠를 하나도 건드리지 않는다.** 2안이 반드시 깨뜨리는 흰 바탕·둥근 베젤·파란 KOR 필드가
   그대로 남는다. `Content/` 가 gitignore 인 이 저장소에서 **에셋을 새로 만들지 않는 것 자체가 큰 이득**이다.
3. **폰트 문제를 이미 푼 자산을 재사용한다.** `UTextRenderComponent` 가 Runtime 캐시 폰트를 못 그려
   위젯으로 우회했던 그 Pretendard 를, Text3D 는 **폰트 아웃라인(FreeType)** 으로 읽으므로 그대로 쓸 수 있다
   *(→ 6장 검증 1번. 이것이 뒤집히면 3-B 로 간다)*.
4. **3-B 보다 먼저 3-A 를 고르는 이유는 측정 없이 최적화하지 않기 위해서**다.
   3-B 의 이점은 성능뿐이고, 성능이 실제로 문제인지는 아직 모른다. 이행 기준은 6장에 수치로 박아 둔다.

### 정직하게 말해 둘 한계 — CCTV 거리에서는 안 보인다

이 프로젝트의 주 관측은 CCTV 다. 저장된 실측으로 계산하면:

```
zoom 6 → hfov 약 10°, 31 m 에서 화면 폭 5.5 m, 렌더타깃 960 px
→ 1 px ≈ 5.7 mm
→ 양각 1.5 mm = 0.26 px   (서브픽셀, 관측 불가)
```

**즉 양각의 시각적 이득은 자유비행 카메라로 다가간 근접 뷰에서만 난다.**
동시에 이는 안전을 뜻하기도 한다 — 번호판 지오메트리는 `scenario.*` 가림률 색 마스크의 대상이 아니고
크기도 서브픽셀이라 **기존 가림률 기준선을 움직이지 않는다**.
"CCTV 화면에서 번호가 또렷해지는 것"이 목표라면 양각이 아니라 해상도·줌·글자 대비의 문제이며, 별건이다.

## 6. 구현 계획 (각 단계 = 검증 가능한 목표)

| # | 단계 | 검증 |
|---|------|------|
| 1 | **`Text3D` 가 Pretendard(Runtime 캐시 폰트)를 압출하는지 단독 확인** — 빈 액터에 `UText3DComponent` 하나, `SetFont(Pretendard)`, `SetText("672우 3269")` | 한글 `우` 포함 8글자가 3D 로 보이면 통과. **실패 시 즉시 3-B 로 전환**(글리프를 에디터에서 굽는다) |
| 2 | `.uproject` 에 `Text3D` 활성화 후 **패키지 쿡 통과 확인** | 쿡 성공 + 패키지 실행. `AllToolsets` 로 쿡이 깨진 전례가 있으므로 **개별 플러그인 하나만** 켠다 |
| 3 | `ACarActor` 에 `FrontPlateText3D`/`BackPlateText3D` 컴포넌트 추가, `AlignPlateAndText` 에서 위젯과 같은 축·원점으로 배치. Extrude 0.15 cm, 바닥은 판 표면에 0.02 cm 묻어 z-fighting 회피 | `[CarPlate]` 로그에 3D 텍스트 world 위치가 판 면 바깥으로 찍히고, 근접 캡처에서 측벽 명암 확인 |
| 4 | 기존 번호 **위젯을 숨긴다**(컴포넌트는 폴백용으로 남긴다 — `UTextRenderComponent` 선례) | 번호가 이중으로 보이지 않을 것. Text3D 생성 실패 시 위젯을 되살려 번호가 사라지지 않을 것 |
| 5 | 문자 크기·자간을 현재 위젯 결과와 맞춘다 | A/B 캡처를 겹쳐 글자 높이·좌우 위치가 같을 것 (파란 KOR 스트립 오른쪽 기준 중앙 정렬 유지) |
| 6 | **65대 로딩 성능 측정** | 로딩 시간 증가와 드로우콜 델타를 기록 |

**3-B 이행 기준(수치로 못 박음)**: 6번에서 **65대 로딩 추가 지연 > 1.5초** 또는 **드로우콜 +150 이상**이면
글리프 사전 굽기 + HISM(3-B)으로 옮긴다. 그 아래면 3-A 를 유지한다.

### 구현 시 주의

- **축을 코드에 박지 말 것.** 판 메시의 얇은 축/넓은 축은 반드시 바운즈에서 읽는다
  (`AlignPlateAndText` 의 기존 방식). 콘텐츠 교체 때 글자가 모서리로 서서 사라진 적이 있다.
- **`ACarActor` 는 네이티브 클래스로 스폰된다**([CarPlacementManager.cpp:16,73-74](Park3D/Source/Park3D/CarPlacementManager.cpp#L16)) —
  쿠킹된 BP 파생이 없으므로 `UPROPERTY` 컴포넌트 추가로 `Bad export index` 가 나지 않는다.
  (이 경고는 **쿠킹된 WBP 의 C++ 베이스**에 해당하며 여기엔 적용되지 않는다.)
- **번호 생성 시점은 그대로.** `InitFromPos → InitializePlateNumberOnce → UpdatePlatePresentation` 경로에서
  이미 결정적 번호(`MakeDeterministicPlateNumber`)가 확정되므로 **"처음 차량을 로딩할 때" 요구는 자동으로 충족**된다.
- **양각 높이는 규격대로 1.5 mm 를 쓴다.** 근접에서 과장이 필요하다는 판단이 서면 그때 올리되,
  임의로 3~5 mm 를 넣으면 근접 캡처에서 장난감처럼 보인다.

## 7. 미검증 / 열린 항목

- **Text3D 가 Pretendard 한글 글리프를 압출하는가** — 6장 1단계에서 확정. 이 문서의 선택은 이 가정 위에 있다.
- **Text3D 플러그인이 이 프로젝트의 쿡을 통과하는가** — `GeometryProcessing`/`GeometryScripting`/`GeometryMask` 를 끌고 온다.
- **반사필름식 번호판에 양각이 있는가** — 조사로 확정하지 못했다. 우리가 재현하는 것은 사용자가 제시한
  2·3번 이미지, 즉 **페인트식 압인 번호판**이다.
- 이 문서는 방안 제시까지다. **코드는 아직 한 줄도 바꾸지 않았다.**
