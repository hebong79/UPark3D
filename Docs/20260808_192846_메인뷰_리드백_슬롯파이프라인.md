## 1. 문제 — 블로킹은 없앴는데 처리량이 떨어졌다

배포 후 `cam.streamStatus.main` 실측(지시서 제공):

```
captureAvgMs   167.9 → 10.6      (씬 0.41 · 리드백 0.018 · 인코딩 12.1)
targetFps          5 → 10
fps             4.94 → 2.96      ← 오히려 내려갔다
captureSamples  56 / 18초 ≈ 3.1 회/초
```

게임 스레드 비용은 무너졌다(10.6ms → 이론상 90fps). 그런데 **요청 자체가 초당 3번뿐**이다.

원인은 **한 장짜리 파이프라인**이다. 직전 구현은 `Stage != Idle` 이면 새 요청을 건너뛰므로,
요청 → Ready 까지의 왕복 지연(실측 역산 약 300ms)이 그대로 처리량 상한(1/L ≈ 3.3장/초)이 된다.
지시서에 따르면 창을 포그라운드로 올려도 2.97fps 로 같았다.

## 2. 한 일

### 2-1. 슬롯 링

`TSharedPtr<FCamStreamMainReadback>` 하나였던 것을 **링 배열**로 바꿨다.

| 멤버 | 역할 |
|------|------|
| `MainReadbackRing` | 슬롯 배열(크기 = `MainReadbackSlots`). 원소가 null = 아직 안 쓴 슬롯 |
| `MainRingWrite` | 다음 요청을 걸 위치 |
| `MainRingRead` | 다음에 수거할(가장 오래된) 위치 |
| `MainSkippedNoSlot` | 빈 슬롯이 없어 건너뛴 누적 횟수 |

새 함수: `EnsureMainReadbackSlots()`, `HasFreeMainReadbackSlot()`, `GetMainReadbackInFlight()`,
`PollMainReadbackSlot()`. 기존 `RequestMainCapture`/`PollMainReadback`/`TryTakeMainFrame`/
`ReleaseMainReadback` 은 링 위에서 돌도록 고쳤다.

틱 흐름:

```
PollMainReadback()      진행 중인 슬롯 전부를 렌더 스레드에서 확인시킨다
TryTakeMainFrame()      MainRingRead 슬롯 1개만 수거 → 인코딩 → 송출
페이싱 도달 시           MainRingWrite 슬롯이 Idle 이면 요청, 아니면 skippedNoSlot++
```

### 2-2. 순서 보장

요청은 `MainRingWrite` 에서만 시작하고 앞으로만 간다. 수거는 `MainRingRead` 에서만 한다.
**뒤에 건 슬롯이 먼저 Ready 가 되어도 Read 가 그 자리에 올 때까지 나가지 못한다** →
내보내는 순서 = 요청한 순서. 영상이 뒤로 튀지 않는다.

(부수 효과: Read 슬롯이 막히면 뒤 슬롯도 못 나간다 — head-of-line blocking. §5 위험 참조.)

### 2-3. 틱당 1장 수거

`TryTakeMainFrame()` 은 `MainRingRead` **한 슬롯만** 본다. 여러 장이 한 틱에 Ready 가 되어도
그 틱에 나가는 것은 1장이고 나머지는 다음 틱으로 미뤄진다 — 인코딩이 12ms 라 3장을 한 틱에
인코딩하면 36ms 스파이크가 난다. 구조로 강제되므로 별도 카운터가 필요 없다.

### 2-4. 슬롯 수 설정

```cpp
UPROPERTY(config, EditAnywhere, Category = "CamStream|Main", meta = (ClampMin = "1"))
int32 MainReadbackSlots = 3;
```

`DefaultGame.ini` 의 `[/Script/Park3D.CamStreamSubsystem]` 에 `MainReadbackSlots=3` 을 주석과 함께 추가.

### 2-5. 진단 값 3개 + 로그

`cam.streamStatus.main` 에 추가:

| 키 | 의미 |
|----|------|
| `skippedNoSlot` | 빈 슬롯이 없어 요청을 건너뛴 **누적** 횟수 |
| `inFlight` | 요청했지만 아직 프레임으로 나가지 않은 슬롯 수(Pending + 수거 대기) |
| `tickFps` | 게임 스레드 틱/초(최근 1초 실측) |

(`readbackSlots` = 설정된 슬롯 수도 함께 낸다. 어느 설정에서 잰 수치인지 응답만 보고 알 수 있게.)

`tickFps` 는 `UCamStreamSubsystem::Tick()` 최상단에서 잰다 — `bDisabled` early-return 앞이라
스트리밍이 꺼져 있어도 값이 나온다. **스트림은 이 값보다 빠를 수 없다**(틱당 1장 수거).

주기 로그에도 `틱 N/s, 슬롯 a/b 사용, 슬롯없어 건너뜀 n` 을 붙였다.

### 2-6. 단계별 계측을 슬롯으로 이동

여러 장이 동시에 날아다니므로 `MainPendingSceneMs`/`MainPendingReadbackMs`(서브시스템 멤버)를
`FCamStreamMainReadback::SceneMs`/`ReadbackGameMs`(슬롯 멤버)로 옮겼다. 게임 스레드에서만
읽고 쓰므로 뮤텍스 대상이 아니다. 기록 시점(슬롯 공개 순간)과 링 4개는 그대로다.

## 3. 정리·해상도 변경 시 슬롯 회수

`ReleaseMainReadback()` 이 **모든 슬롯**을 돈다. 수명 규약은 슬롯 1개일 때와 동일하다:

1. 게임 스레드가 `bAbandoned = true`, `Stage = Idle`, `Pixels.Empty()` (뮤텍스 안)
2. 게임 스레드가 자기 참조(`SlotRef`)를 놓는다
3. 정리용 렌더 커맨드가 **마지막 참조**를 쥐고 있다 → `delete Readback` 은 항상 렌더 스레드에서,
   그 슬롯에 앞서 걸어둔 복사·폴링 커맨드보다 **뒤에서** 실행된다(렌더 커맨드는 FIFO)
4. 링을 `Reset()`, `MainRingWrite = MainRingRead = 0`

호출 지점:

| 지점 | 이유 |
|------|------|
| 클라이언트 0명 (`TickMainChannel`) | 유휴 상태로 스테이징 3벌을 들고 있지 않게 |
| `StopMainChannel()` | 렌더타깃을 놓기 전에 |
| 해상도 불일치 (`PollMainReadback`) | 슬롯 하나만 버릴 수 없다 — 스테이징 크기가 제각각이 되면 순서도 크기도 못 맞춘다 |
| 슬롯 수 변경 (`EnsureMainReadbackSlots`) | 링 크기를 살린 채 늘리면 Read/Write 위치의 의미가 어긋나 순서가 뒤집힌다 |

## 4. `MainReadbackSlots=1` 이면 예전 동작과 같은가 — 그렇다

| | 예전(단일) | 새 구현, N=1 |
|---|---|---|
| 요청 조건 | `Stage != Idle` 이면 skip | `HasFreeMainReadbackSlot()` = `Stage == Idle` |
| 수거 대상 | 그 하나 | `MainRingRead`(=0, 유일한 슬롯) |
| 링 인덱스 | 없음 | `(0+1) % 1 = 0` — 항상 제자리 |
| 리드백 객체 | 1개 재사용 | 슬롯 0의 1개 재사용 |
| 통계 | 서브시스템 멤버 | 슬롯 0의 멤버(값 동일) |

유일한 차이는 `skippedNoSlot` 카운터가 새로 세어진다는 것뿐이다(동작 변화 없음).
되돌릴 길은 살아 있다 — ini 한 줄로 되돌아간다.

## 5. 위험

| 위험 | 평가 / 대응 |
|------|-------------|
| **순서 뒤집힘** | 구조적으로 불가능하다. 수거는 `MainRingRead` 한 곳에서만 하고 인덱스는 단조 증가(mod N)다. 각 슬롯은 자기 `Width/Height/Pixels` 를 들고 있어 섞이지 않는다 |
| **head-of-line blocking** | 순서 보장의 대가다. `MainRingRead` 슬롯이 영영 Ready 가 안 되면 뒤 슬롯이 다 Ready 여도 스트림이 멈추고, 결국 Write 도 그 슬롯에서 막힌다. 명시적 실패는 `Ready + bFailed` 로 올려 수거되지만, **`IsReady()` 가 계속 false 인 경우의 워치독은 없다**(요청 범위 밖). `inFlight` 가 슬롯 수에 붙어 있고 `fps` 가 0 이면 이 상황이다 |
| **슬롯 누수** | 슬롯은 `TSharedPtr` 다. 게임 스레드가 참조를 놓아도 정리 커맨드가 마지막 참조를 쥐고 있어 렌더 스레드에서 `delete` 된 뒤 소멸한다. `ReleaseMainReadback()` 이 **모든** 슬롯을 돌므로 일부만 남는 경로가 없다. 다만 **실기 검증은 못 했다**(재기동 금지) |
| **메모리** | 슬롯 3개면 스테이징 텍스처 3벌 = 960×540×4B ≈ 2.07MB × 3 ≈ **6.2MB**(행 정렬 패딩 포함 시 조금 더). 수거 대기 중인 `TArray<FColor>` 도 최대 3벌 ≈ 6.2MB. 합계 **약 12MB** — 계산값이며 실측하지 않았다 |
| **GPU 부하 증가** | 초당 씬 캡처 횟수가 3.1회 → 최대 10회로 늘어난다. 게임 스레드 비용은 그대로지만 **GPU/렌더 스레드 부담은 3배** 가까이 늘 수 있다. 화면 fps 가 떨어지면 `MainFps` 나 `MainReadbackSlots` 를 내리는 것이 손잡이다. **추측이다 — 측정해야 안다** |
| **틱당 1장 상한** | 스트림 fps ≤ `tickFps` 가 구조적으로 강제된다. `tickFps` 가 10 미만이면 목표를 못 채우는 이유가 그것이고, 그때 손댈 곳은 스트림이 아니라 앱이다 |
| **컴파일 미검증** | 빌드하지 않았다. 새 free 함수·익명 네임스페이스 헬퍼는 추가하지 않았고(모두 클래스 멤버), `ENQUEUE_RENDER_COMMAND` 이름 3개(`Park3DMainViewReadbackEnqueue`/`Poll`/`Release`)는 저장소 전체에서 이 파일에만 있다 — 지시서가 경고한 unity 빌드 이름 충돌은 확인해 두었다 |

## 6. 예상 효과와 근거

**확인된 사실**: 요청 3.1회/초, 페이싱은 10회/초 허용 → 왕복 지연 ≈ 320ms 가 상한이었다.

**추론(측정 필요)**: 320ms 의 정체는 둘 중 하나다.

1. 진짜 GPU 왕복 지연이 300ms 대 → 슬롯 3개면 상한이 3/0.32 ≈ **9.4장/초**
2. 틱 granularity — 한 장에 최소 3틱(요청/폴링/수거)이 필요하므로, `tickFps ≈ 10` 이면
   3틱 = 300ms → 3.3fps. 지금 숫자와 거의 정확히 맞는다. 이 경우 슬롯 3개면
   **틱마다 1장씩 수거**되어 `tickFps` 에 붙는다(≈ 10fps)

**어느 쪽이든 슬롯 3개면 목표 10fps 에 닿는다**는 것이 예상이다. 다만 최종 상한은
`min(MainFps, tickFps, 슬롯수/지연)` 이고, 세 항 중 무엇이 걸렸는지는 이번에 넣은
`tickFps`·`inFlight`·`skippedNoSlot` 로 배포 후 바로 갈린다:

- `skippedNoSlot` 이 계속 늘고 `inFlight == 3` → 슬롯이 모자란다(4~5로 올린다)
- `skippedNoSlot` ≈ 0 이고 `fps ≈ tickFps` → 앱 틱이 상한이다(스트림이 아니라 앱을 봐야 한다)
- `skippedNoSlot` ≈ 0 이고 `fps < tickFps` → 페이싱(`MainFps`)이 상한이다
