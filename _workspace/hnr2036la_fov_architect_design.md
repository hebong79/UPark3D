## 1. 요구사항 · 성공 기준

### 1.1 기능 요구사항

| ID | 요구사항 |
|---|---|
| R1 | `ZoomToHFov(zoom)` 를 탄젠트 모델 `2·atan( tan(DefaultHFov/2) / clamp(zoom,1,MaxZoom) )` 로 교체한다(입출력 단위는 **도**). |
| R2 | `HFovToZoom(hfov)` 를 역함수 `clamp( tan(DefaultHFov/2) / tan(hfov/2), 1, MaxZoom )` 로 교체한다. |
| R3 | `DefaultHFov` 기본값을 `58.f → 56.5f` 로 바꾼다(라이브러리 헤더 기본 인자 2곳 + `APTZCameraActor` UPROPERTY 1곳). |
| R4 | `MaxZoom = 36.f` 및 `config_pmaker.json` 의 `max_zoom: 36.0` 은 **변경하지 않는다**(사양서 광학 x36 확인). |
| R5 | 기존 경계·클램프 계약(§3)을 한 건도 바꾸지 않는다. |
| R6 | 선형 모델을 서술하는 주석(헤더 §줌↔FOV 블록, cpp 블록 주석, `PTZCameraActor.h` 의 "Unity DEFAULT_FOV=58 수평")을 새 모델·새 근거로 갱신한다. |
| R7 | `CameraControlLibraryTest.cpp` 의 TP-FOV 단정(58 기준 9건 + 라운드트립)을 새 기대값으로 갱신한다. |

### 1.2 제약

- **시그니처 변경 금지 범위 준수** — 소비자 6곳(§2.3)은 라이브러리를 경유하므로 시그니처를 바꾸지 않으면 무수정이다.

## 2. 클래스 / 데이터 구조 / 인터페이스

### 2.1 데이터 구조 — 변경 없음

`FCamVec3` / `FCamPtz` / `FCamDir` / `FCameraPos` / `FCameraPosList`(`CameraControlTypes.h`) 는 **변경하지 않는다.**
JSON 스키마도 변경 없다. `FCamDir::zoom` 의 의미(“줌 배율(1~36), FOV 아님”)와 `FCamPtz::z` 의 의미가 그대로 유지되는 것이 §5 권고 A의 전제다.

> **관찰(설계 판단 근거)**: `FCameraPosList` 에는 `isUnreal` 뿐이고 **스키마 버전 필드가 없다.** 즉 “이 파일이 마이그레이션되었는가”를 표시할 자리가 없다 — §5에서 결정적으로 작용한다.

### 2.2 인터페이스 — 시그니처 유지

```
static float ZoomToHFov(float Zoom, float MaxZoom = 36.f, float DefaultHFov = 56.5f);   // 58.f → 56.5f
static float HFovToZoom(float HFov, float MaxZoom = 36.f, float DefaultHFov = 56.5f);   // 58.f → 56.5f
```

**결정: 시그니처(인자 개수·타입·순서·UFUNCTION 메타)를 유지한다.** 바꿀 이유가 없다 — 변경은 기본 인자의 *값* 과 함수 *본문* 뿐이므로 호출부 무수정이 성립한다. Blueprint 노드 시그니처도 보존되어 에셋 재컴파일 리스크가 없다.

- 외부 스크립트(`_workspace/**/*.py|ps1|js`)에서 `cam.setFOV` 나 화각 숫자를 하드코딩한 곳은 **없다**(grep 결과 0건).

### 2.4 `56.5` 중복 정의 — 결정과 근거

현재 `58` 은 두 종류의 자리에 중복되어 있다.

| 자리 | 역할 |
|---|---|
| `CameraControlLibrary.h:45,49` 기본 인자 | 순수 함수를 **인자 없이** 호출할 때의 값(유닛 테스트·BP 노드 기본핀) |
| `PTZCameraActor.h:55` UPROPERTY | **액터 인스턴스별로 에디터에서 조정 가능한** 값. `MaxZoom` 과 한 쌍으로 액터가 라이브러리에 넘긴다 |

**결정: 중복을 유지한다(단일 소스로 통합하지 않는다).**

근거:
1. 두 자리는 목적이 다르다. 하나는 “라이브러리 단독 사용 시의 폴백”, 다른 하나는 “인스턴스 상태”다. `MaxZoom` 도 정확히 같은 구조로 이미 중복되어 있으며(`36.f` × 3곳: 라이브러리 기본 인자 2 + 액터 UPROPERTY 1 + 매니저 `CameraMaxZoom`), 기존 관례를 따르는 것이 정합적이다.
2. 통합하려면 (a) 공용 상수 헤더/네임스페이스 신설 → 새 심볼·새 include 로 범위 확대, 또는 (b) 기본 인자 제거 → 무인자 호출부(테스트 다수)를 전부 수정, 둘 중 하나다. 어느 쪽도 “화각 규격 정정”이라는 요청에서 직접 추적되지 않는 변경이다 → **CLAUDE.md 3번 위반.**
3. 중복의 실제 위험(“한쪽만 고쳐서 어긋남”)은 리팩터링 대신 **테스트로 봉인**한다: `GetDefault<APTZCameraActor>()` CDO 값과 라이브러리 기본 인자 결과가 같은지 단정(§6.4, S6). 이는 신규 파일·신규 심볼 없이 1건의 단정으로 끝나며, 중복이 어긋나면 즉시 빨간불이 된다.

**보완 조치(코드 변경 아님, 주석):** 두 자리에 상호 참조 주석을 남긴다 — “`CameraControlLibrary.h` 의 기본 인자와 한 쌍. 모델 교체 시 동시 수정(테스트 `Park3D.CameraControl.Fov` 가 불일치를 잡는다).”

## 3. 경계 · 클램프 동작 — 보존 계약과 신규 위험

### 3.1 보존해야 할 기존 계약 (전부 유지)

| 케이스 | 기존 동작 | 신규 동작 | 유지 |
|---|---|---|---|
| `ZoomToHFov(0)` | 1로 선클램프 → 58 | 1로 선클램프 → **56.5** | O |
| `ZoomToHFov(-5)` | 1로 선클램프 → 58 | → **56.5** | O |
| `ZoomToHFov(100)` | MaxZoom(36) 클램프 → 1.611 | → **1.71021** | O |
| `ZoomToHFov(z, MaxZoom<1)` | `MaxZ=1` 보정 → 58 | → **56.5** | O |
| `HFovToZoom(0)` | `MaxZ` 반환(36) | **36** | O |
| `HFovToZoom(음수)` | `MaxZ` 반환(36) | **36** | O |
| `HFovToZoom(아주 작은 양수)` | 상한 클램프 → 36 | **36** | O |
| `HFovToZoom(hfov > DefaultHFov)` | 하한 클램프 → 1 | **1** | O |
| `HFovToZoom(h, MaxZoom<1)` | `MaxZ=1` 보정 | 동일 | O |

클램프의 **순서**도 그대로다: `ZoomToHFov` 은 “MaxZoom 정상화 → zoom 클램프 → 변환”, `HFovToZoom` 은 “MaxZoom 정상화 → HFov<=0 조기 반환 → 변환 → 결과 클램프”.

### 3.2 탄젠트 모델이 새로 만드는 정의역 위험 (열거)

| # | 위험 | 발생 조건 | 결과(방어 없을 때) |
|---|---|---|---|
| W1 | `tan(hfov/2)` 가 0 → **0 나눗셈** | `hfov = 0` 또는 `hfov = 360°` | `hfov=0` 은 기존 조기 반환이 이미 막는다. `hfov=360` 은 `tan(180°)` = 이론상 0 → `x/0` = `+inf` → `Clamp(inf,1,36)` = **36**. 의미상 정반대(360°는 극단적 광각 → zoom 1이어야 함). |
| W2 | `tan(hfov/2)` **부호 반전** | `180° < hfov < 360°` | `tan(90°~180°)` 은 음수 → 비율 음수 → `Clamp(음수,1,36)` = **1**. 결과적으로는 우연히 맞지만, 부호 반전에 의존하는 코드는 리뷰 불가·회귀 취약. |
| W3 | `tan(hfov/2)` **발산** | `hfov → 180°` | `tan(89.99…°)` 은 거대하지만 유한 → 비율 ≈ 0 → 클램프 1. 정확히 `hfov = 180.0f` 면 `tanf(π/2)` 가 플랫폼에 따라 `±1.6e16` 또는 `inf`. |
| W4 | `NaN` 전파 | `0/0` (`DefaultHFov=0` 이면서 `hfov=360`) | `Clamp(NaN,…)` 은 UE에서 정의되지 않은 결과. 조용한 오염. |
| W5 | `DefaultHFov` 정의역 이탈 | UPROPERTY 이므로 에디터에서 `0`, 음수, `≥180` 설정 가능 | `ZoomToHFov` 이 **음수 화각**을 반환(`tan` 음수 → `atan` 음수). 현행 선형 모델은 `0/z = 0` 으로 조용히 0을 냈으므로 “새로 생긴” 위험은 아니지만 성질이 나빠진다. |
| W6 | `Tan/Atan` 의 라디안 오용 | 도 값을 그대로 `FMath::Tan` 에 투입 | 전 구간 무의미한 값. 컴파일 에러가 안 나므로 가장 위험한 구현 실수. §4 참조. |

### 3.3 방어 설계 — 반각 탄젠트 헬퍼 1개로 W1~W5 일괄 차단

`CameraControlLibrary.cpp` 에 **파일 로컬 익명 네임스페이스 헬퍼 1개**를 둔다(헤더 노출 없음, 신규 공개 심볼 없음).

- 이름(예): `TanHalfFovDeg(float FovDeg)`
- 동작: `FovDeg` 를 **(0, 180) 열린구간의 안전한 경계로 클램프**한 뒤 `FMath::Tan(FMath::DegreesToRadians(Clamped * 0.5f))` 를 반환.
  - 하한 상수: `0.001f` (반각 0.0005° → `tan ≈ 8.727e-6`, **항상 양수·비영**)
  - 상한 상수: `179.999f` (반각 89.9995° → `tan ≈ 1.146e5`, **유한**)
- 두 함수 모두 `tan` 을 이 헬퍼로만 호출한다.

이 한 수로 얻는 성질:

- **분모가 항상 유한한 양수** → W1(0나눗셈)·W4(NaN) 원천 차단.
- **부호가 항상 양수** → W2(부호 반전) 제거. `hfov ∈ (180,360]` 은 “180 근처의 매우 넓은 화각”으로 해석되어 비율 ≈ 0 → 클램프 1. **의미상으로도 옳은 결과**(기본 화각보다 넓으면 줌 최소)이며, 이제 부호 우연이 아니라 정의역 클램프에서 나온다.
- **발산 없음** → W3 제거.
- 분자 `TanHalfFovDeg(DefaultHFov)` 도 같은 헬퍼를 통과 → W5 제거(`DefaultHFov ≤ 0` → 하한 클램프 → 분자 극소 → `ZoomToHFov` 이 “거의 0인 양수 화각”을, `HFovToZoom` 이 1을 반환. 음수 화각·NaN 없음).

> 이 헬퍼는 “발생 불가능한 시나리오에 대한 에러 처리”(CLAUDE.md 2번)가 아니다. `HFov` 는 `cam.setFOV` 로 **외부 RPC 입력이 직접 들어오는 값**이고, `DefaultHFov` 는 **에디터에서 편집 가능한 UPROPERTY** 다. 둘 다 정의역을 벗어난 값이 실제로 도달 가능하다. 또한 기존 코드가 이미 `MaxZoom<1` 과 `HFov<=0` 을 방어하고 있으므로 동일 스타일의 최소 확장이다.

### 3.4 신규 클램프의 부작용 없음 확인

`(0.001, 179.999)` 클램프가 **정상 입력을 건드리지 않는지** 확인: 실사용 화각 범위는 `[1.710, 56.5]` (zoom 36~1), `cam.setFOV` 의 현실적 입력도 UE `FOVAngle` 의 통상 범위(1~170) 안이다. 클램프가 발동하는 것은 이미 비정상 입력뿐이다.

## 4. 정밀도 — 라디안 변환 지점과 허용 오차

### 4.1 도↔라디안 변환 지점 (구현 지시)

`FMath::Tan` / `FMath::Atan` 은 **라디안** 이다. 본 설계의 공개 API는 **전부 도** 다. 변환은 정확히 아래 3지점에서만 일어난다.

| 함수 | 지점 | 변환 |
|---|---|---|
| `TanHalfFovDeg` (헬퍼) | 입력 | `FMath::DegreesToRadians(ClampedDeg * 0.5f)` — **반각을 먼저 취하고 라디안화** |
| `ZoomToHFov` | 출력 | `FMath::RadiansToDegrees( 2.f * FMath::Atan(...) )` — **`Atan` 결과(라디안)를 2배한 뒤 도로 환산** (2배와 환산의 순서는 선형이므로 무관하나 식 그대로 두는 것이 검증 쉬움) |
| `HFovToZoom` | 없음 | 분자·분모 모두 헬퍼가 처리 → 무차원 비율. 추가 변환 **금지**(이중 변환이 전형적 실수) |

> 구현 주의: `2·atan(x)` 를 `atan(2x)` 로 쓰거나, `tan(H/2)` 를 `tan(H)/2` 로 쓰는 실수는 컴파일 에러 없이 통과한다. §6 기대값 표가 이를 잡는다(둘 다 zoom=2 에서 30.076 이 나오지 않는다).

### 4.2 float 정밀도 — 기존 허용 오차 1e-3 유지 가능한가

**결론: 유지 가능하다. 변경 불필요.**

`float32` 로 전 경로를 시뮬레이션한 결과(`tan → 나눗셈 → atan → 도 환산 → 반각 → 라디안 → tan → 나눗셈`, 각 단계 float32 반올림 적용):

| 항목 | 실측 |
|---|---|
| 라운드트립 `HFovToZoom(ZoomToHFov(z))`, `z ∈ [1,36]` 0.005 간격 전수 | **최악 절대오차 5.646e-6** (z=35.545), 최악 상대오차 1.59e-7 |
| 순방향 특이점 검증 `ZoomToHFov(1)` | `56.500000` (오차 0) |
| 역방향 5자리 리터럴 입력 | 최악 편차 1.9e-5 (`hfov 3.07787 → 20.000019`) |

허용 오차 1e-3 대비 **약 177배 여유**다. 이유: 이 합성 함수는 조건수가 좋다. 큰 zoom 구간에서는 화각이 작아 `tan x ≈ x`, `atan x ≈ x` 로 거의 항등에 가깝고, 작은 zoom 구간에서는 각도 자체가 커서 상대오차가 흡수된다. 오차가 커지는 “두 큰 수의 차” 같은 상쇄 패턴이 없다.

**단, 기대값 리터럴의 자릿수는 늘려야 한다.** 기존 테스트는 `58.f / 36.f` 처럼 정확한 식을 썼지만, 탄젠트 값은 식으로 쓰면 테스트가 구현을 그대로 베끼는 동어반복이 된다. 따라서 **독립 계산된 소수 리터럴**을 쓰되, 3자리(`15.301`)는 1e-3 예산의 47%를 리터럴 절삭에만 소비한다(`15.301` vs 실제 `15.301469`). → **소수 5자리 리터럴 + 허용 오차 1e-3 유지**를 채택한다(§6 표). 이러면 리터럴 절삭 오차가 ≤ 5e-6 로 예산의 0.5% 만 쓴다.

### 5.1 실측 데이터 (설계 근거)

### 5.3 대안 비교

#### 대안 A — 무변환 (저장 파일 그대로 둔다)

`zoom` 숫자를 보존한다. 같은 숫자가 조금 다른 화각을 의미하게 된다.

- **장점 1 (결정적) — `zoom` 은 화각이 아니라 실장비 PTZ 명령값이다.** `FCamDir::zoom` 주석이 명시한다: *“줌 배율(1~36), FOV 아님”*. `ptzmin.z`/`ptzmax.z` 는 실기 PTZ 명령 범위이며, 저장된 프리셋은 현장 카메라의 프리셋 위치(pan/tilt/zoom 명령 3종)에 대응한다. **시뮬레이터의 임무는 “이 명령을 받은 실기가 보여줄 그림”을 재현하는 것**이다. 지금 고치는 것은 바로 그 재현식(잘못된 화각)이지, 명령값이 아니다. 명령값을 고쳐서 예전의 *틀린* 그림을 유지하는 것은 수정의 목적을 정면으로 뒤집는다.
- **장점 2 — 다수 데이터에서 마이그레이션이 애초에 불가능하다.** 화면 보존식 `z' = tan(28.25°)/tan((58/z)/2°)` 을 `z=1` 에 적용하면 **`z' = 0.969`** 로 하한 1 미만이다. 56.5° < 58° 이므로 zoom=1 의 기존 화각은 새 모델로 **표현 자체가 불가능**하다. 저장 zoom 의 73%가 여기 해당한다. 즉 대안 B는 데이터의 3/4에 대해 아무것도 못 하면서 나머지 1/4만 흔든다.
- **장점 3 — 되돌리기 자유.** 파일 무변경 → 이번 변경을 되돌리면 화면도 100% 원복된다.
- **장점 4 — 멱등성 문제 없음.** §2.1 관찰대로 `FCameraPosList` 에는 스키마 버전 필드가 없다. 마이그레이션 여부를 표시할 자리가 없으므로 **B는 두 번 실행되면 두 번 변환된다**(zoom 2.0 → 2.078 → 2.158). 로드 경로(`NormalizeLoaded`)에서 자동 변환을 걸면 저장→로드 반복마다 값이 표류한다. 이를 막으려면 스키마 확장이 필요하고 그건 범위 밖이다.
- **단점** — 이번 커밋 이후 같은 프리셋 파일을 열면 화면이 미세하게(−2.6%~+6%) 달라진다. 사용자가 “왜 화면이 바뀌었나”를 물을 수 있다.

#### 대안 B — 화면 보존 마이그레이션 (파일의 zoom 재계산)

- **장점** — 변경 직후 기존 프리셋의 화면이 (표현 가능한 범위에서) 그대로 보인다.
- **단점 1 (치명)** — 저장값이 실기 PTZ 명령값이라는 스키마 계약을 깬다. 마이그레이션된 `zoom 2.078` 을 실기에 보내면 실기는 2.078배로 당긴다. **시뮬은 맞고 실기는 틀리는** 상태가 되며, 이건 지금 고치려는 오차보다 나쁜 결함이다.
- **단점 2** — 73%(zoom=1)를 변환할 수 없다(위 장점 2). 목표인 “화면 보존”이 데이터 대부분에서 달성되지 않는다.
- **단점 3** — 되돌리기 어렵다. 27개 파일을 일괄 재작성해야 하고, 그중 5개는 이미 워킹트리에서 수정 상태다(`git status` 상 `CamPos_40Face_동대문.json` 등). 역변환은 반올림 손실 때문에 완전 복원이 아니다.
- **단점 4** — 멱등하지 않다(위 장점 4).
- **단점 5** — 사람이 손으로 넣은 라운드 값(`1.5`, `2.9`, `7.4`)이 `1.531`, `3.047`, `7.844` 같은 비직관 값으로 바뀌어 이후 편집·검토를 방해한다.

### 5.4 권고

> ### **대안 A(무변환)를 권고한다. 저장 파일은 한 바이트도 건드리지 않는다.**

`zoom` 은 실장비에 보내는 PTZ 명령값이므로 숫자를 보존하는 것이 스키마 계약과 시뮬레이션 목적 모두에 맞다. 이번 변경의 본질은 **“같은 명령값에 대한 화각 재현식을 실기 규격에 맞춘 것”** 이며, 화각이 바뀌는 것은 부작용이 아니라 **정확히 의도한 수정 결과**다.

**부수 조치(코드 아님):**
- 최종 한글 문서(doc-writer 단계)에 §5.2 표를 그대로 실어 “이 변경 이후 기존 프리셋의 화각이 −2.6%~+6% 달라지며 이는 의도된 정정”임을 명시한다.
- `Park3D/Save/3D/CameraPos/*.json` 는 **수정 금지 목록**으로 구현·QA 단계에 전달한다. QA는 `git status` 로 무변경을 확인한다(S8).

**미확정으로 남기는 항목(추측 금지):** 실기와의 최종 대조(현장 카메라에 zoom=2 를 보내고 시뮬 화면과 비교)는 실장비 접근이 필요하므로 이번 단계에서 검증할 수 없다. 사양서 대조까지가 이번 범위다.

```
 (FCamDir::zoom)
```

- `Capture->FOVAngle` 은 `USceneCaptureComponent2D` 규약상 **수평 화각(도)** 이다. 라이브러리 출력 단위와 정확히 일치하므로 aspect 변환은 여전히 불필요하다(기존 §7.3 전제 유지). **탄젠트 모델로 바뀌어도 이 전제는 영향받지 않는다** — 바뀐 것은 zoom→화각 매핑뿐이고, 화각→렌더는 엔진 몫이다.
- 생성자 `PTZCameraActor.cpp:29` 의 `Capture->FOVAngle = DefaultHFov` 는 zoom=1 초기 상태를 뜻한다. `ZoomToHFov(1) = DefaultHFov` 가 새 모델에서도 **항등으로 성립**하므로(`2·atan(tan(H/2)/1) = H`) 생성자 코드는 **수정 불필요**하며 초기 상태가 자동으로 56.5° 가 된다. ✅

### 7.2 `GetZoom ← FOVAngle`

```
Capture->FOVAngle ─→ HFovToZoom(FOVAngle, MaxZoom, DefaultHFov) ─→ zoom
                          ├→ RPC cam.getPTZ.zoom
                          └→ RpcModuleSupport::CamToDto → cam.list / cam.get
```

- `HFovToZoom` 이 `ZoomToHFov` 의 **정확한 역함수**이므로(§6.3, 오차 ≤ 5.6e-6) `SetZoom(z)` 직후 `GetZoom()` 은 항상 `z` 를 돌려준다. 단, `z` 가 `[1, MaxZoom]` 밖이면 클램프된 값이 돌아온다 — 이는 **기존과 동일한 계약**이다(선형 모델에서도 그랬다).
- 위젯은 슬라이더 값을 자체 상태로 들고 있고 `GetZoom()` 을 되읽지 않으므로(`ApplyControlToCamera` 는 단방향) UI 드리프트 경로가 없다.

### 7.3 RPC `cam.setFOV` — 모델 우회 경로

`CamRpcModule.cpp:260` 은 `Capture->FOVAngle` 에 값을 **직접 대입**한다(라이브러리 미경유). 일관성 판정:

- **일관된다.** `FOVAngle` 은 언제나 단일 진리원(single source of truth)이고, `GetZoom()` 은 **항상** 그 값을 `HFovToZoom` 으로 역산한다. 따라서 `setFOV(30.07595)` 직후 `getPTZ.zoom` 은 2.000 을 반환한다(E4). 두 경로가 같은 상태를 공유하므로 모델 교체와 무관하게 정합적이다.
- **주의(호환성 노트, 코드 변경 아님)**: `setFOV` 로 넣는 화각의 *의미* 는 변하지 않지만, 그 화각에 대응하는 `zoom` 역산 결과는 변한다. 예: `setFOV(29)` → 기존 `zoom 2.000`, 신규 `zoom 2.078`. 앞서 확인한 대로 저장소 스크립트에 `setFOV` 하드코딩은 0건이므로 깨질 호출부는 없다. 문서에 남긴다.
- `cam.getFOV` 메서드는 **존재하지 않는다**(등록 목록에 없음). 신설하지 않는다(범위 밖).

### 7.4 좌표·단위 규약 적용 확인

이번 변경은 **각도 단위(도↔라디안)** 만 다루며, 미터→cm(×100)·Unity→UE 축 변환(`z,x,y`)·faceRot/groupRot 분리·사선 보정 등 공간 규약은 **일절 접촉하지 않는다**. `PanTiltToRotator`/`RotatorToPanTilt`, `NormalizeLoaded` 의 좌표 정규화도 무수정이다.
