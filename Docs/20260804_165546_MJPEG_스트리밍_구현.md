# Park3D MJPEG 스트리밍(`GET /stream`) 구현

- 작성: 2026-08-04 16:55:46
- 대상: `Park3D/Source/Park3D/Rpc/` (C++)
- 엔진: UE 5.8
- 설계·영향도·QA 원본: `_workspace/mjpeg_*.md` (5건)

---

## 1. 무엇을 만들었나

Park3D exe 하나로 **브라우저에서 카메라 영상을 실시간으로 볼 수 있게** 하는 MJPEG 스트리밍 엔드포인트.

```html
<img src="http://<PC-IP>:13510/stream?camId=1&token=<TOKEN>">
```

외부 프로세스(파이썬 브리지) 없이 동작한다. RPC 서버가 자동 기동되므로 exe 실행만으로 `/stream` 이 함께 열린다.

Unity 원본(`CRpcServer.cs`)의 `/stream` 을 UE 로 포팅한 것이며, 기존 `cam.captureJPG`(단발 base64)와 달리 하나의 HTTP 응답으로 프레임을 계속 흘린다.

| 파라미터 | 기본값 | 범위 | 의미 |

| 응답 | 조건 |
|------|------|
| 200 + `multipart/x-mixed-replace` | 정상 |

## 3. 왜 이렇게 만들었나 — 엔진의 함정 두 개

UE 5.8 은 5.6 이전에 없던 HTTP 스트리밍 응답을 지원한다. 다만 소스를 읽어보면 **모드 두 개가 각각 다른 이유로 MJPEG 에 단독으로는 못 쓴다.**

### 함정 ① 큐 모드는 메모리가 무한 증가한다

`HttpConnectionResponseWriteContext.cpp:78,86`

```cpp
Response->Body.Append(Chunk);              // append 만 한다
BodyBytesWritten >= Response->Body.Num()   // 보낸 바이트는 offset 으로만 추적
```

이미 전송한 바이트가 버퍼에서 제거되지 않는다. 한 응답으로 계속 흘리면 **1시간에 약 900MB** 가 쌓인다.

### 함정 ② 콜백 모드는 느린 클라이언트에서 크래시한다

`HttpConnection.cpp:202-212`

```cpp
checkf(!SharedThisPtr->PendingResponse,
    TEXT("...received a third synchronous OnComplete while a response was already queued."));
```

대기 슬롯이 1개뿐인데 **엔진은 "쓰기가 끝났다"는 신호를 핸들러에 주지 않는다.** 매 프레임 콜백을 호출하는 구현은 클라이언트가 느려지는 순간(브라우저 탭 백그라운드 등) 죽는다.

### 해법 — 세그먼트 롤오버

두 모드를 결합했다.

```
[세그먼트 1] 큐에 60프레임 enqueue  →  Complete=true
                                          ↓ 연결은 AwaitingProcessing 으로 대기(타임아웃 없음)
[세그먼트 2] OnComplete(새 응답, SkipHeaderWrite, 새 큐)   ← 여기서 누적 Body 를 통째로 폐기
             큐에 60프레임 enqueue  →  ...
```

- **메모리**: 세그먼트 1개(최대 4MB / 60프레임)로 상한이 걸린다
- **크래시**: `OnComplete` 호출이 세그먼트당 1회(약 12초에 1회)라 대기 슬롯이 2개 이상 쌓일 수 없다
- **클라이언트**: 같은 TCP 연결·같은 HTTP 응답이라 세그먼트 경계를 인지하지 못한다. 재연결 불필요

### 연결 종료 감지

엔진은 종료 콜백을 주지 않는다. 대신 소유권으로 추론한다 — 연결이 죽으면 응답 객체가 소멸하며 큐 참조가 풀리므로, 매니저 쪽 `TSharedPtr` 이 `IsUnique()` 가 된다.

```cpp
if (S.Queue.IsUnique()) { /* 클라이언트 종료 */ }
```

엔진 내부 수명 규약에 기대는 추론이므로 `maxSec` 백스톱을 함께 뒀다.

## 5. 인증 — `?token=` 을 허용한 이유

`<img src>` 는 **커스텀 헤더를 붙일 수 없다.** 기존 `X-Park3D-Token` 헤더만 고수하면 브라우저에서 볼 수 없다.

```
1. X-Park3D-Token 헤더  (있으면 우선 — 프로그램 클라이언트)
2. ?token= 쿼리         (없으면 폴백 — <img> 용)
```

**판정 로직(`Park3DRpcAuth::Authorize`)·루프백 폴백·Origin 거부는 전혀 바뀌지 않았다.** 토큰의 운반 경로만 하나 늘었고, 그것도 `/stream` 에만 적용된다(`/rpc`·`/rpc/catalog` 는 종전대로 헤더 전용).

⚠ **트레이드오프**: URL 에 실린 토큰은 브라우저 히스토리·`Referer`·프록시 로그에 남을 수 있다. 서버는 쿼리스트링을 로깅하지 않는다. 사설망 + 방화벽 출발지 한정이라는 기존 전제 안에서 수용했으나, **정책 판단이므로 사용자 승인이 필요하다.** 되돌리려면 `HandleStream` 의 `bAllowQueryToken` 을 `false` 로 바꾸면 된다(대신 `<img>` 직접 사용 불가).

## 7. 게임 스레드 비용 — 반드시 알아야 할 수치

**캡처 1프레임이 게임 스레드를 약 48ms 점유한다**(1280×720). 로그의 프레임 인덱스와 타임스탬프로 산출했다.

| 부하 | 앱 틱 레이트 |
|------|-------------|
| 준무부하(fps=1) | 21.7 fps |
| 스트림 1개 @ fps=5 | **16.5 fps** |
| 스트림 1개 @ fps=10 | 11.3 fps |
| 스트림 4개 @ fps=10 | **4.6 fps** (스트림당 4.57fps 로 균등 저하) |

캡처 처리량 상한은 합계 약 18프레임/초다. 4스트림 10fps 는 물리적으로 불가하며, 크래시 없이 균등하게 떨어진다.

**이 계측 때문에 기본 `fps` 를 10 → 5 로 확정했다.** 더 부드러운 영상이 필요하면 호출자가 `?fps=` 로 올린다 — 비용을 아는 쪽이 정하도록 했다.

> 개선 여지: JPEG 인코딩을 워커 스레드로 옮기면 일부(대략 1/3 추정) 절감이 가능하다. `ReadPixels` 자체는 게임 스레드에서 렌더 플러시를 유발하므로, 근본 해결은 비동기 GPU 리드백(`FRHIGPUTextureReadback`)이 필요하다. 이번 범위에는 넣지 않았다.

### 구현 중 잡은 페이싱 결함
최초 구현은 10fps 요청에 8.6fps 만 냈다. 다음 프레임 시각을 매번 `Now + 1/fps` 로 잡아 틱 양자화(60Hz=16.7ms)만큼 주기가 계속 밀린 것이다. 목표 기준(`NextFrameTime += Period`)으로 바꿔 9.93~10.00fps 로 교정했다.

## 8. 영향도

### 회귀 없음
기존 79개 RPC, 4개 라우트, 인증 정책, 카메라 액터·매니저 코드 모두 무변경·무영향. 기존 함수 시그니처 변경은 `PassAuthOrRespond` 1건이며 기본 인자라 호출부는 무수정이다.

### 새로 생긴 것
1. 스트림 없을 때도 티커가 매 틱 돈다(빈 배열 즉시 반환 — 비용 무시 가능)
2. 클라이언트 종료마다 엔진이 `LogHttpConnection: Error: socket_send_failure` 를 남긴다. **정상 동작의 부산물**(이 에러가 곧 종료 감지의 트리거)이나 Error 레벨이라 오탐 소지가 있다
3. 인증 통과자가 앱 틱을 4.6fps 까지 떨어뜨릴 수 있다(DoS 유사). 신뢰 경계 안이지만 `MaxConcurrentStreams` 를 낮출 여지는 남는다

**LAN IP(192.168.0.125) 접속 실측**

| 요청 | 결과 |
|------|------|
| `GET /health` | 200 `{"ok":true}` |
| `POST /rpc` `cam.list` (헤더 토큰) | 200, 카메라 1대 |

## 10. 별건 발견

`cam.setPanTilt` 은 **존재하지 않는 메서드**다(-32601). 실제 이름은 `cam.setPTZ`/`cam.setPan`/`cam.setTilt`/`cam.setZoom`. 이번 변경과 무관한 기존 사실이며, 문서에만 반영했다.
