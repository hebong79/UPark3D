### 2.3 렌더링 (Lumen / VSM) — 사전 우려는 실현되지 않았다

| 항목 | 실제 |
|------|------|
| `CastShadow = false` | ✅ 적용 확인. **VSM 페이지 낭비 제거 + 근접 동일평면 셀프섀도 아크네 벡터를 원천 제거.** 바닥이 그림자를 **받는 것**은 유지. 사전 우려(M-4)가 실현되지 않은 데 이것이 기여했을 가능성이 높다(단, Z=2cm 자체로도 충분했을 수 있어 **단독 귀인은 불가**). |
| Lumen 이중 표면 빛샘 | **관측되지 않음.** Landscape(Z=0) + 아스팔트(Z=2cm) 2cm 간격에서 빛샘·GI 깜빡임 없음. |
| Z-fighting | **없음** (QA 온스크린 캡처 근거). |
| 오버드로 | Landscape 가 아스팔트에 가려져도 계속 그려진다. **순수 낭비이나 160m 규모에선 무시 가능.** |
| **⚠️ 숨은 결합** | **Landscape 를 지우거나 숨기면 커서 피킹 6곳이 전부 죽는다.** 바닥이 NoCollision 이므로 **트레이스를 받아주는 유일한 표면이 Landscape** 다. "아스팔트를 깔았으니 이제 Landscape 는 필요 없다"는 자연스러운 정리 충동이 **조용한 전면 회귀**를 부른다. → **`AMapFloorActor.h` 주석에 이미 한 줄 있으나, `Docs/` 에 크게 못박을 것.** |

## 4. 🔴 NEW-1 — 맵을 키우면 차량 JSON 좌표가 오염된다 (사전·QA 모두 놓침)

### 4.1 인과 사슬

1. 사전 분석 H-1 의 처방대로 바닥은 **`NoCollision`** 이다. → 커서 피킹(`ECC_Visibility`) 6곳은 **Landscape 를 히트한다.**
2. 즉 이 설계는 **"Landscape 표면은 Z=0 으로 평탄하다"** 는 전제 위에 서 있다. 나는 사전 분석에서 **원점과 (±8000, ±8000) 3지점만** 재어보고 *"160m 범위에서 평탄"* 이라고 썼다 — **160m 범위 안에서만 검증한 것이다.**
3. 그런데 이번 변경은 **맵 크기를 최대 `MaxSizeM = 1000` m 까지 키우는 UI 를 새로 만들었다.** 1000m 맵의 반경은 **±500m = ±50000uu** 다.
4. **Landscape 는 거기까지 평탄하지 않다.**

### 4.2 실측 — Landscape 지형 프로파일 (`SceneTools.trace_world`, 지면 월드 Z)

### 4.3 실패 시나리오 (구체적)

사용자가 크기 UI 에 **`1000` × `1000`** 을 입력하고 [적용] 한다 (UI 가 허용하는 정상 입력이다).

- **(a) 시각적 파탄**: 아스팔트는 Z=2cm 평면인데, +X 500m 지점의 Landscape 지형은 **Z=808cm** 다. → **언덕이 주차장 아스팔트를 8m 뚫고 솟아오른다.**
- **(b) 좌표 오염 (심각)**: 그 지점을 Ctrl+클릭해 차량을 배치하면 `TraceFloor` 가 **Landscape 의 Z=808.6** 을 히트한다.
  → `CarPlacementWidget.cpp:134` → `AddCarAtWorld(Hit.ImpactPoint)` → `CarPlacementLibrary` 의 `UEToUnityPos` 에서 **`unity.y = UE.Z / 100`**
  → **JSON 에 `pos.y = 8.086` 이 저장된다.**
  **이것은 내가 H-1 에서 경고한 바로 그 스키마 드리프트다 — 다만 크기가 `0.02` 가 아니라 `8.09` 이고, 들어온 문(門)이 다르다.** (메모리 노트 *"Unity 원본이 스키마 권위"* 정면 위반)
- **(c) 무반응**: 대각선 (400m, 400m) 부근은 Landscape 가 아예 없다 → 트레이스 실패 → **아스팔트가 눈앞에 보이는데 클릭해도 아무 일도 일어나지 않는다**(조용한 무동작).

### 4.4 왜 아무도 못 잡았나

- **사전 분석(나)**: Landscape 평탄성을 **±80m 까지만** 재어놓고 *"평탄"* 이라 결론지었다. 그런데 **같은 문서에서 최대 1000m 맵을 다루는 UI 를 검토하고 있었다.** 검증 범위와 기능 범위의 불일치를 스스로 눈치채지 못했다.
- **설계서**: `MaxSizeM = 1000` 을 **§11-R4 에서 "사용자 확정 사항이 아닌 설계자 가정"** 이라고 정직히 명시했다. **그 가정을 아무도 검증하지 않았다.**
- **QA**: 160×160 과 120×200 만 테스트했다 — **반경 최대 100m**, 평탄 구간 한복판이다. 클램프 테스트(`9999 → 1000`)는 **스케일 숫자만** 확인했지 그 크기에서 **월드가 성립하는지**는 보지 않았다.

### 향후 "벽 추가" 시 고려사항 (설계서 §3.5 훅)

- `AMapFloorActor::SetFloorSize()` 가 리사이즈 유일 진입점이므로 벽 역스케일(`CResizeFloor`: `wallScale = fixedThickness / floorScale`)을 **여기 한 곳**에 붙이면 된다. **설계가 이 확장을 제대로 준비해 뒀다.**
- ⚠️ **단, 벽은 바닥과 달리 콜리전이 필요할 가능성이 높다**(차량이 벽을 통과하면 안 되므로). 벽에 콜리전을 주는 순간 **H-1 의 피킹 회귀가 벽을 통해 되살아난다** — 벽이 `ECC_Visibility` 를 블록하면 벽 근처 클릭이 벽을 히트해 차량이 벽 위에 배치된다. → **벽은 `ECC_Visibility` 를 `Ignore` 하고 물리 채널만 블록하도록** 설계할 것.
- 벽 높이는 `FloorZ = 2cm` 기준으로 올라가야 하며, 벽이 **데칼 투영 박스 `[-20, +30]cm`** 를 가리지 않는지 확인할 것.
- **NEW-1 이 미해결이면 벽도 같은 함정에 빠진다** — 큰 맵에서 벽 밑동이 언덕에 묻히거나 공중에 뜬다.

## 7. 분석 한계 (추측하지 않은 것)

1. **NEW-1 은 코드·지형 실측으로부터의 연역이다.** 1000m 맵에서 실제로 차량을 배치해 JSON 을 저장하는 **엔드투엔드 재현은 하지 않았다**(분석 전용 역할 + 모달 저장 다이얼로그 제약). 지면 Z 실측(±50000uu 에서 808.6)과 `UEToUnityPos` 의 `unity.y = UE.Z/100` 는 **둘 다 확정 사실**이므로 결론의 신뢰도는 높으나, **QA 재현(§6-②)으로 확정할 것.**
2. **NEW-2 의 "placeholder 렌더" 역시 연역이다.** `Parent = None` 은 **실측 확정**이고, 동일 실패 모드의 선례가 **코드 주석에 기록**되어 있다. 다만 데칼 모드를 실제로 켜서 화면을 보지는 않았다(§6-④로 확정).
3. **`CastShadow(false)` 가 Lumen 빛샘 부재에 얼마나 기여했는지 단독 귀인 불가.** Z=2cm 자체로 충분했을 수 있다. 둘 다 유지 권장.
4. 그룹 B/C/D/E/F 결손 에셋들이 **레벨의 World Partition 액터(`__ExternalActors__` 130여 개) 내부**에서 참조되는지는 개별 액터를 열어보지 않았다. 레벨 로드 시 관련 `LoadErrors` 가 관측되지 않았으므로 **미사용으로 판단**했으나, **100% 단정은 아니다.**
