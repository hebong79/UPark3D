## 1. 배경 — 무엇이 왜 틀렸는가

선행 문서 두 건이 순차로 원인을 좁혔다.

1. `20260806_191513` — 참조 문서였던 `HTTP_API_Hucoms_V1.22.pdf`(CGI 프로토콜 명세)에는 FOV·화각·초점거리 규격이 **한 줄도 없다.** Park3D의 `DefaultHFov = 58.0f`는 이 문서가 아니라 Unity 원본 상수(`CObjCamera.cs: DEFAULT_FOV = 58.0f`)를 그대로 옮긴 값이며 출처 주석조차 없었다. 동시에 Park3D는 줌→화각을 **선형**(`58/zoom`)으로 계산하는데, 같은 `unity/` 트리의 최신 경로(`_MoveTmp/CPtzSpaceVehiclePlacer.cs`)와 RPC 레퍼런스 문서는 **탄젠트**(`2·atan(tan(29°)/zoom)`) 모델을 쓰고 있었다.
2. `20260806_192741` — 실제 렌즈 사양서 `Hucoms_HNR_Korean_191224.pdf`를 확보해 4개 모델을 대조한 결과, **58.0°는 어느 모델과도 정확히 일치하지 않는다.** Park3D `MaxZoom=36`에 대응하는 실제 모델은 **HNR-2036LA**이고 그 광각은 **H 56.5° / V 33.63°(16:9)**다. 58°는 30배 모델(HNR-2030WA, 58.9°) 쪽 값에 가깝다. 또한 4개 모델 중 3개에서 탄젠트 모델의 텔레 화각 예측 오차가 2.6% 이내인 반면 선형 모델은 7~12% 낮게 어긋나 **탄젠트 모델을 사양서가 뒷받침**한다.

**사용자가 실장비를 휴컴스 HNR-2036LA로 확정**함에 따라 이번 작업에서 다음 정정을 구현했다.

| 항목 | 기존 | 정정 후 |
|---|---|---|
| `DefaultHFov` | 58.0° | **56.5°** |
| 줌→화각 | `H0 / clamp(zoom,1,MaxZoom)` (선형) | **`2·atan( tan(H0/2) / clamp(zoom,1,MaxZoom) )`** (탄젠트) |
| 화각→줌 | `clamp(H0/hfov, 1, MaxZoom)` | **`clamp( tan(H0/2)/tan(hfov/2), 1, MaxZoom )`** |
| `MaxZoom` | 36 | 36 (유지 — 사양서 광학 x36으로 재확인) |

사양서 근거 수치:

| 모델 | 광학줌 | H 화각(Wide) | V 화각(Wide, 16:9) |
|---|---|---|---|
| **HNR-2036LA (실장비)** | x36 | **56.5°** | **33.63°** (사양서 표기와 정확히 일치 — 16:9 기준) |

## 2. 설계 결정과 기각된 대안

### 2-1. 저장 파일(`CamPos_*.json`)을 마이그레이션할 것인가 — 대안 A(무변환) 채택, 대안 B(화면 보존 재계산) 기각

`FCamDir::zoom` 필드는 주석상 "줌 배율(1~36), FOV 아님"이며 **실장비에 보내는 PTZ 명령값**이다. 화각 재현식을 고치는 이번 작업 이후, 같은 zoom 숫자가 가리키는 화각이 미세하게 달라진다(§5 참조). 이때 저장 파일의 zoom 값을 "예전과 같은 화면이 나오도록" 역산해 재기록하는 대안(B)을 검토했으나 **원리적으로 성립하지 않아 기각했다.**

**대안 B가 불가능한 이유:**

1. **보정계수가 1 미만이다.** 화면 보존식 `z' = tan(28.25°) / tan((58/z)/2°)`을 `z=1`에 대입하면 `z' = 0.969`가 나온다. 신 모델의 zoom 하한이 1이므로 `0.969`는 **표현 자체가 불가능**하다. 원인은 단순하다 — 새 기준 화각(56.5°)이 옛 기준 화각(58°)보다 **좁으므로**, zoom=1(가장 넓은 화각)에서조차 옛 화면을 재현하려면 zoom을 1 미만(광각을 더 벌리는 방향)으로 내려야 하는데 그런 배율은 정의되어 있지 않다.
2. **데이터의 73%가 여기 해당한다.** `Park3D/Save/3D/CameraPos/*.json` 27개 파일, zoom 항목 총 85건 중 `zoom = 1.0`이 53건, 로드 시 1로 보정되는 `zoom = 0.0`이 9건 — 합쳐서 **62건(73%)**이 정확히 이 표현 불가 구간에 들어간다. 대안 B는 데이터의 4분의 3에 대해 아무것도 하지 못하면서, 나머지 4분의 1의 zoom 값만 사람이 이해하기 어려운 소수(`1.5→1.531`, `2.9→3.047`, `7.4→7.844`)로 바꾸는 결과를 낳는다.
3. **멱등성을 보장할 수단이 없다.** `FCameraPosList` 스키마에는 "이 파일이 이미 마이그레이션되었는가"를 표시할 버전 필드가 없다. 마이그레이션을 한 번 걸어두면 로드→저장을 반복할 때마다 값이 표류한다(`zoom 2.0 → 2.078 → 2.158 → …`). 이를 막으려면 스키마 확장이 선행되어야 하고, 이는 "화각 규격 정정"이라는 요청 범위를 벗어난다(CLAUDE.md 3번, 외과적 변경).
4. **명령값을 고치는 것은 수정의 목적을 뒤집는다.** 이번 정정의 본질은 "실기 명령값(zoom)에 대한 화각 재현식을 실기 규격에 맞추는 것"이다. 명령값 자체를 손대 예전의(틀렸던) 화면을 억지로 재현하면, 시뮬레이터가 실기와 다시 어긋나게 된다.

**채택한 대안 A: 저장 파일은 한 바이트도 건드리지 않는다.** 화면이 −2.6%~+6% 달라지는 것은 부작용이 아니라 **정확히 의도한 정정 결과**다. QA가 `CamPos_office.json`의 SHA-256이 작업 전후 동일함을 실측해 이 결정이 코드 수준에서 지켜졌음을 확인했다(§6).

### 2-2. `58.0` 상수 3중 중복 — 통합하지 않고 테스트로 봉인

`58.0`(현재는 `56.5`)은 `CameraControlLibrary.h`의 두 함수 기본 인자(47행, 52행)와 `PTZCameraActor.h`의 `UPROPERTY`(60행) 세 곳에 중복돼 있었다. 단일 상수로 통합하는 안도 검토했으나, `MaxZoom`도 동일한 3중 구조(라이브러리 기본 인자 2 + 액터 UPROPERTY 1 + 매니저 `CameraMaxZoom`)로 이미 존재하는 기존 관례이고, 통합하려면 새 심볼·새 include(공용 상수 헤더) 또는 기존 무인자 호출부(테스트 다수) 전면 수정이 필요해 요청 범위를 벗어난다. 대신 `GetDefault<APTZCameraActor>()`의 값과 라이브러리 기본 인자 결과가 일치하는지 단정하는 신규 테스트(N1)로 **"한쪽만 고치면 즉시 실패"하도록 봉인**했다. 사후 영향도가 3개 지점 중 어느 하나를 되돌려도 이 봉인이 실제로 걸리는지 산술로 검산했고, 세 지점 모두 걸림을 확인했다(§6-2).

**최종 공식:**

```
TanHalfFovDeg(FovDeg) = Tan( DegToRad( Clamp(FovDeg, 0.001, 179.999) · 0.5 ) )   // 헤더 미노출, cpp 내부 전용

ZoomToHFov(Zoom, MaxZoom=36, DefaultHFov=56.5):
    MaxZ = (MaxZoom < 1) ? 1 : MaxZoom
    ZoomClamped = Clamp(Zoom, 1, MaxZ)
    return RadToDeg( 2 · Atan( TanHalfFovDeg(DefaultHFov) / ZoomClamped ) )

HFovToZoom(HFov, MaxZoom=36, DefaultHFov=56.5):
    MaxZ = (MaxZoom < 1) ? 1 : MaxZoom
    if (HFov <= 0) return MaxZ
    Zoom = TanHalfFovDeg(DefaultHFov) / TanHalfFovDeg(HFov)
    return Clamp(Zoom, 1, MaxZ)
```

도↔라디안 변환은 정확히 두 지점(헬퍼 입력, `ZoomToHFov` 출력)에서만 일어나며 `HFovToZoom`은 무차원 비율이라 추가 변환이 없다. 클램프 순서·경계 계약 9종은 diff상 무변경 라인이며, 바뀐 것은 변환식 한 줄씩뿐이다.

| 정의역 방어(`setFOV` 0/180/200/360) | 전부 유한값, 크래시·NaN·Inf 없음 |
| 3점 캡처(zoom 1/1.23/7.4) | 파일 크기·육안 모두 줌 방향과 일치(155,170B→158,239B→145,437B) |
| `CamPos_office.json` 로드→해시 대조 | 로드 정상(zoom 2.4 반영), 작업 전/후 SHA-256 동일(`bb078c74…`), `diff` `IDENTICAL` |

### 5-3. 관찰(회귀 아님, 참고)

`cam.setFOV(360)` 직후 캡처가 검은 화면이었다. `cam.setFOV`는 라이브러리(`TanHalfFovDeg` 가드)를 **우회**해 `Capture->FOVAngle`에 값을 직접 대입하는 기존 경로(`CamRpcModule.cpp:260`)이며, 이 파일은 `git diff`상 이번 변경과 무관함(빈 diff)을 확인했다. 구/신 모델 양쪽에서 `setFOV(360)`은 동일하게 `FOVAngle=360.0`이 그대로 들어가 동일하게 검게 나온다 — **회귀가 아니라 기존부터 있던 무검증 우회 경로**이며, 저장소 내 `setFOV` 하드코딩 호출부는 0건이라 실사용 노출도 없다.

## 6. 영향도 요약

- **호출 그래프**: `ZoomToHFov`/`HFovToZoom`의 게임 코드 소비자는 `APTZCameraActor` 단 하나(정방향 1곳, 역방향 1곳)이며, 그 상위로 `SetZoom` 4곳·`GetZoom` 2곳이 모두 무수정으로 확인됐다. 시그니처(인자 개수·타입·순서·UFUNCTION 메타)를 바꾸지 않았으므로 블루프린트·에셋 영향은 0건(Content 2,858개 파일 전수 바이트 스캔, 9개 심볼×2인코딩 = 18패턴 전부 0매치).
- **UI**: `CameraControlWidget`은 배율(1~36)만 다루고 화각을 표시·계산하지 않는다. 코드 변경 없음.
- **저장/로드**: `GetZoom()`(화각 역산)은 저장 경로에 존재하지 않는다 — UI가 저장하는 값은 화각 모델을 통과하지 않는 배율 텍스트 그대로다. 스키마 자체는 호환되나 **같은 zoom 값이 다른 화각을 의미**하게 된다(§4-3).
- **렌더/스트림**: `Capture->FOVAngle`을 공유하는 프리뷰·MJPEG 스트림·`cam.captureJPG`가 전부 동일하게 영향받는다. `camera_distance`(거리·각도 측정) 기능은 화각·zoom을 전혀 사용하지 않아 **0.000% 영향**.
- **빌드**: 신규 include·모듈 의존 없음. `Park3D.Build.cs` 무변경. `.generated.h` 재생성(UFUNCTION 기본 인자 변경)이 필요했고 정식 빌드·링크가 성공했다(DLL mtime > 소스 mtime로 실증).
- **회귀**: 사후 영향도 결론 — **회귀 없음.** 사전에 식별한 고위험 3건(58 상수 3중 중복, 탄젠트 정의역 미정의 동작, 운용 프리셋 구도 변화)과 가드레일 12건 중 완전/초과 이행 10건, 부분 이행 2건(G-4는 명시적 조기 반환 대신 클램프 조합의 부작용으로 동일 결과, G-7은 아래 §7 R-4)이었다.

## 7. 잔여 위험과 후속 조치

사후 영향도 분석(`_workspace/hnr2036la_fov_impact_post.md`)이 식별한 중간 위험 4건을 그대로 승계한다.

### R-1. `_workspace/lightport/` 측정 기준선 무효 — **사전 분석의 방향·수치가 틀렸다, 이 문서에서 정정한다**

`_workspace/lightport/regions.json`의 `cam` 프로파일(조명 루마·뭉갬·클리핑 측정용 절대 픽셀 ROI)은 구 화각(58°) 기준으로 고정돼 있다. **사전 영향도 분석은 이 ROI의 이동량을 zoom=1을 가정해 계산했으나("1.0316배 확대, x=1220→1238로 18px 바깥"), 실제로 lightport가 캡처하는 카메라는 zoom=1이 아니다.** `capture_cam.py`는 zoom을 별도로 설정하지 않고 기동 시 로드된 프리셋의 zoom을 그대로 쓰는데, 현재 `config_pmaker.json`이 가리키는 `CamPos_office.json`의 Preset 1은 **zoom=2.4**다(QA가 `cam.list`로 실측 확인).

zoom=2.4 기준으로 다시 계산하면 방향과 크기가 모두 다르다:

| | 구 모델 | 신 모델 | 이미지 배율 |
|---|---|---|---|
| zoom 2.4 화각 | 24.167° | 25.239° | **0.9562배(축소 — 화면이 넓어짐, 사전 분석의 "확대"와 정반대)** |

| ROI | 기존 사각형 | 이동 후 | 사전 분석 대비 |
|---|---|---|---|
| `ground` | (60,195,1220,275) | (85.4, 202.2, 1194.6, 278.7) | x **±25px 안쪽**(사전: 18px 바깥) |
| `decal` | (30,450,420,480) | (56.7, 446.1, 429.6, 474.7) | x **+27px** |
| `sky` | (60,20,1220,140) | (85.4, 34.9, 1194.6, 149.6) | y **+15/+10**(사전 추정 3~5px의 약 3배) |

`vp` 프로파일(1296×759 게임 창 캡처)은 PTZ 캡처가 아니므로 영향 없다.
**후속 조치**: `regions.json` `cam` 프로파일에 재검증 대상 경고 주석 삽입, `_roi_cam_check.png` 계열 확인 샷 재촬영 후 `cam` 프로파일 베이스라인(`baseline*.json`) 재취득. 재취득 전까지 기존 `baseline*.json`과 신규 측정치를 직접 비교하지 말 것.

### R-2. `Package/Windows/Park3D.exe` 미갱신 — 같은 프리셋이 두 가지 그림

패키지 산출물(`Package/Windows/Park3D/Binaries/Win64/Park3D.exe`, 345MB)의 타임스탬프는 **2026-08-06 18:39:43**이고, 이번 변경이 반영된 에디터 모듈(`UnrealEditor-Park3D.dll`)은 **21:27:56**이다. 패키지는 변경보다 2시간 48분 앞서 있어 **구 규격(선형/58°) 코드로 신 규격 저장 파일을 읽는다.** 패키지는 자기 `Save/`를 스테이지 루트에 별도로 가지며(`Package/Windows/Save/3D/CameraPos/CamPos_office.json` 존재 확인), `config_pmaker.json`의 `rpc_port`도 에디터와 동일한 13510이라 인스턴스 두 개가 동시에 뜨면 PID 확인 없이는 구분할 수 없다.

카메라 1(zoom 2.4) 기준 같은 프리셋을 열어도 **패키지 24.167° vs 에디터 25.239° — 구도 4.4% 불일치**가 발생한다. 이번 89/89 Automation·왕복 실측·클램프 검증은 전부 에디터 모듈 대상이며 **패키지 바이너리는 한 건도 검증되지 않았다.**

**후속 조치**: 배포·데모·외부 검증 전 재패키징 필수. 재패키징 전까지 `Package/Windows/`를 "구 규격 산출물"로 명시 표시할 것.

### R-3. zoom 값 의미 혼재 — 저장하는 순간부터 발생(현재 0건)

저장 파일의 `zoom`은 여전히 실기 PTZ 명령값이고 스키마·필드는 그대로다. 그러나 `CamPos_office.json`처럼 소수 첫째 자리에서 끊긴 값(2.4/2.9/3.4/4.4/7.4)은 "사람이 화면을 보며 다이얼로 맞춘" 결과로 보이며, 그 숫자는 **구 모델에서 원하는 구도를 내던 값**이라는 정보를 담고 있다. 사용자가 이번 정정 이후 UI에서 같은 구도를 다시 맞추고 [저장]을 누르는 순간, 예를 들어 zoom 2.4(구 모델 24.167°)와 같은 화각을 신 모델에서 내려면 **zoom 2.510**을 입력해야 하고 그 값이 파일에 기록된다. `FCameraPosList`에는 스키마 버전 필드가 없어 "이 파일의 zoom이 구 모델 기준인지 신 모델 기준인지" 구분할 수단이 없다.

**현재 혼재 0건**(27개 파일 전부 구 모델 기준 상태 그대로). 데이터 무결성 문제가 아니라 운영·추적성 문제다.

**후속 조치**: 파일명·문서·주석으로 "규격 정정 이후 저장" 여부를 남기는 규약을 검토한다. 근본 해결(스키마 버전 필드 도입)은 별도 설계 대상이며 이번 범위 밖이다.

### R-4. 구버전 바이너리 소실로 신/구 픽셀 대조 영구 불가

가드레일 G-7(구현 전후 동일 zoom 캡처 확보)은 "구현 전 조건"이었으나 실제로는 구현 후 QA 단계에서 착수되어 **구현 전 캡처가 남아있지 않다.** 구버전 에디터 바이너리도 이미 신규 DLL로 교체되어 더 이상 존재하지 않는다. 따라서 신/구 모델의 실제 렌더 화면을 픽셀 단위로 나란히 비교하는 것은 **이 세션뿐 아니라 이후로도 재현이 불가능**하다.

**대체 근거**: Automation `Park3D.CameraControl.Fov`의 `FOVAngle` 절대값 단정(예: `SetZoom(1)→56.500`, 구 모델 58.000 대비 좁아짐 확인)과 사양서 대조 수치(§1)가 유일한 근거다. 사후 영향도는 이를 "회복 불가"로 명시했다. **후속 조치**: 없음(회복 불가). 앞으로 유사한 렌더 파라미터 변경 시에는 **구현 착수 전에** 전/후 캡처를 확보하는 순서를 지킬 것.
