# GPU 0(Intel UHD 630) + GPU 1(RTX 2080 Super) 동시 사용 가능성 및 Park3D 2개 실행 성능 진단

- 작성일: 2026-09-05 09:58:36
- 성격: **질문 답변 + 실측 진단**. 저장소 파일 변경 없음(이 문서만 신규).
- 질문
  1. GPU 0번을 GPU 1과 같이 사용할 수 있는 방법이 있나?
  2. 같이 사용하면 GPU 부족 현상 및 속도 저하를 막을 수 있나?
  3. Park3D를 2개 띄울 때 너무 느린데, GPU 2개를 쓰면 어느 정도 해결되는가?

## 0. 요약 (결론 먼저)

| 질문 | 답 |
|------|-----|
| 1. 두 GPU 동시 사용 | **한 프로세스가 두 GPU로 렌더링하는 것은 불가능.** 다만 "인스턴스 A는 RTX, 인스턴스 B는 Intel"처럼 **프로세스 단위 분배는 가능**(`-graphicsadapter=N`). |
| 2. 부족·저하 해소 | **아니오.** VRAM 압박은 풀리지만, iGPU로 보낸 인스턴스가 이 프로젝트의 렌더 기능 요구(Lumen·Nanite·VSM·RayTracing)를 못 채워 **느려지는 정도가 아니라 렌더가 깨지거나 기동에 실패할 가능성이 높다.** |
| 3. 2개 실행 문제 해결 | **해결되지 않는다.** 진짜 원인은 GPU가 1개라서가 아니라 **VRAM 8GB 초과**다. 실측상 인스턴스 1개가 이미 5.6GB를 쓴다. 해결책은 GPU를 늘리는 게 아니라 **인스턴스당 VRAM을 줄이는 것**(또는 VRAM 큰 GPU로 교체). |

## 2. 질문 1 — 두 GPU를 같이 쓸 수 있나?

### 2.1 "한 프로세스가 두 GPU로 동시 렌더링" → **불가능**

- UE5에도 mGPU(멀티 GPU) 경로는 있지만, 쓸 수 있는 범위가 매우 좁다.
  - **nDisplay**(다중 디스플레이 클러스터)와 **Movie Render Queue**(오프라인 렌더) 한정이다.
  - 일반 게임 렌더 패스(우리가 쓰는 경로)에는 적용되지 않는다.
  - 전제 조건이 **동일 계열 NVIDIA GPU 여러 장**이다. **Intel iGPU + NVIDIA dGPU 혼합은 대상이 아니다.**
- DX12의 explicit multi-adapter(이종 GPU 조합)는 API 레벨에서는 존재하지만 UE5의 기본 렌더러가 지원하지 않는다. 엔진 렌더러를 직접 개조하는 수준의 작업이며, 현실적인 선택지가 아니다.
- SLI는 RTX 20 시리즈 이후 사실상 종료됐고, 애초에 iGPU와는 묶이지 않는다.

### 2.2 "프로세스마다 다른 GPU를 쓰게 한다" → **가능**

이건 된다. 두 가지 방법이 있다.

**방법 A — UE 커맨드라인 (권장, 인스턴스별로 명확)**

```
Park3D.exe -graphicsadapter=0   ... (Intel UHD 630)
Park3D.exe -graphicsadapter=1   ... (RTX 2080 Super)
```

- UE의 D3D RHI가 읽는 인자다. 기본값은 -1(가장 성능 좋은 어댑터 자동 선택)이라, 지금은 **두 인스턴스가 모두 RTX로 간다.**
- 어댑터 인덱스는 작업관리자의 "GPU 0 / GPU 1" 번호와 반드시 일치하지는 않는다. 기동 로그의 어댑터 선택 줄로 실제로 어디에 붙었는지 확인해야 한다.

**방법 B — Windows 설정**

`설정 > 시스템 > 디스플레이 > 그래픽`에서 `Park3D.exe`를 추가하고 "절전(=Intel)" 또는 "고성능(=NVIDIA)" 지정.
단, **exe 단위 설정이라 같은 exe를 두 개 띄우면 둘 다 같은 쪽으로 간다.** 인스턴스별 분리에는 방법 A를 써야 한다.

## 3. 질문 2 — 같이 쓰면 부족·저하가 해소되나?

**아니오.** 이유가 두 가지고, 두 번째가 결정적이다.

### 3.1 VRAM 압박은 실제로 풀린다 (이건 사실)

인스턴스 하나를 iGPU로 보내면 RTX의 VRAM 5.6GB가 비므로, 남은 인스턴스는 8GB를 혼자 쓴다. **RTX 쪽 인스턴스는 실제로 지금보다 빨라진다.**

### 3.2 그러나 iGPU로 간 인스턴스는 "느리게라도 도는" 게 아니다

이 프로젝트의 렌더 설정(`Park3D/Config/DefaultEngine.ini:11-31`)은 다음과 같다.

```ini
[/Script/Engine.RendererSettings]
r.AllowStaticLighting=False              ; 정적 라이팅 없음 → 동적 GI 필수
r.GenerateMeshDistanceFields=True
r.DynamicGlobalIlluminationMethod=1      ; Lumen GI
r.ReflectionMethod=1                     ; Lumen 반사
r.RayTracing=True
r.Substrate=True
r.Shadow.Virtual.Enable=1                ; Virtual Shadow Maps
```

여기에 Nanite 메시가 다수 있다(CLAUDE.md 2026-09-04 항목: Nanite 메시 44종).

**Lumen · Nanite · Virtual Shadow Maps는 모두 D3D12 + Shader Model 6 을 요구한다.** Intel UHD 630(Gen9.5, 2017년 아키텍처)은 이 요구를 온전히 채우지 못한다. 또 `r.RayTracing=True`인데 **UHD 630은 DXR 하드웨어 레이트레이싱을 지원하지 않는다.**

예상되는 결과는 "20fps로 느리게 돌아간다"가 아니라 다음 중 하나다.
- Nanite/Lumen이 폴백으로 떨어져 **화면이 어둡거나 형상이 다르게 보인다** — 이 프로젝트는 이미 "간접광이 빠져 스트림만 어둡고 갈색으로 나오는" 증상을 겪은 이력이 있다(`DefaultGame.ini:126-128` 주석).
- `Missing global shader` 또는 셰이더 모델 미충족으로 **기동 실패**.

> ⚠ **이 PC에서 실제로 `-graphicsadapter`로 iGPU 기동을 시도해 보지는 않았다.** 위는 하드웨어 사양과 UE5 요구사항에서 나온 예측이다. 확인하려면 실제로 띄워 보면 되고, 그건 5분이면 판정된다(아래 6절).

### 3.3 성능 격차 (참고 수치)

| 항목 | RTX 2080 Super | Intel UHD 630 | 배율 |
|------|----------------|---------------|------|
| FP32 연산 | 약 11.15 TFLOPS (3072SP × 2 × 1.815GHz) | 약 0.46 TFLOPS (24EU × 8 × 2 × 1.2GHz) | **약 24배** |
| 메모리 대역폭 | 496 GB/s (GDDR6 256bit) | 약 46.9 GB/s (DDR4-2933 듀얼채널, **CPU와 공유**) | **약 10.6배** |
| 하드웨어 RT | 지원 | 없음 | — |

설령 렌더가 돌아간다 해도 iGPU 쪽 인스턴스는 **쓸 수 있는 속도가 나오지 않는다.** 게다가 iGPU가 시스템 RAM 대역폭을 CPU와 나눠 쓰므로, **RTX 쪽 인스턴스의 CPU 성능(게임 스레드)까지 같이 떨어진다.**

## 4. 질문 3 — Park3D 2개가 느린 진짜 원인

### 4.1 원인은 GPU 개수가 아니라 VRAM 초과다

인스턴스 1개 실측(5,603MB)으로 2개 실행 시를 계산하면:

```
Park3D × 2      : 5,603 × 2 = 11,206 MB
데스크톱·기타    :               762 MB
─────────────────────────────────────
합계             :            11,968 MB
가용 VRAM        :             8,192 MB
─────────────────────────────────────
초과             :            -3,776 MB   ← 46% 초과
```

VRAM이 넘치면 Windows WDDM이 초과분을 **시스템 RAM("공유 GPU 메모리")으로 밀어내고**, GPU가 그 데이터를 쓸 때마다 **PCIe 3.0 x16(약 15.8 GB/s)**로 왕복시킨다. VRAM 대역폭 496 GB/s 대비 **약 31배 느린 경로**다.

이것이 "너무 느려서 사용하기 힘든" 증상의 정체다. **VRAM 초과는 완만한 성능 저하가 아니라 절벽이다** — 넘치는 순간 프레임이 급락하고 끊긴다.

### 4.2 연산도 포화 상태이긴 하다 (그러나 이건 부차적)

3D 엔진 사용률이 인스턴스 1개에 54.6%다. 2개면 **109%로 100%를 넘는다.**
다만 이건 선형적인 저하다(각자 대략 절반 속도). VRAM 초과의 절벽에 비하면 훨씬 덜 치명적이다.

### 4.3 그래서 GPU 2개를 쓰면?

- **RTX 쪽 인스턴스 1개**: VRAM 독점 + 연산 독점 → 크게 개선된다.
- **iGPU 쪽 인스턴스 1개**: 3절의 이유로 **사용 불가 수준이거나 아예 안 뜬다.**

결국 "쓸 수 있는 인스턴스가 1개"라는 점은 지금과 같다. **문제가 해결되지 않는다.**

## 5. 실효성 있는 대안 (효과 큰 순서)

목표는 **인스턴스당 VRAM을 5.6GB → 3.5GB 이하로** 낮추는 것이다. 그러면 2개가 8GB 안에 들어간다.

### 5.1 텍스처 스트리밍 풀 축소 — 가장 직접적

현재 `Config`에 `r.Streaming.PoolSize` 설정이 **없다**(엔진 기본값 사용). 두 번째 인스턴스에만 커맨드라인으로 건다.

```
Park3D.exe -ExecCmds="r.Streaming.PoolSize 800"
```

CLAUDE.md 2026-08-04 기록에 이 프로젝트 차량 메시가 매우 무겁다는 실측이 있다(개당 1.0~4.5GB 요구, 삼각형 평균 170만). 텍스처 풀이 VRAM의 상당 부분일 가능성이 높다.

### 5.2 레이트레이싱 끄기 — 실제로 안 쓴다면 순수 이득

`r.RayTracing=True`는 **씬의 RT 가속 구조(BVH)를 VRAM에 상주시킨다.** Lumen을 소프트웨어 트레이싱으로 쓰고 있다면 이 BVH는 통째로 낭비다.

```
Park3D.exe -ExecCmds="r.RayTracing 0"
```

> ⚠ 이건 화면이 바뀔 수 있으므로 **캡처 이미지로 A/B 확인이 필수다.** 이 프로젝트는 "값이 들어갔는데 화면은 다르다"에 세 번 속은 이력이 있다(CLAUDE.md 2026-08-17).

### 5.3 Virtual Shadow Map 물리 페이지 풀 축소

```
Park3D.exe -ExecCmds="r.Shadow.Virtual.MaxPhysicalPages 2048"
```
(기본 4096. VSM 풀은 고정 크기로 VRAM을 점유한다.)

### 5.4 두 번째 인스턴스의 해상도 축소

```
Park3D.exe -ResX=1280 -ResY=720 -windowed
```
렌더 타깃·G버퍼·Lumen 자료구조가 전부 해상도에 비례한다. Substrate를 켠 상태라 G버퍼가 특히 무겁다.

### 5.5 Lumen 하향을 화면에도 적용

현재 `DefaultGame.ini:130-134`의 Lumen 하향(`MainLumen*Quality=0.5`)은 **캡처 전용**이며 플레이어 화면에는 걸리지 않는다(`DefaultGame.ini:107-108` 주석 명시). 두 번째 인스턴스는 화면에도 걸어 볼 수 있다.

```
Park3D.exe -ExecCmds="r.Lumen.SceneLightingQuality 0.5, r.Lumen.ScreenProbeGather.Downsample 2"
```

### 5.6 근본 해결 — GPU 교체

인스턴스를 3개 이상 띄울 계획이라면 튜닝으로는 한계가 온다. **VRAM 16GB 이상** 제품(RTX 4070 Ti Super 16GB, 4080/5070 Ti 등)이면 5.6GB × 2 = 11.2GB가 여유롭게 들어가고, 연산도 2080 Super 대비 2~3배라 3D 엔진 포화(109%) 문제도 함께 풀린다.

**Intel UHD 630은 이 문제에 대한 답이 아니다.**

## 6. 확인 방법 (실측으로 판정할 것)

### 6.1 VRAM 초과가 진짜 원인인지 확정

Park3D를 2개 띄운 상태에서:

```powershell
nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv
(Get-Counter '\GPU Process Memory(*)\Shared Usage').CounterSamples |
  Where-Object { $_.CookedValue -gt 100MB } |
  ForEach-Object { [pscustomobject]@{ Inst=$_.InstanceName; MB=[math]::Round($_.CookedValue/1MB,0) } }
```

**`Shared Usage`가 0이 아니면 VRAM이 넘쳐 시스템 RAM으로 밀려난 것이 확정된다.** 이게 이 진단의 결정적 증거이며, 아직 측정하지 않은 항목이다.

### 6.2 iGPU 기동이 가능한지 판정

```
Park3D.exe -graphicsadapter=0 -windowed -ResX=1280 -ResY=720
```
로그에서 어댑터 선택 줄과 셰이더 모델 경고를 본다. **판정은 로그가 아니라 화면 캡처로 한다** — 이 프로젝트의 반복된 교훈이다.

## 7. 미검증 항목 (정직하게)

- **Park3D 2개 동시 실행 상태를 직접 측정하지 않았다.** 4.1의 11,968MB는 1개 실측값(5,603MB)에서 계산한 값이다.
- **`-graphicsadapter=0`으로 iGPU 기동을 시도하지 않았다.** 3.2의 결론은 하드웨어 사양과 UE5 요구사항에 근거한 예측이다.
- 5절 대안들의 VRAM 절감폭을 실측하지 않았다. 어느 항목이 5.6GB 중 얼마를 차지하는지는 `stat memory` / `r.Streaming.PoolSize` A/B로 재야 한다.
