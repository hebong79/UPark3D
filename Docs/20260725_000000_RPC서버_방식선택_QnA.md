# 질문 답변: RPC 서버 구현 — Goal/Loop vs 기존(표준 오케스트레이터) 방식

작성일: 2026-07-25
질문: "goal/loop 방식과 기존 방식 중 어느 쪽이 좋은가?" (Unity RPC 91 method → Unreal 포팅 작업 기준)

## 결론
**기존 방식(표준 오케스트레이터) 기반**을 추천. 단, 34개 핸들러 배선 구간은 loop식 리듬(구현→수동 컴파일→automation/HTTP 검증→수정 반복)으로 운용하는 **하이브리드**.

## 비교
| 관점 | 기존(표준) | Goal/Loop(parking-cpp-loop) |
|---|---|---|
| 강점 | 설계 게이트·역할분리·영향도·문서 게이트 | 자율 반복, 컴파일만 수동 게이트, 실패 시 자동 재구현 |
| 적합 문제 | 계약 확정 well-specified 구현, 파급 큰 아키텍처 | 정답 미상의 PIE 시각/동작 수렴형(try→관찰→재설계) |

## 이유
1. RPC 서버 코어(HttpServer 스레딩·JSON-RPC 프로토콜·에러코드 매핑·디스패처·씬 게이트)는 34개 전체에 파급 → 설계 게이트로 먼저 확정해야 한다. Loop는 코어를 자율로 흔들 위험.
2. 각 method 계약(파라미터/응답/위임)이 md에 이미 확정 → Loop의 핵심 가치(자율 재설계 반복)가 불필요. 실패는 컴파일·JSON 형식 같은 기계적 수정.
3. 신규 모듈·Build.cs 변경·CORS·엔드포인트 등 영향도/문서 게이트가 중요한 규모.

## Goal/Loop가 더 나았을 상황
"카메라 거리감이 자연스럽게 보일 때까지" 같은 PIE 시각 수렴형. 이번 RPC는 계약이 결정적이라 비해당.

## 사용자 결정
"추천대로 진행" → 표준 방식, Phase 1 = 서버 코어 + 백엔드 실재 34개 표면(28 실동작 + 6 정직한 미구현).
