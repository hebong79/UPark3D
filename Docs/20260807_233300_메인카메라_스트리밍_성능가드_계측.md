## 2. 구현 중 발견한 함정 — ShowFlags는 등록 후에 걸어야 한다

이번 작업에서 가장 중요한 지점이다. 엔진 소스를 확인하지 않았으면 **가드가 조용히 아무 효과도 내지 않는**
코드를 작성할 뻔했다.

`USceneCaptureComponent::OnRegister()`는 내부에서 `UpdateShowFlags()`를 호출한다
(`Engine/Private/Components/SceneCaptureComponent.cpp:292`). 그리고 그 함수는 이렇게 생겼다.

```cpp
void USceneCaptureComponent::UpdateShowFlags()
{
    USceneCaptureComponent* Archetype = Cast<USceneCaptureComponent>(GetArchetype());
    if (Archetype)
    {
        ShowFlags = Archetype->ShowFlags;      // ← 통째로 되돌린다
    }
    for (FEngineShowFlagsSetting ShowFlagSetting : ShowFlagSettings) { ... }
}
```

즉 `RegisterComponent()` **앞에서** `ShowFlags`를 설정하면 아키타입 값으로 덮여 전부 사라진다.
컴파일도 되고 런타임 에러도 없다. 그냥 가드가 안 걸릴 뿐이라 발견이 어렵다.

그래서 호출 순서를 이렇게 고정하고 주석으로 못 박았다.

```cpp
Actor->SetRootComponent(Capture);
Capture->RegisterComponent();   // ← OnRegister() 가 UpdateShowFlags() 로 ShowFlags 를 초기화
ApplyMainCaptureGuards();       // ← 반드시 그 뒤
```

부수적으로 확인한 것: `ShowFlags`는 `GENERATED_UCLASS_BODY()`(74행) 이후 `public:`(199행) 구간에 있어
직접 접근 가능하고, 5.5 deprecation 경고는 바로 위의 `ShowFlagSettings` 배열에 붙은 것이지
`ShowFlags`에 붙은 것이 아니다. 따라서 직접 대입해도 deprecation 경고가 나지 않는다.

## 3. Lumen — 끄지 않고 품질만 낮춘 방법

### 3.1 왜 끄면 안 되는가

선행 작업에서 이미 지적한 그대로다. `LumenGlobalIllumination` / `LumenReflections` 쇼플래그를 끄면
간접광이 통째로 빠져 **스트림만 어둡고 갈색으로** 나온다
(`Park3D/Docs/Bug/20260806_163723_Park3D_스트림영상_간접광누락_진단.md`).

따라서 이 두 쇼플래그는 **의도적으로 건드리지 않았다.** 코드 주석에도 그 이유를 남겨,
나중에 "성능 때문에 Lumen 껐다"는 변경이 무심코 들어오지 않게 했다.

### 3.2 대신 한 것 — 같은 경로를 더 싼 품질로

`FPostProcessSettings`의 Lumen 품질 스칼라 4종을 캡처 전용으로 오버라이드한다.

```cpp
FPostProcessSettings& PP = MainCapture->PostProcessSettings;

PP.bOverride_LumenSceneLightingQuality = 1;
PP.LumenSceneLightingQuality = FMath::Clamp(MainLumenSceneLightingQuality, 0.25f, 2.f);

PP.bOverride_LumenFinalGatherQuality = 1;
PP.LumenFinalGatherQuality = FMath::Clamp(MainLumenFinalGatherQuality, 0.25f, 2.f);

PP.bOverride_LumenSceneDetail = 1;
PP.LumenSceneDetail = FMath::Clamp(MainLumenSceneDetail, 0.25f, 4.f);

PP.bOverride_LumenReflectionQuality = 1;
PP.LumenReflectionQuality = FMath::Clamp(MainLumenReflectionQuality, 0.25f, 2.f);

MainCapture->PostProcessBlendWeight = 1.f;
```

클램프 범위는 엔진 `Scene.h`의 `meta=(ClampMin=…, UIMax=…)`에서 그대로 가져왔다
(`LumenSceneDetail`만 상한이 4, 나머지는 2). 엔진 기본값은 모두 1.0이고 우리는 0.5로 낮춘다.

**노출은 건드리지 않는다는 점이 중요하다.** `bOverride_`를 세운 항목만 블렌드에 참여하므로,
월드 PostProcessVolume의 `PP_FixedExposure` 설정은 그대로 적용된다. 스트림 밝기가 화면과 갈라지지 않는다.

## 4. 꺼도 되는 것들 — 캡처 전용 ShowFlags

```cpp
FEngineShowFlags& Flags = MainCapture->ShowFlags;
if (bMainDisableMotionBlur)             { Flags.SetMotionBlur(false); }
if (bMainDisableBloom)                  { Flags.SetBloom(false); }
if (bMainDisableDepthOfField)           { Flags.SetDepthOfField(false); }
if (bMainDisableScreenSpaceReflections) { Flags.SetScreenSpaceReflections(false); }
if (bMainDisableAntiAliasing)
{
    Flags.SetAntiAliasing(false);
    Flags.SetTemporalAA(false);
}
```

**이 플래그는 캡처 패스에만 걸린다.** 화면(플레이어 뷰)의 렌더링에는 아무 영향이 없다 —
`SceneCaptureComponent`의 `ShowFlags`는 그 캡처의 `ViewFamily`에만 적용되기 때문이다.

### 두 가지 짚어둘 점

**(a) SSR을 꺼도 반사가 사라지지 않는다.** 이 프로젝트는 Lumen을 쓰므로 반사는 Lumen Reflections가
담당한다. SSR 쇼플래그는 레거시 경로라 꺼도 화면에서 반사가 없어지지 않고, Lumen 반사는 위 §3.2에서
품질만 낮춘 채 살아 있다.

**(b) AA를 끄는 것에는 실질적 트레이드오프가 있다.** `AntiAliasing`을 끄면 TSR/TAA 경로가 통째로 빠지는데,
TSR은 단순 계단 제거만 하는 게 아니라 **Lumen의 시간적 노이즈를 걸러주는 디노이저 역할도 한다.**
따라서 이 가드는 비용을 줄이는 대신 캡처가 지글거리게 만들 수 있다.

> 스트림이 거칠어 보이면 `bMainDisableAntiAliasing=False`가 첫 번째 손잡이다.
> 요청대로 기본값은 True로 두되, 되돌릴 수 있게 config로 뺐다.

`bAlwaysPersistRenderingState = true`는 그대로 유지했다(요구사항 4). AA를 꺼도 Lumen은 여전히
뷰 스테이트 히스토리를 사용하므로 이 값은 계속 필요하다.

## 5. 해상도 960×540

기본값을 1280×720에서 960×540으로 낮췄다. 픽셀 수는 921,600 → 518,400으로 **56%**다.

GPU 리드백(`ReadPixels`)과 JPEG 인코딩 비용은 픽셀 수에 거의 선형이므로, 캡처 비용을 낮추는 가장
확실하고 예측 가능한 손잡이다. `MainWidth`/`MainHeight`로 조절 가능하며 재빌드가 필요 없다.

## 6. 계측 — 추정이 아니라 숫자로

### 6.1 무엇을 재는가

캡처 1회의 **게임 스레드 총 비용**을 잰다. 세 단계를 합쳐서 재는 이유는, 프레임 스파이크로 체감되는
값이 바로 이 합이기 때문이다.

```
씬 캡처(CaptureScene) + GPU 리드백(ReadPixels) + JPEG 인코딩(EncodeColors)
```

```cpp
const double CaptureStartSeconds = FPlatformTime::Seconds();
... // 시점 미러링 → CaptureScene → ReadPixels → EncodeColors
RecordMainCaptureMs((float)((FPlatformTime::Seconds() - CaptureStartSeconds) * 1000.0));
```

**성공한 캡처만 기록한다.** 실패 경로(플레이어 없음, RHI 없음)는 거의 공짜라, 섞이면 평균이
비현실적으로 낮게 나와 판단을 흐린다.

### 6.2 링 버퍼

최근 `MainStatWindow`(기본 60)회를 링 버퍼에 담고 평균·최대를 낸다.

```cpp
MainCaptureMsRing[MainCaptureMsNext] = Ms;
MainCaptureMsNext = (MainCaptureMsNext + 1) % Window;
MainCaptureMsCount = FMath::Min(MainCaptureMsCount + 1, Window);
```

링을 0부터 순차로 채우므로 가득 차기 전에는 `[0, Count)`가 곧 유효 구간이다. 덕분에 창이 다 차기 전에도
평균이 0으로 희석되지 않고 정확하다. 창 크기가 바뀌면(설정 변경) 통계를 처음부터 다시 쌓는다.

**평균만이 아니라 최대치를 함께 내는 것이 이번 요청의 핵심이다.** 프레임 스파이크는 평균이 아니라
꼬리에서 발생하므로, 평균 12ms / 최대 90ms 같은 분포가 보여야 판단이 된다.

### 6.3 로그

`MainStatLogSeconds`(기본 30초)마다 한 줄.

```
[CamStream] 메인 뷰 캡처 비용: 평균 12.34ms / 최대 28.71ms / 직전 11.90ms
            (표본 60, 창 60, 960x540, 목표 5.0fps 실측 4.9fps, 가드=1)
```

실시간(`FPlatformTime`) 기준이라 일시정지·저프레임 구간에서도 주기가 일정하다.
표본이 0이면 로그를 남기지 않고 **시각도 갱신하지 않는다** — 갱신해 버리면 첫 표본이 쌓이기 전에
주기 한 칸을 헛되이 소모하기 때문이다.

채널이 멈추면 통계를 버린다. 다음 세션 수치에 이전 세션 표본이 섞이면 판단이 흐려진다.

### 6.4 `cam.streamStatus` 응답

`main` 블록에 계측값과 가드 상태가 함께 나온다. 가드 상태를 같이 내는 이유는, A/B 측정 시
**어느 쪽 수치인지 응답만 보고 구분**할 수 있게 하기 위해서다.

```json
{
  "main": {
    "enabled": true, "port": 13600, "serving": true, "clients": 1,
    "fps": 4.9, "targetFps": 5.0, "width": 960, "height": 540,

    "captureAvgMs": 12.34,
    "captureMaxMs": 28.71,
    "captureLastMs": 11.90,
    "captureSamples": 60,
    "statWindow": 60,

    "guard": {
      "enabled": true,
      "motionBlurDisabled": true,
      "bloomDisabled": true,
      "depthOfFieldDisabled": true,
      "ssrDisabled": true,
      "antiAliasingDisabled": true,
      "lumenQualityLowered": true,
      "lumenSceneLightingQuality": 0.5,
```

## 7. 설정 전체 (`Park3D/Config/DefaultGame.ini`)

```ini
[/Script/Park3D.CamStreamSubsystem]
...
MainWidth=960
MainHeight=540

; 마스터 스위치 — A/B 측정 시 이 한 줄만 바꾼다
bMainGuardEnabled=True

bMainDisableMotionBlur=True
bMainDisableBloom=True
bMainDisableDepthOfField=True
bMainDisableScreenSpaceReflections=True
bMainDisableAntiAliasing=True

; Lumen 은 끄지 않고 품질만 하향
bMainLowerLumenQuality=True
MainLumenSceneLightingQuality=0.5
MainLumenFinalGatherQuality=0.5
MainLumenSceneDetail=0.5
MainLumenReflectionQuality=0.5

MainStatWindow=60
MainStatLogSeconds=30.0
```

전부 재빌드 없이 이 파일만 고치고 **재기동**하면 반영된다(설정은 기동 시 읽힌다).

### `bMainGuardEnabled`를 둔 이유

요구사항 7이 "숫자로 판단"이므로, 비교 대상이 있어야 숫자가 의미를 갖는다.
이 스위치 하나로 가드 전/후를 같은 장면에서 측정할 수 있다.

```
1) bMainGuardEnabled=False → 기동 → 30초 대기 → main.captureAvgMs / captureMaxMs 기록
2) bMainGuardEnabled=True  → 기동 → 30초 대기 → 같은 값 기록 → 비교
```

## 10. 재기동 후 측정 절차 (사용자용)

선행 문서 §8의 재기동 방법을 그대로 따르되(exe 교체 또는 재패키징), **`DefaultGame.ini`가 이번에도
바뀌었으므로 스테이지 쪽 config도 반드시 함께 갱신해야 한다.** 이번에는 C++ 기본값과 ini 값이 같아서
갱신을 빠뜨려도 동작은 하지만, 이후 튜닝이 전혀 먹지 않는 상태가 된다.

### 측정

```powershell
# 1) 스트림 접속(측정은 클라이언트가 붙어 있어야 시작된다 — 0명이면 캡처를 안 한다)
Start-Process 'http://localhost:13600/'

# 2) 30초 뒤 로그에서 확인
#    [CamStream] 메인 뷰 캡처 비용: 평균 ...ms / 최대 ...ms ...

# 3) 또는 RPC 로 즉시 조회
#    cam.streamStatus → main.captureAvgMs / captureMaxMs / captureSamples
```

### 판단 기준

`MainFps=5.0`이면 캡처 간격이 200ms다. 캡처 1회가 평균 12ms면 게임 스레드의 약 6%를 쓴다.
**최대치가 프레임 예산(60fps 기준 16.7ms)을 크게 넘으면 그 순간이 곧 체감 스파이크다.**

튜닝 우선순위(효과가 큰 순서):

1. `MainFps` 낮추기 — 스파이크 빈도가 선형으로 준다. 가장 확실하다.
2. `MainWidth/MainHeight` 낮추기 — 리드백·인코딩 비용이 픽셀 수에 비례한다.
3. `MainLumenFinalGatherQuality` → `MainLumenSceneLightingQuality` 낮추기 — 씬 캡처 비용.
4. `JpegQuality` 낮추기 — 인코딩 비용(다만 카메라 채널과 공유하는 값이다).

## 11. 남은 과제

1. **§9.4의 실측 전부.** 재기동 후 수행 필요.
2. **단계별 분해 계측이 없다.** 현재는 총 시간 하나만 낸다. "리드백이 비싼가, 씬 캡처가 비싼가"를
   가르려면 `CaptureScene` / `ReadPixels+Encode`를 분리해 재야 한다. 총 시간만으로 판단이 안 되면
   그때 추가하는 것이 순서다(지금 넣으면 링 버퍼가 3배가 된다).
3. **가드는 메인 뷰 전용이다.** PTZ 카메라 채널에는 적용되지 않았다. 카메라 스트림에서도 같은 문제가
   보이면 같은 방식으로 확장할 수 있다.
4. **동기 캡처(P1) 구조는 그대로다.** 근본 해결은 비동기 GPU 리드백(P2)이며, 이번 가드는 그 전까지
   비용을 줄이는 완화책이다.
