# 클로드 내장 루프 기능 vs 하네스 Goal/Loop — 존치 판단 (2026-08-04)

## 질문
1. 하네스의 Goal/Loop가 없어도 클로드 자체에 Goal/Loop 기능이 탑재되어 있는가?
2. 현재 하네스의 Goal/Loop(`parking-cpp-loop`)를 없애도 괜찮은가?

---

## 1. 클로드(Claude Code) 내장 루프 기능 — 있다

| 내장 기능 | 반복 방식 | 종료 조건 | 사람 개입 대기 |
|---|---|---|---|
| 에이전트 루프 | 도구 호출 → 결과 → 재호출 | 도구를 안 부르면 턴 종료 | 턴 종료로만 |
| `/loop` 스킬 | 지정 간격(`/loop 5m ...`) 또는 자기 페이싱(`ScheduleWakeup`)으로 프롬프트 재실행 | 사용자 중단 또는 `stop` | ✕ — **시간**에 반응하지 사람의 "완료" 신호에 반응하지 않음 |
| `Workflow` 도구 | JS 스크립트로 결정적 반복. `loop-until-dry` / `loop-until-count` / `loop-until-budget` 패턴 내장 | 스크립트 조건 | ✕ — **서브에이전트는 사용자에게 질문할 수 없음** |
| `Agent`(서브에이전트) | 각자 자기 에이전트 루프 보유 | 자체 판단 | ✕ — 동일 제약 |
| `CronCreate` / `ScheduleWakeup` | 스케줄 기반 재기동 | 삭제 시까지 | ✕ |

**답: 예, 탑재되어 있다.** 특히 `Workflow`는 "실패하면 다시" 류의 루프를 하네스보다 **결정적으로** 돌린다. 반복 제어 자체는 내장 기능이 더 낫다.

### 그러나 내장 기능이 못 하는 것 하나
**"턴을 끝내고 사람이 Ctrl+Alt+F11을 누를 때까지 기다렸다가, '완료' 신호를 받고 이어서 돈다."**

- `/loop`는 **시각**에 깨어난다. 사람의 완료 신호를 기다리지 않는다.
- `Workflow`·`Agent`의 서브에이전트는 **사용자에게 질문·대기가 불가능**하다. 게이트를 넣으면 그 자리에서 멈추거나 실패한다.
- 에이전트 루프는 턴 종료로 대기할 수 있지만, 재개 시 무엇을 이어가야 하는지에 대한 프로토콜이 없다.

`parking-cpp-loop`의 존재 이유가 정확히 이 지점이다(`SKILL.md:11` 확정 사실 — MCP로 Live Coding 트리거 불가).

## 2. 없애도 되는가 — **권고: 존치. 대신 슬림화.**

### 삭제 시 실제로 사라지는 것

| # | 자산 | 대체 가능? | 근거 |
|---|---|---|---|
| 1 | **수동 컴파일 게이트 프로토콜** (게이트 메시지 형식, `LogLiveCoding` 교차확인, 헤더 변경 시 PIE 정지 권고) | ✕ 불가 | 위 1절. 내장 루프 어느 것도 사람 신호 대기를 못 함 |
| 2 | **확정 사실 5건** (`SKILL.md:10~16`) — MCP 컴파일 트리거 불가, `SlateInspector.Click` UMG `OnClicked` 미발화, `StartPIE/StopPIE` 정상, UBT 사전 문법점검 우회 | ✕ **유일본** | 스킬이 참조하는 메모리 4건(`slateinspector-pie-umg-click-limit`, `mcp-pie-start-crash`, `ue58-native-mcp-toolset`, `park3d-build-test-livecoding`)은 **메모리 디렉터리에 실제로 존재하지 않음(dangling link)**. 이 스킬 파일이 마지막 기록이다 ★ |
| 3 | **검증 수단 우선순위** (Automation 테스트 > PIE Snapshot, 합성 클릭 금지) | △ 재작성 필요 | C++ 전용 방침 대응 절차 |
| 4 | **산출물 계약** (`loop_iteration_N.md` 등) | △ | 실제로 이 계약으로 26개 파일이 생성됨 |
| 5 | **Codex 쌍둥이** `.agents/skills/parking-cpp-loop/SKILL.md` | — | CLAUDE.md "Codex 동등성" 규칙상 한쪽만 지우면 동등성이 깨짐. 지우려면 양쪽 + `AGENTS.md` + 오케스트레이터 라우팅(`SKILL.md:29`)까지 동시 정리 필요 |
| 6 | 3회 동일 원인 중단 안전장치 | ○ 내장으로 대체 가능 | `Workflow`가 더 잘함 |

**2번이 결정적이다.** 메모리 링크가 끊겨 있어, 스킬을 지우면 "MCP로는 C++ 컴파일을 못 건다"는 실측 결론이 저장소에서 사라진다. 다음에 같은 시도를 반복하게 된다.

## 3. 결론
1. 클로드에 내장 루프 기능은 **있다**(`/loop`, `Workflow`, 서브에이전트, 에이전트 루프). 순수 반복 제어만 보면 내장이 더 결정적이다.
2. 그러나 **사람의 수동 컴파일 완료 신호를 기다리는 루프는 내장 기능으로 구현 불가**하며, 이것이 `parking-cpp-loop`의 유일한 존재 이유다.
3. 따라서 **삭제 비권고**. 실사용 26회 기록이 있고, 소실 위험이 있는 유일본 지식(확정 사실 5건)을 품고 있다.
4. 정 정리하려면 순서는 — ① 확정 사실을 메모리로 승격 → ② 역할 분리 중복 축약 → ③ 그래도 남는 게 컴파일 게이트뿐이면 그때 재판단.
