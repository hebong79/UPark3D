# 서버(3090)에서 렌더한 3D 화면을 실시간으로 현재 PC 로 가져오는 방법

작성: 2026-08-26 18:53
질문: "서버 사이드에서 3D 오브젝트를 렌더링해서 현재 PC 로 3D 오브젝트를 가져오는 방법" (서버 = RTX 3090, **실시간 사용**)

---

## 0. 먼저 — 질문이 두 갈래로 읽힌다

"서버에서 **렌더링**해서 3D 오브젝트를 **가져온다**"는 문장은 서로 다른 두 구조를 동시에 가리킨다.
이 둘은 필요한 대역폭·지연·클라이언트 요구사항이 완전히 다르므로 먼저 갈라야 한다.

| | A. 픽셀(영상)을 가져온다 | B. 3D 데이터(지오메트리·좌표)를 가져온다 |
|---|---|---|
| 렌더 주체 | **서버 3090** | **내 PC GPU** |
| 서버가 보내는 것 | 인코딩된 영상 프레임 | 메시/텍스처(1회) + 좌표·상태(지속) |
| 내 PC 에 필요한 것 | 브라우저만 있으면 됨 | 같은 3D 에셋 + 렌더러(UE/Unity/three.js) |
| 대역폭(1080p60) | 8~20 Mbps 상시 | 초기 수백 MB, 이후 수십 KB/s |
| 지연 | 왕복 인코딩 지연이 붙음(LAN 30~60ms) | 상태 지연만(수 ms) |
| "3D 로 만질 수 있나" | 아니오 — 화면일 뿐 | 예 — 클라에 진짜 오브젝트가 있음 |

"서버에서 렌더링해서"라는 표현을 그대로 살리면 **A** 다. 3090 을 산 이유가 렌더링이라면 A 가 맞고,
클라이언트에서 3D 오브젝트를 직접 조작·계측해야 하면 B 다. 아래에 둘 다 적되 A 를 중심으로 쓴다.

---

## A. 픽셀 전송 — 서버 3090 이 렌더하고 내 PC 는 본다

### A-1. Pixel Streaming 2 (WebRTC + NVENC) — 실시간·조작까지 필요하면 이것

**이 프로젝트에서 실시간 요건에 맞는 표준 답이다.** UE 5.8 엔진에 이미 들어 있다(검증 완료):

- `Engine/Plugins/Media/PixelStreaming2/` 존재, `"IsBetaVersion": false` (정식)
- 의존 플러그인에 `NVCodecs` 포함 → 3090 의 **NVENC 하드웨어 인코더**를 그대로 쓴다
- 모듈: `PixelStreaming2Core / RTC / Input / Servers / Editor / HMD`

동작 구조:

```
[3090 서버]                                   [내 PC]
 Park3D.exe (-game)                            브라우저(Chrome/Edge)
   └ 백버퍼 캡처 → NVENC H.264 인코딩            └ WebRTC 로 영상 수신
        │  WebRTC(UDP/SRTP)  ───────────────────►  화면 표시
        │◄─────────────────── 키보드/마우스 입력 (DataChannel)
        └ 시그널링(WebSocket) ◄──► [시그널링 서버(Node)] ◄──► 브라우저
```

핵심은 **입력이 되돌아온다**는 점이다. 단순 영상 스트림과 달리 브라우저의 마우스/키보드가
DataChannel 로 서버 UE 에 주입되므로, 내 PC 에서 Park3D 를 직접 조작하는 것처럼 쓸 수 있다.

#### 적용 절차

1. **플러그인 활성화** — `Park3D/Park3D.uproject` 의 `Plugins` 에 추가

```json
{ "Name": "PixelStreaming2", "Enabled": true }
```

2. **시그널링 서버 받기** (Node.js 필요, 인터넷 연결 필요)

```
C:\Program Files\Epic Games\UE_5.8\Engine\Plugins\Media\PixelStreaming2\Resources\WebServers\get_ps_servers.bat
```
   → PixelStreamingInfrastructure(시그널링 웹서버·플레이어 페이지·SFU·TURN)를 내려받는다.
   엔진에 스크립트만 들어 있고 서버 본체는 **없다** — 이 단계를 건너뛰면 붙을 곳이 없다.

3. **서버에서 시그널링 서버 기동** → 기본 포트: 플레이어 페이지 80(또는 8080), 스트리머 8888

4. **Park3D 를 스트리머로 기동** (UE 5.6 부터 인자명이 바뀌었다 — 아래가 5.8 기준)

```
Park3D.exe -RpcPort=13510 ^
  -PixelStreamingConnectionURL=ws://127.0.0.1:8888 ^
  -PixelStreamingCodec=H264 ^
  -PixelStreamingWebRTCFps=60 ^
  -PixelStreamingEncoderTargetBitrate=15000000 ^
  -RenderOffScreen -Unattended -ForceRes -ResX=1920 -ResY=1080
```

5. **내 PC 브라우저**에서 `http://<서버IP>/` 접속

#### 검증된 인자 규칙 (`PixelStreaming2PluginSettings.cpp`)

- 커맨드라인은 `-PixelStreaming` + 설정명 형태다: `ConnectionURL` → `-PixelStreamingConnectionURL=`
- 구 이름 `-PixelStreamingURL` / `-PixelStreamingIP` / `-PixelStreamingPort` / `-PixelStreamingSignallingURL`
  은 **레거시 매핑으로 아직 받아 준다**(`GetLegacyCmdArg`) — 인터넷 예제가 구버전이어도 대개 동작한다.
- 오타·미지원 인자는 조용히 무시되지 않고 로그에 남는다:
  `Unknown PixelStreaming command line arg: {0}` → **인자가 먹었는지 로그 한 줄로 확인 가능**
- 주요 손잡이: `-PixelStreamingCodec`(H264/VP8/VP9/AV1), `-PixelStreamingWebRTCFps`,
  `-PixelStreamingWebRTCMinBitrate/MaxBitrate`, `-PixelStreamingEncoderMinQuality/MaxQuality`,
  `-PixelStreamingID`(스트리머 이름), `-PixelStreamingEncoderMaxSessions`

#### 3090 을 쓸 때 알아야 할 하드웨어 사실

- **GA102(3090)의 NVENC 는 AV1 인코딩을 못 한다** (AV1 *디코드*만 된다. AV1 인코드는 Ada/RTX 40 부터).
  → `-PixelStreamingCodec=AV1` 을 주면 소프트웨어 인코딩으로 떨어지거나 실패한다. **H264 를 쓸 것.**
- 3090 은 NVENC 엔진 **1개**. 1080p60 H.264 인코딩 자체는 몇 ms 수준이라 렌더 대비 무시할 만하다.
- GeForce 드라이버는 동시 NVENC 세션 수에 상한이 있다(Quadro/데이터센터 카드와 다름).
  시청자가 여러 명이면 인코더를 늘리지 말고 **PixelStreamingInfrastructure 의 SFU** 를 앞에 둬서
  인코딩 1회 → N 명 배포로 간다.

#### 지연 예산 (LAN 기준 대략)

| 구간 | 비용 |
|---|---|
| 렌더 1프레임 | 16.7ms (60fps 기준) |
| 백버퍼 캡처 + NVENC | 3~8ms |
| 네트워크(사내망) | 1~5ms |
| 브라우저 디코드·표시 | 10~25ms |
| **합계** | **약 35~60ms** |

WAN/VPN 이면 여기에 왕복 지연이 그대로 더해진다. 조작감이 중요하면 서버와 같은 LAN 이어야 한다.

### A-2. 이미 우리 프로젝트에 있는 MJPEG 스트림 — "지금 당장" 이 필요하면

**추가 개발 없이 오늘 바로 되는 길이다.** `UCamStreamSubsystem` 이 이미 서버 사이드 렌더 결과를
HTTP MJPEG 로 내보내고 있다:

- 메인 뷰(플레이어 시점): `http://<서버IP>:13600/`
- PTZ 카메라 1번: `http://<서버IP>:13611/`, 2번 `:13612/` … (`config_pmaker.json` 의 `cam_port_min`)
- 브라우저 주소창에 넣거나 `<img src="http://서버:13600/">` 로 바로 뜬다

한계(설계상 그렇게 만든 것):

- **감시용이라 fps 가 낮다** — `TotalFps=5` 예산을 실사용 채널로 나눠 쓴다(1명 ≈5fps, 2명 ≈2.5fps).
  실시간 조작감을 위한 것이 아니라 "여러 카메라를 동시에 본다"는 목적의 구조다.
- MJPEG 는 프레임 간 압축이 없어 대역이 비효율적이다(같은 화질에 H.264 의 5~10배).
- 영상만 간다 — **입력이 되돌아가지 않는다**. 조작은 별도로 13510 RPC 를 쳐야 한다.
- 메인 뷰 캡처는 비동기 리드백(`MainReadbackSlots=3`)으로 처리량을 늘려 뒀지만, PTZ 캡처는
  아직 동기(게임 스레드에서 약 33ms/장)다.

즉 **"실시간 조작" 이 목적이면 A-1, "실시간 관찰(다중 카메라 감시)" 이 목적이면 A-2 로 이미 충분하다.**

### A-3. 코드 0 짜리 우회 — Sunshine/Moonlight, Parsec, RDP

Park3D 를 전혀 건드리지 않고 서버 데스크톱 화면을 통째로 실시간 전송한다.
Sunshine(서버) + Moonlight(클라)는 NVENC 를 쓰고 지연도 Pixel Streaming 과 비슷하다.

- 장점: 재빌드·재쿡 없음. 오늘 30분이면 끝난다. UI 패널·에디터까지 그대로 보인다.
- 단점: 브라우저로 여러 명이 접속하는 구조가 아니고(1:1), 웹에 임베드할 수 없으며,
  프로그램적으로 제어(자동 접속·해상도 협상)하기 어렵다.

**Pixel Streaming 도입 전에 "3090 서버 렌더가 실제로 쓸 만한가"를 하루 만에 검증하는 용도로 유용하다.**

## B. 3D 데이터 전송 — 내 PC 가 렌더한다

실시간이라는 조건에서 이 갈래를 택한다면, 핵심은 **매 프레임 지오메트리를 보내지 않는 것**이다.
메시를 실시간으로 전송하는 구조는 대역·인코딩 비용 모두 감당이 안 된다. 정석은 둘로 나누는 것:

1. **정적 에셋은 1회 배포** — 주차장·차량 메시를 glTF/GLB 로 뽑아 클라이언트에 미리 심는다.
   (UE 는 `GLTFExporter` 플러그인으로 에디터에서 내보낼 수 있다. 런타임 익스포트는 제한적이라
   "미리 뽑아서 배포"가 현실적이다.)
2. **실시간에는 상태만 흘린다** — 차량 id·좌표·회전·카메라 PTZ 만. 대상 100대 × 7 float ≈ 3KB/틱,
   10Hz 면 30KB/s 수준. 이게 3D 오브젝트를 "가져오는" 실시간 구조의 정답이다.

우리 프로젝트에서의 현실:

- 상태 조회 API 는 **이미 있다** — `car.*`, `cam.list`, `env.list`, `sim.list`, `car.catalog`(메시 실측 치수) 등 13510 RPC.
- 다만 RPC 는 **요청-응답(pull)** 이라 실시간 푸시가 없다. 실시간으로 쓰려면 둘 중 하나가 필요하다:
  - 클라가 10~30Hz 로 폴링 (구현 0, 지연·부하 있음 — 프로토타입용으로는 충분)
  - 상태 푸시 채널(WebSocket) 신설 (제대로 된 길, 서버 측 개발 필요)
- 클라이언트에도 **같은 차량 에셋이 있어야 한다**. 없으면 박스로 대체 표시된다.

이 갈래는 "웹 대시보드에서 주차장을 3D 로 돌려 보고 싶다", "다른 엔진/도구에서 시뮬 상태를 시각화하겠다"
같은 목적일 때만 의미가 있다. 단지 원격에서 Park3D 를 보고 조작하려는 것이면 A-1 이 훨씬 싸다.

## 이 프로젝트에서 밟을 함정 (미리 적어 둔다)

1. **플러그인 추가는 exe 교체로 반영되지 않는다.**
   이 프로젝트의 상용 절차인 "패키지 복제 후 exe 만 갈아끼우기"는 **코드만** 갱신한다.
   `PixelStreaming2` 를 켜면 플러그인 바이너리·설정이 패키지에 들어가야 하므로 **전체 재빌드 + 재쿡**이 필요하다.
   (같은 이유로 `DefaultGame.ini` 는 pak 안에 구워져 있어 exe 교체로 안 바뀐다 —
   재쿡 전에는 `Park3D/Saved/Config/Windows/Game.ini` 사용자 레이어로 덮어야 한다.)

2. **포트 충돌.** 이미 쓰는 포트: RPC 13510, MCP 브리지 13520, 메인 뷰 스트림 13600,
   카메라 스트림 13611~13650. Pixel Streaming 은 80(또는 8080)·8888 을 쓰므로 겹치지 않지만,
   같은 PC 에 인스턴스를 여러 개 띄우는 이 프로젝트의 관행상 **스트리머마다 시그널링 포트를 분리**해야 한다.

3. **`-nullrhi` 로는 아무것도 안 된다.** Pixel Streaming 도 CamStream 캡처도 실제 RHI 를 요구한다.
   서버를 화면 없이 돌리려면 `-nullrhi` 가 아니라 `-RenderOffScreen` 이다.

4. **인코딩 부하와 캡처 부하는 별개다.** Pixel Streaming 을 켠 상태에서 기존 MJPEG 채널까지 돌리면
   게임 스레드 캡처 비용(PTZ 는 동기, 약 33ms/장)이 그대로 더해진다. 둘을 동시에 쓸 거라면
   `TotalFps` / `MaxCapturesPerTick` 을 다시 잡을 것.

5. **보안은 넣지 않는다** (연구단계 정책 — `park3d-no-security`).
   Pixel Streaming 도 인증 없이 열되, 사설망/VPN 안에서만 쓴다는 전제다.
   외부 인터넷 경유가 필요해지면 그때는 TURN 서버가 필요해진다(NAT 통과 목적, 보안 목적 아님).

## 확인이 필요한 것

- 목적이 **조작 포함**인가, **관찰 전용**인가? (A-1 vs A-2 가 갈린다)
- 서버와 이 PC 가 **같은 LAN** 인가, VPN/외부망인가? (지연과 TURN 필요 여부가 갈린다)
- 동시 시청자가 몇 명인가? (2명 이상이면 SFU 구성을 처음부터 넣는 게 낫다)
