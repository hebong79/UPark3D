# 질문 답변: UBT란 무엇이며, 왜 에디터를 종료하고 재빌드해야 하는가

- 관련: [P1 구현·검증](20260702_183304_CameraControlUI_P1_구현검증.md), [CameraControl 설계서](20260702_145215_CameraControlUI_설계서.md)

> **⚠️ 정정(2026-07-02 추가, §3·§6 참조)**: 최초 작성 시 "신규 파일·새 리플렉션 타입은 Live Coding이 못 받는다"고 서술했으나 이는 **과장된 설명이었다.** 이 프로젝트의 기존 C++ UI(위젯 클래스·신규 USTRUCT)는 사용자가 `Ctrl+Alt+F11`(Live Coding)로 재부팅 없이 계속 컴파일해 왔다. **이번 P1이 재부팅을 요한 실제 이유는 "자동화 에이전트가 Live Coding을 트리거할 수 없어 외부 UBT를 썼고, UBT는 에디터 실행 중엔 항상 거부되기 때문"**이다(§6). 아래 §1·§2의 UBT/DLL/Live Coding 원리 설명은 유효하되, §3의 "P1이라서 재빌드가 필요했다"는 인과는 §6의 정정으로 대체한다.

## 1. UBT(UnrealBuildTool)란?

**UBT는 언리얼 엔진의 빌드 오케스트레이션 도구**다. Epic이 엔진과 함께 배포하는 C# 프로그램이며, **컴파일러 자체가 아니라 컴파일러(MSVC/clang)를 지휘하는 관리자**다.

### UBT가 하는 일
| 단계 | 내용 |
|------|------|
| 구성 해석 | `.Build.cs` / `.Target.cs`를 읽어 모듈·의존성·매크로(`PublicDefinitions`)·인클루드 경로 결정 |
| 리플렉션 생성 | **UHT(UnrealHeaderTool)** 실행 → `UCLASS`/`USTRUCT`/`UPROPERTY`/`UFUNCTION`의 `.generated.h`/`.gen.cpp` 생성 |
| 증분 판정 | 의존성 그래프로 무엇을 다시 컴파일할지 계산 |
| 컴파일·링크 | 실제 컴파일러/링커 명령을 생성·실행 → **모듈 DLL** 산출(예: `UnrealEditor-Park3D.dll`) |

- `Build.bat`은 UBT를 실행하는 얇은 래퍼일 뿐이다.
- 우리가 사용한 명령: `Build.bat Park3DEditor Win64 Development -Project=...\Park3D.uproject -WaitMutex -FromMsBuild`

## 2. 왜 에디터를 종료해야 하는가

핵심은 **DLL 파일 잠금**과 **Live Coding**이다.

### 2.1 실행 중인 에디터가 DLL을 잠근다
에디터가 켜져 있으면 모듈 DLL(`UnrealEditor-Park3D.dll`)을 자기 프로세스에 로드(메모리 매핑)한다. **Windows는 로드된 DLL 파일을 덮어쓸 수 없다.** 일반 UBT 빌드는 이 DLL을 새로 써야 하므로 차단된다.

### 2.2 언리얼의 우회책 = Live Coding
에디터를 끄지 않고 재컴파일하기 위한 기능이 **Live Coding**(Live++ 기반)이다.
- 바뀐 코드만 **패치 조각**으로 컴파일해 실행 중 프로세스 메모리에 **핫패치**한다.
- 메인 DLL을 덮어쓰지 않으므로 잠금 문제를 피한다.
- 함수 본문 수정 정도는 에디터에서 `Ctrl+Alt+F11`로 즉시 반영 가능.

### 2.3 Live Coding의 한계 (이번 사례의 원인)
Live Coding은 **기존 코드를 패치**하는 방식이라 다음은 제대로 못 받는다:
- **새 소스 파일 추가**
- **새 리플렉션 타입 추가**(`UCLASS`/`USTRUCT`/`UPROPERTY` 등) — UHT 리플렉션 재생성 + 모듈 전체 재링크 필요
- **새 모듈 추가**

또한 Live Coding이 활성이면 UBT가 **의도적으로 외부 빌드를 거부**한다:
```
ERROR: Unable to build while Live Coding is active. Exit the editor or press Ctrl+Alt+F11.
(exit code 6)
```
잠긴 DLL·패치 상태와의 충돌을 막기 위한 안전장치다.

## 3. 이번 P1이 재빌드를 필요로 한 이유

CameraControl P1은 **신규 파일 4개**였고, 그 안에 **새 `USTRUCT`(`FCamVec3`/`FCamPtz`/`FCamDir`/`FCameraPos`/`FCameraPosList`)와 새 `UBlueprintFunctionLibrary`(`UCameraControlLibrary`)**가 들어 있었다. 이는 Live Coding이 못 받는 전형적 케이스다.

따라서 확실한 경로:
```
① 에디터 종료   → DLL 잠금 해제 + Live Coding 비활성
② UBT 전체 재빌드 → 새 UnrealEditor-Park3D.dll 생성 (UHT 리플렉션 포함)
③ 에디터 재실행  → 새 DLL 로드
```
실제로 P1은 이 경로로 성공했다(빌드 Succeeded, 9.36초).

## 4. 판단 기준 (요약)

| 변경 유형 | 권장 방법 |
|-----------|-----------|
| 기존 함수 **본문만** 수정 | `Ctrl+Alt+F11` (Live Coding) — 에디터 유지 |
| **새 파일 / 새 리플렉션 타입 / 새 모듈** 추가 | **에디터 종료 → UBT 재빌드 → 재실행** |
| `.Build.cs` 의존성 변경 | 에디터 종료 → UBT 재빌드 |

> 결론: Live Coding은 "빠른 반복(함수 수정)"용이고, 구조가 바뀌는 변경(파일/타입/모듈 추가)은 정식 UBT 재빌드가 안전하다.

## 6. 정정: 기존 C++ UI 작업과 이번 P1의 진짜 차이 (후속 질문 반영)

**후속 질문**: "기존 UI들도 블루프린트가 아닌 C++ 기반으로 제작됐고 그때는 에디터 재부팅이 없었다. 무엇이 다른가?"

이 질문이 §3의 인과 설명이 부정확했음을 드러냈다. 정정한다.

### 6.1 차이는 "블루프린트 vs C++"도, "신규 타입이라서"도 아니다
- 기존 UI(`UCarPlacementWidget`, `UPresetMakerWidget` 등)도 **C++ 클래스 + 신규 `USTRUCT`**(`ParkingCarTypes.h` 등)를 새로 추가하며 만들었고 재부팅이 없었다. 정상이다.
- UE5.8 Live Coding은 **신규 `.cpp/.h`와 새 클래스/`USTRUCT`도 대부분 처리**한다. "신규 파일이라 Live Coding 불가"는 사실이 아니다.

### 6.2 진짜 차이 = "누가 어떻게 컴파일했는가"
| 구분 | 기존 UI 작업 | 이번 P1 |
|------|-------------|---------|
| 컴파일 주체 | **사용자가 직접** | **자동화 에이전트** |
| 방법 | 에디터에서 `Ctrl+Alt+F11`(Live Coding) | 외부 UBT(`Build.bat`) |
| 신규 파일/타입 | Live Coding이 처리 → 재부팅 불필요 | — |
| 재부팅 사유 | 없음 | UBT는 에디터가 DLL을 잡고 있으면 **항상** 거부 → 종료 필요 |

- `Ctrl+Alt+F11`은 **에디터 내 수동 키 입력**이며 스크립트/콘솔로 트리거하는 API가 없다 → 에이전트가 못 누른다.
- 그래서 에이전트의 유일한 프로그램적 빌드 경로는 외부 UBT였고, UBT는 에디터 실행 중 항상 거부하므로 종료가 불가피했다(신규 파일 여부와 무관).
- **사용자가 평소처럼 `Ctrl+Alt+F11`을 눌렀다면 P1도 재부팅 없이 컴파일됐을 가능성이 높다.** 검증 없이 재부팅 경로를 "권장"으로 제시한 것이 부정확했다.

### 6.3 수정된 기본 방침
- C++ 신규 코드 작성 후 → **우선 사용자에게 `Ctrl+Alt+F11` 요청**.
- 에디터 종료+UBT 재빌드는 **(a) Live Coding이 실제로 실패할 때** 또는 **(b) 에이전트가 헤드리스 자동화 테스트까지 무인으로 돌려야 할 때**만.
