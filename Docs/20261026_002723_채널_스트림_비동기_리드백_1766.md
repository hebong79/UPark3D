## 1. 배경

#1765 로 채널 SceneCapture 에 TemporalAA 를 켰다. 그 exe(782b8c5)를 .125 정본에 넣은 뒤 두 가지가 나빠졌다(#1764 c5264).
- 게임 틱: 34 → 22 /s
- cam 2 채널: 30 → 22 fps

이때 GPU 사용률은 52 % 에 그쳤다.

원인 추정: 채널 경로가 동기라는 점이다.
- `ProduceJpeg` 는 `CaptureOnce` 다음 `ReadPixels` 를 부른다. `ReadPixels` 는 렌더 커맨드를 flush 하고 GPU 완료를 기다린다.
- TSR 이 캡처의 GPU 작업을 늘리자 그 대기만큼 틱이 길어졌다.
- 메인 뷰(:13600)는 이미 비동기 슬롯 링이다(`readbackSlots`/`inFlight`).

## 2. 변경 (`Rpc/CamStreamSubsystem.cpp/.h` 만)

- **`FCamStreamReadbackRing`(신규)**: 채널 1개의 슬롯 링이다. 규약은 메인 뷰 링과 같다.
  - 요청은 Write 에서 앞으로만 간다.
  - 수거는 Read(가장 오래된 것)에서만 한다. 그래서 프레임이 뒤로 튀지 않는다.
  - 메서드: `HasFreeSlot`, `InFlight`, `Request`, `Poll`, `TakeReady`, `Release`.
- **채널 틱**: 한 틱에 아래 순서로 한다.
  1. Pending 슬롯마다 완료 확인 커맨드를 건다.
  2. Ready 가 된 가장 오래된 1장을 JPEG 으로 인코딩해 `UpdateFrame` 한다.
  3. 만기이고 빈 슬롯이 있으면 `CaptureOnce()` 뒤에 `EnqueueCopy` 를 건다. GPU 를 기다리지 않는다.
  4. 슬롯이 다 찼으면 이번 차례는 건너뛴다. 부채는 쌓지 않는다(`Accum = Interval`). `skippedNoSlot` 을 1 올린다.
- **안 보는 채널**(슬롯 없음 또는 클라이언트 없음)은 링을 비운다. 스테이징 버퍼를 들고 있지 않는다.
- **채널을 닫을 때**와 `StopAllChannels` 에서도 링을 정리한다.
- **렌더 스레드 단계 공유**: 복사·폴링·정리 코드를 `CamStreamReadback::EnqueueCopy/EnqueuePoll/Abandon` 으로 옮겼다.
  - 메인 뷰도 이 함수를 그대로 쓴다. 코드 본문은 같고 동작은 바뀌지 않는다.
  - 이름공간을 둔 이유는 유니티 빌드 C2084 를 피하려는 것이다.
- **새 ini 키** `ChannelReadbackSlots`(기본 3).
- **동기 폴백**: 렌더타깃이 BGRA8 이 아니면 예전 `ProduceJpeg` 로 찍는다. 실제로는 쓰이지 않는다(`RTF_RGBA8_SRGB` = BGRA8).
- **`cam.streamStatus`** 에 필드를 더했다. 기존 필드는 그대로다.
  - 채널별 `inFlight`, `skippedNoSlot`
  - 루트 `channelReadbackSlots`
- **X-Frame-Id**: 지금처럼 캡처를 건 순간의 장면 순번이다. 그래서 `view.waitFrame` 의미는 같다.

### 같은 렌더타깃을 쓰는 다른 캡처
- 카메라 렌더타깃은 스트림, 뷰어(`CaptureForViewer`), 같은 크기 `cam.captureJPG` 가 함께 쓴다.
- 그래도 복사 커맨드가 캡처 직후 렌더 커맨드 큐에 들어가므로, 뒤이은 캡처가 그 프레임을 덮기 전에 복사된다.
- 크기가 다른 단발 캡처는 별도 타깃이라 무관하다.

### 남은 게임 스레드 비용
- JPEG 인코딩(1280×720)은 아직 게임 스레드에서 한다.
- .125 에서 틱이 충분히 돌아오지 않으면 다음 단계는 인코딩을 작업 스레드로 옮기는 것이다.
