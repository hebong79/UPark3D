# 카메라 스트림 포트 대역 — 질의응답 및 상한 13650 결정

- 작성일: 2026-08-06
- 관련: `Docs/20260806_095159_카메라_스트림_포트대역_config_이관_구현.md`,
  `Docs/20260805_230638_시작시_설정파일_자동로딩_구현.md`

## 결정: `cam_port_max = 13650`

```json
{
    "rpc_port": 13510,
    "preset_file": "001_Preset_Seo_1.json",
    "carpos_file": "CarPos_Seoshin_2Cam.json",
    "camerapos_file": "CamPos_Seosin.json",
    "max_zoom": 36.0,
    "cam_port_min": 13601,
    "cam_port_max": 13650
}
```

**사유(사용자 판단): 카메라 대수가 50대를 넘어갈 일이 거의 없다.**
기본값 13610(10대)에서 13650(50대)으로 넓혔다. 대역은 상한일 뿐이라 넓혀도 비용이 없고(§2),
대수 초과 시 일어나는 자동 대역 확장이 실질적으로 트리거되지 않아 앱이 git 추적 파일인
config 를 덮어쓰는 일(§1의 형식 변경 문제)도 사실상 발생하지 않는다.

---

## 1. 질문 — config_pmaker.json 에 앱이 덮어쓰는 내용은 무엇인가

### 1-1. 값은 2개만 바뀐다

`Park3DAppConfig.cpp:96-97`

```cpp
Root->SetNumberField(TEXT("cam_port_min"), NewMin);   // 현재 대역 시작(BasePort+1) — 값 불변
Root->SetNumberField(TEXT("cam_port_max"), NewMax);   // min + 카메라수 - 1 (65535 클램프)
```

- `cam_port_min` 은 값이 바뀌지 않는다. 현재 대역 시작을 그대로 다시 쓴다.
  **키가 없던 파일에만 새로 생긴다**(패키지 배포본이 그 경우였다 — 이 동작이 없으면 확장이
  다음 기동에 소멸한다. 구현 문서의 H1 참조).
- `cam_port_max` 만 실제로 커진다. 11대 → 13611, 12대 → 13612.
- **나머지 키와 사람이 손으로 넣은 미지의 키는 값이 보존된다.** 구조체를 통째로 직렬화하지 않고
  원본 JSON 오브젝트를 읽어 이 두 필드만 교체하기 때문이다.
  유닛테스트 `Park3D.AppConfig.UpdateCamPortRange` 가 `unknown_key` 보존까지 확인한다.

### 1-2. 언제 쓰는가

`카메라 대수 > 현재 대역 크기` 일 때만이다(`CamStreamSubsystem.cpp:63-68`).

| 시점 | 호출 지점 |
|---|---|
| 카메라위치 파일 **열기** + **시작 자동 로딩**(같은 함수) | `CameraControlWidget.cpp:839` |
| 카메라위치 파일 **저장** 성공 직후 | `CameraControlWidget.cpp:876` |

쓰지 않는 경우: 대수가 대역 이내 / `-NoCamStream` 으로 스트리밍이 꺼짐 / config 파일 없음
(이 경우 대역만 메모리에서 넓히고 로그로 남긴다).

### 1-3. 값 외에 함께 바뀌는 것 — diff 가 커지는 원인

파일 전체가 UE JSON 라이터로 다시 쓰이므로 손대지 않은 줄의 **형식**도 바뀐다.

| 항목 | 사람이 쓴 원본 | 앱이 쓴 뒤 |
|---|---|---|
| 들여쓰기 | 스페이스 4칸 | **탭** |
| 줄바꿈 | LF | **CRLF** (QA 관측 선두 바이트 `7B 0D 0A 09`) |
| 숫자 표기 | `"max_zoom": 36.0` | `"max_zoom": 36` (값은 동일) |
| EOF 개행 | 있음 | 없음 |
| 인코딩 | UTF-8 | UTF-8 유지(BOM 없음) — 구현 시 `ForceUTF8WithoutBOM` 로 고정 |
| 키 순서 | — | 유지됨(관측 확인) |

의미상 바뀌는 것은 `cam_port_max` 한 줄인데 git diff 에는 파일 전체가 바뀐 것으로 뜬다.
**이번 13650 결정으로 이 상황 자체가 거의 발생하지 않게 된다.**

## 2. 질문 — 처음부터 max 를 크게 잡으면 문제가 생기나 (카메라를 미리 만들어 두는 등)

### 결론: max 를 크게 잡아도 그 자체로는 아무 일도 일어나지 않는다

`max` 는 **상한(cap)이지 예약이 아니다.** 포트는 실제 존재하는 카메라 수만큼만 바인드된다.

`CamStreamPolicy.cpp` `DiffChannels`:

```cpp
const int32 NewEff = FMath::Clamp(NewCount, 0, MaxCameras);   // NewCount = 실제 카메라 수
for (int32 CamId = OldEff + 1; CamId <= NewEff; ++CamId) OutToOpen.Add(CamId);
```

`Channels` 배열도 실제 카메라 수만큼만 잡히고 슬롯 스케줄러도 이 배열만 순회한다.
max 가 13650 이든 65535 든, 카메라가 2대면 열리는 포트는 13601·13602 두 개다.

### 비용은 "카메라를 실제로 만들 때" 생긴다 (max 와 무관)

카메라 1대당:

| 항목 | 비용 |
|---|---|
| 포트 | 1개 바인드 |
| 스레드 | 2개(리스너 + 송신 워커) |
| 렌더타겟 | 1280×720 RGBA8 ≈ **3.5MB** (`PTZCameraActor.cpp:51`) |
| 캡처(프레임) 비용 | **0** — 보는 클라이언트가 없으면 슬롯 후보에서 제외 |

`CamStreamPolicy.cpp`: *"후보 = 클라이언트가 붙은 채널뿐. 10대가 있어도 보는 사람이 없으면
캡처 비용은 0이다."* 즉 카메라를 미리 만들어 두는 것은 메모리·스레드·포트만 쓰고 앱 틱은 깎지
않는다(카메라 캡처 1프레임 ≈ 48ms 라는 실측 비용이 드는 쪽은 "보고 있는" 카메라뿐이다).

### 큰 max 에서 주의할 것 3가지

1. **OS 임시 포트 대역과 겹치면 바인드 실패** — 이 PC 는 `49152~65535`(`netsh int ipv4 show
   dynamicport tcp` 로 확인). max 를 그 위로 잡으면 카메라가 그만큼 늘었을 때 OS 가 이미 쓰는
   포트를 잡으려다 실패한다. 실패해도 `camId-1` 인덱스 규약 유지를 위해 채널 자리는 남기므로
   **뒤 카메라의 포트가 밀리지는 않는다.** 실질 상한은 49151 아래.
2. **기존 서비스 포트와의 겹침은 검증하지 않는다** — `PortRangeToBase` 는 `2 <= min <= max <= 65535`
   만 본다. min 을 13510(RPC)·13520(MCP 브리지) 아래로 내리면 카메라가 많아졌을 때 충돌한다.
   현재 값은 13601 부터 위로만 가므로 안전하다.
3. **초과분은 조용히 스트림만 없다** — 카메라가 max 를 넘으면 그 카메라는 채널을 받지 못하고
   경고 로그만 남는다. 앱은 정상 동작한다.

## 3. 질문 — rpc_port 와 cam_port 는 다른 것인가

**완전히 다르다. 용도·프로토콜·개수가 모두 다르다.**

| | `rpc_port` | `cam_port_min` ~ `cam_port_max` |
|---|---|---|
| 값 | 13510 **한 개** | 13601~13650 **대역**(카메라당 하나) |
| 역할 | **명령/조회** — 앱 원격 조작 | **영상** — 카메라 화면을 계속 송출 |
| 프로토콜 | JSON-RPC 2.0 over HTTP(POST) | MJPEG(`multipart/x-mixed-replace`) |
| 쓰는 쪽 | MCP 브리지, 자동화 스크립트, curl | 브라우저, 영상 클라이언트 |
| 카메라와의 관계 | 몇 대든 **1개 고정** | camId 1 → 13601, camId 2 → 13602 … |

- **rpc_port(13510)**: 앱 전체에 하나뿐인 제어 창구. `POST /rpc`, `GET /health`,
  `GET /rpc/catalog` (`RpcServerSubsystem.cpp:278-284`). `cam.setPan`·`car.create`·`preset.list`
  같은 82개 메서드가 여기로 간다. 카메라를 100대 만들어도 이 포트는 하나다.
- **cam_port_*(13601~)**: 카메라 한 대당 전용 포트. `http://<IP>:13601/` 을 열면 쿼리도 명령도
  없이 그 카메라 영상이 계속 흐른다. 요청을 파싱하지 않고 접속 즉시 JPEG 프레임을 밀어낸다.

### 헷갈리기 쉬운 지점 2가지

1. **13510 에도 스트림 경로가 하나 있다** — `GET /stream?camId=N`(`RpcServerSubsystem.cpp:286`).
   카메라별 전용 포트 이전 방식이고 지금도 **병존**한다. 같은 영상을 두 경로로 받을 수 있다:
   - `http://<IP>:13510/stream?camId=2` (구 방식, 쿼리로 카메라 지정)
   - `http://<IP>:13602/` (신 방식, 포트가 곧 카메라)
2. **정지 화면 한 장은 RPC 쪽이다** — `cam.captureJPG` 는 13510 으로 호출하면 base64 이미지
   한 장을 돌려준다. 136xx 는 연속 스트림이다.

두 대역이 겹치면 안 된다. 현재 값(13510 vs 13601~13650)은 안전하다.
