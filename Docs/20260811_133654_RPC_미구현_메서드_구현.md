# RPC 미구현 메서드 구현 (9/10) — 외부 노출 완료

- 작성일: 2026-08-11
- 브랜치: `feature/rpc-implement-unimplemented`
- 목적: Park3D JSON-RPC 서버에서 이름만 등록되고 `-32000(미구현)`을 돌려주던 10개 메서드 중 **9개를 실동작으로 결선**하여 외부(MCP 브리지·스크립트)에서 사용 가능하게 만든다.

## 1. 배경 — 무엇이 왜 미구현이었나

`GET /rpc/catalog` 에는 86개 메서드가 등록되어 있었으나, 그중 10개는 등록만 되어 있고 호출하면 `-32000` 과 함께 "포트 백엔드 부재" 사유를 돌려주었다.

| 메서드 | 기존 사유(코드에 적혀 있던 것) | 실제 상태 |
|---|---|---|
| `cam.savePreset` / `loadPreset` / `applyPreset` | per-camera 프리셋 메모리 없음 | **사유 유효** — 인메모리 프리셋 저장소가 실제로 없었다 |
| `car.setMetallic` | 포트에 metallic 도색 파라미터 없음 | **사유 유효** — `UCarColorComponent` 가 색만 다뤘다 |
| `preset.setBoxVisible` | 렌더러가 **면 단위** 큐브 가시성 미지원 | **사유가 틀렸음** — Unity 원본(`SPresetObjUI.ShowQubeLineList`)은 면이 아니라 **프리셋 단위** 토글이다 |
| `random.slotPlace` / `slotJitter` / `frontBack` / `randomizeAll` | 주차면 슬롯(CFaceRect) 백엔드 없음 | **사유가 낡았음** — `AParkingPresetManager::ComputeSlotCorners()` 가 이미 면별 4코너를 주는 순수 함수로 존재한다(데칼 렌더 도입 때 추가됨) |
| `random.placeInView` | PTZ 뷰포트 배치 백엔드 없음 | **사유 유효** — Unity `CPtzSpaceVehiclePlacer` 의 6단계 게이트가 미이식 |

즉 미구현 10건 중 5건은 백엔드가 이미 생겼는데 사유 메시지가 그대로 남아 있던 것이고, 4건은 백엔드를 새로 만들어야 했으며, 1건(`placeInView`)만 진짜로 큰 이식 작업이 남아 있었다.

## 4. 메서드별 상세

### 4.1 `cam.savePreset` / `cam.loadPreset` / `cam.applyPreset`

세 메서드의 차이(Unity 레퍼런스 §14와 동일):

| | `savePreset` | `loadPreset` | `applyPreset` |
|---|---|---|---|
| 파일 I/O | **쓰기** | **읽기** | 없음 |
| 메모리 | 현재 카메라 상태 → 갱신 | 파일 → **교체** | 읽기만 |
| 카메라 적용 | **없음** | **있음** | **있음** |

**프리셋 메모리는 `FCamRpcModule::PresetMemory`(`FCameraPosList`) 하나다.** 모듈은 `URpcServerSubsystem` 이 `TUniquePtr` 로 들고 있어 호출 사이에 살아 있다.

파라미터 / 응답:

```
cam.savePreset  { camId(필수), presetId?=1, fileName?="CameraPos" }
  → { ok, camId, presetId, pos:{x,y,z}, pan, tilt, zoom, path, fileName }
cam.loadPreset  { camId(필수), presetId?=1, fileName?="CameraPos" }
  → { ok, camId, presetId, pos, pan, tilt, zoom, path, camCount }
cam.applyPreset { camId(필수), presetId?=1 }
  → { ok, camId, presetId, pos, pan, tilt, zoom }
```

파일 위치는 `Park3DDataPaths::GetDataFilePath("CameraPos", "<fileName>.json")` — 카메라 컨트롤 위젯이 쓰는 폴더(`Save/3D/CameraPos/`)와 같다. 확장자는 생략 가능하다.

**함정 하나:** `UCameraControlLibrary::LoadFromJson` 의 `NormalizeLoaded` 는 로드 직후 `pan = rot.y`, `tilt = rot.x` 로 덮어쓴다(원본 `SCamDir.Rot()` setter 대응). 그래서 저장할 때 `pan`/`tilt` 만 쓰면 라운드트립에서 PTZ가 0으로 날아간다. `savePreset` 은 `rot` 도 반드시 함께 기록한다.

`applyPreset` 은 메모리에 데이터가 없으면 Unity와 동일하게 실패한다(Unity는 `InvalidOperationException`, 여기서는 `-32000` + "먼저 cam.savePreset 또는 cam.loadPreset 을 호출하세요").

### 4.2 `car.setMetallic`

```
car.setMetallic { carNameId(필수), metallic(필수, 0~1), smoothness?=0.5 }
  → { ok, carNameId, metallic, smoothness, applied }
```

차량 도색 머티리얼은 glTF Interchange 로 임포트된 `carpaint` 이고, 그 부모 마스터(`M_Default`)가 `BaseColorFactor`/`MetallicFactor`/`RoughnessFactor` 스칼라를 노출한다(엔진 `Engine/Plugins/Interchange/Assets/Content/gltf/Materials/M_Default` 에서 확인). 따라서 동적 머티리얼 인스턴스에 두 스칼라를 넣으면 된다.

**Unity smoothness 는 UE roughness 의 반대 개념**이므로 `roughness = 1 - smoothness` 로 변환한다.

`applied` 필드는 이 포트에서 추가한 것이다. `SetScalarParameterValue` 는 **없는 파라미터를 조용히 무시**하기 때문에, 차종에 따라 머티리얼이 다르면 "ok:true 인데 화면은 그대로"가 될 수 있다. `SetMetallic` 은 `GetScalarParameterValue` 로 파라미터 존재를 먼저 확인한 뒤 실제 적용 여부를 돌려주고, RPC 는 그 값을 `applied` 로 전달한다.

### 4.3 `preset.setBoxVisible`

```
preset.setBoxVisible { idx(필수), visible(bool, 필수) }
  → { ok, idx, visible, show3D, useDecal }
```

Unity 원본은 프리셋 단위 토글이다(기존 코드의 "면 단위" 주석은 오독이었다). `AParkingPresetManager::HiddenBoxPresetIdxs` 에 숨길 `PresetIdx` 를 담고, `RebuildAll` 이 프리셋마다 `bShow3D && !HiddenBoxPresetIdxs.Contains(...)` 로 큐브 그리기를 건너뛴다. 바닥 사각형은 영향받지 않는다.

**Unity와 다른 점:** Unity는 큐브가 GameObject라 `SetActive` 만으로 끝나 재빌드가 없지만, 이 포트의 큐브는 **영구 디버그 라인**이라 다시 그리지 않으면 화면이 바뀌지 않는다. 그래서 토글 후 `RefreshView()` 를 호출한다. 바닥 사각형은 같은 값으로 다시 그려지므로 결과는 동일하다.

**주의:** 데칼 모드(`bUseDecalView=true`, 기본값)나 3D 토글이 꺼져 있으면 큐브 자체를 그리지 않으므로 이 설정이 화면에 나타나지 않는다. 응답의 `show3D`/`useDecal` 로 그 상태를 확인할 수 있다. 큐브를 보려면 먼저 `preset.rebuildAll {"showQubeBox":true,"useDecal":false}` 를 호출한다.

### 4.4 `random.slotPlace`

```
random.slotPlace { presetId?=1, random?=true, seed?=0, persist?=false, randomColor?=false }
  → { ok, placedCount, slotCount, presetId, seedHonored }
```

Unity `CPresetSlotPlacer.PlaceVehiclesOnSlots` 포팅.

1. `AParkingPresetManager::ComputeSlotCorners(P, j, MetersToUU, FaceHeightZ=0, Out)` 로 면별 4코너를 얻는다. **라인/데칼 렌더와 동일한 순수 함수를 공유**하므로 그려진 사각형 위에 정확히 차량이 올라간다. 차량은 바닥에 놓이므로 `FaceHeightZ=0`(면 라인의 5cm 띄움은 렌더 전용).
2. 슬롯 중심 = 4코너 평균. 슬롯 번호 `slotId = 면 인덱스 + 1`.
3. 길이축 yaw: 두 변 중 **긴 쪽**(주차 깊이 = 차량 길이축)의 방향. Unity yaw = `atan2(x, z)` 이고 Unity x→UE Y, z→UE X 이므로 UE 에서는 `atan2(Δ.Y, Δ.X)`.
4. 전/후면: 프리셋의 `CameraIdx` 카메라를 기준으로 **전면(번호판)이 카메라를 향하는 쪽**을 고른다. 차량 전방은 Unity `(sin,0,cos)` → UE `(cos, sin, 0)`. 카메라가 없으면 축을 그대로 쓴다.
5. 차종: `random=true` 면 카탈로그 무작위, `false` 면 슬롯 순 결정적 순환(`i % catalogCount`).
6. 랜덤 오프셋(`random=true` 에서만): Unity x ±0.15m / z ±1.0m / 회전 ±5°.

**Unity와 동일하게 "추가"만 하고 기존 차량을 지우지 않는다.** 같은 프리셋에 두 번 호출하면 차량이 겹친다 — 필요하면 먼저 `car.deleteAll` 을 호출한다.

**`persist` 는 받되 동작이 없다.** Unity는 `CDataMgr.AddCarPosData` 로 별도 저장 구조체에 기록해야 했지만, 이 포트는 `ACarPlacementManager` 의 차량 목록 자체가 저장 권위(`ToCarPosDatas`)라 스폰과 동시에 이미 반영된다. 파일 쓰기는 `car.save` 가 담당한다.

### 4.5 `random.slotJitter` / `random.frontBack`

```
random.slotJitter { presetId?=1, slotIndex?=-1, seed?=0 } → { ok, appliedCount, frontCount, seedHonored }
random.frontBack  { presetId?=1, seed?=0 }               → { ok, appliedCount, frontCount, seedHonored }
```

둘은 오프셋 폭과 전면 확률만 다른 같은 로직(`FRandomRpcModule::JitterPresetCars`)이다.

| | X 오프셋 | Z 오프셋 | 회전 지터 | 전면 확률 | slotIndex |
|---|---|---|---|---|---|
| `slotJitter` | ±0.15m | ±1.0m | ±5° | 80% | 지원(-1=전체) |
| `frontBack` | ±0.15m | ±0.3m | ±5° | 50% | 없음 |

대상은 `presetId` 가 일치하고 `slotId` 가 프리셋의 면 범위 안에 있는 차량뿐이다(노이즈 차량 = `slotId <= 0` 은 기준 사각형이 없어 제외).

**두 가지 설계 판단(Unity 원본 `CRandomPlacementOps` 는 이 저장소에 없어 규약만 레퍼런스에서 확인했다):**

1. **위치는 항상 "슬롯 중심 + 새 오프셋"으로 다시 계산한다.** 현재 위치에 오프셋을 더하면 반복 호출마다 차량이 누적 이동(drift)해 결국 면을 벗어난다. 슬롯 기하는 언제든 다시 구할 수 있으므로 매번 기준으로 되돌린다.
2. **후면 주차는 `rotY` 를 뒤집지 않고 `isFront=false` 만 세운다.** `ACarActor::ApplyTransformFromData` 가 `isFront==false` 일 때 이미 +180°를 붙이므로, 여기서도 뒤집으면 이중 반전이 된다.

### 4.6 `random.randomizeAll`

```
random.randomizeAll { presetId?=1, seed?=0, randomShow?=true }
  → { ok, shownCount, hiddenCount, noiseShownCount, ambient, seedHonored }
```

세 가지를 한 번에 한다.

1. **슬롯 지터** — `slotJitter` 와 같은 상수(±0.15 / ±1.0 / ±5° / 전면 80%).
2. **노이즈 차량 표시 추첨** — `slotId <= 0` 인 차량을 40% 확률로 표시. `randomShow=false` 면 표시 상태를 건드리지 않고 현재 표시 대수만 센다.
3. **주변광** — Unity `RenderSettings.ambientIntensity` 를 [0.85, 1.15] 절대값으로 넣는다. UE 대응물은 **SkyLight 광량**이라 `ALightControlManager::CaptureCurrent`/`ApplySettings` 의 `SkyIntensity` 를 쓴다.

**주변광 표류 방지:** 매번 "현재값 × 배율"을 하면 반복 호출로 밝기가 지수적으로 흘러간다. 그래서 `FRandomRpcModule::AmbientBaseSky` 에 **최초 1회의 SkyIntensity** 를 잡아 두고 이후에는 항상 그 기준값에 배율을 곱한다. 응답의 `ambient` 는 실제로 적용된 절대값이다.

### 4.7 `random.placeInView` — 보류

사용자 판단으로 이번 범위에서 제외했다. 사유 메시지만 사실에 맞게 갱신했다:

> `미구현(random.placeInView): PTZ 뷰포트 배치 게이트 미이식 — 슬롯 배치는 random.slotPlace 사용`

Unity `CPtzSpaceVehiclePlacer.PlaceVehicles` 는 배치 후보 하나마다 6단계 게이트를 통과시킨다: ① 뷰포트 거리균등 샘플링 → 지면 교점, ② 맵 박스/콜라이더 지면 검증, ③ 기존 차량과 XZ 최소 간격 4m, ④ **신규 차량 번호판이 카메라에서 보이는가**(번호판 bounds 5점 다중 레이캐스트), ⑤ **신규 차량이 기존 차량 번호판을 가리는가**(동일 검사 재수행), ⑥ 화면 2D AABB 겹침 비율 임계. ④⑤ 는 차량 메시 콜리전 프로파일에 결과가 좌우되어 별도 검증 사이클이 필요하다.

이식하려면 `ACarActor` 의 `FrontPlateComp`/`BackPlateComp`(이미 존재)와 `USceneCaptureComponent2D` 의 뷰-프로젝션 행렬을 써서 UE 라인트레이스/투영으로 옮기면 된다.

## 5. 축·단위 규약 (이번 작업에서 반복 등장)

| Unity | UE | 비고 |
|---|---|---|
| `x` (좌우) | `Y` | 오프셋 ±0.15m 가 여기에 걸린다 |
| `z` (앞뒤) | `X` | 오프셋 ±1.0m / ±0.3m |
| `y` (높이) | `Z` | 차량은 0 |
| yaw = `atan2(x, z)` | `atan2(Δ.Y, Δ.X)` | 축 스왑이 그대로 인자 순서에 반영됨 |
| forward = `(sin, 0, cos)` | `(cos, sin, 0)` | 전/후면 판정 내적에 사용 |

미터 → cm 는 `×MetersToUU`(기본 100).

## 6. 빌드에서 걸린 것

`RandomRpcModule.cpp` 의 슬롯 기준 구조체를 처음에 `FSlotBase` 로 지었더니 엔진 SlateCore 의 `FSlotBase`(`Runtime/SlateCore/Public/SlotBase.h`)와 충돌해 C2872(모호한 기호)가 났다. 익명 네임스페이스 안에 있어도 unqualified lookup 이 전역 엔진 타입을 함께 후보로 잡는다. `FPresetSlotBase` 로 개명해 해결했다.

> **교훈:** RPC 모듈 로컬 타입에 `FSlot*`, `FMenu*` 처럼 엔진이 즐겨 쓰는 접두사를 붙이지 말 것. 도메인 접두사(`FPreset...`)를 붙인다.

## 7. 검증

### 7.1 방법

- 빌드: `Build.bat Park3DEditor Win64 Development` → **Succeeded** (에디터 미기동이라 DLL 잠금 없음).
- 실행: `UnrealEditor.exe Park3D.uproject -game -RpcPort=13511 -NoCamStream -windowed`
  (`-NoCamStream` 은 사용자가 돌리고 있는 13510 인스턴스의 스트림 포트 13600/13601 과 충돌하지 않기 위함).
- **사용자의 패키지 인스턴스(13510)는 건드리지 않았다.** 검증 후 13511 인스턴스만 종료하고 13510 이 살아 있음을 `system.health` 로 재확인했다.

### 7.3 검증 이미지

`preset.setBoxVisible` 렌더 확인용 캡처(스크래치패드, 커밋 안 함):

- `visible:true` — 바닥 사각형 5칸 + 그 위 3D 큐브 프레임(파란 선)
- `visible:false` — **바닥 사각형 5칸만** 남고 큐브 프레임이 전부 사라짐

Unity 레퍼런스의 "3D 육면체만 토글하며 바닥 FaceRect 는 건드리지 않는다"와 일치한다.

## 8. 남은 일 / 알려진 제약

- `random.placeInView` 미이식(위 4.7).
- `preset.setBoxVisible` 은 디버그 라인 모드에서만 화면에 보인다(데칼 모드는 큐브를 그리지 않음).
- `random.slotPlace` 는 중복 호출 시 차량이 겹친다(Unity 동작 그대로).
- 패키지(`Package/Windows/Park3D.exe`)는 **재빌드하지 않았다.** 이번 변경을 배포판에서 쓰려면 `BuildPackage.bat` 로 재패키징이 필요하다. 검증은 별도 인스턴스(포트 13511)에서만 수행했다.
