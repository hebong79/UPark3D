# [설계 의견] 차량 오브젝트 ID 단일 권위(Single Source of Truth) 방안

작성일: 2026-07-22 17:05:55
질문: "자동차 오브젝트 ID를 어디서든 한곳에서 가지고 있어야 한다. 그래야 혼선이 생기지 않는다(파일 저장 후 로딩할 때). SQLite / enum 상수 / id↔차량오브젝트 연결 UI / config 중 한 가지는 필요하다. 의견을 달라."

> 본 문서는 **설계 의견서**이며 코드 변경은 하지 않았다. 방향 확정 후 별도 설계서(`parking-design`)로 진행한다.

## 0. 요약 (결론 먼저)

| 제안 | 판정 | 한 줄 이유 |
|------|------|-----------|
| SQLite | **반대** | 13행짜리 정적 룩업에 DB 엔진은 과잉. 에디터 편집 불가 + 서드파티 의존 |
| enum 상수 | **부분 채택** | 권위로 삼으면 안 됨(차량 추가마다 C++ 재컴파일). 단 **검증용**으로는 가치 |
| config(ini/json) | **반대** | `DT_CarCatalog` 와 중복되는 **두 번째 권위**를 새로 만드는 것 |
| id↔오브젝트 연결 UI | **이미 존재** | UE DataTable 에디터가 그 UI다. 새로 만들 필요 없음 |

**권고: 새 저장소를 만들지 말고 `DT_CarCatalog`(DataTable)를 단일 권위로 "승격"시킨다.** 지금 문제는 저장소가 없어서가 아니라, **저장소가 이미 2개인데 둘을 묶는 규약과 검증이 없어서** 생긴다.

승격에 필요한 것은 3가지다:
1. **JSON에 `prefabName` 병기** — 카탈로그가 재정렬돼도 과거 파일이 살아남게 하는 안정 키 (혼선의 핵심 해결책)
2. **카탈로그 무결성 검증 + 조용한 폴백 제거** — 지금은 잘못된 id 가 경고 없이 첫 차량으로 바뀐다
3. **`CatalogFromTable` 정렬 보장** — 콤보 표시 순서가 현재 비결정적이다

## 1. 현재 상태 조사 (사실)

### 1.1 권위가 이미 2개다

| 저장소 | 위치 | 내용 |
|--------|------|------|
| Unity `CScoCarData` (ScriptableObject) | `unity/CarObject/CScoCarData.cs` | `m_Idx`(1부터), `m_Type`, `m_PrefabName` |
| UE `DT_CarCatalog` (DataTable) | `Park3D/Content/Data/DT_CarCatalog.uasset` | `Idx`, `Type`, `PrefabName`, `Mesh` |

UE 쪽 DT 는 Unity ScriptableObject 의 **수동 복제본**이며, 두 저장소를 동기화하는 장치가 **전혀 없다.**

### 1.2 Unity 자체가 이미 이 문제로 다친 적이 있다

`CScoCarData.cs:5-7` 클래스 주석:
```
/// CCarObjListUI의 m_PrefabList 갯수 및 순서가 동일해야 한다.
```
→ 즉 Unity 도 "ScriptableObject 데이터"와 "실제 프리팹 배열" 이라는 **이중 권위**였고, 주석으로 동기화를 강제하려 했다.

그리고 실제로 깨졌다. `CCarPlacementDlg.cs:193-199`:
```csharp
// m_PrefabList 인덱스 순서와 SCarData.m_Idx 값은 일치하지 않을 수 있다.
// (인스펙터에서 m_PrefabList 를 직접 셋팅하고, ScriptableObject 의 m_Idx 에
//  누락/중복이 존재해 nPos+1 == m_Idx 가정이 깨짐.)
// → 프리팹 이름으로 SCarData 를 찾는다.
CScoCarData.SCarData kCarData = m_ScoCarData.m_Datas.Find(x => x.m_PrefabName == prefabName);
```

**주목할 점: Unity 는 깨진 뒤 "정수 인덱스"를 버리고 "이름 매칭"으로 도망쳤다.** 이 사실이 §2 권고의 근거다.

### 1.3 저장 파일은 정수 id 만 들고 있다

`Park3D/Save/3D/CarPos/` — JSON 30개 실측:

| prefabId | 건수 |
|----------|------|
| 1 | 283 |
| 2~13 | 각 6~32 |
| **0** | **2 (오염 데이터)** |

- 사용 범위는 **1~13**. 카탈로그는 13종 규모.
- JSON 에는 **정수 `prefabId` 뿐이고 이름·해시가 없다.** → 카탈로그가 바뀌면 30개 파일 전부가 **조용히 다른 차량으로** 로드된다. 이것이 질문의 "파일 저장 후 로딩할 때 혼선" 이다.
- `isUnreal` 키를 가진 파일은 0개 → 전부 Unity legacy 좌표 파일.

### 1.4 조용한 폴백 (경고 없음)

`CarPlacementManager.cpp:16-30` `FindEntryByPrefabId()`:
```cpp
return Catalog.Num() > 0 ? &Catalog[0] : nullptr;   // 못 찾으면 첫 항목
```
로그 한 줄 없이 첫 차량으로 대체된다. §1.3 의 `prefabId=0` 2건이 지금 이 경로로 조용히 처리되고 있다. **데이터가 틀려도 화면상 그럴듯해 보여서 발견이 안 된다.**

### 1.5 콤보 표시 순서가 비결정적

`CarPlacementManager.cpp:39` `CatalogFromTable()`:
```cpp
for (const TPair<FName, uint8*>& Row : Table->GetRowMap())   // TMap 순회
```
`GetRowMap()` 은 `TMap` 이라 **행 순서를 보장하지 않는다.** 행을 추가/삭제/재임포트하면 콤보 목록 순서가 바뀔 수 있다.

- `prefabId` 자체는 행의 `Idx` 필드에서 오므로 **값은 안전하다**(오늘 추가한 `PrefabIdFromComboIndex` 포함).
- 하지만 **사용자가 보는 목록 순서가 흔들린다.** "3번째 항목이 트럭"이라는 조작 기억이 깨진다.

## 2. 각 제안에 대한 의견

### 2.1 SQLite — 반대

| 항목 | 평가 |
|------|------|
| 데이터 규모 | 13행. 인덱스도 조인도 트랜잭션도 필요 없다 |
| 변경 빈도 | 런타임 불변(차량 종류는 개발 중에만 바뀜). DB 의 강점이 쓰일 데가 없다 |
| 편집성 | **에디터에서 못 고친다.** 별도 편집 툴을 만들어야 하고, 그 툴이 또 하나의 유지보수 대상이 된다 |
| 배포 | 서드파티 모듈 의존 + 패키징/플랫폼별 검증 부담 |
| 프로젝트 규칙 | CLAUDE.md 2번 "단순함 우선 / 요청하지 않은 유연성 추가 금지" 에 정면으로 걸린다 |

**주차면·프리셋까지 포함해 수만 행 규모의 조회가 필요해지면** 그때 재검토할 가치가 있다. 지금은 아니다.

### 2.2 enum 상수 — 권위로는 반대, 검증용으로는 채택

권위로 삼을 때의 문제:
- 차량 1종 추가마다 **C++ 재컴파일**. 오늘 겪은 Live Coding/풀빌드 마찰이 매번 반복된다.
- 아티스트·기획이 차량을 못 늘린다. 엔지니어 병목.
- 메시 경로는 결국 enum 밖 어딘가(=DT)에 있어야 한다 → **또 이중 권위**.

다만 다음은 유효하다:
- `ECarType`(소형/중형/대형/SUV/봉고/트럭)처럼 **개수가 고정된 분류**는 이미 enum 이고, 그대로 두는 게 맞다.
- `prefabId` 는 **개수가 늘어나는 데이터**라 성격이 다르다. enum 부적합.

### 2.3 config(ini/json) — 반대

`DT_CarCatalog` 가 이미 그 역할이다. config 를 추가하면 "DT 와 config 중 뭐가 맞나"라는 **§1.2 에서 Unity 가 이미 겪은 실패를 그대로 재현**한다. 저장소를 늘리는 방향은 문제를 키운다.

### 2.4 id↔차량오브젝트 연결 UI — 이미 존재

UE 의 **DataTable 에디터가 정확히 그 UI** 다(행 = id, 컬럼 = Idx/Type/PrefabName/Mesh, 더블클릭 편집). 새로 만들 필요가 없다.

**단, 지금 빠진 것은 "편집 UI"가 아니라 "검증 UI"다** — 잘못 입력했을 때(Idx 중복, Mesh 비어있음) 알려주는 장치. 이건 §3.2 로 해결한다.

## 3. 권고안 — `DT_CarCatalog` 를 단일 권위로 승격

### 3.1 [핵심] JSON 에 `prefabName` 병기 — 안정 키 도입

문제의 본질은 **저장 파일이 "정수 위치"에만 의존**한다는 것이다. 정수는 카탈로그가 흔들리면 같이 흔들린다. Unity 도 §1.2 에서 이름 매칭으로 도망쳤다.

```
저장 시: prefabId(정수) + prefabName(문자열) 둘 다 기록
로드 시: 1) prefabName 으로 카탈로그 조회  ← 우선
        2) 실패하면 prefabId 로 조회        ← 구 파일 호환
        3) 둘 다 실패하면 폴백 + 경고 로그   ← 조용히 넘어가지 않음
```

| 장점 | 설명 |
|------|------|
| 하위 호환 | `prefabName` 없는 기존 30개 파일은 2)번 경로로 지금과 동일하게 동작. **마이그레이션 불필요** |
| 상위 호환 | Unity 가 이 키를 모르면 무시한다(JSON 객체는 미지 키에 관대). `color` 필드를 이미 같은 방식으로 확장했다 |
| 진짜 해결 | 카탈로그 재정렬·Idx 변경이 있어도 과거 파일이 **올바른 차량으로** 열린다 |

`FCarPos::color` 확장 때 쓴 것과 **동일한 패턴**이라 새 규약을 발명하는 것도 아니다(`ParkingCarTypes.h:85-87`).

### 3.2 카탈로그 무결성 검증 + 조용한 폴백 제거

`ValidateCatalog()` 순수 함수를 추가해 위젯 `NativeConstruct` 와 유닛 테스트에서 호출:

| 검사 | 조치 |
|------|------|
| `Idx` 중복 | Error 로그 — 어느 행이 충돌하는지 명시 |
| `Idx <= 0` | Error 로그 (§1.3 의 `prefabId=0` 오염이 여기 걸린다) |
| `Mesh` 미설정 | Warning — 스폰 시 빈 차량이 되는 것을 미리 잡는다 |
| `PrefabName` 공백/중복 | Warning — §3.1 의 이름 매칭이 무력해지므로 |

그리고 `FindEntryByPrefabId()` 의 조용한 첫-항목 폴백에 **경고 로그를 넣는다.** 폴백 자체는 유지(런타임 안정성) 하되, 침묵은 없앤다.

### 3.3 `CatalogFromTable` 정렬 보장

`GetRowMap()` 순회 결과를 **`Idx` 오름차순 정렬**해 반환한다. 1줄 추가로 콤보 순서가 결정론적이 된다. `prefabId` 산출은 `Idx` 기준이라 정렬해도 값은 안 바뀐다(오늘 추가한 `PrefabIdFromCombo` 테스트가 이를 보장).

### 3.4 Unity↔UE 이중 권위 해소

§1.1 의 두 저장소 문제는 **Unity 의 존속 여부에 따라 답이 갈린다.** 이것이 진행 전 확정이 필요한 유일한 항목이다(§5).

| 시나리오 | 방안 |
|----------|------|
| A. UE 가 Unity 를 **대체** (Unity 는 원본 참조용) | Unity SO → CSV 로 **1회 익스포트** 후 DT 임포트. 이후 DT 가 유일 권위. 가장 단순 |
| B. Unity 와 UE 를 **병행 운영** | Unity SO 를 마스터로 두고 CSV 익스포트 → DT 임포트를 **재현 가능한 절차**로 문서화·스크립트화. 양방향 편집은 금지 |

어느 쪽이든 **"DT 를 손으로 베껴 쓰는" 현재 방식은 중단**해야 한다.

## 5. 진행 전 확정이 필요한 것 (1건)

**Unity 프로젝트를 계속 병행 운영하는가, UE 로 완전 대체하는가?** (§3.4 의 A/B 분기)

- A(대체)면: 1회 임포트로 끝. 작업량 최소.
- B(병행)면: 익스포트 파이프라인을 재현 가능하게 만들어야 하므로 범위가 늘어난다.

## 6. 별건 — 인스턴스 `id` 문자열 문제 (다른 이슈)

질문의 "차량 오브젝트 ID" 를 **개별 배치 차량의 `id` 문자열**로 해석할 경우, 이는 §1~5 와 **별개의 문제**다. 앞선 문서 `20260722_164205_차량오브젝트id_상수지정_조사.md` §5 참조:

`MakeCarId(CarData.datas.Num())` 가 배열 길이를 인덱스로 쓰므로, **삭제 후 재추가 시 같은 초 안에서 id 가 완전히 중복**될 수 있다. `FindByNameId()` 오매칭 위험.

이쪽도 단일 권위가 필요하다면 해법은 다르다 — "다음 발급 번호"를 `FCarPosDatas` 에 들고 다니거나(파일에 저장), `기존 최대 인덱스+1` 로 발급. 필요하면 별도로 다룬다.
