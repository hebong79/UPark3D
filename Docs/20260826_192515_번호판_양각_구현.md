## 1. 결과

차량을 로딩할 때 번호를 **압출 지오메트리로 만들어 번호판에 붙인다.** 평면 위젯이 그리던 번호를
실제 두께가 있는 3D 글자가 대체했고, 조명(태양·채움광)을 받아 측벽에 명암이 생긴다.

| 항목 | 실측 |
|------|------|
| 글자 폭 | 37.6 ~ 41.8 cm (번호 영역 42.08cm 안) |
| 글자 높이 | 5.0 ~ 6.0 cm (판 높이 11cm) |
| 양각 두께 | **1.0 mm** (규격 1.3~1.6mm 대비 얇음 — 6장 한계 참조) |
| 한글 압출 | 가·다·수·마·로·고·머·주 등 정상 |
| 폴백 위젯 | 앞·뒤 모두 자동으로 꺼짐(`폴백위젯=0/0`) |

검증은 에디터 `-game` 모드에서 23대를 띄우고 PTZ 카메라로 근접 촬영해 확인했다.

## 3. 설계

### 3.1 구성

```
FrontPlateComp (SM_Plate_F)
 ├ FrontPlateWidget   ← 평면 번호(폴백). 양각이 확인되면 꺼진다
 ├ FrontPlateText     ← 레거시 TextRender. 이제 항상 꺼 둔다
 └ FrontPlateEmboss   ← UText3DComponent (양각)
      Font      = /Game/Widgets/Fonts/Pretendard/Pretendard, Typeface "Bold"
      Extrude   = 0.15cm, Bevel 0.02 Convex 2세그먼트
      Front/Bevel/Extrude/Back Material = 검정 MID
```

### 3.2 축과 위치 — 판 메시에서 읽는다

판의 얇은 축·긴 축을 코드에 박으면 콘텐츠 교체 때 글자가 모서리로 서서 사라진다(2026-08-16 전례).
그래서 축 계산을 `FCarPlateFrame` 으로 뽑아 **글자·위젯·양각이 같은 기준틀을 쓴다.**

- Text3D 로컬 규약: 글리프는 **YZ 평면**, 압출은 **+X**, **읽는 면은 -X** 를 본다.
  근거는 엔진 소스 — `Text3DGlyphMeshBuilder` 가 Front 를 X=0, Back 을 X=Extrude 에 미러로 놓으므로
  X=0 면의 법선이 -X 다. `CalculateTextScale` 이 `Scale.Y ← 폭`, `Scale.Z ← 높이` 로 쓰는 것도 같은 규약.
- 그래서 컴포넌트 +X 를 판 바깥의 **반대**로 보내고, 세로(+Z)는 판의 세로로 맞춘다.
  글자가 흐르는 +Y 는 `Z ^ X` 로 따라온다(`MakeFromXZ` 규약).
- 좌우 반전이 나면 `PlateEmbossFaceSign` 한 곳만 뒤집으면 회전·흐름·영역 오프셋이 함께 따라온다.

### 3.3 번호 영역

위젯(`UCarPlateNumberWidget`)의 여백과 **같은 비율**을 쓴다 — 좌 80/520, 우 20/520, 상하 10/110.
폴백으로 위젯이 켜져도 번호가 옆으로 튀지 않는다. 판 크기(실측 52.10×11.00cm)에서 매번 계산하므로
판 메시가 바뀌어도 따라간다. 영역 42.08×9.00cm, 중심은 판 중심에서 KOR 스트립 반대쪽으로 +3.0cm.

### 3.4 폴백

Text3D 빌드는 프레임 예산(기본 2ms)으로 쪼개져 나중에 끝난다. `OnTextGenerated` 를 **앞·뒤 각각**
걸어 두고, 완료 시 바운즈가 0이 아니면 그 판의 평면 위젯을 끈다. 양각을 못 만들면 위젯이 그대로
남으므로 번호가 통째로 사라지는 일이 없다.

## 4. 검증 중 드러난 것들 (전부 실측)

### 4.1 ★ 셰이더를 등록하는 플러그인을 추가하면 **exe 교체로는 검증할 수 없다**

이 프로젝트의 상용 절차인 "패키지 복제 후 exe 만 갈아끼우기"로 띄우자 즉사했다.

```
Fatal error: Missing global shader FGeometryMaskJFtoDFCS1's permutation 0,
Please make sure cooking was successful.
```

Text3D 가 끌고 오는 **GeometryMask** 플러그인이 글로벌 셰이더를 등록하는데, 패키지의 글로벌
셰이더맵은 그 플러그인 없이 쿠킹된 것이다. **쿠킹된 WBP 의 C++ 베이스에 `UPROPERTY` 를 추가하면
`Bad export index` 로 즉사하는 것과 같은 계열의 함정**이며, 이 경우도 전체 재쿡이 필요하다.
→ 우회로: `UnrealEditor.exe <uproject> -game` (언쿡 콘텐츠 + 셰이더 온디맨드 컴파일). 이번 검증은 전부 이 경로로 했다.

부수 사고: 패키지 루트의 `Park3D.exe` 는 **171KB 부트스트랩**이고 실제 바이너리는
`Park3D/Binaries/Win64/Park3D.exe`(336MB) 다. 루트를 갈아끼우면 아무 일도 안 하고 떠 있는다.

### 4.2 ★ Text3D 의 자동 영역 맞춤(MaxWidth/MaxHeight)은 쓰면 안 된다

두 가지 이유로 이 용도에는 해롭다.

1. **압출 축까지 줄인다.** `Text3DDefaultLayoutExtension::CalculateTextScale` 의 마지막이
   `if (bScaleProportionally) Scale.X = Scale.Y;` 다. 규격 1.5mm 가 축소분만큼 깎여
   실측 0.06mm(축소율 0.04)까지 얇아졌다.
2. **Max 값이 월드 cm 로 비교되지 않는다.** 영역 폭 42.08cm 를 그대로 넣고 폰트를 키웠더니
   글자가 커지기는커녕 **2.2cm 로 쪼그라들고 프로세스 메모리가 21GB 까지 치솟았다.**

→ 자동 맞춤을 끄고(`SetHasMaxWidth/Height(false)`) **처음부터 영역에 맞는 폰트 크기로 그린다.**
   환산 상수는 실측으로 잡았다(`PlateEmbossWidthPerFontSize`). 축소를 안 타므로 압출도 정확해진다.

### 4.3 ★ 머티리얼은 생성자에서 걸면 안 되고, 컴포넌트 지정만으로도 부족하다

- 생성자에서 `SetFrontMaterial` 등을 걸었더니 **글자가 통째로 흰색**으로 나왔다(빌드가 자기
  기본 머티리얼로 덮는다). → 런타임(`AlignPlateEmboss`)에서 건다.
- 런타임에 4종(Front/Bevel/Extrude/Back)을 다 지정해도 **측벽만 흰색으로 남았다** — 근접 캡처에서
  글자 아래·오른쪽 가장자리에 흰 테두리가 떴다. → 빌드가 만든 글자 메시 컴포넌트를 순회해
  **머티리얼 슬롯을 전부 직접 칠한다**(`PaintPlateEmboss`). 이래야 남는 슬롯이 없다.

### 4.4 ★ 두 점으로 직선을 긋지 말 것 — 두께는 0.1cm 단위로 양자화된다

압출 입력 → 완성 메시 두께 실측:

| 입력(cm) | 실측 두께(cm) |
|---------|--------------|
| 0.150 | 0.100 |
| 0.1875 | 0.100 |
| 0.225 | 0.200 |

처음 두 점(0.150→0.100, 0.225→0.200)만 보고 `두께 = 4/3 × 입력 − 0.1` 로 읽어 0.1875 를
넣었는데, 세 번째 점이 그 직선을 반증했다. 세 점 모두 **`내림(입력, 0.1cm)`** 에 맞는다.

→ 1.3~1.6mm 를 정확히 맞출 수단이 없다. 규격값 0.15 를 그대로 넣고 실효 1.0mm 로 간다(6장).

### 4.5 그 밖에

- **레거시 `UTextRenderComponent` 가 실제로 그려지고 있었다.** `UpdatePlatePresentation` 이 그것까지
  켜고 있어 양각 뒤에 흰 글자가 하나 더 깔렸다. 헤더 주석은 "숨긴다"였는데 코드가 달랐다 →
  항상 꺼 둔다.
- **`OnTextGenerated` 를 앞판에만 걸면 뒤판 폴백 위젯이 켜진 채로 남는다.** 앞·뒤 각각 건다.
- **두께 로그는 축에 정렬된 차량만 읽어야 한다.** `GetBounds` 는 월드 AABB 라 비스듬히 선 차량은
  폭이 두께 축에 섞여 들어온다(같은 빌드에서 0.100 과 0.889 가 같이 나온다).
- **지역 변수를 `Children` 으로 두면 `AActor::Children` 을 가려 C4458 이 에러로 승격된다**
  (2026-08-12 `Dir` 과 같은 함정). `EmbossParts` 로 바꿨다.
- `UText3DComponent::GetBounds()` 는 오버로드가 둘인데 **`FBox` 를 돌려주는 쪽은 export 되지 않아**
  모듈 밖에서 LNK2019 가 난다. out 파라미터 버전만 `TEXT3D_API` 다.
- `ACarActor` 는 네이티브로 스폰되고(`CarPlacementManager.cpp:16,73-74`) `Content/Actors/Car/BP_Car`
  는 `/Script/Engine.Actor` 파생이라 무관하다 → `UPROPERTY` 컴포넌트 추가가 안전하다(확인함).

## 5. 성능

선행 답변에서 예측한 대로다 — **초기 로딩 1회만이고, 끝나면 Text3D 는 틱을 끈다.**
실측(23대, 에디터 -game): 첫 차량 완료까지 지도 로드 후 약 8초, 전체 23대 약 12초.
언쿡 콘텐츠 + 첫 실행 셰이더 컴파일이 섞인 값이므로 패키지 실측은 재쿡 후에 다시 재야 한다.

충돌은 `DefaultText3D.ini` 에서 전역으로 껐다(엔진 설정 주석: *"Text3D with collisions can have a
significant hit on perf"*). 그림자는 끈다 — 1.5mm 자기 그림자는 그림자맵 해상도 아래다.

## 6. 한계 / 미검증

- **양각 두께가 1.0mm 로 규격(1.3~1.6mm)보다 얇다.** 4.4의 양자화 때문이며, 2.0mm 로 올릴 수는
  있으나 규격 상한을 넘는다. 얇은 쪽을 골랐다.
- **패키지(쿡) 검증은 아직 하지 않았다.** 4.1 때문에 전체 재쿡이 필요한데, 재쿡은 실행 중인
  `Park3D.exe` 2개를 닫아야 해서 진행하지 않았다. **패키지에 반영하려면 `BuildPackage.bat` 로
  전체 재쿡이 필요하다** — exe 교체로는 안 된다.
- 성능 수치는 언쿡 기준이다. 선행 문서의 3-B(글리프 사전 굽기 + HISM) 이행 기준(로딩 +1.5초,
  드로우콜 +150)은 **쿡된 패키지에서 다시 재야** 판단할 수 있다.
- `PlateEmbossWidthPerFontSize` 는 Pretendard Bold + 8자 형식 기준 실측이다. 폰트나 번호 형식이
  바뀌면 다시 재야 한다.
- 뒷판 양각의 시각 확인은 하지 않았다(로그로 생성·크기만 확인). 앞판과 같은 경로다.

## 7. 조작 메모 (다음 검증 때 시간 절약용)

- 에디터 `-game` 기동: `UnrealEditor.exe <uproject> -game -RpcPort=13541 -windowed -ResX=1600 -ResY=900 -unattended`
  → 기동 ~2분(엔진 초기화 60초 + 맵 로드 50초).
- `cam.setPosition` 의 `pos` 는 **`{x, z}` 가 지면**이고 높이는 `cam.setHeight` 로 따로 준다.
  `cam.get` 이 돌려주는 `pos` 는 `x`·`z` 가 지면, `y` 가 높이다(둘의 키 이름이 어긋난다).
- **tilt 는 양수가 아래**다(음수가 위).
- 메인 뷰 스트림(13600)은 `view.set` 으로 옮긴 화면과 다른 것을 보여 준다 — 근접 확인은
  PTZ 카메라를 옮겨(`cam.setPosition`/`setHeight`/`setPTZ`) `cam.capturePNG` 로 했다.
- 이번 검증에 쓴 시점: 카메라 2를 지면 `(23.2, 5.245)` 높이 0.62m, `pan 145.6 / tilt 0.30 / zoom 36`
  → BMW 앞 번호판이 화면을 채운다.
