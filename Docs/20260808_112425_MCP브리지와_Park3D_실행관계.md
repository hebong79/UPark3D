# MCP 브리지(park3d-rpc-mcp)와 Park3D의 실행 관계

- 작성: 2026-08-08 11:24:25
- 대상: `park3d-rpc-mcp/`(TypeScript 브리지), Park3D JSON-RPC 서버(13510)
- 배경: 브리지를 **Windows 서비스로 등록**하고 nodemon으로 수정분을 자동 반영하려 함.
  서비스를 내렸다 올리지 않고도 고칠 수 있는지, Claude/Codex가 그 구조에서 붙을 수
  있는지, Park3D 기동 순서에 종속되는지를 확인한 결과를 정리한다.
- 결론: **현재 상태 그대로 진행해도 무리 없다.** 단 서비스화는 http 전송에서만 성립한다.

## 1. 프로세스 구성

```
 [Claude CLI / Codex]                 [park3d-rpc-mcp 브리지]            [Park3D (UE5)]
        MCP 클라이언트     ──MCP──▶      Node 프로세스        ──HTTP──▶   RpcServerSubsystem
                                        툴 2개 노출                        POST /rpc
                                        park3d_catalog                     GET  /rpc/catalog
                                        park3d_rpc                         :13510
```

브리지는 **양쪽 모두에 대해 클라이언트/서버가 뒤바뀐 중계자**다.
- 왼쪽(MCP 경계): 브리지가 **서버**. 클라이언트는 Claude/Codex.
- 오른쪽(RPC 경계): 브리지가 **클라이언트**. 서버는 Park3D의 13510.

두 경계는 완전히 독립적이며, 서로의 생존을 전제하지 않는다.

## 2. 전송 방식이 실행 관계를 결정한다

| | stdio (현재 기본) | http (streamable-http) |
|---|---|---|
| 프로세스를 띄우는 주체 | **클라이언트가 자식 프로세스로 spawn** | **독립 프로세스**(서비스 가능) |
| 클라이언트 설정 | `command`/`args` (실행 명령) | `type: "http"`, `url` |
| 미리 띄워둔 프로세스에 붙기 | **불가능**(stdin/stdout으로만 대화) | 가능 |
| 서버 재시작의 영향 | 세션이 끊김 | 세션 없음 → 다음 요청부터 그대로 붙음 |
| 서비스 등록 | 의미 없음 | 적합 |

즉 **서비스 등록 + nodemon 자동 반영**이라는 목표는 stdio와 원리적으로 상충한다.
클라이언트가 직접 띄우는 자식 프로세스라, 서비스로 올려둔 프로세스에 붙을 수단이 없다.
http로 바꾸면 Claude/Codex 모두 사용할 수 있으며, 클라이언트 설정은 이미 `unreal`
서버가 쓰는 형태와 같다.

```json
// .mcp.json
"park3d-rpc": { "type": "http", "url": "http://localhost:13520/mcp" }
```
```toml
# .codex/config.toml
[mcp_servers.park3d-rpc]
url = "http://localhost:13520/mcp"
```

http 모드가 **세션 없는(stateless)** 구현이라는 점이 여기서 이득이 된다. `Mcp-Session-Id`를
요구하지 않으므로 브리지가 중간에 재시작돼도 클라이언트가 세션을 잃지 않는다.
(실측: 사전 `initialize` 없이 곧바로 `tools/call` 을 보낸 요청이 정상 처리됨.)

## 3. Park3D 기동 순서와 무관하다 — 실측

브리지는 **기동 시점에 Park3D에 접속하지 않는다.** 연결을 유지·캐시하는 클라이언트
객체가 없고, 툴이 호출될 때마다 `fetchRpc()`가 그 자리에서 새 요청을 만든다
(`src/server.ts`). 이를 죽은 포트(13599)로 브리지를 띄운 뒤 대상 서버를 뒤늦게
올리고 내리는 순서로 확인했다.

| 단계 | 결과 |
|------|------|
| 대상 서버 없이 브리지 기동 | 정상 기동. `리슨 시작` 로그 출력, `GET /health` → `{"ok":true}` 200 |
| 그 상태로 툴 호출 | `{"ok":false,"error":"서버 연결 실패(http://localhost:13599): TypeError: fetch failed. Park3D가 실행 중인지 확인하라."}` — 프로세스는 죽지 않고 오류만 반환 |
| 대상 서버를 나중에 기동 → **브리지 재시작 없이** 호출 | `{"ok":true,"methods":[...]}` / `{"ok":true,"result":{...}}` — 즉시 연결 |
| 대상 서버를 다시 내림 | 다시 `서버 연결 실패` 로 복귀 |

운영상 의미:
- **기동 순서 제약이 없다.** 브리지 서비스를 부팅 시 자동 시작으로 걸고, Park3D는
  필요할 때 켜면 된다. Park3D를 껐다 켜도 브리지는 손댈 필요가 없다.
- 반대로 **브리지가 살아 있다는 것이 Park3D가 살아 있다는 뜻은 아니다**(4절).

## 4. 상태 확인 지점이 두 개다

| 확인 대상 | 방법 | 주의 |
|---|---|---|
| 브리지 자신 | `GET http://localhost:13520/health` | 토큰 게이트 면제. **Park3D 상태는 보지 않는다** |
| Park3D | `GET http://localhost:13510/rpc/catalog` 또는 툴 `park3d_rpc {"method":"system.ping"}` | 월드/맵 로드가 필요한 도메인 메서드는 별개 |

`/health` 200 만 보고 "정상"이라 판단하면, Park3D가 죽어 있는 상태를 놓친다.
서비스 감시는 `/health`, 실제 사용 가능 여부는 `system.ping` 으로 나눠 볼 것.

## 5. 서비스 등록 시 걸리는 항목

1. **http 모드는 `PARK3D_RPC_TOKEN` 을 기동 필수로 요구한다**(Python 판부터 있던 게이트).
   현재 Park3D(13510)는 토큰이 설정돼 있지 않아 **아무 값이나 통과한다** — 실측으로
   임의 토큰 `dummytoken` 을 붙여 `system.ping` 이 `{"ok":true}`, `/rpc/catalog` 도 200.
   따라서 더미 값 하나만 넣으면 코드 수정 없이 기동된다.
2. **루프백 바인드면 `PARK3D_MCP_TOKEN` 은 없어도 된다**(무인증 경고만 출력).
   이 프로젝트의 무보안 정책과도 맞는다. 외부 개방(0.0.0.0) 시에는 필수이며,
   `PARK3D_MCP_ALLOWED_HOSTS` 로 DNS 리바인딩 보호를 함께 켜야 한다.
3. **로그는 stderr로 나간다.** stdio 모드에서 stdout은 MCP 프로토콜 채널이므로 기동
   배너·경고·오류를 전부 stderr로 낸다. 서비스 래퍼에서 stderr를 파일로 리다이렉트하지
   않으면 진단 정보가 통째로 사라진다.
4. **작업 디렉터리를 프로젝트 폴더로 지정할 것.** nodemon이 `nodemon.json` 을 찾지 못하면
   기본 동작으로 떨어져 `ts-node` 를 실행하려다 실패한다.
5. **Park3D 본체는 서비스로 올릴 수 없다.** GUI 앱이라 Session 0에서 기동되지 않는다.
   서비스 대상은 브리지 하나뿐이고, Park3D는 사람이 띄운다.

권장 구성(가장 단순한 형태):

```
PARK3D_MCP_TRANSPORT=http
PARK3D_MCP_HOST=127.0.0.1
PARK3D_MCP_PORT=13520
PARK3D_RPC_URL=http://localhost:13510
PARK3D_RPC_TOKEN=dummy      # 기동 게이트 통과용. Park3D는 현재 토큰 미검사
# PARK3D_MCP_TOKEN 미설정   # 루프백 전용 무인증
```

## 6. nodemon 자동 반영의 실제 범위 — 실측

| 변경 | 재시작 |
|---|---|
| `src/server.ts` 내용 수정 | **O** (배너 문구에 표식을 넣어 재시작 후 출력이 바뀌는 것까지 확인) |
| `src/` 에 새 `.ts` 추가 | **O** |
| `package.json` 수정 | **X** (`watch: ["src"]`, `ext: "ts"` 밖) |
| `nodemon.json` 수정 | **X** — nodemon 자체를 다시 띄워야 적용 |

한계:
- **재시작 순간의 진행 중 요청은 실패한다.** 다음 요청은 정상. "무중단"이 아니라
  "서비스 재등록 없이 자동 반영"이 정확한 표현이다.
- **문법 오류가 있으면 crash 후 파일 변경까지 대기**한다. 그동안은 `/health` 도 죽는다.
- **`dist/` 는 갱신되지 않는다.** nodemon은 `node src/server.ts` 를 돌린다.
  실측: `src` 를 고쳐도 `dist/server.js` 에는 반영되지 않았고 타임스탬프도 그대로였다.

## 7. `.ts` 직접 실행 가능 여부

`.mcp.json`/`config.toml` 의 실행 명령은 임의 명령이므로 `.ts` 를 직접 가리켜도 된다.
이 PC의 Node 24.10은 `process.features.typescript === "strip"` — 타입 스트리핑이
**기본 활성**이며, `node src/server.ts` 로 stdio 서버를 띄워 `initialize` →
`tools/list` → `system.ping` 까지 정상 확인했다.

대가로 감수할 것: 실행 시 **타입 검사가 없다**(`npm run typecheck` 가 유일한 게이트),
Node 22.18+ 필요, erasable 문법만 허용(`enum`·`namespace`·생성자 파라미터 프로퍼티 불가.
tsconfig에 `"erasableSyntaxOnly": true` 로 미리 막을 수 있다).

현 시점에는 전환하지 않았고, `.mcp.json`/`config.toml` 은 `dist/server.js` 를 가리킨다.
따라서 **소스를 고치면 `npm run build` 가 필요하다.**

## 8. 현재 상태 판단

- 브리지는 Park3D 생존과 무관하게 뜨고, 나중에 Park3D가 올라오면 재시작 없이 붙는다 → **서비스화에 적합**.
- 서비스로 쓰려면 전송을 **http 로 전환**해야 하며, 그때 Claude/Codex는 `url` 형태로 붙는다.
- stdio를 유지하는 한 서비스 등록은 의미가 없고, 클라이언트가 매번 프로세스를 띄운다.

미결(진행 시 결정 필요):
1. 클라이언트 설정을 http로 전환할지(전환하면 stdio 경로는 개발용으로만 남는다).
2. 서비스 래퍼 선택 — nssm(로그 리다이렉트·자동 재시작 내장)이 가장 단순.
3. 실행 대상을 `dist/server.js` 로 둘지 `src/server.ts` 직접 실행으로 바꿀지(7절).
