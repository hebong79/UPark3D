## 1. 문제

## 2. 한 일

### 2-1. 계측을 세 단계로 분리

`FCamStreamMsRing` 링 버퍼 구조체를 새로 만들고(기존 `MainCaptureMsRing`/`Next`/`Count`/`Last`
4개 멤버를 이 구조체로 흡수), 링을 4개 둔다.

| 멤버 | 의미 |
|------|------|
| `MainSceneMs` | `CaptureScene()` 구간 |
| `MainReadbackMs` | 리드백 구간 — **비동기이므로 "게임 스레드가 실제로 쓴 시간"**(렌더 커맨드 등록 + 픽셀 인수인계). GPU 대기 시간이 아니다 |
| `MainEncodeMs` | JPEG 인코딩 구간 |
| `MainTotalMs` | 위 셋의 합 = 기존 `captureAvgMs`/`captureMaxMs` 가 읽던 값(키·의미 유지) |

한 프레임의 세 단계는 서로 다른 틱에서 일어난다(요청 틱 / 완료 틱). 그래서 요청 시점의 값을
`MainPendingSceneMs`·`MainPendingReadbackMs` 에 모아 두었다가, 프레임을 공개하는 순간 네 링에
한꺼번에 기록한다. 창 크기는 기존 `MainStatWindow`(기본 60)를 네 링이 공유한다.

주기 로그도 단계별 값을 함께 찍도록 확장했다.

```
[CamStream] 메인 뷰 캡처 비용(게임 스레드): 합계 평균 x / 최대 x / 직전 x
            [씬 a/b · 리드백 c/d · 인코딩 e/f] (표본 n, 창 60, 960x540, 목표 10.0fps 실측 y, 가드=1)
```

### 2-2. 리드백을 비동기로

`FRHIGPUTextureReadback`(UE 5.8 `Engine/Source/Runtime/RHI/Public/RHIGPUReadback.h`)으로 교체했다.

```
틱 A : CaptureScene()  →  ENQUEUE_RENDER_COMMAND(EnqueueCopy)   ← 기다리지 않는다
틱 B~: ENQUEUE_RENDER_COMMAND(Poll) → 렌더 스레드에서 IsReady() 확인
                                       참이면 Lock → 행 단위 복사 → Unlock → Stage=Ready
틱 C : 게임 스레드가 픽셀 인수 → JPEG 인코딩 → UpdateFrame()
```

`ProduceMainJpeg()` 하나를 아래 넷으로 쪼갰다.

| 함수 | 역할 |
|------|------|
| `RequestMainCapture()` | 시점 반영 → `CaptureScene()` → 복사 커맨드 등록 |
| `PollMainReadback()` | 완료 확인 커맨드 등록(게임 스레드는 커맨드만 넣는다) |
| `TryTakeMainFrame()` | 완료됐으면 픽셀 인수 → JPEG 인코딩 → 통계 기록 |
| `ReleaseMainReadback()` | 진행 중인 요청을 안전하게 버린다 |

#### 틱 사이 상태

`FCamStreamMainReadback` 을 `TSharedPtr<..., ESPMode::ThreadSafe>` 로 들고 다닌다.

- `Stage`(`Idle`/`Pending`/`Ready`), `bAbandoned`, `bFailed`, `Width`/`Height`, `Pixels`
  → `FCriticalSection Mutex` 로 보호.
- `FRHIGPUTextureReadback* Readback` → **렌더 스레드 전용**(`Lock()` 이 즉시
  `FRHICommandListImmediate` 를 만지므로 게임 스레드에서 부르면 안 된다). 그래서 뮤텍스 밖.

#### 겹침 방지

페이싱이 돌아왔을 때 `Stage != Idle` 이면 새 캡처를 **건너뛴다**. `Accum` 은 한 프레임치(`Interval`)로
묶어 두어 다음 틱에 곧바로 재시도하되 부채가 무한 누적되지 않게 했다.

#### 정리

- 클라이언트 0명 / 채널 정지(`StopMainChannel`) / 해상도 변경 감지 시 `ReleaseMainReadback()`.
- 게임 스레드는 `bAbandoned=true` 만 세우고 자기 참조를 놓는다. 마지막 참조는 **정리용 렌더 커맨드**가
  쥐고 있으므로, `Readback` 의 `delete` 는 항상 렌더 스레드에서, 그리고 앞서 걸어둔 복사·폴링
  커맨드보다 **뒤에서**(렌더 커맨드는 FIFO) 일어난다.
- 해상도 변경 시 통째로 버리는 이유: `FRHIGPUTextureReadback::EnqueueCopy` 는 스테이징 텍스처를
  재사용할 때 크기가 같다고 가정한다(엔진 주석: *"Assume for now that every enqueue happens on a
  texture of the same format and size (when reused)"*). 크기가 바뀌면 새 객체가 필요하다.
- 반대로 **같은 해상도에서는 리드백 객체를 재사용**한다. 매 프레임 새로 만들면 스테이징 텍스처와
  GPU 펜스를 프레임마다 다시 만들게 되어 비동기로 얻은 이득을 도로 까먹는다.

#### row pitch

`Lock(OutRowPitchInPixels, &OutBufferHeight)` 가 돌려주는 행 간격은 **픽셀 단위**이며 폭보다 클 수
있다(D3D12 는 `Footprint.RowPitch / BytesPerPixel`, 즉 `D3D12_TEXTURE_DATA_PITCH_ALIGNMENT` 로
정렬된 값). 그대로 인코더에 넘기면 행마다 시작점이 밀려 영상이 비스듬해진다. 그래서 행 단위로
`W * sizeof(FColor)` 씩만 복사한다.

```cpp
for (int32 Y = 0; Y < CopyH; ++Y)
{
    FMemory::Memcpy(Pixels.GetData() + Y * W, Src + Y * RowPitchInPixels, W * sizeof(FColor));
}
```

`RowPitchInPixels < W` 이면 실패로 처리한다. 스테이징 버퍼 높이가 요청보다 작으면 남는 행을 0으로
채운다(초기화되지 않은 메모리를 인코더에 넘기지 않기 위해).

#### 픽셀 포맷

렌더타깃은 `RTF_RGBA8` → `PF_B8G8R8A8`(`TextureRenderTarget2D.h::GetPixelFormatFromRenderTargetFormat`).
`FColor` 의 메모리 배치가 B,G,R,A 라 **변환 없이 재해석**할 수 있다. 기존 `ReadPixels` 경로도
`SetLinearToGamma(false)` 라서 8비트 BGRA 를 그대로 복사했으므로 색 규약이 같다.

포맷이 BGRA8 이 아니면 색이 뒤집힌 영상을 조용히 내보내는 대신 **에러 로그 + 실패**로 끝낸다.

#### 실패 경로 보존

- `GameThread_GetRenderTargetResource()` 가 null(`-nullrhi`) → 기존대로 false.
- 렌더 스레드에서 소스 텍스처 없음 / `Lock` 실패 / row pitch 이상 → `bFailed=true` 이면서
  `Stage=Ready` 로 올려 **게임 스레드가 수거**하게 한다. Pending 으로 남기면 스트림이 조용히 멈춘다.
- 수거 시 `LogCamStreamSub Warning` 을 남기고 그 프레임만 버린다.

## 4. `MainFps` 10 만들기

`DefaultGame.ini` 의 `MainFps=5.0` → `10.0` 으로 변경(다음 패키징부터 기본값).

지금 도는 것은 패키지 빌드이고 그 ini 는 pak 안에 있다(`Manifest_UFSFiles_Win64.txt` 에

exe 만 갈아끼우는 배포로는 반영되지 않는다.

### 커맨드라인 ini 오버라이드 — 소스로 확인한 정확한 표기

```
Park3D.exe -ini:Game:[/Script/Park3D.CamStreamSubsystem]:MainFps=10
```

근거(UE 5.8 소스, 실행해 보지는 않음):

- `Core/Private/Misc/ConfigCacheIni.cpp:2321` 주석 — `-ini:IniName:[Section1]:Key=Value`,
  예시 `-ini:Engine:[/Script/Engine.Engine]:bSmoothFrameRate=False`.
- 같은 파일 `CommandlineOverrideSpecifiers`(1714~1724): `-ini:` / `:[` / `]:` / 구분자 `,`.
- `IniName` 은 `FPathViews::GetBaseFilename(BaseIniName)` 과 대조되므로 `DefaultGame.ini` 계열은 `Game`.
- 게이트: `ConfigCacheIni.h:57` `#define ALLOW_INI_OVERRIDE_FROM_COMMANDLINE (UE_SERVER || !(UE_BUILD_SHIPPING))`.
  `BuildPackage.bat` 이 `-clientconfig=Development` 이므로 **켜져 있다**(Shipping 이면 무효).
- 바이너리 config 우회 여부: 스테이지 매니페스트에 `Config.bin` 류가 없어 텍스트 config 경로를 타므로
  `FConfigContext` 의 오버라이드 적용 지점(`ConfigContext.cpp:1115`, `1370`)을 지난다.

### 대안 1 — 파일 통째로 바꿔치기 (검증: 소스 기준)

```
Park3D.exe -iniFile=<절대경로>\Park3D\Config\DefaultGame.ini
```

`ConfigCacheIni.cpp:1728 OverrideFileFromCommandline` 이 pak 안의 같은 상대경로 ini 를 이 파일로
치환한다. `IPlatformFilePak.cpp:4600` 의 `IsNonPakFilenameAllowed` 도 `-iniFile=` 로 지정된 ini 만
예외적으로 허용한다.

### 안 되는 방법

스테이징 폴더에 그냥 `Park3D/Config/DefaultGame.ini` 를 떨궈 두는 것: `FPakPlatformFile::FileExists`
(`IPlatformFilePak.h:2285`)가 **pak 을 먼저 본다**. pak 안에 같은 파일이 있으므로 느슨한 파일은
가려진다. (`DISABLE_NONUFS_INI_WHEN_COOKED` 가 0 이라 "금지"는 아니지만 "우선순위"에서 진다.)

## 5. 위험

| 위험 | 근거 / 대응 |
|------|-------------|
| 영상이 비스듬해짐 | row pitch 를 행 단위로 걷어내 처리했고 `RowPitchInPixels < W` 는 실패 처리. 다만 **실기 확인은 못 했다**(앱 재기동 금지). 다음 빌드 후 반드시 눈으로 볼 것 |
| 색이 뒤집힘(BGR↔RGB) | RT 가 `PF_B8G8R8A8` = `FColor` 배치와 동일하므로 이론상 없음. 다른 포맷이면 실패로 끊는 가드를 넣었다. 역시 실기 미확인 |
| 상하 반전 | 스테이징 복사는 원본과 같은 방향이라 반전이 없어야 한다. **소스로 추론했을 뿐 실측하지 않았다** |
| 프레임 지연 1~3틱 | 설계상 허용(감시 스트림). 다만 앱 틱이 매우 느리면 지연이 눈에 띌 수 있다 |
| 리드백이 영영 안 끝나면 | `Stage` 가 `Pending` 에 갇혀 스트림이 멈춘다. 실패 경로는 `Ready`+`bFailed` 로 올려 로그를 남기지만, **`IsReady()` 가 계속 false 인 경우의 워치독은 넣지 않았다**(요청 범위 밖) |
| 스킵 가시성 없음 | 겹침으로 건너뛴 횟수를 노출하지 않는다. fps 가 목표에 못 미칠 때 원인이 스킵인지 페이싱인지 수치로 구분되지 않는다. 필요하면 `main.skippedBusy` 카운터 1개 추가를 권한다 |
| 렌더 스레드 부담 이동 | GPU 대기가 게임 스레드에서 렌더 스레드로 옮겨간 것이 아니라(폴링 방식이라 대기 자체가 없다) 사라진다. 다만 매 틱 렌더 커맨드 1개가 추가된다 |
| PTZ 채널은 그대로 | `ProduceJpeg` 는 여전히 동기다(지시대로 손대지 않음) |

## 8. 추가 — `ViewRpcModule` 익명 네임스페이스 함수 개명 (커밋 `d535b38`)

이 문서 작성 시점(17:59) 이후, 커밋 시점에 같은 변경 묶음으로 들어간 파일이 하나 더 있다.

`GetMainStreamSubsystem` 으로 개명했다. `CamRpcModule.cpp` 에 동명 함수가 있어
**unity 빌드에서 한 번역단위로 합쳐지며 C2084(재정의)** 로 빌드가 깨졌기 때문이다.

> ⚠ adaptive unity 는 **변경된 파일을 unity 빌드에서 빼기 때문에**, 그 파일을 고친 직후의
> 빌드는 통과해 버리고 나중에(파일이 다시 unity 로 들어갈 때) 터진다.
> §6 의 빌드로 확인할 때 "직후 빌드 통과"를 안전 근거로 삼으면 안 된다.
