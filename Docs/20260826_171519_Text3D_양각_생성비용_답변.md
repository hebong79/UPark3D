## 질문

> 3-A로 진행할 때 양각 번호판을 실시간으로 만드는 데 걸리는 시간은 어느 정도인가?
> 차량이 약 40~50대일 때 **초기 로딩할 때만** 사용하는 것인지, 아니면 **실시간으로 매번 동작**하고 있는지.

## 한 줄 답

**초기 로딩 때 1회만이다. 다 만들고 나면 Text3D 는 틱 자체를 끈다(`ETickableTickType::Never`).**
그 뒤 남는 비용은 "만드는 비용"이 아니라 "이미 만든 메시를 그리는 비용"뿐이다.

아래는 추정이 아니라 UE 5.8 플러그인 소스에서 직접 읽은 내용이다
(`Engine/Plugins/VirtualProduction/Text3D`).

---

## 1. 상시 동작하지 않는다 — 근거 5가지

| # | 근거 | 위치 |
|---|------|------|
| 1 | 빌드 큐가 비면 **틱을 완전히 끈다** — `if (!IsBuildingText()) { … SetTickableTickType(ETickableTickType::Never); return; }` | `Private/Subsystems/Text3DBuildSystem.cpp:222-229` |
| 2 | `UText3DComponent` 에는 **`TickComponent`·`bCanEverTick` 자체가 없다**(grep 결과 0건) → 컴포넌트가 매 프레임 도는 일이 없다 | `Private/Text3DComponent.cpp` |
| 3 | 재빌드는 **속성이 바뀔 때만** 요청된다(`RequestTextBuild`). 우리는 로딩 시 `SetText` 1회 후 번호·폰트·압출값을 건드리지 않는다 | `Text3DBuildSystem.cpp:68` |
| 4 | 빌드는 **프레임 예산 2ms** 로 잘라 여러 프레임에 나눠 지불한다 — `Text3D.Build.BuildTimeBudget` 기본 `0.002`초 | `Text3DBuildSystem.cpp:29-32` |
| 5 | 빌드 중인 프리미티브는 **씬 뷰에서 숨긴다**(`HidePrimitivesBeingBuilt`) → 반쯤 만들어진 글자가 깜빡이지 않는다 | `Public/IText3DBuildSystem.h:31` |

즉 구조가 **"로딩 스파이크를 피하도록 설계된 1회성 빌드"** 다. 상시 갱신 루프가 아니다.

## 2. 비용이 차량 수에 비례하지 않는다 — 글리프 메시 캐시

압출된 글자 메시는 **엔진 서브시스템에 전역 캐시**된다.

- 캐시 키 = `(FontFace 해시, GlyphIndex, FGlyphMeshParameters)`
  → `FGlyphMeshParameters` 는 압출/베벨/크기 등이다. **폰트·압출값이 같으면 50대가 같은 메시를 공유한다.**
  (`Private/Subsystems/Text3DEngineSubsystem.h:32-118`, `CachedFontFaces`)
- 압출 계산은 **멀티스레드**다 — `BuildGlyphMesh` 주석 "This is called from multiple threads",
  `ProcessBuildGlyphMeshes` 주석 "Processes the queued mesh descs … across multiple threads".
- 캐시 청소는 **안 쓰이게 된 뒤** `FontFaceGlyphCleanupDelay`(기본 **5초**) 후.
  → 차를 지웠다 5초 안에 다시 만들면 그대로 캐시 히트.

### 우리 번호 체계로 계산한 실제 압출 횟수

`ACarActor::MakeDeterministicPlateNumber` 의 문자 공간
([CarActor.cpp:216](../Park3D/Source/Park3D/CarActor.cpp#L216)):

- 숫자 `0~9` = **10종**
- 용도 한글 pool = **34종** (`가나다라마바사거너더러머버서어저고노도로모보소오조구누두루무부수우주`)
- 구분 공백 1종

차량 50대일 때 실제로 등장하는 한글의 기댓값은 `34 × (1 − (1 − 1/34)^50) ≈ 26종`.

```
고유 글리프 ≈ 10(숫자) + 26(한글) + 1(공백) ≈ 37개
전체 글자 자리 = 50대 × 2판 × 8자 = 800자리
→ 실제 압출 37회, 나머지 763자리는 전부 캐시 히트 (95%)
```

**핵심**: 압출 비용에는 상한이 있다. 차량이 200대여도 pool 이 34종이라 고유 글리프는 **45개(10+34+1)에서 포화**한다.
40대든 50대든 100대든 압출 총량은 거의 같다.

## 3. 걸리는 시간 — 추정치와 계산 근거

⚠ **아래 숫자는 소스에서 읽은 구조 위에 얹은 추정이다. 실측은 6장 절차로 해야 한다.**

| 항목 | 추정 | 근거 |
|------|------|------|
| 글리프 1개 압출(윤곽 로드 → 삼각분할 → 압출 → 베벨) | 0.5 ~ 3 ms | 일반적인 폰트 아웃라인 메시화 비용. 한글은 획이 많아 숫자보다 비싸다 |
| 고유 글리프 37개 총합 | **20 ~ 110 ms** (CPU 합계, 멀티스레드라 벽시계는 더 짧음) | 위 × 37 |
| 컴포넌트 100개(앞뒤 판) 레이아웃 + 등록 | **10 ~ 50 ms** | 글자당 StaticMeshComponent 생성·등록. 렌더러가 `BatchRemove/ReleasePrimitives` 로 묶어 처리한다 |
| **CPU 작업 총량** | **약 0.03 ~ 0.16 초** | |

이 총량을 **프레임당 2ms 예산**으로 나눠 지불하므로:

```
0.03~0.16초 ÷ 0.002초/프레임 = 약 15 ~ 80 프레임
60fps 기준 → 로딩 후 약 0.3 ~ 1.3초에 걸쳐 번호판이 순차적으로 나타난다
```

**프레임 히치는 나지 않는다** — 프레임당 2ms 를 넘기지 않도록 스스로 끊는다.
대신 "차는 떴는데 번호판이 잠깐 뒤에 붙는" 그림이 된다(빌드 중에는 숨겨져 있다).

### 즉시 다 보여야 한다면

`UText3DBuildSystem::BlockBuildTexts()` 로 몰아칠 수 있다. 단 엔진 주석이 명시한다 —
*"This can cause a hitch and should only be used when the result is needed immediately regardless of hitch."*
로딩 화면 뒤에서라면 써도 되지만, **기본(incremental)을 권장**한다.

## 4. 빌드가 끝난 뒤 매 프레임 남는 비용

생성 비용은 0 이고, **렌더링 비용만** 남는다.

| 항목 | 값 | 비고 |
|------|-----|------|
| Text3D 빌드 시스템 틱 | **0** | 틱 타입이 `Never` 로 꺼진다 |
| Text3D 컴포넌트 틱 | **0** | 틱 함수 자체가 없다 |
| StaticMeshComponent 수 | 50대 × 2판 × 8자 = **800개** | 글자마다 1개(`CharacterMeshes`) |
| 드로우콜 | **측정 필요** | 고유 글리프 메시가 37종뿐이라 auto-instancing 이 잘 먹으면 크게 접힌다. 반대로 안 접히면 수백 단위 — **3-B(HISM) 이행 판단의 핵심 수치** |

**반드시 켤 것 — 충돌 끄기.**
엔진 설정 주석에 *"Text3D with collisions can have a significant hit on perf"* 라고 적혀 있다
(`Text3DProjectSettings.h:166-171`). 번호판 글자는 충돌이 전혀 필요 없다
→ `bForceDisableTextCollision = true` 또는 컴포넌트별 `NoCollision`.

---

## 5. "실시간으로 다시 도는" 유일한 경우

다음 중 하나를 **런타임에 바꿀 때만** 재빌드가 걸린다.

- 번호 문자열 변경 (`SetText`)
- 폰트/타입페이스 변경
- Extrude / Bevel / 크기 변경

우리 설계에서는 번호가 `MakeDeterministicPlateNumber` 로 로딩 시 확정되고 이후 불변이므로
**재빌드는 발생하지 않는다.** 단 주의할 것 하나 —

> `UpdatePlatePresentation()` 이 여러 번 호출되더라도 **문자열이 같으면 `SetText` 를 호출하지 말 것.**
> 값이 같아도 setter 를 부르면 빌드 요청이 다시 들어갈 수 있다. `if (기존 != 새 값)` 가드를 둔다.

## 6. 실측 절차 (구현 3단계 이후)

| # | 방법 | 얻는 것 |
|---|------|---------|
| 1 | `Log LogText3D VeryVerbose` 켜고 첫 `Requesting … text build` ~ `No more build jobs left` 로그의 **시각차** | 실제 벽시계 소요 시간 |
| 2 | `Text3D.Build.EnableBuildTimeBudget 0` 으로 한 프레임에 몰아친 뒤 `stat unit` | **순수 CPU 총량**(예산 분할 없는 값) |
| 3 | 번호판 유/무 상태에서 `stat rhi` 드로우콜 델타 | 3-B(HISM) 이행 여부 판단 |
| 4 | 40대 / 50대 / 100대로 반복 | 캐시 포화 가설(차량 수에 비례하지 않음) 검증 |

**3-B 이행 기준(선행 문서와 동일)**: 65대 로딩 추가 지연 > 1.5초 또는 드로우콜 +150 이상.
3장 추정(0.3~1.3초)이 맞다면 **3-A 로 충분하다**. 어긋나면 3-B 로 옮긴다.

---

## 7. 요약

- **초기 로딩 1회만**이다. 상시 동작하지 않고, 끝나면 **틱까지 꺼진다**.
- 압출은 **글자 모양 단위로 전역 캐시**되어 50대가 공유한다 → 실제 압출 **약 37회**, 800자리 중 95%가 캐시 히트.
- 비용이 **차량 수에 비례하지 않는다**. 문자 pool 이 34종이라 45개에서 포화한다.
- 추정 소요 **0.3~1.3초**, 프레임당 2ms 로 나눠 지불하므로 **히치 없음**. 대신 번호판이 살짝 늦게 붙는다.
- 남는 상시 비용은 렌더링뿐이며, **충돌은 반드시 끈다**.
- 위 수치는 소스 구조 위의 추정이다 — **6장 절차로 실측한 뒤 확정한다.**
