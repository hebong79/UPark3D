# 시나리오 파일 스키마와 `scenario.*` RPC 설계

- 날짜: 2026-08-13
- 성격: **설계 문서**. 코드 변경 없음. 이 문서를 쓰는 동안 소스·런타임을 바꾸지 않았다.
- 목적: 가림 연출 시나리오 5종([20260813_155500](20260813_155500_차량가림연출_시나리오기획_5종.md))을
  **저장·재현·랜덤 변주·원격 실행**할 수 있는 형태로 묶는다.
- 검증 기준: 기획서 5종을 이 스키마로 **실제로 표현할 수 있는가**. §5 에서 하나씩 대조했고,
  표현되지 않는 2건을 찾아 필요한 확장을 명시했다.

---

## 1. 왜 필요한가 — 세 질문이 한 곳으로 모인다

| 질문 | 지금 상태 | 막히는 지점 |
|---|---|---|
| 아무 주차장에서나 되는가 | 절차는 이식되나 **수치가 박혀 있다**(pan 58.1°, 좌표 -19.371 …) | 레이아웃이 바뀌면 사람이 다시 계산 |
| 저장·재현·랜덤이 되는가 | 부품은 다 있다(car/cam/preset 저장, seed) | **묶는 파일이 없다**. 4~5개를 따로 로드하고 순서를 사람이 기억 |
| RPC 화가 되는가 | `sim.scenario` 선례 있음 | 주행 1건짜리. 배치·카메라·조명·촬영을 포괄하지 못함 |

셋 다 "**장면 전체를 하나의 선언으로 적고, 그것을 실행하는 주체**"가 없어서 생긴다.

## 2. 현재 RPC 표면 점검 (실측)

등록된 모듈 8개: `Cam` `Car` `Map` `Measure` `Preset` `Random` `Sim` `View`.

| 시나리오 구성요소 | RPC | 상태 |
|---|---|---|
| 주차면 | `preset.load/save/create/update/...` | ✅ |
| 차량 배치 | `car.load/save/create/setPosition/setColor/show/...` | ✅ |
| 차량 랜덤 | `random.*` (8곳 전부 `seed` 노출) | ✅ |
| 카메라 위치·PTZ | `cam.setPosition/setHeight/setPTZ/savePreset/loadPreset/applyPreset` | ✅ |
| 캡처 | `cam.captureJPG/capturePNG` (base64 + width/height) | ✅ |
| 주행 | `sim.start/scenario/exit/stop/status/list/replay` (`seed` 노출) | ✅ |
| 맵 크기 | `map.get/resize/save/load` | ✅ |
| **조명·노출** | — | ❌ **RPC 없음** |
| **시나리오 묶음** | — | ❌ 없음 |

**조명이 빠져 있는 것이 이번 설계에서 가장 중요한 발견이다.** 가림률을 픽셀 수로 재기 때문에
측정 중 노출이 달라지면 수치가 통째로 오염된다. 재현 가능한 시나리오라면 조명이 정의에 들어가야 한다.

다행히 적용 API는 이미 있다 — `ALightControlManager::ApplySettings(FLightSettings)`,
`CaptureCurrent(FLightSettings&)`, `GetLastApplied()`. 직렬화도 `ULightControlLibrary::ToJson/FromJson/
SaveToFile/LoadFromFile` 가 갖춰져 있다. **RPC 모듈 하나만 얹으면 된다**(다른 모듈과 같은 패턴, 약 60줄).

## 3. 시나리오 파일 스키마

저장 위치: `Save/3D/Scenario/<name>.json` (신규 디렉터리). UTF-8(BOM 없음) — 기존 저장 규약과 동일.

```jsonc
{
  "isUnreal": true,
  "name": "occ1_side_carnival",
  "desc": "옆칸 대형차 측면 가림 30~60%",
  "seed": 20260813,                       // 0 = 비결정. 하위 seed 가 없으면 여기서 파생한다(§6)

  // ── 바탕 장면: 파일 참조. 이름만 적고 경로는 런타임이 해석한다 ──
  "scene": {
    "presetFile": "001_Preset_office.json",
    "carFile":    "CarPos_office_20.json",   // null 이면 차량 없이 시작
    "lightFile":  "Sangmyung.json",
    "map":        null                        // {"width":..,"height":..} 또는 null(현 상태 유지)
  },

  // ── 카메라: 절대값 또는 "무엇을 겨냥하라"는 선언 ──
  "cameras": [
    {
      "camId": 1,
      "pos": { "x": -36.3, "y": -13.6, "z": 13.5 },   // null 이면 현 위치 유지
      "aim": {                                        // aim 이 있으면 pan/tilt/zoom 을 계산해 덮는다
        "presetIdx": 1, "slot": 6,
        "widthSlots": 3                               // 화면 가로에 슬롯 몇 칸이 들어오게 할지 → zoom
      },
      "ptz": null                                     // {"pan":..,"tilt":..,"zoom":..} 직접 지정(aim 과 배타)
    }
  ],

  // ── 장면 위에 덧붙이는 배치. carNameId 를 쓰지 않는다(§6) ──
  "actors": [
    { "role": "target",
      "at": { "presetIdx": 1, "slot": 6 },
      "prefabName": "현대_캐스퍼", "rotY": 180, "isFront": true,
      "color": "magenta" },                           // 측정용 순색. null 이면 원본색
    { "role": "occluder",
      "at": { "presetIdx": 1, "slot": 5 },
      "prefabName": "기아_카니발", "rotY": 180 },
    { "role": "occluder",
      "at": { "world": { "x": -26.0, "y": 2.9 } },    // 슬롯 밖(통로) 배치
      "prefabName": "기아_봉고_탑차", "rotY": 90 }
  ],

  // ── 동적 요소(주행). 없으면 정적 시나리오 ──
  "runs": [
    { "dir": "enter", "presetIdx": 1, "slot": 1, "parkMode": "rear",
      "prefabName": "기아_봉고_탑차",                 // ← 신규 필요(§7-③)
      "seed": null, "replay": true, "replaySpeed": 0.2 }
  ],

  // ── 촬영 계획. A/B 쌍을 파일이 직접 표현한다 ──
  "shots": [
    { "tag": "N0", "camId": 1, "when": "afterPlace", "format": "png",
      "hideRoles": ["occluder"] },                    // 가리개 숨긴 기준 컷
    { "tag": "N1", "camId": 1, "when": "afterPlace", "format": "png",
      "hideRoles": [] }                               // 가린 컷
  ],

  // ── 측정 힌트. 판정은 외부에서 한다(§4 경계) ──
  "measure": {
    "type": "colorAB",                                // colorAB | slotPolygon
    "targetRole": "target",
    "expect": { "occlusionMin": 0.30, "occlusionMax": 0.60 }
  }
}
```

### 설계에서 의도적으로 정한 것

**① 대상을 `carNameId` 로 가리키지 않는다.**
차량 id 는 `{idx}-{HH.mm.ss}` 로 **시각 기반**이라 재현할 때마다 달라진다. id 로 쓰면 재현 즉시 깨진다.
그래서 `role` + `(presetIdx, slot)` 로 지정하고, 실행 시점에 생성된 실제 id 는 런타임이 역참조표로 들고 있는다.

**② 카메라를 `aim` 으로 적을 수 있게 한다.**
`pan 58.1 / tilt 21.7 / zoom 4.9` 는 office 전용 숫자다. 대신 "1번 프리셋 6번 면을 화면 폭 3칸으로 본다"고
적으면 주차장이 바뀌어도 같은 문장이 성립한다. **이것이 §1의 첫 질문(레이아웃 독립)에 대한 답이다.**
계산은 슬롯 중심(`ComputeSlotCorners`)과 카메라 위치로 정해진다:

```
pan  = atan2(slotY - camY, slotX - camX)
tilt = atan(camZ / 수평거리)                      // tilt 양수 = 하향
zoom = HFovToZoom( 2·atan( (widthSlots·xSize/2) / 수평거리 ) )
```

**③ A/B 캡처 쌍을 파일이 표현한다.**
`hideRoles` 하나로 "가리개 숨긴 컷"과 "가린 컷"이 같은 정의 안에 들어간다.
외부 스크립트는 두 PNG 의 색 픽셀 수만 세면 되고, 어떤 차를 숨겨야 하는지 알 필요가 없다.

**④ `scene` 은 파일 참조, `actors` 는 덧붙임.**
바탕(20대 배치)을 통째로 복제하지 않고 참조만 해서 시나리오 파일이 작게 유지된다.
같은 바탕 위에 시나리오 5종을 얹는 형태가 된다.

## 4. `scenario.*` 인터페이스

```
scenario.list   {}                        → [{name, desc, hasRuns, shotCount}]
scenario.get    {name}                    → 정의 그대로
scenario.load   {name, seed?}             → scene 복원 + cameras 적용 + actors 배치. runs/shots 는 실행 안 함
scenario.run    {name, seed?}             → load + runs 시작 → {runIds:[..]}
scenario.shoot  {name, tag?}              → shots 실행 → {shots:[{tag, path, width, height}]}
scenario.save   {name, fromWorld:true}    → 현재 월드 상태를 시나리오로 덤프(역방향)
```

`load` / `run` / `shoot` 를 나눈 이유: 배치만 확인하고 싶을 때, 주행을 여러 번 돌리고 싶을 때,
캡처만 다시 뜨고 싶을 때가 각각 따로 있다. `run` 은 내부적으로 `load` 를 부른다.

### 경계 — RPC 안에서 못 닫는 것

**가림률 판정은 밖에 남는다.** 캡처는 base64 PNG 로 나오지만 픽셀 계수는 외부(파이썬)에서 한다.
C++ 에 이미지 분석을 넣지 않는 한 `scenario.shoot` 이 "가림률 45%"를 반환할 수는 없다.
따라서 **`scenario.run` 이 `ok:true` 를 돌려줘도 연출이 의도대로 됐다는 뜻은 아니다** — 파일이 나왔다는 뜻이다.
`measure.expect` 는 외부 스크립트가 읽는 힌트일 뿐 런타임이 검사하지 않는다.

**주행은 비동기다.** `scenario.run` 은 즉시 반환하고 `sim.status {runId}` 로 폴링한다.
`sim.*` 이 이미 `runId` 라우팅으로 풀어 둔 방식을 그대로 따른다.

## 5. 기획서 5종 표현 검증

**이 절이 설계의 합격 여부다.** 5종을 위 스키마로 실제로 적어 봤다.

| # | 시나리오 | 표현 가능? | 걸린 것 |
|---|---|---|---|
| 1 | 옆칸 카니발 | ✅ 그대로 | — |
| 2 | 통로의 탑차 | ✅ 그대로 | `cameras[].pos.z = 3.0` + `actors[].at.world` 로 해결됨 |
| 5 | 비었는데 차 있어 보임 | ✅ 그대로 | `measure.type = "slotPolygon"` 힌트만 남기고 판정은 외부 |
| 3 | 지나가는 차 | ⚠️ **확장 필요** | 연사 캡처 + 주행 차종 지정 |
| 4 | 열 끝까지 겹겹이 | ⚠️ **확장 필요** | 슬롯별 A/B 반복(스윕) |

### ⚠️ 3번이 요구하는 확장 — 시간축 촬영

현재 `shots` 는 단발이다. 3번은 "가림률이 0 → 최대 → 0 으로 변하는 연속 프레임 묶음"이 산출물이라
**주행 중 일정 간격 연사**가 필요하다.

```jsonc
{ "tag":"seq", "camId":1, "when":"duringRun", "runIndex":0,
  "everySec":0.1, "maxCount":100, "format":"png" }
```

캡처 1프레임이 앱 틱을 약 48 ms 먹으므로 `everySec` 을 너무 줄이면 주행 자체가 느려져 궤적이 달라진다.
그래서 기획서의 권장대로 **본주행 1회 → `replaySpeed 0.2` 저속 재생 중 연사**를 기본으로 한다
(같은 궤적을 5배 느리게 재현하므로 타이밍 리스크가 사라진다).

### ⚠️ 4번이 요구하는 확장 — 스윕

4번은 "슬롯 k만 순색 도색 + 그 앞 1..k-1 숨김"을 슬롯 수만큼 반복해 가림률 곡선을 만든다.
`shots` 를 12벌 손으로 적는 건 스키마의 실패다.

```jsonc
{ "tag":"sweep", "camId":1, "when":"afterPlace", "format":"png",
  "sweep": { "over":"slots", "presetIdx":1, "from":1, "to":12,
             "colorRole":"$k", "hideSlotsBefore":"$k" } }
```

### 검증 결론

**5종 중 3종은 설계 그대로, 2종은 `shots` 에 시간축(`duringRun`)과 반복(`sweep`)을 더하면 표현된다.**
둘 다 `shots` 안에서 끝나고 스키마의 다른 부분(`scene`/`cameras`/`actors`/`runs`)은 손대지 않는다 —
설계의 축이 맞게 잡혔다는 신호로 본다.

## 6. 재현성 규약

**seed 전파.** `scenario.seed` 가 있고 하위(`runs[].seed`, 랜덤 배치)가 `null` 이면
`파생seed = scenario.seed + 항목인덱스` 로 정한다. 하위에 값이 있으면 그것이 이긴다.
`scenario.run {seed}` 인자는 파일의 `seed` 를 덮는다 — **"같은 시나리오, 다른 표본"이 이 한 인자로 된다.**

| 쓰임 | 방법 |
|---|---|
| 똑같이 재현 | `scenario.run {name}` (파일 seed 사용) |
| 같은 규칙 다른 표본 | `scenario.run {name, seed:N}` 을 N 을 바꿔가며 |
| 완전 비결정 | `seed: 0` |

**재현이 깨지는 알려진 지점:**

- 차량 id 가 시각 기반 → §3-① 로 회피(role/slot 지정).
- `cam.savePreset` 은 **카메라 프리셋 파일 전체를 덮어쓴다**. 시나리오가 카메라를 저장할 때
  기존 5개를 잃지 않도록 `scenario.save` 는 카메라를 시나리오 파일 안에 적고 CamPos 파일은 건드리지 않는다.
- 프리셋 메이커 위젯 목록과 매니저 `StoredPresets` 이원화가 남아 있다. 시나리오는 **RPC 경로만** 쓴다
  (`preset.load`). UI 로 만든 프리셋은 시나리오에 안 잡힌다.
- 조명이 정의에 없으면 노출이 바뀐 채로 재현돼 가림률이 어긋난다 → `light.*` 이 선행 과제인 이유.

## 7. 필요한 신규 코드

| # | 항목 | 대상 | 규모 | 비고 |
|---|---|---|---|---|
| ① | `light.get/set/apply/save/load` | 신규 `LightRpcModule` | 小 (~60줄) | `ALightControlManager::ApplySettings/CaptureCurrent` 가 이미 있다 |
| ② | `cam.aimSlot {camId, presetIdx, slot, widthSlots}` | `CamRpcModule` | 小 (~40줄) | §3-② 계산. **레이아웃 독립성의 핵심** |
| ③ | `sim.start` 에 `prefabId`/`prefabName` | `SimRpcModule`, `ParkingSimManager` | 小 (~15줄) | 현재 입차 차종이 랜덤(`ParkingSimManager.cpp:667`) |
| ④ | `scenario.list/get/load/run/shoot/save` | 신규 `ScenarioRpcModule` | 中 (~300줄) | 기존 RPC 를 순서대로 부르는 오케스트레이션 |
| ⑤ | `shots` 의 `duringRun` 연사 | `ScenarioRpcModule` | 中 | 타이머 + 리플레이 연동 |
| ⑥ | `shots` 의 `sweep` | `ScenarioRpcModule` | 中 | 슬롯 순회 |
| ⑦ | (선택) 면 단위 fill 데칼 | `ParkingPresetManager`, `PresetRpcModule` | 中 | 시나리오 5 측정 정밀화. 없어도 기하 투영으로 대체 |

②는 작지만 효과가 크다. 이것이 있으면 시나리오 파일에서 **모든 카메라 하드코딩 각도가 사라지고**
다른 주차장에 그대로 올려도 카메라가 알아서 맞는다.

## 8. 단계 제안

각 단계가 끝날 때마다 검증 가능한 산출물이 남도록 끊었다.

1. **`light.*` + `cam.aimSlot`** (①②) → 검증: `cam.aimSlot` 으로 시나리오 1의 구도가 손계산 없이 잡히는가.
2. **`scenario.load/save` + 정적 시나리오 3종**(1·2·5) → 검증: 저장 → 재기동 → `scenario.load` 로 같은 화면이 나오는가.
3. **`scenario.run/shoot` + A/B 캡처** → 검증: 외부 스크립트로 가림률이 목표 구간(30~60%)에 드는가.
4. **`sweep`**(⑥) → 시나리오 4. 검증: 슬롯별 가림률이 단조 증가하는가.
5. **`duringRun` 연사 + 주행 차종 지정**(③⑤) → 시나리오 3. 검증: 가림률 곡선에 봉우리가 있는가.

1~3 단계까지만 해도 정적 시나리오 3종이 **저장·재현·랜덤 변주·원격 실행** 전부 된다.

## 9. 미확인 · 가정

1. **`cam.aimSlot` 의 zoom 식이 실제 캡처와 맞는지 미검증.** `captureJPG` 가 `width/height` 를 반환하는 것은
   확인했으나 실제 값과 수직 화각 매핑은 미확인이고, 메인 뷰에 16:9 하드코딩 이력이 있어 검증 전엔 신뢰할 수 없다.
   1단계에서 캡처로 실측해야 한다.
2. **차량 메시 실치수가 여전히 없다.** `measure.expect` 의 목표 가림률이 맞는지는 실측 후에야 안다.
3. **`scenario.save {fromWorld:true}` 로 role 을 복원할 수 없다.** 월드에는 "이 차가 가리개였다"는 정보가 없다.
   역방향 덤프는 `actors` 를 전부 `role:"extra"` 로 뱉고 사람이 손보는 형태가 된다 — 한계로 남긴다.
4. **동시 주행 중 캡처의 타임스탬프 정합은 근사다.** 기록 json 은 0.05 s 프레임이고 캡처는 RPC 왕복에 좌우된다.
5. 조명 적용이 카메라 캡처(SceneCapture)에 즉시 반영되는지 프레임 단위로 확인하지 않았다.
   `scenario.load` 후 첫 캡처에 이전 조명이 남을 가능성이 있다 — 1단계에서 확인 대상.
6. 시나리오 파일에 `presetIdx` 를 쓰는데, **주차면 프리셋 idx** 다. 차량 데이터의 `presetId`(이제 카메라 프리셋
   번호)와 다른 공간이므로 구현 시 혼동하지 말 것 —
   [20260813_200601](20260813_200601_car.assignPreset_카메라프리셋기준_presetId_재배정.md) 참조.
