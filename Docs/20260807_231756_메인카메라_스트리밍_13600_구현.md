## 1. 배경 — 기존 인프라와 비어 있던 자리

Park3D에는 이미 카메라별 MJPEG 스트리밍이 구축되어 있었다.

| 구성 요소 | 역할 |
|---|---|
| `UCamStreamSubsystem` | 카메라 채널 관리자(게임 스레드). 채널 증감·슬롯 스케줄링·페이싱·캡처 |
| `FMjpegStreamServer` | 채널 1개 = 전용 TCP 리스너 + 송신 워커 1개 |
| `Park3DCamStream` (CamStreamPolicy) | 포트 부여·채널 diff·슬롯 선택의 순수 로직(유닛 테스트 대상) |

포트 대역은 `Save/Config/config_pmaker.json`의 `cam_port_min=13601` / `cam_port_max=13650`에서 온다.
내부 표현으로 환산하면 `BasePort = cam_port_min - 1 = 13600`, `camId 1 → 13601`, `camId 2 → 13602` … 이다.

즉 **13600은 카메라 대역 바로 앞자리로 비어 있었다.** 요청하신 포트가 메인 뷰 자리에 정확히 들어맞는다.

한편 "메인 카메라"는 `Park3DGameMode::DefaultPawnClass = AParkFlyPawn`(에디터 플라이캠 방식의 `ADefaultPawn`)이
만드는 **플레이어 시점**이다. PTZ 카메라(`APTZCameraActor`)와 결정적으로 다른 점이 하나 있다.

> PTZ 카메라는 `USceneCaptureComponent2D` + 전용 `UTextureRenderTarget2D`를 이미 들고 있어서
> 그 렌더타깃을 읽기만 하면 되지만, **메인 뷰에는 렌더타깃이 없다.** 화면에 직접 그려질 뿐이다.

따라서 "픽셀을 어디서 얻을 것인가"를 먼저 정해야 했다.

## 2. 설계 판단 — 두 가지 해석과 선택 근거

| | **A. SceneCapture 미러링 (채택)** | B. 뷰포트 백버퍼 리드백 |
|---|---|---|
| 결과물 | 3D 씬만 (UMG UI **미포함**) | 화면 그대로 (UI **포함**) |
| 해상도 | 1280×720 고정 | 창 크기에 따라 변동 |
| 렌더 비용 | 씬을 한 번 더 그림 (PTZ 1대분) | 추가 렌더 없음, GPU 리드백만 |
| 구현 복잡도 | 기존 PTZ 파이프라인과 동일 규약 | 렌더스레드 훅 필요 |

**A를 택한 근거 세 가지:**

1. 요청이 "메인 **화면**"이 아니라 "메인 **카메라**"였다. 카메라 시점 = UI를 걷어낸 3D 씬이 더 충실한 해석이다.
2. 해상도가 창 크기에 묶이지 않는다. B는 사용자가 창을 리사이즈하면 **스트림 도중 해상도가 바뀌어**
   클라이언트가 깨질 수 있다.
3. PTZ 채널과 완전히 동일하게 취급된다 — 클라이언트는 `:13600`을 다른 카메라 포트와 똑같이 붙으면 된다.
   JPEG 인코딩·multipart 바운더리·색 규약이 전부 같은 코드 경로를 탄다.

**A의 대가(명시적으로 감수한 것):** 메인 뷰를 보는 동안 씬이 한 번 더 렌더된다.
다만 아래 §3.3의 클라이언트 게이트 덕분에 **보는 사람이 없으면 비용이 정확히 0**이다.

UI가 포함된 화면이 필요해지면 B로 교체 가능하다. 교체 지점은 `ProduceMainJpeg()` 한 함수뿐이다.

## 3. 구현 상세

### 3.1 슬롯 스케줄러 밖에 두었다

기존 카메라 채널은 `ActiveSlots`(기본 1)로 "지금 프레임을 만드는 카메라 수"를 제한하고, 여러 카메라가
슬롯을 돌아가며 점유한다. 병목이 포트가 아니라 게임 스레드 캡처 비용(1프레임 ≈ 48ms @1280×720)이기 때문이다.

메인 뷰는 이 스케줄러에 **넣지 않았다.**

- 채널이 하나뿐이라 순환시킬 대상이 없다. 슬롯에 넣으면 카메라들과 자리를 다투며 메인 뷰가 끊긴다.
- `Channels` 배열은 `인덱스 = camId - 1`이라는 1-based 규약에 묶여 있다. 여기에 메인 뷰를 끼워 넣으면
  뒤 카메라들의 포트가 통째로 밀린다. 별도 멤버 `MainChannel`로 분리해 이 규약을 건드리지 않았다.
- 대신 `MainChannel.CamId = 0`으로 두어 "카메라가 아니다"라는 표식을 남겼다.

### 3.2 미러링 캡처는 지연 생성한다

`EnsureMainCapture()`가 첫 프레임이 필요한 순간에만 액터와 렌더타깃을 만든다.

```cpp
FActorSpawnParameters SpawnParams;
SpawnParams.ObjectFlags |= RF_Transient;                       // 레벨 저장 대상에서 제외
SpawnParams.SpawnCollisionHandlingOverride = ESpawnActorCollisionHandlingMethod::AlwaysSpawn;

AActor* Actor = World->SpawnActor<AActor>(AActor::StaticClass(), FTransform::Identity, SpawnParams);
Actor->SetActorHiddenInGame(true);
Actor->SetActorEnableCollision(false);   // 바닥/폴대 트레이스 오탐 방지
Actor->SetActorTickEnabled(false);
```

`UCamStreamSubsystem`은 원래 "스폰하지 않는다(스트리밍이 월드 상태를 만들면 안 된다)"는 규율을 지켜 왔고,
`FindCameraManager()`도 매니저를 찾기만 한다. 이번이 **유일한 예외**이므로 그 근거와 안전장치
(RF_Transient · 숨김 · 콜리전 off · 틱 off)를 코드 주석에 남겨 두었다.

### 3.3 캡처 설정은 PTZ 카메라와 한 글자도 다르지 않게 맞췄다

```cpp
Capture->bCaptureEveryFrame = false;
Capture->bCaptureOnMovement = false;
Capture->CaptureSource = ESceneCaptureSource::SCS_FinalColorLDR;
Capture->bAlwaysPersistRenderingState = true;   // ★
```

★ 표시한 `bAlwaysPersistRenderingState`가 특히 중요하다. 이 값이 빠지면 `bCaptureEveryFrame = false`인
캡처마다 엔진(`USceneCaptureComponent::GetViewState`)이 뷰 스테이트를 파괴해 **Lumen GI·리플렉션·TSR
히스토리가 사라진다.** 과거 `/stream`만 간접광이 빠져 어둡고 갈색으로 보이던 버그
(`Park3D/Docs/Bug/20260806_163723_Park3D_스트림영상_간접광누락_진단.md`)의 원인이 정확히 이것이었다.
같은 함정을 새 코드에서 반복하지 않도록 주석으로 못 박았다.

### 3.4 시점 미러링

```cpp
FVector ViewLocation; FRotator ViewRotation;
PC->GetPlayerViewPoint(ViewLocation, ViewRotation);
MainCaptureActor->SetActorLocationAndRotation(ViewLocation, ViewRotation);

if (PC->PlayerCameraManager)
{
    MainCapture->FOVAngle = PC->PlayerCameraManager->GetFOVAngle();
}
MainCapture->CaptureScene();
```

- `GetPlayerViewPoint()`는 **최종** 시점을 준다. 뷰 타깃이 플라이 폰이든 시네마틱이든 화면과 같은 시점이 나온다.
- `PlayerCameraManager`의 FOV도 `SceneCapture`의 `FOVAngle`도 **수평** 화각이라 변환 없이 그대로 대입한다
  (설계 §7.3의 PTZ 줌↔화각 규약과 동일한 근거).
- 렌더타깃 화면비(16:9)가 창과 다르면 **수평 화각은 일치하고 상하로 더/덜 보인다.** 좌우가 잘리지 않는 쪽을 택했다.

### 3.5 페이싱과 유휴 비용 0

```cpp
if (!MainChannel.Server->HasClients()) { return; }   // ← 유휴 비용 0의 근거
```

클라이언트가 0명이면 캡처도, 액터 생성도 하지 않는다. 포트는 열려 있으므로 재접속은 언제든 된다.

페이싱은 카메라 채널과 같은 규약을 썼다.

```cpp
MainChannel.Accum = FMath::Min(MainChannel.Accum - Interval, Interval);
```

잔여 시간을 보존해야 실효 fps가 목표에 수렴한다(0으로 리셋하면 틱 경계로 양자화되어 항상 미달).
동시에 한 프레임치로 클램프해서, 게임 fps가 목표보다 낮은 구간에서 부채가 무한 누적되지 않게 한다.

### 3.6 기동 실패 래치

포트가 점유되어 `StartServer`가 실패하면 `bMainStartFailed = true`로 래치한다.
이 실패는 틱마다 재시도해도 풀리지 않으므로, 래치가 없으면 초당 수십 줄의 에러 로그가 쏟아진다.

## 4. 설정 (`Park3D/Config/DefaultGame.ini`)

```ini
[/Script/Park3D.CamStreamSubsystem]
...
bMainViewEnabled=True
MainPort=13600
MainFps=5.0
MainWidth=1280
MainHeight=720
```

| 키 | 기본값 | 설명 |
|---|---|---|
| `bMainViewEnabled` | True | 메인 뷰 채널 on/off. `bEnabled=False` 또는 `-NoCamStream`이면 이 값과 무관하게 꺼진다 |
| `MainPort` | 13600 | 메인 뷰 전용 포트 |
| `MainFps` | 5.0 | 카메라 슬롯 예산(`TotalFps`)과 **별도로** 계산된다 |
| `MainWidth` / `MainHeight` | 1280 / 720 → **현재 960 / 540** | 창 크기와 무관하게 고정. 후속 성능 가드 작업에서 기본값이 낮아졌다 |

**`MainPort`는 카메라 대역과 달리 `config_pmaker.json`이 덮지 않는다.** 카메라 대수가 늘어 `cam_port_max`가
자동 확장되더라도 메인 뷰 자리가 밀리지 않아야 하기 때문이다. 카메라 대역은 `cam_port_min`부터 위로 자라고,
메인 뷰는 그 바로 앞자리 한 칸을 고정으로 쓴다.

## 5. 상태 조회 — `cam.streamStatus`

`BuildStatusJson()` 응답에 `main` 객체를 추가했다. 메인 뷰는 슬롯 스케줄러 밖이므로
`channels` 배열이 아니라 별도 필드로 낸다(배열에 섞으면 `camId 0`이 슬롯 통계를 오염시킨다).

```json
{
  "channels": [ { "camId": 1, "port": 13601, "...": "..." } ],
  "slots": 1,
  "basePort": 13600,
  "maxCameras": 50,
  "main": {
    "enabled": true,
    "port": 13600,
    "serving": true,
    "clients": 0,
    "fps": 0.0,
    "targetFps": 5.0,
    "width": 1280,
    "height": 720
  }
}
```

`serving`은 소켓이 실제로 바인드되었는지, `clients`는 지금 보고 있는 수, `fps`는 1초 창 실측값이다.
`serving: false`인데 `enabled: true`면 포트 점유(§3.6 래치)를 의심하면 된다.

C++ 쪽에는 `GetMainStreamPort(int32& OutPort)`도 함께 열어 두었다(기존 `GetCameraStreamPort`와 대칭).

### 7.2 바이너리 반영 실증

빌드 로그의 "Succeeded"만으로는 실제 반영을 단정할 수 없어, 산출물에서 신규 리터럴을 직접 확인했다.
`TEXT()` 리터럴은 UTF-16이라 ASCII grep에 걸리지 않으므로 Unicode로 디코딩해서 검색했다.

```powershell
$bytes = [IO.File]::ReadAllBytes('...\Park3D\Binaries\Win64\Park3D.exe')
[Text.Encoding]::Unicode.GetString($bytes) -match 'MainViewCapture'   # → FOUND
```

### 7.3 미검증 — 실제 접속 확인은 하지 않았다

**사용자 제약에 따라 재기동과 실제 스트림 수신 확인은 수행하지 않았다.**
실행 중인 `Park3D.exe`(PID 19212)가 13510 포트를 서빙 중이고 다른 시스템이 거기에 의존하기 때문이다.

작업 전후로 프로세스 생존을 확인했다 — PID 19212, 2144 모두 최초 기동 시각(15:38:06)을 유지한 채 살아 있다.
빌드는 `Park3D/Binaries/Win64`에 쓰고 실행 중인 인스턴스는 `Package/Windows/`의 스테이지 복사본을
쓰므로 경로가 겹치지 않아 간섭이 없었다.

따라서 **다음 항목은 아직 확인되지 않았다.**

- `:13600` 소켓이 실제로 바인드되는지
- 프레임이 실제로 수신되는지, 시점·화각이 화면과 일치하는지
- 실측 fps와 게임 스레드 부하 영향

## 8. 재기동 및 확인 방법 (사용자용)

### 8.1 현재 실행 중인 인스턴스

| PID | 경로 | 비고 |
|---|---|---|
| 19212 | `Package\Windows\Park3D\Binaries\Win64\Park3D.exe` | 13510 서빙 중 — 보존 대상 |
| 2144 | `Package\Windows\Park3D.exe` | 런처 격 프로세스(같은 시각 기동) |

> ⚠ 인스턴스가 2개 살아 있다. 둘 다 "13510 서버 시작" 로그를 남길 수 있으므로,
> 검증 시 어느 PID가 응답하는지 먼저 확인하는 편이 안전하다.

### 8.2 이번 빌드 산출물을 패키지에 반영하려면

빌드는 `Park3D/Binaries/Win64/Park3D.exe`에만 반영되었다. 실행 중인 인스턴스가 쓰는
`Package/Windows/` 아래 스테이지 복사본은 **아직 낡은 상태**다. 둘 중 하나를 해야 한다.

**(a) 재패키징** — 정공법

```powershell
& 'C:\Program Files\Epic Games\UE_5.8\Engine\Build\BatchFiles\RunUAT.bat' BuildCookRun `
  -project="D:\Work\UnrealWork\Parking\Park3D\Park3D.uproject" `
  -noP4 -platform=Win64 -clientconfig=Development -cook -build -stage -pak -archive `
  -archivedirectory="D:\Work\UnrealWork\Parking\Package"
```

> `RunUAT`는 exit 0이어도 실패하는 경우가 있으니 로그로 성공을 판정할 것.

**(b) exe만 교체** — 빠른 확인용. C++만 바뀌었고 콘텐츠 변경이 없으므로 이번 건에는 유효하다.

```powershell
Copy-Item 'D:\Work\UnrealWork\Parking\Park3D\Binaries\Win64\Park3D.exe' `
          'D:\Work\UnrealWork\Parking\Package\Windows\Park3D\Binaries\Win64\Park3D.exe' -Force
```

단 `DefaultGame.ini`도 바뀌었으므로 **스테이지 쪽 `Config/DefaultGame.ini`도 함께 갱신**해야
`MainPort` 등이 먹는다. 그러지 않으면 C++ 기본값(13600, 5fps, 1280×720)으로 동작한다 —
기본값이 원하는 값과 같으므로 실제로는 동작하지만, 나중에 값을 바꿀 때 혼란이 생긴다.

### 8.3 에디터에서 확인 (PID 19212를 건드리지 않는 경로)

에디터 PIE는 별도 프로세스이므로 실행 중인 패키지 인스턴스와 무관하게 확인할 수 있다.
다만 **RPC 포트 13510이 겹치므로** `-RpcPort=`로 다른 포트를 주는 편이 안전하다.

### 8.4 동작 확인

```powershell
# 포트 리슨 확인
Get-NetTCPConnection -LocalPort 13600 -State Listen -ErrorAction SilentlyContinue

# 브라우저로 접속 (MJPEG는 브라우저가 바로 렌더한다)
Start-Process 'http://localhost:13600/'

# 상태 조회 (RPC)
#   cam.streamStatus → 응답의 main.serving / main.clients / main.fps 확인
```

기동 시 로그에 다음 줄이 뜨면 정상이다.

```
[CamStream] 메인 뷰 채널 기동: http://<IP>:13600/
```

> 리슨 중인데 접속이 안 되면 앱이 아니라 **방화벽**을 먼저 의심할 것. 규칙이 없으면 패킷이 커널에서
> 버려져 앱 로그에 아무것도 남지 않는다(로컬 접속은 영향 없음).

## 9. 남은 과제 / 알려진 한계

1. **UMG UI가 스트림에 포함되지 않는다.** §2의 설계 선택에 따른 의도된 동작이다.
   화면 그대로가 필요하면 `ProduceMainJpeg()`를 뷰포트 백버퍼 리드백으로 교체하면 된다.
2. **캡처 1대분 비용이 추가된다.** 메인 뷰를 보는 동안에만이며, 슬롯 예산(`TotalFps`) 밖에서 계산된다.
   부하가 문제되면 `MainFps`를 낮추는 것이 첫 번째 손잡이다.
3. **화면비 불일치 시 상하 여백 차이.** 창이 16:9가 아니면 수평 화각은 같고 상하로 더/덜 보인다.
4. **동기 캡처(P1)다.** 카메라 채널과 마찬가지로 P2에서 비동기 GPU 리드백으로 교체할 여지가 있다.
5. **실제 접속 검증 미실시** — §7.3 참조.
