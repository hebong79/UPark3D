## 1. 문제

참조 파일 `001_Preset_Seo_1.json` 은 **Unity 스키마**인데, 기존 C++ 저장 포맷(`FParkingPreset` PascalCase → FJsonObjectConverter camelCase)과 **키가 대부분 불일치**하여 그대로는 로드 시 대다수 필드가 기본값으로 들어갔다.

| Unity 파일 키 | 기존 C++ 저장 키 | 일치 |
|---|---|---|
| `idx` | `presetIdx` | ✗ |
| `offsetPos{x,y,z}` | `offset{x,y,z}` | ✗ |
| `faceRot` / `groupRot` | `faceRotate` / `groupFaceRotate` | ✗ |
| `xSize` / `zSize` | `boxSizeX` / `boxSizeZ` | ✗ |
| `useBaseWidth` | `bIsBaseWidth` | ✗ |
| `camIdx` | `cameraIdx` | ✗ |
| `presetName`,`faceCount`,`dirType` | 동일 | ✓ |

## 2. 설계 (결정 반영)

- **방식:** Unity 키 전용 **DTO 구조체** 도입 + 도메인 `FParkingPreset` ↔ DTO 매핑. 도메인 필드명은 그대로 두어 다른 코드(매니저·위젯·기하계산) 영향 0(외과적).
- **기본 경로:** `ProjectDir/Save/3D/Preset/preset.json` — `ProjectSavedDir()`(Saved) 대신 **`ProjectDir()/Save`** 사용(사용자 결정, 실제 데이터 위치).
- **bUse3D:** Unity 파일에 없는 필드 → DTO에 `use3D` 확장 키로 **보존**(Unity 파일은 키 없으면 기본 false 로드).

## 4-B. 좌표 축 변환 보정 (16:40 추가)

### 증상
`001_Preset_Seo_1.json` 로드 시 값은 정상이나, 3D 출력이 유니티와 달리 **프리셋들이 공중에 수직으로 쌓인 사다리꼴**로 표시됨(유니티는 지면에 넓게 분산).

### 원인
도메인 `FParkingPreset::Offset` 은 **UE 월드 좌표**로 설계됨 — 마우스 피킹(`P.Offset.X/Y = Hit.X/Y`), 키보드 이동(WASD→`Offset.X/Y`), 매니저(`Origin = Offset*U`)가 모두 `Offset.X/Y` 를 월드 지면으로 사용. 그러나 최초 JSON 변환이 Unity `offsetPos(x,y,z)` 를 **축 변환 없이** `Offset(x,y,z)` 로 대입 → Unity z(지면 전방)가 UE Z(높이)로 들어가 프리셋이 높이 방향으로 쌓임.

### 수정 (JSON 경계 변환, 설계 §7.1/§12-K = `UnityPosToUE` 규약)
| 방향 | 매핑 |
|------|------|
| 로드 `FromDTO` | `Offset = (offsetPos.x, offsetPos.z, offsetPos.y)` — Unity z→UE Y(전방), Unity y→UE Z(높이) |
| 저장 `ToDTO` | `offsetPos = (Offset.X, Offset.Z, Offset.Y)` — 역변환(라운드트립 보존) |

- 매니저·UI·마우스·키보드는 **변경 없음**(모두 UE 월드 Offset 기준으로 이미 일관). 변환은 JSON 경계 한 곳에만.
- **UI 표기 주의:** Offset 필드는 UE 월드값을 표시(지면 = X,Y / 높이 = Z). 예) Preset 3 은 UE (-3.549, 3.586, 0). 저장하면 파일엔 Unity (-3.549, 0, 3.586) 로 기록되어 참조 파일과 동일.
- 유닛테스트 축 단언 갱신(`offsetPos.z→Offset.Y`, `offsetPos.y→Offset.Z`) + Offset.Y/Z 라운드트립 추가.
