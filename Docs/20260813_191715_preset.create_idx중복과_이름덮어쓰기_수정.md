# `preset.create` 의 idx 중복 · 이름 덮어쓰기 수정

- 날짜: 2026-08-13
- 대상: `Park3D/Source/Park3D/Rpc/Modules/PresetRpcModule.cpp`

## 발단

주차면 가림 연출 시나리오를 기획하며 런타임 상태를 조사하던 중,
실행 중인 인스턴스의 `preset.list` 가 프리셋 6건을 **전부 `idx:1`** 로,
이름을 `[Preset 6, Preset 1, Preset 1, Preset 1, Preset 1, Preset 1]` 로 돌려주는 것을 발견했다.

파일(`Save/3D/Preset/001_Preset_office.json`)은 정상이다 — 저장소 사본과 패키지 사본
둘 다 읽어 대조했고 내용·크기·mtime 이 동일하며, idx 는 `1,2,3,4,5,7`(6번 결번),
이름은 `Preset 1`~`Preset 6` 이다. 즉 **파일이 아니라 런타임 목록이 깨져 있었다.**

`presetId` 를 받는 모든 호출(`preset.get/update/move/rotate/…`, `sim.start`)은
`AParkingPresetManager::FindPresetByIdx` 로 대상을 찾는데, 이 함수는 **첫 일치**를 돌려준다.
따라서 `presetId:1` 은 언제나 목록의 0번(= UE `(-19.371, 1.059)`, 12면)만 가리키고
**나머지 5개는 지정할 방법이 없었다.**

## 원인 — 버그 두 개가 겹쳤다

### ① 자동 번호 부여가 돌지 않는다

`FParkingPreset::PresetIdx` 의 기본값이 **1** 이다(`ParkingPresetTypes.h:28`, "1부터, 0=미설정").
`preset.create` 는 `PresetIdx` 를 채우지 않으므로 값이 1인 채로 `AddPreset` 에 들어간다.

```cpp
int32 AParkingPresetManager::AddPreset(const FParkingPreset& InPreset)
{
    FParkingPreset P = InPreset;
    if (P.PresetIdx <= 0)          // ← 1 이므로 통과하지 못한다
    {
        P.PresetIdx = NextPresetIdx();
    }
    StoredPresets.Add(P);
    return P.PresetIdx;
}
```

`<= 0` 조건에 걸리지 않아 `NextPresetIdx()` 가 호출되지 않고, **만드는 족족 idx=1** 이 된다.

### ② 생성 직후 되찾기가 남의 것을 집는다

```cpp
const int32 NewIdx = Mgr->AddPreset(Pr);
FParkingPreset* Added = Mgr->FindPresetByIdx(NewIdx);   // ← 첫 일치 = 0번
Added->PresetName = ...;
```

①로 idx 가 전부 1이 된 상태에서 `FindPresetByIdx(1)` 은 **0번**을 돌려준다.
그래서 `preset.create` 를 부를 때마다 **0번 항목의 이름만 계속 덮어썼다.**

관측된 이름 배열이 이것으로 정확히 설명된다 — 6번째 생성의 이름 `Preset 6` 이 0번에 박히고,
1~5번은 손대지 않아 구조체 기본값 `Preset 1`(`ParkingPresetTypes.h:31`)로 남았다.

### 따라서 현재 런타임 목록은 파일에서 온 것이 아니다

`StoredPresets` 를 채우는 경로는 `preset.load`(파일 idx 그대로 복사)와 `preset.create` 둘뿐이다.
게임모드도 프리셋 메이커 위젯도 이 배열을 건드리지 않는다(위젯은 자기 `Presets` 배열을 쓰고
그리기용으로 `RebuildAll` 만 호출한다 — 알려진 "프리셋 목록 이원화").
`preset.load` 였다면 idx 가 `1,2,3,4,5,7` 로 나왔어야 하므로,
**그 목록은 `preset.create` 6회로 만들어진 것**이다.

## 수정

`preset.create` 두 곳만 고쳤다. 매니저(`AddPreset`/`FindPresetByIdx`)는 건드리지 않았다 —
"첫 일치를 돌려준다"는 동작 자체는 idx 가 유일하다는 전제 아래 정상이고,
전제를 깬 쪽이 `preset.create` 이기 때문이다.

```cpp
FParkingPreset Pr;
// 구조체 기본값이 PresetIdx=1 이라 그대로 두면 AddPreset 의 자동 번호(PresetIdx<=0 조건)가
// 돌지 않아 만드는 족족 idx=1 이 된다 — 0 으로 낮춰 번호 부여를 매니저에 위임한다.
Pr.PresetIdx = 0;
```

```cpp
const int32 NewIdx = Mgr->AddPreset(Pr);
// 방금 추가한 것은 배열의 끝이다. FindPresetByIdx 는 첫 일치를 돌려주므로
// idx 가 겹친 목록에서는 남(0번)의 이름을 덮어쓴다.
FParkingPreset* Added = Mgr->StoredPresets.Num() > 0 ? &Mgr->StoredPresets.Last() : nullptr;
```

②는 ①만 고쳐도 증상이 사라지지만(idx 가 유일해지면 `FindPresetByIdx` 가 옳은 것을 집는다),
잠재 결함이라 함께 막았다.

## 런타임 정리 절차

이미 깨진 목록은 파일을 다시 읽어 되돌린다.

```
preset.load { "fullPath": "<스테이지루트>/Save/3D/Preset/001_Preset_office.json" }
```

**패키지에서는 `fileName` 만 주면 실패한다.** `ResolvePresetPath` 의 기본 디렉터리가
`FPaths::ProjectDir()/Save/3D/Preset` 인데 패키지의 `Save/` 는 ProjectDir 밖(스테이지 루트)에 있다.
실제 실패 메시지: `프리셋 로드 실패: ../../../Park3D/Save/3D/Preset/001_Preset_office.json`.
→ `fullPath` 로 절대경로를 넘길 것.

## 검증 (전부 실행 확인)

수정본 빌드 → `Result: Succeeded` → 패키지 exe 교체(해시 일치 확인) → 재기동.

1. `preset.load` 후 `preset.list` — idx `1,2,3,4,5,7`, 이름 `Preset 1`~`Preset 6`. **파일과 일치.**
2. `preset.create {offset:(40,40), faceCount:3, presetName:"IDX_FIX_TEST"}`
   → 응답 `idx:8`(= max(7)+1 자동 부여, 수정 전이라면 1이었다).
3. 직후 `preset.list` — 새 항목만 `IDX_FIX_TEST`, **0번은 `Preset 1` 그대로**(수정 전이라면 0번 이름이 덮였다).
4. `preset.delete {idx:8}` 로 테스트 프리셋 제거 — 목록 6건 복귀.

## 남은 것 · 미확인

- **idx 6 결번**은 파일 자체가 그렇다(`Preset 6` 의 idx 가 7). 버그가 아니라 데이터 상태이며 손대지 않았다.
- 프리셋 메이커 **위젯의 목록과 매니저의 `StoredPresets` 가 여전히 별개**다. 이번 수정은 RPC 경로만 정상화했다.
- 위 깨진 목록을 **누가 언제 `preset.create` 로 만들었는지는 확인하지 못했다.** 이번 세션 이전의 상태다.
- `car.list` 상 모든 차량의 `presetId` 가 1로 보인다. 이번 수정 범위 밖이고 원인 미확인.
