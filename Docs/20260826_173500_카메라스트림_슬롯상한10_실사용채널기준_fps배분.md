## 2. 왜 Ask 2 가 Ask 1 의 전제인가

기존 `channelFps = TotalFps / ActiveSlots` 였다. 즉 **아무도 안 보는 슬롯이 보는 사람의 fps 를 깎았다.**
`hardMaxSlots` 만 10 으로 올리고 운영자가 `slots=10` 을 넣으면 혼자 보는 사람이 `5/10 = 0.5fps` 를
받는다 — 요청자가 "raising the cap makes the single-viewer case slower even when nobody else is
connected" 이라고 지적한 그대로다. 그래서 두 항목은 **같이 가야만 의미가 있다.**

바꾼 뒤: `channelFps = TotalFps / (지금 슬롯을 쥐고 있고 시청자도 있는 채널 수)`.

- 시청자 1명 → 5fps 전부
- 시청자 2명 → 2.5fps 씩
- 총 캡처량은 시청자 수와 무관하게 항상 `TotalFps` 로 묶인다 → **슬롯을 열어 두는 것 자체가 공짜다.**

`ActiveChannels = 0`(아무도 안 봄)이면 1 로 취급한다. 조회 응답에서 그 값이 "다음 시청자 1명이
받게 될 값"이라 그게 맞다.

- `cam.streamStatus` 에 **`activeChannels`(신규 필드)**. `channelFps` 의 나눗수다.

## 4. Ask 3 을 하지 않은 이유 — 전제가 재현되지 않았다

요청 근거는 "슬롯을 못 받은 채널은 `clients=1 holdsSlot=false fps=0.00` 으로 붙어만 있고
첫 프레임이 영영 안 와서 `<img>` 의 `onload`/`onerror` 가 둘 다 안 뜬다" 였다.

**변경 전 빌드**(로컬 sim1, RPC 13510)에서 `slots=1` + 시청자 2명으로 직접 재현을 시도했다:

```
t+0s   cam1 clients=1 holdsSlot=true  fps=4.94    cam2 clients=1 holdsSlot=false fps=0
t+~6s  cam1 clients=1 holdsSlot=false fps=0       cam2 clients=1 holdsSlot=true  fps=0
```

**슬롯은 실제로 순환했고, 두 클라이언트 모두 프레임을 받았다** — 25초 수신 바이트
`cam1 13,041,664 B` / `cam2 6,815,744 B`, 멀티파트 바운더리 `park3dframe` 각각 71/50 개.
즉 `holdsSlot=false fps=0` 은 **영구 상태가 아니라 순환의 한 순간**이다
(`SelectSlots` 의 기아 방지 점수가 초당 +1 로 자라 `MinHoldSeconds`(2초) 뒤에 뒤집는다).

첫 프레임까지의 대기 시간은 대략 `(시청자 수 / 슬롯 수) × MinHoldSeconds` 다. 요청자 환경
(슬롯 2, 채널 3)에서는 몇 초, 슬롯 2에 시청자 10명이면 10초쯤 — 브라우저에서는 "연결 중…"
으로 보이므로 **증상 신고 자체는 사실이고, 원인이 '거절되지 않은 연결'이 아니라 '슬롯 대기'** 였다.
그 대기는 Ask 1+2 로 사라진다(슬롯 ≥ 시청자면 순환 자체가 일어나지 않는다).

동작하는 순환을 끊고 연결을 거절하는 쪽은, 재현되지 않은 증상을 근거로 검증된 MJPEG 서버
(`MjpegStreamServer.*` — 헤더에 "원본 그대로, 임의 개조 금지"가 붙어 있다)를 고치는 일이라
하지 않았다. 요청자에게 이 실측을 그대로 회신했다.

## 5. 구현 중 드러난 것 두 가지 (둘 다 실측이 알려줬다)

### 5-1. 커서를 루프 안에서 갱신하면 채널이 통째로 빠진다

틱당 캡처 상한을 넣으며 "다음 틱은 다음 채널부터" 커서를 뒀는데, 그 커서를 **루프 안에서 바로
갱신**하고 같은 루프의 인덱스 계산(`(CaptureCursor + Step) % N`)에도 쓰고 있었다. 캡처가 한 번
일어나면 남은 `Step` 의 인덱스가 함께 밀려 **어떤 채널은 두 번 방문되고 어떤 채널은 그 틱에 아예
빠진다.** 빠진 채널은 `Accum += DeltaTime` 조차 못 받아 목표 fps 에 계속 미달한다.

- 증상: 시청자 2명에서 목표 2.5fps 인데 실측 `1.838 / 1.908` (합계 3.75 < 예산 5)
- 원인 판정은 계산으로 했다 — 틱 11.8fps·간격 0.4s 의 양자화만으로는 2.26fps 가 나와야 하는데
  1.84 는 그보다 18% 낮았다. "틱이 느려서"로 넘기면 안 되는 크기였다.
- 수정: 시작점 `ScanStart` 를 틱 동안 고정하고 새 커서는 `NextCursor` 에 모아 루프 뒤에 대입.

### 5-2. 틱당 1장 상한은 처리량의 천장을 곧 틱 fps 로 만든다

`MaxCapturesPerTick=1` 이면 초당 최대 캡처 수 = 틱 fps 다. 창이 뒤로 가 틱이 2.5fps 로 떨어지면
`TotalFps=5` 를 **영영 못 채운다** — 실측 `sum(fps)=2.500 = tickFps 2.50` 으로 정확히 일치했다.

상한이 예산을 깎으면 안 되므로 실효 상한에 바닥을 뒀다:

```
실효 상한 = max(MaxCapturesPerTick, ceil(TotalFps / 실측 틱fps))
```

틱이 충분히 빠르면(30fps ≫ 5fps) 이 항은 1 이라 설정값이 그대로 쓰이고, 느린 구간에서만 풀린다.

**틱당 상한을 왜 두는가:** PTZ 캡처는 동기다(`CaptureOnce` → `ReadPixels` → JPEG 인코딩이 전부
게임 스레드). 실측 캡처 1장 ≈ 33ms(시청자 0→1 에서 틱 14.85→12.41fps, 초당 5장 기준 역산).
슬롯 10 에서 열 채널의 만기가 같은 틱에 겹치면 그 틱 하나가 ≈330ms 가 된다. 예산은 초당 총량만
묶을 뿐 **한 틱에 몰리는 것을 막지 못한다.** 밀린 채널은 `Accum` 을 그대로 들고 다음 틱에 잡히므로
초당 총량은 손실이 없다.

### 6-2. 런타임 실측

검증 인스턴스는 **패키지 복제 + exe 교체**로 만들었다(원본 실행창 `Package/Windows` 는 건드리지 않음).

- `Package/Work13540`, RPC **13540**, 메인 뷰 13800, 카메라 13811~13850
- ⚠ **패키지의 `DefaultGame.ini` 는 pak 안에 구워져 있다**(`Package/*/Park3D/Config/` 가 비어 있다).
  exe 만 갈아끼우면 낡은 `HardMaxSlots=2` 가 그대로 이긴다 → 재쿡 없이 검증하려고
  `Park3D/Saved/Config/Windows/Game.ini` 사용자 레이어로 덮었다. **실제 배포에는 재쿡이 필요하다.**

요청서의 검증 절차 그대로:

```
POST /rpc {"method":"cam.setStreamSlots","params":{"slots":10}}
  → {"slots":10, "requested":10, "hardMaxSlots":10}          ✓ (기대값과 동일)
```

| 시청자 | slots | activeChannels | channelFps | 실측 fps | 합계 | 틱 fps |
|--------|-------|----------------|-----------|----------|------|--------|
| 0명 | 10 | 0 | 5.000 | — | 0 | 3.15 |
| 1명 (cam1) | 10 | 1 | 5.000 | **5.688** | 5.69 | 10.82 |
| 2명 (cam1+cam2) | 10 | 2 | 2.500 | 2.680 / 2.692 | 5.37 | 4.49 |

- **변경 전이라면 1명일 때 `5/10 = 0.5fps` 였다.** 요청의 핵심 항목이 그대로 확인된다.
- 시청자 2명일 때 두 채널이 **동시에** 슬롯을 쥔다(`holdsSlot=true` 둘 다) — 순환 대기가 없다.
- 합계가 예산 5 근처로 유지된다 → 슬롯을 10 으로 열어도 게임 스레드 총 부하는 그대로.

**실측이 목표를 조금 웃도는 것(5.69 vs 5, 2.68 vs 2.5)은 기존 동작이다** — 잔여 시간 보존
(`Accum = Min(Accum - Interval, Interval)`)이 틱이 느릴 때 한 프레임치까지 만회하기 때문이며,
이번 변경으로 생긴 것이 아니다. 합계가 예산을 크게 넘지는 않는다.

⚠ 틱 fps 가 3~11 로 낮은 것은 **이 PC 에서 UE 인스턴스 두 대가 GPU 를 나눠 쓰기 때문**이고
(원본 sim1 단독은 30fps대), 배포 환경 수치가 아니다.

## 7. 배포 시 주의

1. **`DefaultGame.ini` 변경은 exe 교체로 반영되지 않는다.** pak 안에 구워지므로 재쿡·재패키지가
   필요하다. 그 전까지는 `Save/`(config_pmaker.json)가 아니라 각 배포본의
   `Park3D/Saved/Config/Windows/Game.ini` 에 아래를 넣으면 즉시 먹는다:

   ```ini
   [/Script/Park3D.CamStreamSubsystem]
   ActiveSlots=10
   HardMaxSlots=10
   MaxCapturesPerTick=1
   ```

2. `ActiveSlots` 기본값을 1 → **10** 으로 올렸다. 요청자의 "10 concurrent camera channels" 목표를
   맞추려면 상한만 올려서는 부족하고(런타임 기본이 1), 새 fps 모델에서 슬롯을 열어 두는 비용이
   0 이라 기본으로 열어 두는 편이 맞다고 판단했다. **부하가 문제면 이 한 줄만 낮추면 된다.**

3. 시청자가 실제로 10명이면 각자 `5/10 = 0.5fps` 다. 이건 예산 `TotalFps=5` 의 결과이며 새 모델의
   결함이 아니다(요청자도 "if it's too slow, users should just use fewer cameras" 로 동의).
   더 필요하면 `TotalFps` 를 올려야 하는데 **이를 바꾸는 RPC 는 아직 없다**(Ask 2(b), 미구현).
