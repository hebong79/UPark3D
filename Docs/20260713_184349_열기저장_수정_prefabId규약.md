## 2. 근본 원인 (핵심)

### 2.1 주원인 — 파일 다이얼로그 부모 윈도우 핸들이 `nullptr`

`CarPlacementWidget`/`CameraControlWidget`의 `PromptOpenFilePath`·`PromptSaveFilePath`가 `IDesktopPlatform::OpenFileDialog`/`SaveFileDialog`에 **부모 윈도우 핸들로 `nullptr`을 전달**하고 있었다. 이 경우 네이티브 다이얼로그가 **표시되지 않고 함수가 즉시 `false`를 반환**한다.

그 결과로 나타난 두 증상:

| 기능 | 실제로 벌어진 일 |
|------|------------------|
| **열기** | `PromptOpenFilePath`가 `false` → `HandleOpen`이 **조기 반환** → 아무 일도 일어나지 않음 |
| **저장** | `false` → 기본 경로로 폴백해 **조용히 엉뚱한 파일에 기록** |

**카메라 콤보박스가 안 생기던 것도 같은 원인이다.** 콤보 생성 로직(`RebuildCameraCombo()` / `RebuildPresetCombo()`)은 `HandleOpen` 내부의 조기 반환 지점 **아래**에 있었기 때문에 **아예 실행되지 않았을 뿐**, 콤보 로직 자체는 원래부터 정상이었다. 따라서 이번 수정에서 콤보 관련 코드는 **한 줄도 건드리지 않았다.**

정상 동작하던 `UPresetMakerWidget`은 같은 자리에 다음을 넘기고 있었다. 이 차이가 원인의 전부다.

```cpp
FSlateApplication::Get().FindBestParentWindowHandleForDialogs(nullptr)
```

### 2.2 부차 원인 — 기본 경로가 실제 데이터 폴더와 불일치

기본 경로가 엔진 `Saved/` 하위를 가리켜, 실제 참조 데이터 폴더(`Save/3D/CarPos/`, `Save/3D/CameraPos/`)와 달랐다. 이 때문에:

- `Park3D/Saved/CarPos/CarPos_SNum.json` (18바이트, 내용 `{"datas":[]}`) 이라는 **버그 산물 파일이 실제로 생성**되어 있었음 → 이번에 삭제.
- CameraControl은 `Saved/CameraPos` 폴더가 **존재조차 하지 않아** 저장이 그대로 실패했음.

### 4.3 `CarPlacementManager.cpp` — prefabId 0-based 시도 → **롤백** (이 문서의 핵심, 재발 방지)

최초 작업에서는 "참조 데이터의 `prefabId`가 0-based로 보인다"는 전제로 아래처럼 바꿨었다.

```
FindEntryByPrefabId:  E.Idx == PrefabId   →   E.Idx - 1 == PrefabId   (0-based 시도)
PreloadCatalogMeshes: 캐시 키 E.Idx       →   캐시 키 E.Idx - 1        (0-based 시도)
```

**그러나 이 전제가 틀렸다.** Unity 원본(`unity/CarObject/`)을 재조사한 결과 `prefabId`는 **1-based**이며, UE 카탈로그 `Idx`와 **동일한 공간**임이 확인되어 **전량 롤백**했다.

#### Unity 원본 근거 (권위 소스)

| 파일:라인 | 코드 | 의미 |
|-----------|------|------|
| `unity/CarObject/CCarObjListUI.cs:142` | `GetCarPrefab(kCarPos.prefabId-1);  // prefabId는 1부터 시작함.` | prefabId(1-based)를 **배열 인덱스(0-based)로 변환**하기 위해 `-1`. 주석이 "1부터 시작"이라고 명시. |
| `unity/CarObject/CCarObjListUI.cs:203` | `carIdx = idx + 1;  // prefabId는 1부터 시작` | 배열 인덱스(0-based) → prefabId(1-based) 변환 시 `+1`. |
| `unity/CarObject/CCarObjListUI.cs:336-338` | 0-based 값을 그대로 저장하면 잘못된다고 경고하는 코드 + `+1` 보정 | 0-based를 그대로 쓰면 버그라는 것을 Unity 코드 스스로 경고. |
| `unity/CarObject/CCarPlacementDlg.cs:781` | `kCarPos.prefabId = m_cboCarPrefabs.value + 1;` | UI 콤보(0-based `.value`)에서 저장 시 `+1` 하여 **1-based로 저장**. |
| `unity/CarObject/CSavePolePosData.cs:15` | `int prefabId = -1;  // ( 1부터 시작 )` | 필드 선언 주석에도 "1부터 시작" 명시. |

**결론: Unity의 `-1`/`+1`은 "0-based 배열 인덱스 ↔ 1-based prefabId" 상호 변환용이지, prefabId 자체의 진법을 바꾸는 게 아니다.** prefabId는 시종일관 1-based로 저장·취급된다. UE 카탈로그 `Idx`도 1-based이므로 **원래의 `E.Idx == PrefabId`가 옳았다.**

#### 실데이터 히스토그램(뒷받침 증거)

참조 데이터(`Save/3D/CarPos/*`)의 `prefabId` 값 분포: **`1`이 229건, `0`은 단 2건.** 절대다수가 1-based를 뒷받침하며, `0`인 2건은 Unity 코드가 §4.3 표에서 경고하는 **저장 버그로 발생한 오염 데이터**로 판단된다. 이 2건은 카탈로그에 `Idx == 0`이 없으므로 `FindEntryByPrefabId`가 못 찾고 **기존 로직 그대로 `Catalog[0]`(첫 항목) 폴백**으로 처리된다. 별도 특수 처리는 추가하지 않았다.

#### 롤백 결과 (원복 완료)

```
FindEntryByPrefabId:  E.Idx - 1 == PrefabId   →   E.Idx == PrefabId   (원복, 근거 주석 추가)
PreloadCatalogMeshes: 캐시 키 E.Idx - 1       →   캐시 키 E.Idx        (원복)
```

### 4.5 (신규) Shipping 등 대화상자 비가용 빌드 폴백

`HandleSave`에 "취소 시 중단" 로직을 넣으면서 생긴 사각지대를 이번에 함께 막았다. `PromptOpenFilePath`/`PromptSaveFilePath`(Car·Camera 양쪽)에서 `IDesktopPlatform`을 얻지 못하는 빌드(예: Shipping)는 다이얼로그를 아예 띄울 수 없어 지금까지의 로직이면 매번 "취소"로 간주되어 **저장이 완전히 불능**이 된다. `#else` 분기를 추가해 이 경우 **기본 경로로 자동 폴백**하도록 해 회귀를 방지했다.

## 5. 호환성 주의

- prefabId는 **롤백으로 원래 규약(1-based, `E.Idx == PrefabId`)이 그대로 유지**되므로 저장 데이터 해석 방식에 변화가 없다. 기존 참조 데이터(`Save/3D/CarPos/*`, 229건 `prefabId=1` 등)는 이전과 동일하게 정상 해석된다.
- 참조 데이터 중 `prefabId=0`인 2건은 §4.3에서 밝힌 대로 Unity 측 저장 버그로 발생한 오염 데이터이며, 카탈로그에 대응 항목이 없어 기존과 동일하게 `Catalog[0]`(첫 항목) 폴백으로 처리된다. 별도 조치는 하지 않았다.
- §2의 다이얼로그·기본 경로 수정(열기/저장)은 prefabId 롤백과 무관하게 **그대로 유효**하다.
