## 1. 요구사항

| # | 요구 | 판정 기준 |
|---|------|-----------|
| R1 | 카메라 1대당 카메라 뷰(렌더타겟)가 설정된다 | 카메라 N대일 때 RT N개가 각각 유효하고, 서로 다른 시점의 그림이 나온다 |
| R2 | 외부 스트리밍 접속 URL이 **포트당 카메라 1개**로 매칭된다 | `http://<IP>:13601/` = 1번 카메라, `:13602/` = 2번 카메라 … 쿼리 파라미터 불필요 |
| R3 | 카메라당 전용 스레드 1개를 쓴다 | 한 카메라의 느린 클라이언트가 다른 카메라 스트림·게임 스레드를 막지 않는다 |
| R4 | 검증된 baro 코드를 그대로 재사용한다 | `FMjpegStreamServer` 는 로그 카테고리/경계 문자열 외 로직 무수정 이식 |

### 요구사항 해석 — 명시적 가정

- **A1. "카메라 뷰"는 화면 UI가 아니라 캡처용 렌더타겟이다.** 현재도 `APTZCameraActor::RenderTarget` 이 카메라당 1개 생성된다(§2). R1의 실질 격차는 "RT 존재"가 아니라 **"선택되지 않은 카메라도 실제로 렌더되는가"** 이다. 뷰어 위젯(`CameraViewerWidget`)의 표시 대상 변경은 이번 범위에 넣지 않는다.
- **A2. 포트 매칭 단위는 `camId`(1-based 인덱스)** 다. 기존 RPC(`cam.list`/`cam.setPTZ`/`/stream?camId=`)가 전부 이 인덱스를 카메라 신원으로 쓰고 있으므로 포트도 같은 기준을 따른다. 결과적으로 카메라 삭제 시 인덱스가 밀리면 포트가 가리키는 카메라도 함께 밀린다(§4.2에 명시).
- **A3. 기존 `GET /stream?camId=` (13510) 은 유지한다.** 이미 패키징·문서화된 경로이고 브라우저 `<img>` 소비자가 있다. 신규 전용 포트는 그와 **병존**한다.

### 2.2 격차

| 격차 | 근거 |
|------|------|
| G1. 선택된 카메라 1대만 매 프레임 캡처 | `CameraControlManager.cpp:113` — `SetCaptureEnabled(i == Index)`. 비선택 카메라의 RT는 마지막 캡처 상태로 정지(stale)해 있다 |
| G2. 스트림 포트가 1개뿐 | `RpcServerSubsystem::Port = 13510` 단일. 카메라 구분은 쿼리(`?camId=`)로만 |
| G3. 스레드 분리가 없다 | `FMjpegStreamManager` 는 **전 세션을 게임 스레드 티커 하나**로 돌린다. 캡처·인코딩·송신이 전부 게임 스레드 |

**G4가 이 작업의 실질 난점이다.** 포트만 나눠도 캡처가 게임 스레드에 남아 있으면 카메라 3~4대 동시 스트리밍에서 앱이 사실상 멈춘다.

## 3. 목표 아키텍처

```
                       [게임 스레드]                          [카메라별 워커]        [외부]
  APTZCameraActor #1 ──RT#1─┐
  APTZCameraActor #2 ──RT#2─┤
  APTZCameraActor #N ──RT#N─┘
                             │
                 UCamStreamSubsystem (UTickableWorldSubsystem)
                   ├ FCamStreamChannel #1 ─ UpdateFrame ─> FMjpegStreamServer(:13601) ─> 송신스레드 ─> 클라이언트
                   ├ FCamStreamChannel #2 ─ UpdateFrame ─> FMjpegStreamServer(:13602) ─> 송신스레드 ─> 클라이언트
                   └ FCamStreamChannel #N ─ UpdateFrame ─> FMjpegStreamServer(:1360N) ─> 송신스레드 ─> 클라이언트

                   (P2) GPU 리드백 → 워커 JPEG 인코딩 → 완료 큐(MPSC) → 게임 스레드 drain
```

### 3.2 스레드 모델 (R3)

| 스레드 | 개수 | 하는 일 |
|--------|------|---------|
| 게임 스레드 | 1 | 채널 Tick — 페이싱 판단, `CaptureScene()`, 픽셀 회수, (P1)인코딩, `UpdateFrame()` |
| 송신 워커 | **카메라당 1** | 소켓 送信 전담. 블로킹 `SendAll`, 새 프레임 이벤트 대기 |
| accept 리스너 | 카메라당 1 (`FTcpListener` 내부) | 200ms 폴링 accept. 검증 코드가 자체 스레드를 만든다 |
| 인코딩 워커 (P2) | 태스크 풀 공유 | JPEG 압축 (`AnyBackgroundThreadNormalTask`) |

⚠ **정직한 고지**: baro 검증 코드를 그대로 쓰면 카메라당 OS 스레드는 **2개**(송신 1 + accept 1)다. "카메라당 1스레드" 문구와 다르므로 §12-D에서 선택지를 제시한다. 요구의 실질(카메라 간 간섭 차단)은 송신 스레드 분리로 달성된다.

## 4. 인터페이스

### 4.1 `FMjpegStreamServer` (이식, 시그니처 원본 유지)

```cpp
bool  StartServer(int32 Port, int32 InFps);   // 리스너 + 워커 기동
void  StopServer();
void  UpdateFrame(const TArray<uint8>& Jpeg); // 게임 스레드가 최신 프레임 갱신(시퀀스 증가 + 이벤트)
bool  HasClients() const;                     // 게임 스레드의 "캡처할까?" 판단 기준
int32 GetClientCount() const;
```

핵심 성질(원본 주석 근거):
- 워커는 **프레임 시퀀스가 갱신됐을 때만** 송신 → 중복 전송·고정 sleep 없음. 페이싱은 producer(게임 스레드)가 결정.
- 송신 중에는 `ClientsLock` 을 잡지 않는다 → 느린 원격 클라이언트가 게임 스레드의 `HasClients()` 를 얼리지 않는다.
- 클라이언트 없으면 게임 스레드가 캡처를 아예 안 한다 → **아무도 안 볼 때 렌더 비용 0**.

### 4.2 포트 부여 — `CamStreamPolicy` (순수 함수)

```cpp
namespace Park3DCamStream
{
    /** camId(1-based) → 포트. Base + camId. 범위 밖(≤0 또는 >MaxCameras)이면 0(미개설). */
    int32 ResolvePort(int32 BasePort, int32 CamId, int32 MaxCameras);

    /** 카메라 수 변화 → 개설/정지할 camId 목록(순수 계산). SyncChannels 가 이 결과대로만 소켓을 만진다. */
    void DiffChannels(int32 OldCount, int32 NewCount, TArray<int32>& OutToOpen, TArray<int32>& OutToClose);

    /** 슬롯 스케줄러(§15). 후보 중 지금 캡처할 camId 집합을 고른다. 시간·난수 비의존(Now 주입). */
    void SelectSlots(const TArray<FSlotCandidate>& Candidates, int32 Slots, double Now,
                     float MinHoldSeconds, float PtzRecentSeconds, TArray<int32>& OutHolders);

    /** 슬롯 수 → 채널당 목표 fps. bShare=false 면 TotalFps 그대로(채널당 고정). */
    float ResolveChannelFps(float TotalFps, int32 Slots, bool bShare);
}
```

- 기본 `BasePort = 13600` (기존 13510 RPC / 13520 MCP 브리지와 충돌 없음).
- 상한: 동시 채널 수 `MaxCameras = 10` (포트 13601~13610). 초과 카메라는 채널 미개설 + Warning 로그.
- ⚠ **카메라 삭제 시 인덱스가 밀린다**(`RemoveCameraAt` 이 `TArray::RemoveAt`). 포트↔카메라 매칭도 같이 밀린다. `cam.list`/`cam.setPTZ` 의 camId 와 **동일한 규칙**이므로 시스템 전체로는 일관적이다. 대안(카메라에 안정 ID 부여)은 §6-C 에서 비교.

## 5. 처리 흐름

### 5.1 기동
```
World BeginPlay
 └ APark3DGameMode::BeginPlay → ACameraControlManager::GetOrSpawn → EnsureDefaultCamera   (기존)
 └ UCamStreamSubsystem::OnWorldBeginPlay
     └ SyncChannels()
         ├ 매니저에서 카메라 N대 열거
         ├ 각 카메라: Port = BasePort + CamId
         └ FMjpegStreamServer::StartServer(Port, StreamFps)   ← 리스너+워커 스레드 기동
```

### 5.2 매 틱 (채널마다)
```
1) 카메라 수 변화 감지 → SyncChannels()  (추가분만 Start, 사라진 분만 Stop)
2) 슬롯 재평가(초당 1회) — 클라이언트 있는 채널만 후보 → SelectSlots() → bHoldsSlot 갱신 (§15)
   Fps = ResolveChannelFps(TotalFps, Slots, bShare)
2') if (!Server->HasClients() || !bHoldsSlot) → 캡처 안 함 (비용 0), MeasuredFps=0
     ※ 슬롯 없는 채널도 연결은 유지된다 — 클라이언트 화면엔 마지막 프레임이 남는다
3) Accum += Dt;  if (Accum >= 1/Fps)
     Accum = min(Accum - 1/Fps, 1/Fps)          // 잔여 보존 + 부채 클램프(기존 페이싱 결함 교정 계승)
     [P1 동기]  Cam->CaptureOnce() → RT->ReadPixels → RpcImage::EncodeColors → Server->UpdateFrame(Jpeg)
     [P2 비동기] Idle 이면 SubmitCapture(EnqueueCopy) / Ready 면 CollectReadback → 워커 인코딩 → 완료 큐
4) (P2) DrainCompletedFrames() → Server->UpdateFrame(Jpeg)   // 포트로 채널 조인
```

### 5.3 클라이언트 접속/종료
- 접속: `FTcpListener` accept → `Pending` 대기열 → 워커가 흡수 → 최초 송신 시 HTTP 200 + multipart 헤더.
- 종료: `SendAll` 실패 → 소켓 파괴 + 클라이언트 제거(워커). 클라이언트 0이 되면 게임 스레드가 캡처를 멈춘다.
- 정지: `Deinitialize`/월드 종료 → `StopServer()`(리스너 delete → 워커 join → 소켓 전부 정리). P2 사용 시 **채널 파괴 전 `FlushRenderingCommands()`** 로 in-flight 리드백 소진(baro 의 use-after-free 방지 규율 그대로 이식).

### 5.4 접속 URL (R2 충족 형태)
```html
<img src="http://192.168.0.125:13601/">   <!-- 1번 카메라 -->
<img src="http://192.168.0.125:13602/">   <!-- 2번 카메라 -->
```
`ffmpeg -i http://192.168.0.125:13601/ -f mpjpeg …` 로 RTSP 브리지도 동일하게 붙는다(baro/MediaMTX 선례).

## 6. 대안 비교

### A. 캡처 경로 — 동기 vs 비동기 ★핵심

| | A1 동기(기존 `ProduceFrame` 재사용) | A2 비동기(baro 이식) |
|---|---|---|
| 게임 스레드 점유 | 프레임당 ≈48ms (ReadPixels 가 렌더 플러시 유발) | 제출/회수만, 인코딩은 워커 |
| 4대 × 5fps 예산 | 4×5×48ms = **960ms/초 → 불가(앱 정지)** | 실측 baro 6대 동시 운용 가능 |
| 코드량 | 30줄(기존 함수 호출) | +150줄(리드백 상태머신·MPSC 큐·flush 규율) |
| 검증 | Park3D 기존 경로로 검증됨 | baro 에서 검증됨(0.1.10) |
| 지연 | 즉시 | 1~2프레임(CCTV 무해) |

**권고: A2.** 단 P1(A1)로 포트·스레드·URL 결선을 먼저 검증하고 P2에서 A2로 교체한다. 실패 시 config 로 A1 롤백 가능하게 둔다.

### B. 서버 구현 — 엔진 HTTP 라우터 vs 전용 TCP

- 엔진 `IHttpRouter` 를 포트마다 여는 방식(baro Hucoms CGI 처럼)도 가능하지만, **연속 MJPEG 응답은 엔진 큐 모드에서 메모리 단조 증가**라 Park3D 는 이미 세그먼트 롤오버라는 우회를 쓰고 있다(`Docs/20260804_165546` §3). 전용 TCP(`FMjpegStreamServer`)는 그 우회 자체가 필요 없다.
- **권고: 전용 TCP(검증 코드 그대로).**

### C. 포트↔카메라 신원 — 인덱스 vs 안정 ID

| | C1 인덱스(=camId) | C2 카메라에 안정 ID 부여 |
|---|---|---|
| 일관성 | `cam.*` RPC 전체와 동일 규칙 | RPC는 인덱스, 스트림은 ID → **두 신원 체계 공존** |
| 삭제 시 | 뒤 카메라 포트가 밀림 | 포트 고정 |
| 비용 | 0 | `APTZCameraActor` 필드 + 저장 포맷(JSON) 변경 파급 |

**권고: C1.** 카메라 삭제는 편집 행위이고 그때 스트림 URL이 재배치되는 것은 `cam.list` 와 같은 동작이다. C2는 저장 포맷까지 건드리므로 별건으로 분리한다.

### D. 스레드 수 (R3 문구 정합)

| | D1 검증 코드 그대로 | D2 accept 를 워커에 합침 |
|---|---|---|
| 카메라당 OS 스레드 | 2 (송신 + accept 폴링) | 1 |
| 코드 | **무수정 이식** | 리슨 소켓 직접 생성 + 논블로킹 accept 폴링(검증 코드 수정) |
| 위험 | 없음(검증됨) | 이식 코드 개조 → R4 위반, 재검증 필요 |

**권고: D1** (16대 기준 32스레드, 대기 상태 폴링이라 CPU 영향 무시 가능).

| 항목 | 근거 | 값 |
|------|------|-----|
| RT VRAM | 1280x720 RGBA8 | 카메라당 3.5MB → 16대 56MB |

## 8. 좌표/단위 규약

이번 작업은 **좌표·단위 변환을 새로 만들지 않는다.** PTZ/좌표는 기존 `UCameraControlLibrary` 경유 그대로이며, 스트리밍은 RT 픽셀만 읽는다. 픽셀 규약은 기존 `cam.captureJPG`/`/stream` 과 동일(`RCM_UNorm`, `LinearToGamma=false`, `RpcImage::EncodeColors`).

## 14. baroCCTVSimulator 를 **플러그인으로 붙이는 안** 검토

> 질문: 코드를 복사하는 대신 `baroCCTVSimulator` 를 Park3D 의 플러그인(submodule)으로 등록해 쓰면 어떤가?

### 14.1 그 플러그인이 실제로 제공하는 것

| 클래스 | Park3D 에서의 쓸모 |
|--------|-------------------|
| `FMjpegStreamServer` (Public 헤더, ~400줄) | ✅ **그대로 유용** — Park3D 타입에 의존하지 않는 자립 클래스 |
| `UHucomsServerSubsystem` (채널·포트·비동기 리드백·생명주기, ~1300줄) | ⚠ `APTZCamera` + `UPTZCaptureComponent` 에 **하드 바인딩**. Park3D 카메라(`APTZCameraActor`)로는 못 쓴다 |
| `APTZCamera` / `UPTZCaptureComponent` | ❌ Park3D 는 이미 자기 카메라 스택을 가진다(아래) |
| Hucoms CGI 라우트(`ptzf_status.cgi` 등) | ❌ Park3D 는 JSON-RPC. 프로토콜 이중화 |
| `ABaroSimGameMode`/`HUD`/`PlayerController`, `SceneControlSubsystem`, `CenteringClientComponent` | ❌ Park3D 는 `APark3DGameMode` 스택을 쓴다. 전부 미사용 코드 |

**핵심**: 플러그인을 붙여도 **재사용 가능한 실물은 `FMjpegStreamServer` 하나(~400줄)** 다. 채널 관리·페이싱·리드백은 어차피 Park3D 카메라에 맞춰 새로 써야 한다 — 이 설계서의 §3~§5가 바로 그 작업이며, 플러그인 채택 여부와 무관하게 발생한다.

### 14.2 카메라 스택이 두 벌이 된다는 문제

Park3D 의 카메라 신원은 `APTZCameraActor` 이고, 그 위에 **프리셋 JSON 저장·로드**, `ACameraControlManager`(풀/선택/피킹), `CameraControlWidget`·`CameraViewerWidget`, `cam.*` RPC, 폴대 클릭 선택이 전부 얹혀 있다. 플러그인의 카메라는 `APTZCamera` 이고 좌표·FOV 규약도 다르다(Park3D `zoom 1~36`/`DefaultHFov 58` ↔ 플러그인 `zoompos raw`/`WideHFovDeg 57.14`).

| 채택 방식 | 결과 |
|-----------|------|
| **전면 채택**(플러그인 카메라로 이관) | 프리셋 포맷·매니저·위젯·RPC 전면 개편. 이번 요구(스트리밍)의 10배 규모 공사 |
| **병행**(플러그인 카메라를 따로 스폰) | 카메라가 두 벌 → 프리셋으로 배치한 카메라는 스트리밍 안 되고, 스트리밍되는 카메라는 UI/RPC 로 제어 불가. **요구 자체를 충족 못 함** |
| **라이브러리로만**(모듈 링크, `FMjpegStreamServer` 만 사용) | 기술적으로 성립. 아래 14.3 |
| **파일 이식**(현 설계) | 즉시 진행 |

### 14.3 "라이브러리로만" 안의 실제 비용

| 항목 | 내용 |
|------|------|
| 결선 | `.uproject` 에 플러그인 추가 + `Park3D.Build.cs` 에 `"baroCCTVSimulator"` 의존 + submodule 추가 |
| VCS | Park3D 는 **git(.git 이 SVN 밖) + SVN 혼재** 트리다(`Docs/20260723_174641`). 여기에 submodule 이 하나 더 얹히고, `Park3D/Plugins/*/Binaries·Intermediate` 용 ignore 규칙도 새로 필요 |
| 빌드 | 미사용 클래스 8종(게임모드·HUD·CGI·VLA 클라이언트)이 **항상 컴파일·쿠킹된다** |
| 런타임 부작용 | `UHucomsServerSubsystem` 은 Game/PIE 월드에서 자동 기동한다. Park3D 레벨에 `APTZCamera` 가 없으므로 "서빙할 카메라 없음 → 미기동" 경고로 끝나 실해는 없지만, **끄기 위한 config 관리가 상시 필요**(`bAutoSpawnCameraIfNone=False` 등) |
| 업스트림 | 플러그인은 baro_unreal·baroQuantum 의 **단일 진실 소스**다(README §단일 소스 원칙). Park3D 사정으로 고칠 수 없고, 반대로 업스트림 변경이 Park3D 빌드를 깨뜨릴 수 있다 |
| 얻는 것 | 파일 2개(~400줄) 복사 회피 + 그 클래스의 업스트림 수정 자동 유입 |

### 14.4 결론 — **현 단계는 파일 이식이 효과적**

- 얻는 것(400줄 중복 회피)에 비해 치르는 것(서브모듈·미사용 모듈 상시 빌드·업스트림 결합·config 관리)이 크다.
- `FMjpegStreamServer` 는 **변경이 거의 없는 완성된 클래스**다(소켓 송신 루프). 업스트림 수정이 자주 날 코드가 아니라 자동 유입의 가치가 낮다.
- 연구단계의 속도 우선 방침과도 맞는다 — submodule/빌드 결선 없이 오늘 바로 P1 을 돌릴 수 있다.
- 추적성은 문서로 확보한다: §13 의 이식 매핑 표에 원본 경로를 남기고, 이식 파일 헤더 주석에 `출처: baroCCTVSimulator/Private/MjpegStreamServer.cpp (2026-08-05 시점)` 을 명시한다.

### 14.5 이 조건이면 플러그인 채택을 재검토한다

1. **Park3D 가 실기 Hucoms CGI 프로토콜을 말해야 할 때** — `baro_calory`(AI 에이전트)가 Park3D 에 실기처럼 붙어야 한다면, CGI 표면·PTZ 정준 상태·setcenter 기하까지 통째로 필요하다. 그때는 플러그인 채택이 정답이고, 대신 카메라 스택 일원화(14.2)를 별도 과제로 세워야 한다.
2. **제3의 UE 프로젝트가 같은 스트리밍을 요구할 때** — 소비자가 3곳이 되면 단일 소스의 가치가 복사 비용을 넘는다.
3. **비동기 리드백 파이프라인을 양쪽이 계속 손보게 될 때** — 성능 튜닝이 반복되면 공유가 유리하다.

## 15. 슬롯 스케줄러 — 카메라 10대를 캡처 1~2대로 감당하는 방법

### 15.1 무엇을 제한하는가

희소 자원은 **게임 스레드의 캡처 처리량**(동기 경로 합계 ≈18프레임/초)이지 포트·소켓·스레드가 아니다. 따라서:

- **포트/URL 은 카메라 수만큼 항상 열어 둔다**(13601~13610). 클라이언트는 아무 때나 붙을 수 있고, URL 이 상황에 따라 죽지 않는다.
- **제한 대상은 "지금 프레임을 만드는 카메라 수"**(= 슬롯). 슬롯 없는 채널은 연결을 유지한 채 프레임 갱신만 멈춘다 → 클라이언트 화면엔 **마지막 프레임이 남는다**(MJPEG 특성, 재접속 불필요).

### 15.2 후보 선정과 우선순위

**후보 = 클라이언트가 붙은 채널뿐.** 10대 중 실제 시청자는 보통 1~2대이므로, 대부분의 상황에서 순환 자체가 일어나지 않고 보는 카메라가 슬롯을 계속 점유한다.

점수(높을수록 우선, 동점은 camId 오름차순 — 결정적):

| 가중 | 항목 | 이유 |
|------|------|------|
| +4000 | `bPinned` | 사용자가 "이 카메라 계속"으로 고정 — 순환 중지가 의도된 유일한 경우 |
| +2000 | 최근 `PtzRecentSeconds`(3초) 내 PTZ 조작 | 조작 중 화면이 안 움직이면 제어 불가(시간 제한 우위) |
| +2 | 뷰어 선택 카메라(`SelectedIndex`) | 살짝 가산(≈2초치) |
| +0.1×min(clients,10) | 클라이언트 수 | 동점 해소 |
| +clamp(Now−LastServedTime, 0, 60) | 굶은 시간 | **지배항 — 순환 보장** |

> ⚠ **초안(선택 +1000, 클라이언트 +10/명)은 구현 후 실측에서 폐기했다.** 선택 카메라 가산이
> 기아 점수(최대 60)를 영구히 압도해 20초간 순환이 0회였고, 클라이언트가 붙은 나머지 두 채널이
> 각 1프레임만 받았다. 원칙: **기본은 공평한 순환, 우선순위는 그 위에 얹는 예외**다. 절대 우위는
> pin(영구)과 PTZ(3초 한정)뿐이고 나머지는 굶은 시간에 밀려야 한다.
> 회귀 테스트 `SelectSlots.SelectedNoMonopoly` 로 못 박았다. 실측은 `Docs/20260805_204558_…_P1_구현검증.md` §3.

### 15.3 최소 점유 시간 — 순수 라운드로빈의 함정

슬롯이 매 틱 튀면 각 카메라가 프레임을 한 장씩만 받아 **전부 정지화면처럼 보인다.** 그래서 슬롯을 잡은 채널은 `MinHoldSeconds`(기본 2초) 동안 더 높은 점수의 후보가 나타나도 유지한다. 결과는 "2초씩 돌아가며 보이는 연속 영상"이다.

```
SelectSlots(후보, Slots, Now):
  1) 보유자 중 (Now - SlotSince) < MinHold 인 채널을 먼저 확정(강제 유지)
  2) 남은 자리를 점수 내림차순으로 채운다
  3) 결과에 없는 기존 보유자는 슬롯 반납(LastServedTime = Now)
```
시간·난수를 주입받는 순수 함수라 유닛 테스트로 전 분기를 검증한다(§10 U3~U7).

### 15.4 fps 예산 배분

`TotalFps`(기본 5)를 **총 캡처 예산**으로 두고 슬롯 수로 나눈다: 슬롯 2 → 채널당 2.5fps.
→ **슬롯을 늘려도 게임 스레드 부하가 일정**하다(앱이 갑자기 느려지지 않는다). `bShareFpsBudget=false` 면 채널당 고정 fps(부하는 슬롯 수에 비례).

### 15.5 런타임 제어 (RPC 3종, P1 포함)

| 메서드 | 파라미터 | 반환/동작 |
|--------|----------|-----------|
| `cam.streamStatus` | — | 채널별 `{camId, port, clients, holdsSlot, pinned, fps}` + `{slots, hardMax, totalFps}` |
| `cam.setStreamSlots` | `slots` | 1..`HardMaxSlots` clamp. 초과 요청은 clamp 후 실제 적용값 반환 |
| `cam.pinStream` | `camId`, `on` | 고정/해제. 고정 수가 슬롯 수를 넘으면 초과분은 점수 순으로만 반영(고정이 슬롯을 늘리지는 않는다) |

값 변경은 즉시 다음 재평가에 반영되며 재빌드·재기동이 필요 없다.

### 15.6 하지 않는 것

- **렌더 자원 해제(baro `ReleaseCaptureResources`) 미이식**: Park3D 는 RT 를 항상 들고 있고 `CaptureOnce()` 를 호출하지 않으면 GPU 비용이 0 이다. RT 10개 = 35MB 로 해제 관리의 복잡도를 살 이유가 없다.
- **슬롯 자동 증감**: 부하를 보고 슬롯을 자동으로 늘리지 않는다. 예산은 사람이 정한다(비용을 아는 쪽이 정한다는 기존 원칙).
