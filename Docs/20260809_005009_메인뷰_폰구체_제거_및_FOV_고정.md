- 날짜: 2026-08-09
- 대상: `Park3D/Source/Park3D/ParkFlyPawn.{h,cpp}`, `Park3D/Source/Park3D/Park3DGameMode.{h,cpp}`

## 1. 떠 있는 구체의 정체

### 1.1 결론

**메인 뷰(자유비행) 폰 `AParkFlyPawn` 의 몸통 메시**다. 레벨에 배치된 액터가 아니라, 베이스 클래스
`ADefaultPawn` 이 생성자에서 기본으로 만드는 `MeshComponent`(`/Engine/EngineMeshes/Sphere`) 다.

### 1.2 특정 과정 (전부 실행 중인 인스턴스 + 저장소 에셋으로 확인)

1. **레벨 액터 전수 조사** — `Content/__ExternalActors__/Maps/PresetMaker1` 의 139개 uasset 을
   클래스별로 훑었다. 구체가 될 수 있는 후보는 `StaticMeshActor` 단 1개(`SM_SkySphere`)뿐이었고,
   그 액터의 트랜스폼은 `loc=(0,0,0) rot=identity scale=(400,400,400)` — 하늘 돔이므로 화면의
   작은 공이 될 수 없었다. 나머지는 Landscape/HLOD/조명/안개/구름/PostProcess/PlayerStart 였다.
2. **소스 조사** — `Source/` 에 구체 메시를 스폰·부착하는 코드는 없다.
   `DrawDebugSphere` 호출은 있으나 와이어프레임이라 렌더 결과와 모양이 다르다.
3. **시차(parallax) 측정** — `cam.setPosition` 으로 카메라를 50m, 이어서 5m 옮기자 구체가 화면에서
   완전히 사라졌다. 원거리 천체가 아니라 근거리 물체라는 뜻.
4. **역방향 광선 계산** — 캡처 이미지(1280×720)에서 구체 중심 픽셀 (671, 200), 반지름 46px 를 재고,
   카메라 pose(pos `(-10.52, 28.90, 13.5)`, pan `-148.8`, tilt `15.8`, zoom 1 → hFOV 56.5°)와
   `view.pick` 과 동일한 투영식으로 월드 방향을 구했다 → `(-0.8331, -0.5347, -0.1417)`.
   같은 시점의 `view.get` 폰 위치 `(-18.01, 24.09, 12.23)` 로 향하는 단위벡터는
   `(-0.832, -0.534, -0.141)` — **소수 셋째 자리까지 일치**.
5. **직접 검증** — `view.set` 으로 폰만 `(-25, 18, 12.2)` 로 옮기고 카메라는 그대로 둔 채 재캡처하니
   구체가 폰을 그대로 따라 움직였다.

부수 확인: 메인 뷰 캡처에 바닥에 찍힌 검은 점이 있었는데, 이것도 같은 구체가 떨군 그림자였다.
`view.pick` 라인트레이스가 구체를 통과한 것은 `ADefaultPawn` 이 이 메시를 `NoCollision` 으로
두기 때문이며, 폰 자신은 트레이스 무시 대상이라 정상 동작이었다.

### 1.3 조치

`AParkFlyPawn` 에 생성자를 추가해 해당 서브오브젝트 생성 자체를 막았다.

```cpp
AParkFlyPawn::AParkFlyPawn(const FObjectInitializer& ObjectInitializer)
    : Super(ObjectInitializer.DoNotCreateDefaultSubobject(ADefaultPawn::MeshComponentName))
{
}
```

- 숨기기(`SetHiddenInGame`)가 아니라 **미생성**을 택했다. 숨기면 그림자·오버랩 판정이 남고,
  카메라 렌더타깃은 별도 SceneCapture 라 숨김 플래그 누락에 다시 걸릴 여지가 있다.
- 이동/충돌을 담당하는 `CollisionComponent` 와 `MovementComponent` 는 건드리지 않았다.
  RMB 게이트 이동 로직도 그대로다.

## 2. 메인 뷰 화각 고정

### 2.1 문제

실행 중 인스턴스의 `view.get` 이 `fov: 150` 을 반환했다. 이 값은 소스·Config 어디에도 없다 —
과거 세션에서 `view.set` 으로 넣은 런타임 상태(`LockedFOV`)가 남아 있었던 것이다.
즉 코드 결함은 아니지만, "기본값이 무엇인지"가 어디에도 명시돼 있지 않아 한 번 틀어지면
되돌릴 기준이 없는 상태였다.

메인 렌더타깃은 960×540(16:9)이고, `PlayerCameraManager` 의 FOV 와 SceneCapture 의 `FOVAngle`
은 둘 다 **수평** 화각이다(`CamStreamSubsystem.cpp:761` 주석과 동일 규약).

### 2.2 값 선택 근거

직선투영에서 축으로부터 θ 만큼 벗어난 물체의 늘어짐 배율은 `1/cos θ` 다.

| 수직 화각 | 수평 화각(16:9) | 좌우 끝 늘어짐 | 모서리 늘어짐 |
|---|---|---|---|
| 150° (문제 상황) | 162.86° | 6.68× | 8.5× |
| 60° | 91.49° | 1.43× | 1.55× |
| **45° (채택)** | **72.73°** | **1.24×** | **1.31×** |
| 33.63° (HNR-2036LA 광각단) | 56.50° | 1.14× | 1.19× |
| 30° | 50.94° | 1.11× | 1.14× |

- 60°→45° 는 모서리 왜곡을 1.55×→1.31× 로 크게 줄인다.
- 45°→30° 는 1.31×→1.14× 로 개선폭이 절반 이하인데, 화면에 담기는 폭은 30% 넘게 잃는다.
- 따라서 45° 가 "늘어짐이 눈에 띄지 않으면서 조망을 가장 덜 버리는" 지점이다.

**실장비 화각(수평 56.5°)에 맞추지 않은 이유**: PTZ 카메라 뷰는 휴컴스 HNR-2036LA 를 재현하는
것이 목적이라 56.5°가 사양이지만, 메인 뷰는 배치·검수를 위한 작업 시점이다. 장비가 무엇을
보는지는 렌더타깃 프리뷰가 이미 정확히 보여주므로, 메인 뷰까지 좁히면 얻는 것 없이 이동·조망만
답답해진다. 두 뷰의 화각은 서로 독립이어야 한다.

### 2.3 조치

`APark3DGameMode` 에 수직 화각 프로퍼티와 적용 함수를 추가하고 `BeginPlay` 에서 호출한다.

```cpp
// Park3DGameMode.h
UPROPERTY(EditDefaultsOnly, BlueprintReadWrite, Category = "Park3D|Camera")
float MainViewVerticalFovDeg = 45.f;

// Park3DGameMode.cpp — ApplyMainViewFov()
const float VerticalFov = FMath::Clamp(MainViewVerticalFovDeg, 1.f, 170.f);
const float HorizontalFov = FMath::RadiansToDegrees(
    2.f * FMath::Atan(FMath::Tan(FMath::DegreesToRadians(VerticalFov * 0.5f)) * (16.f / 9.f)));
PC->PlayerCameraManager->DefaultFOV = HorizontalFov;
```

- 설정값을 **수직각**으로 둔 이유: 화면비가 바뀌어도 의미가 흔들리지 않는 축이기 때문이다.
  적용 시점에만 16:9 로 수평각(72.73°)으로 환산한다.
- `SetFOV`(LockedFOV) 대신 `DefaultFOV` 를 바꾼다. `view.set {fov}` 로 일시 변경하는 기존 RPC
  계약과 `fov=0`(잠금 해제) 동작을 그대로 유지하면서, "아무도 건드리지 않았을 때의 값"만 고정한다.
- 적용 로그: `[Park3DGameMode] 메인 뷰 화각 고정: 수직 45.00° → 수평 72.73°(16:9)`

## 3. 곁다리로 고친 것 — `Park3D.Build.cs` 에 `RHI`/`RenderCore` 추가

요청 범위 밖이지만 **패키징 자체가 막혀 있어** 검증을 하려면 고칠 수밖에 없었다.

- 증상: `BuildPackage.bat`(UAT BuildCookRun)이 쿠킹을 위해 **에디터 타깃**을 빌드하는데,
  링크에서 `LNK2019` 16건 뒤 `LNK1120` 으로 죽었다.
- 원인: `CamStreamSubsystem` 의 메인 뷰 비동기 리드백이 `FRHIGPUTextureReadback`,
  `FRHICommandListImmediate`, `FRenderThreadCommandPipe`, `GIsThreadedRendering` 등을 직접 쓰는데
  `Park3D.Build.cs` 에 `RHI`·`RenderCore` 의존이 선언돼 있지 않았다.
  커밋 `d535b38`(비동기 리드백 전환) / `562629b`(다중 슬롯) 에서 유입된 잠복 결함이다.
- 왜 이제야 드러났나: 모놀리식 게임 빌드는 모든 모듈이 한 실행 파일로 링크돼 선언이 없어도
  심볼이 잡힌다. 모듈러(DLL) 에디터 빌드에서만 임포트 선언이 강제된다. 그리고 마지막 패키징이
  2026-08-08 00:15 로 위 커밋들보다 앞서서, 그 사이 아무도 패키징을 돌리지 않았다.
- 조치: `PrivateDependencyModuleNames` 에 `"RHI", "RenderCore"` 추가 → 에디터 타깃 링크 성공.
