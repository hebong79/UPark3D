# config `preset_file: ""` 인데 프리셋 면(번호)이 보이는 현상 — 원인과 수정(RPC 호출 로그)

- 날짜: 2026-09-08
- 대상 인스턴스: 정본 `Package/Windows`(RPC 13510) — **손대지 않음**. 수정 exe 는 작업본 `Package/Work13520`(RPC 13520) 에 넣어 기동해 두었다.
- 변경 파일: `Park3D/Source/Park3D/Rpc/RpcServerSubsystem.h`, `RpcServerSubsystem.cpp`
- 파일 형식·RPC 계약 변경 없음. 로그 한 줄이 늘어난 것이 전부다.

## 1. 신고

카메라 패널(서신지구대, `CamPos_Seosin.json`)을 연 화면에서 바닥에 번호가 1~33 까지 찍혀 있고, 12·13 이 두 번 나온다.
config `config_pmaker.json` 의 `preset_file` 은 최상위·`levels[]` 둘 다 `""` 인데, **마치 프리셋 파일이 들어 있는 것처럼** 프리셋 면이 그려진다. rpc-mcp 를 쓰던 중에 생겼다.

## 2. 원인 — 파일이 아니라 RPC `preset.create` 로 메모리에 만들어진 프리셋

config 는 정상이고 코드가 config 를 잘못 읽은 것도 아니다. 정본 로그(`Package/Windows/Park3D/Saved/Logs/Park3D.log`)가 그대로 말해 준다.

| 시각(로컬) | 로그 | 뜻 |
|---|---|---|
| 12:37~12:40 | `주차면 번호 23개 표시(프리셋 0, 레벨 23)` | 기동 직후. 레벨 면 23개뿐, 프리셋 0 — config 대로 |
| **12:48:21** | `데칼 48개 활성` → `번호 35개(프리셋 12, 레벨 23)` → 47(24) → 59(36) → **71(48)** | 0.3초 사이에 **12면짜리 프리셋 4개**가 하나씩 추가됨 |
| **13:19:49** | 74(51) → 77(54) → 80(57) | **3면짜리 프리셋 3개** 추가 |

- 12면씩 하나씩 늘고 그때마다 데칼·번호가 다시 그려지는 패턴은 `preset.create` 의 경로(`AddPreset` → `RefreshView`) 그대로다. 파일 로딩(`preset.load`, `scenario.load`)은 목록을 통째로 바꾸므로 한 번에 늘어난다. `Save/3D/Preset` 에 12면×4 구성의 파일도 없다.
- 이 프리셋은 **메모리(`AParkingPresetManager::StoredPresets`)에만** 있다. `ResolvePresets()` 는 `StoredPresets` 가 비어 있을 때만 config 의 `preset_file` 을 보므로, RPC 로 하나라도 만들어지는 순간 config 값과 무관하게 그 목록이 바닥 번호·데칼·`preset.numbers`·차량 스냅의 기준이 된다. 화면에서는 파일에서 읽은 프리셋과 구분되지 않는다 — 신고의 "값이 들어 있는 것처럼" 이 정확히 이 상태다.
- 화면의 "12·13 두 번" 은 별개다. 정본 `CamPos_Seosin.json` 에 기준점(레벨 면 #16 → 12, 갯수 2)이 걸려 있어 16·17 이 12·13 으로 바뀌고 원래 12·13 은 그대로 남는다(번호 중복은 막지 않는다는 09-08 결정). 패널의 "기준 면 #16" 안내가 이것이다.

### 누가 불렀는지는 로그로 알 수 없었다

정본 로그에는 `[RPC]` 줄이 서버 시작 한 줄뿐이다 — **호출 자체는 한 줄도 기록되지 않는다**. 결과(번호 재표시)만 남아 있어 메서드·인자·호출자를 역산해야 했다. 확인한 범위:

- 이 PC 의 Claude 세션 기록(오늘 것 전부)에는 12:48·13:19 에 `preset.create` 를 부른 세션이 없다(직전 세션은 전부 `sim2`=13520 대상, 그 시각엔 빌드·git 중).
- SettingManager(팀 보드 #111/#115)의 「일괄설정 › 적용」은 `preset.clear` 뒤 `preset.create` 를 프리셋마다 부른다 — 패턴이 같다. 다만 이 PC 에는 SettingManager 가 없다(13030/13040 미리슨, `simulation_config.json` 없음). 다른 PC 에서 이 정본을 가리켰을 수 있다.
- rpc-mcp 브리지(`park3d-rpc-mcp/instances.json`)의 **기본 대상은 `sim1`=정본 13510** 이다. `sim` 인자를 빼고 부르면 정본으로 간다.

호출자는 특정하지 못했다. 그래서 수정은 "다음엔 로그 한 줄로 끝나게" 하는 쪽이다.

## 3. 수정 — RPC 호출을 한 줄씩 로그에 남긴다

`URpcServerSubsystem::ProcessSingle` 에서 디스패치 결과와 함께 기록한다.

```
LogTemp: [RPC] 127.0.0.1 preset.create {"offset":{"x":0,"z":0},"faceCount":12,"presetName":"repro_1"}
LogTemp: Warning: [RPC] 127.0.0.1 preset.create {"offset":{"x":0,"z":0}} -> 오류 -32000: 필수 파라미터 누락: faceCount
```

- 형식: `[RPC] <피어 IP> <메서드> <params 한 줄 JSON>`. 실패면 Warning 으로 오류 코드·메시지까지.
- params 는 공백 없는 JSON 으로 300자에서 자른다(좌표 목록 같은 큰 인자로 로그를 채우지 않기 위해). 토큰 값은 params 에 없다(헤더).
- **뺀 메서드**: `cam.captureJPG`, `cam.capturePNG`, `cam.streamStatus`, `system.ping`, `system.health` — 초당 여러 번 들어오는 폴링이라 로그를 덮는다. 나머지는 조회형(`preset.numbers`, `cam.list` 등)도 전부 남긴다.
- 배치 요청(JSON 배열)도 항목마다 한 줄씩. 피어 주소는 `HandleRpc` 에서 한 번 뽑아 넘긴다(`ProcessSingle` 시그니처에 `Peer` 추가).

### 하지 않은 것

- `preset.create` 의 동작은 바꾸지 않았다. RPC 로 프리셋을 만들면 바닥에 그려지는 것은 설계 그대로다(시뮬·시나리오가 이 목록을 쓴다).
- config 만으로 되돌리는 스위치는 두지 않았다. 지금 인스턴스에서 지우려면 `preset.clear`(또는 재기동). 파일에 저장되지 않으므로 재기동하면 사라진다.
- `preset.create` 등이 스스로 로그를 남기게 하는 방식(모듈마다 한 줄씩)은 버렸다 — 116개 메서드에 흩어지면 빠지는 곳이 생긴다. 디스패처 한 곳이 맞다.

## 4. 검증 — 작업본 13520 (정본 무간섭)

빌드: `Build.bat Park3D Win64 Development` 성공(24.7초). exe·pdb 를 `Package/Work13520/Park3D/Binaries/Win64` 에 복사하고 `-RpcPort=13520 -log` 로 기동(config 도 13520/13700/13711~ 로 분리돼 있음).

재현 스크립트(`scratchpad/verify_rpc_log.py`) 결과:

| 단계 | `preset.numbers` | 비고 |
|---|---|---|
| 기동 직후 | 프리셋 0 / 레벨 23 / 번호 1~23 | config 대로 |
| `preset.create` 12면 ×4 (offset 0) | **프리셋 48 / 레벨 23 / 번호 71개, 최대 48** | 정본 로그의 `71개(프리셋 48, 레벨 23)` 과 정확히 같은 상태 |
| `preset.create` faceCount 누락 | 오류 -32000 | 오류 로그 형식 확인용 |
| `preset.clear` | 프리셋 0 / 레벨 23 / 번호 23개 | 원복 |

로그(`Package/Work13520/Park3D/Saved/Logs/Park3D.log`)에 `[RPC]` 줄 9개 — 호출 순서·인자·오류가 전부 남았고 `system.health` 폴링은 빠져 있다.

캡처(`PrintWindow`): 생성 직후 건물 앞 도로(원점) 위에 노란 프리셋 번호가 네 겹으로 찍혀 있고(`Docs/shots/20260908_rpc_preset_create_after.png`), `preset.clear` 뒤 사라진다(`Docs/shots/20260908_rpc_preset_clear_after.png`). 신고 화면은 호출자가 오프셋을 주차장 위에 맞춰 만들었기 때문에 번호가 주차면 위에 얹혀 파일처럼 보였을 뿐 같은 현상이다.

자동화 테스트는 돌리지 않았다 — 바뀐 코드는 HTTP 요청 처리 경로(`RpcServerSubsystem`)뿐이고 테스트가 이 경로를 타지 않는다. 검증은 위 실기 왕복으로 대신했다.

## 5. 정본에 반영하려면

1. 정본 인스턴스를 종료한다(사용 중이라 이번엔 하지 않았다).
2. `Park3D/Binaries/Win64/Park3D.exe`(13:32 빌드)를 `Package/Windows/Park3D/Binaries/Win64/` 로 복사한다.
3. 재기동. 그 뒤로는 누가 `preset.create` 를 보내든 로그에 `[RPC] <IP> preset.create {...}` 가 남는다.
4. 지금 정본에 떠 있는 프리셋 57면은 재기동하면 없어진다(파일에 없다). 재기동 전에 지우려면 `preset.clear`.

## 6. 남은 의문

- 12:48 과 13:19 의 호출자. 정본에 새 exe 를 넣은 뒤 같은 일이 생기면 로그의 IP 로 바로 갈린다. 외부 PC 의 SettingManager 「적용」이면 그쪽 `simulation_config.json` 의 `preset_file` 이 이 정본으로 흘러 들어오는 것이므로, 그 파일을 비우거나(#111: 빈 값 = 건드리지 않음) 대상 주소를 바꿔야 한다.
