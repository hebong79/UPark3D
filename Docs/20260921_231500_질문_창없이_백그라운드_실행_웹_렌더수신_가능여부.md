# 질문: Park3D 를 화면 렌더러(창) 없이 백그라운드로만 실행하고, 웹에서 렌더 화면을 통신으로 받아 쓸 수 있나?

작성: 2026-09-21 23:15
질문자 요청: 팀 보드(baro_memo)에 관련 자료가 있으면 찾아서 답할 것.

## 결론

**된다. 추가 개발 없이 지금 패키지 그대로 된다.** 이 세션에서 직접 실행해 확인했다.

```
Park3D.exe -RenderOffScreen -Unattended -NoSound -ForceRes -ResX=960 -ResY=540 -RpcPort=13540
```

- 최상위 창 **0개**(`MainWindowHandle=0`, `EnumWindows` 로 프로세스 소유 창 없음). `-log` 를 붙이면 로그 콘솔 창(`ConsoleWindowClass`) 하나만 뜬다.
- RHI 는 실 GPU(D3D12 SM6, RTX 5060 Ti)로 정상 초기화. **`-nullrhi` 가 아니라 `-RenderOffScreen` 이어야 한다** — nullrhi 는 렌더타깃이 없어 캡처가 전부 `-32000` 으로 실패한다(코드 주석·`Docs/20260726_064500_*` 에 이미 기록).
- JSON-RPC 13540 응답, 메인 뷰 MJPEG(13960)·카메라 채널 MJPEG(13961/13962) 모두 `serving:true`. 6초 읽기로 메인 14~15장, 카메라 1번 14장 수신, 디코드한 프레임이 정상 장면(주차장·차량·번호판)이었다. `cam.captureJPG` 도 1280×720 정상.
- 브라우저는 `<img src="http://<호스트>:13960/stream">` 한 줄로 받는다. 스트림 포트는 인증·CORS 가 없고 `0.0.0.0` 에 바인드된다(보드 #498). RPC 는 이 프로젝트가 `AllowAnonymous=True` 로 출하해 브라우저 `fetch` 도 통과한다.

## 왜 창이 없어도 되는가(코드 근거)

메인 뷰와 카메라 채널 모두 **창 백버퍼가 아니라 `USceneCaptureComponent2D` → 렌더타깃 → `ReadPixels`/비동기 리드백** 으로 캡처한다.

- 메인 뷰: `UCamStreamSubsystem::EnsureMainCapture()` 가 숨김 액터에 `MainViewCapture` 를 스폰하고, `RequestMainCapture()` 가 매 틱 `PlayerController::GetPlayerViewPoint` 로 시점만 따라간다(`CamStreamSubsystem.cpp:583`, `:829`). 화면에 그려지는 것과 무관하게 렌더타깃에 따로 그린다.
- 카메라 채널·`cam.captureJPG`·`scenario.*`: `APTZCameraActor` 의 렌더타깃을 읽는다(`CamRpcModule.cpp:152`).
- 따라서 `-RenderOffScreen` 으로 Slate 창을 안 만들어도 캡처 경로에 빠지는 것이 없다. 코드에 `GameViewport`·`FViewport` 의존이 없음을 grep 으로 확인했다.

## 웹 쪽은 이미 이 구조로 쓰고 있다(보드 자료)

보드에 **UE 헤드리스/오프스크린 실행 자체를 다룬 글은 없다**(`headless`·`RenderOffscreen`·`offscreen`·`nullrhi` 검색 — Chrome headless·Omniverse 글만 걸림). 대신 "웹에서 Park3D 렌더를 받아 쓰는" 쪽은 이미 운영 중이며 다음 글이 그 계약을 적고 있다.

## 실측 수치와 함정

이 PC(RTX 5060 Ti 8GB)에는 정본 13510 이 떠 있어 GPU 를 나눠 썼다. 같은 조건에서 창 모드와 오프스크린을 번갈아 띄운 A/B:

| 인스턴스 | 상태 | 자기 tickFps | 그때 정본 tickFps |
|---|---|---|---|
| 작업본 `-RenderOffScreen` | 창 없음 | **3.1~3.5** | 16.5 |
| 작업본 창 모드(전면) | 창 있음 | **47~48** | 2.5 |
| 정본만 | — | — | 16~20 |

**오프스크린이 느린 게 아니라, 같은 GPU 에서 전면 창을 가진 프로세스가 우선된다.** 창 없는 프로세스는 백그라운드 앱 취급을 받아 GPU 시간을 못 받는다(Windows 스케줄러 우선순위로 추정 — 원인 특정은 안 했다). 실무 함의:

1. **서버 전용 GPU 에서 혼자 돌리면 문제없다.** 오프스크린 자체의 캡처·인코딩 비용은 창 모드와 같다(`captureAvgMs` 2.3~2.5, `encodeAvgMs` 2.2).
2. 같은 PC 에 창 모드 인스턴스(정본)와 같이 두면 오프스크린 쪽이 3fps 대로 떨어진다. 둘을 같이 두려면 정본도 오프스크린으로 돌리거나 GPU 를 분리해야 한다(미검증).
3. VRAM: 인스턴스당 약 3.5~7GB. 8GB 카드에 두 개면 7.4/7.9GB 로 한계.

그 밖의 함정:

- **부트스트랩 exe 를 죽여도 자식(`Park3D/Binaries/Win64/Park3D.exe`)은 남는다.** 이 세션에서 창 모드 테스트의 고아가 13540 을 물고 있어 다음 오프스크린 인스턴스의 RPC 바인드가 조용히 실패했다(스트림 포트는 열렸는데 RPC 만 없음 — #319 와 겉모습이 같다). 종료는 자식 PID 로 할 것.
- 오프스크린에서도 `APlayerController` 와 카메라는 정상 생성된다. 메인 뷰는 `GetPlayerViewPoint` 를 따라가므로 `view.set` 으로 시점을 바꾸면 스트림도 바뀐다(코드 근거, 이번엔 호출 안 함).
- UI 패널(WBP)은 화면이 없으니 조작 불가 — 조작은 전부 RPC(175 메서드)로 한다. 패널이 하는 기능은 이미 RPC 로 올려 두었다(2026-08-14 이력).
- Windows 서비스(세션 0)로 띄우는 것은 시도하지 않았다. GPU 접근이 세션에 묶이므로 **로그인된 사용자 세션에서 `schtasks`/`Start-Process` 로 띄우는 편이 안전**하다(OmniversPark3D 의 .125 배포 #820 도 pm2-over-ssh 가 죽어 `schtasks` 로 갔다).
- 실시간 조작(마우스·키보드 왕복)까지 웹에서 하려면 MJPEG 로는 안 되고 Pixel Streaming 2 가 필요하다(플러그인 추가 → 전체 재빌드·재쿡, `Docs/20260826_185357_*` A-1).

## 이 세션에서 실제로 한 것

- 보드 검색 16개 질의(`headless`, `RenderOffscreen`, `offscreen`, `nullrhi`, `MJPEG`, `UPark3D stream`, `cam.streamStatus`, `Park3D 13600` 등) → 위 표.
- 코드: `Rpc/CamStreamSubsystem.*`, `Rpc/MjpegStreamManager.cpp`, `Rpc/Modules/CamRpcModule.cpp` 의 캡처 경로 확인.
- 실행: `Package/Work13540`(RPC 13540, 스트림 13960~13999, 정본과 포트 분리)을 오프스크린 2회·창 모드 1회 기동, `system.health`/`cam.streamStatus`/`cam.captureJPG` 호출, 13960·13961 스트림 6초 수신 후 프레임 디코드, `EnumWindows` 로 창 유무 확인, 정본은 읽기(`cam.streamStatus`)만 했다.
- 테스트 인스턴스는 모두 종료했고 정본 13510 은 손대지 않았다. 저장소 파일 변경은 이 문서뿐이다.
