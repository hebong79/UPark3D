# 차량 바퀴가 주차장 바닥에 묻히는 문제 수정 — 지면 접지(Ground Snap)

- 날짜: 2026-08-19
- 브랜치: `fix/car-wheel-ground-offset`
- 대상: `Park3D/Source/Park3D/CarActor.h`, `CarActor.cpp`, `CarPlacementWidget.cpp`

---

## 1. 증상

배치된 차량의 바퀴 아랫부분이 노면에 잘려 묻혀 보인다.

## 2. 원인 — 두 겹이었다

### (1) 데이터의 z 가 노면 높이를 모른다

`CarPos_Seoshin_2Cam.json` 23건의 `pos.z` 는 전부 `0 ~ −0.0507 m` 였다.
`ACarActor::ApplyTransformFromData` 는 이 값을 그대로 월드 Z 로 썼다.

차량 메시 23종의 로컬 바운즈 바닥(`car.catalog` 의 `boundsMin.z`)은 −0.4cm ~ 0cm 라
**메시 피벗이 사실상 바퀴 접지면**이다. 즉 액터 Z 가 곧 바퀴 바닥 Z 다.

### (2) 이 레벨의 노면은 Z=0 이 아니라 **Z=10cm** 다

`LV_Park_01` 실측:

| 대상 | Z |
|---|---|
| 노면 아스팔트(`BP_SplineMeshPlane_C_1`) | **10.0cm** |
| 주차면 블루프린트(`BP_ParkingSlot_C_*`) 콜리전 상면 | 10.1cm |
| 폴대(`BP_Pole_C_0`) 밑동 / 노면 데칼(`BP_Decal_C_5`) | 10.0cm |
| `Landscape_0` (보이지 않는 기반면) | 0cm |

따라서 데이터의 z=0 / −5cm 차량은 노면 아래 **10~15cm** 에 놓여 있었다.

원본 데이터가 음수 z 를 갖게 된 경위도 같은 뿌리다 — 차량 배치의 커서 피킹
(`ACarPlacementManager::TraceFloor`, `ECC_Visibility`)이 노면이 아니라 그 아래
`Landscape` 를 맞혀서 노면보다 낮은 좌표를 저장해 왔다.

## 3. 해법 — 물리(리지드바디)가 아니라 라인트레이스 접지

사용자가 언급한 "충돌박스/리지드바디"는 이 문제에 맞지 않는다.

- 차량은 `QueryOnly` 콜리전의 **정적 소품**이다. `SimulatePhysics` 를 켜면 65대가
  매 틱 적분되며 미끄러짐·떨림·상호 관통이 생기고, 픽셀 기반 가림률 측정
  (`scenario.*`)의 재현성이 깨진다.
- 접지는 **트레이스 1회로 결정적으로** 끝난다. 비용도 트레이스 한 번뿐이다.

`ACarActor::SnapToGround(MetersToUU)` 를 신설하고 `ApplyTransformFromData` 끝에서 부른다.

```
바닥Z = 액터Z + 메시로컬바운즈Min.Z        (루트=MeshComp, 스케일 1, 회전 yaw 뿐)
바닥Z ±100cm 구간을 아래로 라인트레이스
새 액터Z = 히트Z − 메시로컬바운즈Min.Z
CarData.pos.z 에도 되쓴다
```

### ⚠ 핵심 함정 — 채널이 아니라 **정적 오브젝트 질의**여야 한다

처음에는 프로젝트의 다른 트레이스(`view.pick`·`measure.*`)와 같은 `ECC_Visibility`
로 짰는데 **통로에서 노면을 못 찾았다**. `LV_Park_01` 의 아스팔트
(`BP_SplineMeshPlane`)는 Visibility 응답이 Ignore 라 트레이스가 그대로 통과해
10cm 아래 `Landscape` 를 맞힌다.

진단 로그(`[SnapDiag]`, 세 방식 동시 측정) 실측:

| 지점 | `ECC_Visibility` | 정적 오브젝트 질의 |
|---|---|---|
| 주차면 (19.2, 5.3) | 10.10cm — `BP_ParkingSlot` 콜리전 | 10.00cm — `BP_SplineMeshPlane` |
| 통로 (13.0, 4.0) | **0.00cm — `Landscape`** | 10.00cm — `BP_SplineMeshPlane` |
| 통로 (−7.0, 20.0) | **0.00cm — `Landscape`** | 10.00cm — `BP_SplineMeshPlane` |
| 다른 차량 위 (8.0, 16.0) | **91.29cm — 남의 차체** | 10.00cm — `BP_SplineMeshPlane` |

주차면 위에서 Visibility 가 그럴듯한 10.10cm 를 준 것이 함정이었다 — 그건 노면이
아니라 `BP_ParkingSlot` 의 콜리전이고, 주차면 밖(통로)에서는 즉시 10cm 어긋난다.
**주차된 차만 보고 판단했으면 통로·주행 차량은 계속 묻힌 채로 남았다.**

그래서 `LineTraceSingleByObjectType(AllStaticObjects)` 를 쓴다. 부수 효과로
**런타임 스폰 차량(Movable = WorldDynamic)이 질의에서 빠져** 주행 시뮬 중 차가
겹치는 순간 남의 지붕에 올라타는 사고도 원천 차단된다(위 표 4행).

### 그 외 규약

- 지면을 못 찾으면 높이를 **지어내지 않고** 데이터 z 를 유지한다
  (`view.pick` 의 `hit=false` 규약과 같은 태도). Verbose 로그만 남긴다.
- 0.1cm 미만 차이는 옮기지 않는다 — 시뮬 주행은 매 틱 `ApplyTransformFromData` 를
  타므로 미세 진동을 막는다.
- 보정한 z 를 `CarData.pos.z` 에도 되쓴다. 안 그러면 `car.list`·저장 파일이 화면과
  다른 값을 보고한다. **저장하면 파일의 잘못된 z 도 함께 고쳐진다.**
- 화살표 그룹 이동(`UCarPlacementWidget::ApplyGroupTranslation`)은
  `ApplyTransformFromData` 를 거치지 않는 유일한 이동 경로라 거기서도 직접 부른다.

`UPROPERTY` 는 추가하지 않았다(쿠킹된 자산의 C++ 베이스에 `UPROPERTY` 를 더하면
패키지가 `Bad export index` 로 즉사한 전례). 트레이스 구간·허용오차는
`static constexpr` 로 뒀다.

## 4. 검증

`Package/Work13530` 에 패키지를 복제하고 exe 만 교체해 별도 포트
(RPC 13530 / 메인뷰 13800 / 카메라 13811~13850)로 기동했다. 사용자 실행본(13510)은
건드리지 않았다.

**수치** — `car.list` 23대의 `pos.z`

| | 최소 | 최대 |
|---|---|---|
| 수정 전(파일 값 그대로) | −0.0507 | 0.0000 |
| 수정 후 | **0.1003** | **0.1027** |

수정 후 값의 편차(2.4mm)는 노면 10.00cm + 차종별 `boundsMin.z` 이며 의도한 결과다.

**통로 접지** — 같은 차를 통로 세 곳으로 옮겨 확인

| 지점 | Visibility 판(중간 빌드) | 최종 |
|---|---|---|
| (13.0, 4.0) | 0.0018 | **0.1018** |
| (−7.0, 20.0) | 0.0018 | **0.1018** |
| (0.0, 0.0) | 0.0018 | **0.1018** |

**시각** — 같은 시점에서 A/B 촬영(메인 뷰 MJPEG). 수정 전에는 타이어 밑동이 노면에
평평하게 잘려 있었고, 수정 후에는 둥근 접지면이 전부 드러난다. 통로에 세운 차량도
동일하게 확인했다.

**자동화 테스트** — 이번 세션에서는 실행하지 않았다(에디터 미기동). 다만 영향 가능성이
있는 두 테스트는 코드상 무영향이 확정된다:
- `CarActorTest.ActorTransformRoundTrip` : `InitFromPos(In, nullptr, ...)` — 메시가 없어
  `SnapToGround` 가 첫 가드에서 false 로 빠진다.
- `CarPlacementManagerTest.ManagerRebuild` : 빈 카탈로그로 스폰 — 역시 메시가 없다.

## 5. 남긴 한계

- `AMapFloorActor`(코드가 까는 단색 바닥, `map_floor:true` 인 빈 부트 맵용)는
  `NoCollision` 이라 트레이스에 안 잡힌다. 그 레벨에서는 `Landscape`(Z=0)에 앉으므로
  바닥면(`FloorZ=2cm`)보다 2cm 낮다. 콜리전을 켜는 것은 과거 영향분석(H-1)에서
  커서 피킹이 바닥을 히트해 좌표가 드리프트한다는 이유로 배제된 바 있어 손대지 않았다.
- 차량 배치의 커서 피킹(`TraceFloor`)은 여전히 `ECC_Visibility` 라 노면보다 낮은
  좌표를 만든다. 다만 스폰 직후 접지가 이를 덮으므로 화면상 문제는 없다.
- `Save/3D/CarPos/*.json` 의 기존 음수 z 는 손대지 않았다. 런타임 접지가 매번 고치고,
  저장하면 고쳐진 값이 파일에 남는다.
