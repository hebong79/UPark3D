# MCP 서버는 API 서버와 패킷을 주고받을 수 있나?

- 작성일: 2026-08-03 23:26:39
- 분류: 질문 답변 (코드 변경 없음)

## 1. 한 줄 답변

**가능하다.** MCP 서버는 그냥 하나의 프로세스이므로, 자기가 원하는 어떤 API 서버(REST/gRPC/WebSocket/JSON-RPC)에도 아웃바운드로 패킷을 보낼 수 있다.
오히려 그것이 MCP 서버의 대표적인 용도다 — "외부 API를 LLM이 쓸 수 있는 툴로 감싸는 어댑터".

## 2. 방향별 정리

| 방향 | 가능 여부 | 설명 |
|------|-----------|------|
| MCP 서버 → 외부 API 서버 | ✅ 자유롭게 가능 | 서버 내부에서 http 클라이언트로 호출. LLM은 결과만 툴 응답으로 받음 |
| MCP 클라이언트(Claude) → MCP 서버 | ✅ MCP 프로토콜로만 | JSON-RPC 2.0 기반, stdio 또는 Streamable HTTP 전송 |
| MCP 클라이언트(Claude) → 임의의 API 서버 직접 | ❌ 불가 | 중간에 MCP 서버(브리지)가 반드시 필요 |
| MCP 서버 → 클라이언트 (역방향) | ⚠️ 제한적 | 진행률/로그 알림, sampling(LLM 호출 요청), elicitation(사용자 입력 요청) 등 프로토콜이 정의한 것만 |

## 3. 핵심 구분 — "MCP ≠ JSON-RPC HTTP"

MCP 자체가 JSON-RPC 2.0을 쓰지만, **아무 JSON-RPC HTTP 서버나 MCP 서버로 인식되지는 않는다.**
MCP는 `initialize` 핸드셰이크, `tools/list`, `tools/call`, capability 협상 같은 규약을 요구한다.
그래서 "JSON-RPC를 쓰니까 그냥 붙겠지"는 성립하지 않는다.

## 4. 이 프로젝트에서의 실제 사례

Park3D가 정확히 이 구조다.

```
Claude Code  --(MCP: stdio/JSON-RPC)-->  park3d-rpc 브리지  --(HTTP JSON-RPC 2.0)-->  Park3D 인스턴스(13110/13120)
   MCP 클라이언트                          MCP 서버 = API 클라이언트                        API 서버
```

- Park3D의 JSON-RPC HTTP 서버(포트 13110)는 MCP 서버가 **아니다** → Claude에 직접 못 붙였다.
- 그래서 `park3d-rpc` 브리지(툴 2개: `park3d_catalog`, `park3d_rpc`)를 만들어 중간에 뒀다.
- 이 브리지가 바로 "MCP 서버가 API 서버와 패킷을 주고받는" 실물 예시다.

## 5. 주의할 점

1. **네트워크는 MCP 서버가 실행되는 호스트 기준** — 브리지가 로컬에 있어야 `localhost:13110`에 닿는다.
2. **인증 정보는 MCP 서버 쪽에 둔다** — API 키를 LLM 컨텍스트에 넣지 말 것. 서버가 보관하고 호출 시점에 붙인다.
3. **대용량 응답은 요약/필터해서 반환** — 툴 응답은 전부 컨텍스트를 소모한다. Park3D 캡처처럼 바이너리는 base64라 특히 크다.
4. **타임아웃 설계** — MCP 툴 호출은 동기적으로 대기한다. 느린 API는 브리지 쪽에서 타임아웃을 걸어야 한다.
5. **원격 MCP 서버 자체가 HTTP 서버일 수 있다** — Streamable HTTP 전송을 쓰면 MCP 서버가 곧 API 서버 형태가 되고, 이때는 OAuth 등 인증을 붙인다.
