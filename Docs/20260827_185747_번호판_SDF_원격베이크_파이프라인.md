## 0. 한 줄 요약

로컬 `bake_glyph_sdf.py` 44글자 베이크를 GPU 서버(RTX 3090)로 넘겼다.
**로컬 39~76초 → 클라이언트 실측 1.8~2.5초**(서버 계산 1.32~1.43초)이고,
아틀라스 PNG 는 **3,145,728 픽셀 전부 일치(다른 픽셀 0개, 최대차 0)**, 메트릭 JSON 도 `atlas` 파일명 필드만 빼고 전부 같다.

다만 **이 작업은 폰트를 바꿀 때만 1회 도는 것**이라 실익은 개발 반복 속도에 한정된다(§7).

## 2. API

인증 없음. 모두 `http://192.168.0.210:8090` 기준.

### `GET /health`

```json
{"status":"ok","service":"park3d-plate-bake","version":"1.0.0",
 "device":"cuda","deviceNote":"","gpus":["NVIDIA GeForce RTX 3090","NVIDIA GeForce RTX 3090"],
 "torch":"2.11.0+cu130","numpy":"2.2.6","pillow":"12.1.0","freetype":"2.14.1",
 "raqm":"0.10.3","layoutEngine":"BASIC(고정)","jobs":0}
```

`device` 는 **지금 실제로 쓸 장치**다. CUDA 를 못 잡으면 `"cpu"` 와 함께 `deviceNote` 에 사유가 적힌다.

### `POST /bake` — multipart/form-data

| 필드 | 기본 | 뜻 |
|------|------|----|
| `font` | (필수) | TTF/OTF **파일 본문**. 서버에 폰트를 상주시키지 않는다 |
| `glyphs` | 숫자10+한글24 | 구울 글자 집합 |
| `cell` / `cols` / `baseline` | 256 / 6 / 200 | 아틀라스 셀·열·베이스라인 |
| `spread` / `ss` | 8.0 / 4 | 거리장 반경(셀px) · 슈퍼샘플 배율 |
| `font_size` | 166 | 셀px 기준 em |
| `label` | 파일명 | metrics.json 의 `font` |
| `device` | `auto` | `auto` \| `cuda` \| `cpu` |
| `batch` | 8 | GPU 한 번에 처리할 글리프 수 |

응답 `{"jobId":"...","state":"queued","total":44}` — **즉시 반환하고 백그라운드 스레드가 굽는다.**

### `GET /bake/{job_id}`

```json
{"jobId":"b8e5...","state":"done","progress":1.0,"done":44,"total":44,
 "fontSha256":"a19e3ead...","elapsed":1.321,"device":"cuda",
 "gpuName":"NVIDIA GeForce RTX 3090","atlasSize":[1536,2048],"warnings":[]}
```

`state` ∈ `queued|running|done|error`. `error` 면 `error` 필드에 사유가 들어간다.
`fontSha256` 은 "클라이언트가 가진 그 파일로 구웠다"의 증거다.

### `GET /bake/{job_id}/result`

`atlas.png` + `metrics.json` 이 든 zip. `done` 이 아니면 409.

### `DELETE /bake/{job_id}`

작업 폴더 삭제.

### 사용 예시 한 줄

```bash
curl -s -X POST http://192.168.0.210:8090/bake -F "font=@suseong.ttf" -F "label=Suseong Dotum"
```

## 4. 수치 일치를 어떻게 지켰나

목표는 "비슷하다"가 아니라 **로컬 산출물과 비트 단위로 같다**였다. 세 가지를 했다.

### 4.1 래스터·평균·양자화 꼬리는 원본 코드를 그대로 옮겼다

GPU 로 바꾼 것은 **거리변환(`edt2d`) 하나뿐**이다. Pillow 래스터, `box_mean`, `clip`,
`(atlas*255+0.5).astype(uint8)` 은 원본 문자열 그대로 numpy(CPU)로 돈다.
GPU 에서 돌아온 `sd` 를 CPU 로 내려 원본 꼬리에 그대로 먹인다.
그러면 부동소수 합산 순서가 달라져 마지막 반올림이 ±1 튀는 사고가 원천봉쇄된다.

### 4.2 GPU 거리변환은 "빠른 근사"가 아니라 같은 값을 내는 다른 계산 순서다

- **가로 패스**는 원본 루프(`dx` 시프트 + `min`)를 그대로 torch 로 옮겼다.
- **세로 패스**만 바꿨다. 원본은 전/후 누적 min-plus 스캔 뒤 `big=radius+1` 로 클램프하는데,
  그 결과는 정확히 `min(같은 열 최근접 True 까지의 행 거리, big)` 이다.
  같은 값을 `dy ∈ [-radius, radius]` 창(窓) min 으로 낸다 — 창 밖이면 거리가 `radius+1` 이상이라
  어차피 클램프에 먹히므로 두 방식의 결과가 **정의상 같다**.
  1024회 순차 스캔이 81회 전체배열 연산으로 바뀌어 GPU 에 맞는다.
- 모든 중간값은 41 이하의 **정수**를 담은 float32 라 min/add 에 오차가 없고,
  마지막 `sqrt` 는 numpy·CUDA 둘 다 IEEE 정확반올림이라 비트까지 같다.

### 4.3 함정 — 서버 Pillow 에는 raqm 이 붙어 있다

| | 로컬 | 서버 |
|---|---|---|
| Pillow | 12.1.0 | 12.1.0 |
| freetype | 2.14.1 | 2.14.1 |
| **raqm** | **없음** | **0.10.3** |

`ImageFont.truetype()` 은 raqm 이 있으면 레이아웃 엔진 기본값이 **RAQM 으로 바뀐다**.
그러면 `getlength`(어드밴스)와 글자 배치가 로컬(BASIC)과 달라져 일치가 깨진다.
→ `sdf_core.load_font()` 에서 `layout_engine=ImageFont.Layout.BASIC` 을 **명시**해 못 박았다.
`/health` 의 `layoutEngine: "BASIC(고정)"` 이 그 사실을 노출한다.

Pillow 버전도 `setup_server.sh` 에서 `Pillow==12.1.0` 으로 고정한다 — 래스터가 달라지면 일치가 깨진다.

## 5. 일치 검증 결과 (실측)

기준선은 이 세션에서 로컬 `bake_glyph_sdf.py` 를 다시 돌려 만들었고,
저장소에 이미 있던 `Tools/plate_sdf/out/{pretendard,suseong}_sdf.png`·`_metrics.json` 과
**바이트까지 같음을 먼저 확인**했다(기준선 자체가 흔들리지 않음을 보장).

| 비교 | 아틀라스 크기 | 다른 픽셀 | 최대 절대차 | metrics.json |
|------|--------------|-----------|-------------|--------------|
| pretendard\_bold — 로컬 vs 원격 **GPU** | 1536×2048 = 3,145,728 px | **0** | **0** | `atlas` 필드 외 전부 동일 |
| suseong — 로컬 vs 원격 **GPU** | 3,145,728 px | **0** | **0** | 동일 |
| suseong — 로컬 vs 원격 **CPU**(`device=cpu`) | 3,145,728 px | **0** | **0** | 동일 |

폰트 sha256: `pretendard_bold.ttf` `c16b88c6…`, `suseong.ttf` `a19e3ead…`.

메트릭의 유일한 차이는 `"atlas"` 값(`"pretendard_sdf.png"` vs `"atlas.png"`)이고,
클라이언트가 실제 저장 파일명으로 고쳐 쓰므로 최종 산출물에는 남지 않는다.
44개 글리프의 `char`/`col`/`row`/`advance`/`boxX0` 는 한 항목도 다르지 않았고,
`spaceAdvance`(49.75 / 38.25)도 같다.

**PNG 파일 크기는 다르다** — 로컬 123,902 B vs 원격 127,294 B(suseong).
zlib 구현/설정이 Windows 휠과 manylinux 휠에서 달라 **압축 바이트열이 다를 뿐 디코드한 픽셀은 동일**하다.
따라서 산출물 비교는 파일 해시가 아니라 **디코드 후 픽셀 비교**로 해야 한다.

변동의 원인은 이 PC 에서 **`Park3D.exe` 2개와 `UnrealEditor-Cmd.exe` 가 동시에 돌고 있는 것**이다

3회 반복, 서버 계산 시간과 클라이언트 벽시계 시간을 따로 쟀다.

|---|---|---|---|---|
| 1 | suseong | 1.346 s | 2.056 s | 123,392 B |
| 1 | pretendard | 1.404 s | 2.101 s | 118,611 B |
| 2 | suseong | 1.427 s | 2.510 s | |
| 2 | pretendard | 1.359 s | 1.828 s | |
| 3 | suseong | 1.357 s | 1.998 s | |
| 3 | pretendard | 1.426 s | 1.869 s | |

**서버 1.32~1.43초, 클라이언트 총 1.83~2.51초.** 차이 약 0.5~1.1초가 폰트 업로드(1.8~2.7MB) +
`/health` + 폴링 + zip 다운로드다. 원격은 로컬과 달리 **회차 간 변동이 거의 없다**(전용 머신).

### 6.3 서버 안에서의 내역 (suseong, 44글자)

| 단계 | 시간 | 장치 |
|---|---|---|
| Pillow 래스터 44자 | 0.078 s | CPU |
| **거리변환 44자** | **1.001 s** | **GPU (RTX 3090)** |
| 같은 거리변환을 서버 CPU 로 | 10.39 s (4자 0.944 s 환산) | CPU |
| 나머지(평균·양자화·PNG·zip) | ≈ 0.25 s | CPU |

- **GPU 가 거리변환에서 얻은 배속은 10.4×** (서버 CPU 대비).
- VRAM 최대 사용 285 MB — 24GB 카드에서는 배치를 훨씬 키울 수 있지만 의미가 없다(§7).
- 서버에서 `device=cpu` 로 강제하면 전체 10.35초. 즉 **로컬(39~76초) → 원격 CPU(10.4초) → 원격 GPU(1.35초)** 로,
  전체 배속의 상당 부분이 GPU 가 아니라 **서버 CPU 가 개발 PC 보다 빠르고 한가한 데서** 온다.
  이걸 GPU 공로로 적으면 거짓말이 된다.

## 7. 정직한 평가 — 이게 값어치가 있나

**있다. 다만 크지 않다.**

- 이 베이크는 **폰트를 바꿀 때만 도는 1회성 작업**이다. 최종 산출물은 텍스처 1장 + JSON 1개고,
  한 번 구우면 런타임은 그걸 읽기만 한다. 파이프라인이 하루에 수백 번 도는 종류가 아니다.
- 그래서 절약되는 절대 시간은 **회당 40~130초**다. 폰트 후보를 비교하며 굽는 단계(지금이 그렇다)에서는
  "굽고 보고 고치고 다시 굽는" 반복이 60초에서 2초로 줄어드는 게 체감되지만,
  폰트가 확정된 뒤에는 사실상 쓸 일이 없다.
- **GPU 자체의 기여는 전체 배속의 일부다**(§6.3). 개발 PC 가 UE 3개를 돌리느라 느린 것이
  로컬 시간의 절반 이상을 설명한다. 서버 CPU 로만 돌려도 10초다.
- 반면 얻은 것 중 시간과 무관한 게 하나 있다 — **개발 PC 의 CPU 를 44글자 거리변환에 60초 동안
  빼앗기지 않는다.** UE 에디터·패키지 2개가 도는 상태에서 이건 무시할 수 없다.
- 결론: **"빨라서" 쓸 만하다기보다 "내 PC 를 안 막아서" 쓸 만하다.**
  로컬 폴백이 항상 살아 있으므로 서버가 없어도 작업이 멈추지 않는다.

## 8. 한계 · 미검증

정직하게 적는다.

1. **재부팅 후 자동 기동을 실제 재부팅으로 확인하지 않았다.**
   `systemctl --user is-enabled` = enabled, `Linger=yes` 는 확인했고 `restart` 후 정상 기동도 확인했지만,
   서버를 실제로 재부팅해 보지는 않았다(공용 머신이라 임의로 못 내린다).
2. **작업 상태는 프로세스 메모리에만 있다.** 서비스가 재시작되면 진행 중이던 job 은 사라지고
   `GET /bake/{id}` 가 404 를 준다(`jobs/` 폴더의 파일은 남는다). 1회성 작업이라 감수했다.
3. **동시 실행은 1건으로 묶었다**(`Semaphore(1)`). GPU 가 2장이지만 두 번째 카드는 쓰지 않는다.
   VRAM 285MB 라 여유는 많지만, 동시 실행은 소요시간 측정만 흐리고 얻는 게 없다고 판단했다.
4. **정확도 검증은 두 폰트(pretendard\_bold, suseong)의 기본 인자 조합에서만 했다.**
   `cell`/`spread`/`ss`/`baseline` 을 바꾼 조합은 원격끼리도, 로컬 대비로도 비교하지 않았다.
   특히 **로컬 `bake_glyph_sdf.py` 는 이 인자들을 CLI 로 받지 않으므로**(모듈 상수) 그 조합은
   애초에 로컬과 비교할 방법이 없다. 클라이언트는 기본값이 아닌 값을 주고 폴백이 걸리면
   "로컬 베이커는 이 인자를 안 받는다"고 stderr 로 경고한 뒤 기본값으로 굽는다.
5. **`glyphs` 를 바꾼 경우도 미검증이다.** 서버는 임의 글자 집합을 받지만 로컬 폴백은 못 받는다.
6. **네트워크 실패 재시도가 없다.** 폴링 중 일시적 오류가 나면 그대로 폴백(또는 `--no-fallback` 이면 중단)이다.
7. **torch 를 `~/vllm-env` 에 의존한다.** 누가 그 venv 를 지우면 이 서비스의 CUDA 경로가 죽고
   `/health` 가 `device:"cpu"` 로 바뀐다(조용히 죽지는 않는다 — CPU 폴백은 결과가 동일함을 §5 에서 확인했다).
8. **저장소 파일은 새로 추가만 했다.** `bake_glyph_sdf.py` 를 비롯한 기존 스크립트, `Park3D/Source`,
   `Park3D/Content` 는 손대지 않았다. 검증 중 `Park3D/Save/Config/plate_glyph_metrics.json` 을
   클라이언트 기본 경로 시험으로 1회 덮었다가 **원본 바이트 그대로 복원**했다(`cmp` 로 확인).
