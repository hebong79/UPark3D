# Korean Docs — 한글 문서화 스킬

CLAUDE.md 3번 규칙을 수행한다. **코드 변경뿐 아니라 사용자 질문에 대한 답변도** 문서로 남긴다.

## 필수 규약 (위반 금지)
| 항목 | 규칙 |
|------|------|
| 파일명 | `yyyyMMdd_HHmmss_이름.md` (예: `20260619_161500_마우스커서_버벅임_수정.md`) |
| 위치 | `Docs/` 폴더 |
| 인코딩 | UTF-8 |
| 언어 | 한글 |

## 타임스탬프 생성
추측하지 말고 실제 시각을 조회한다:
- PowerShell: `Get-Date -Format "yyyyMMdd_HHmmss"`
- Bash: `date +%Y%m%d_%H%M%S`

## 문서 구조 (기존 Docs/*.md 관례 계승)
```markdown
# {제목}

- 작성일시: yyyy-MM-dd HH:mm:ss
- 작성자: {실제 실행 플랫폼 / 역할 / 모델}
- 참고: {관련 원본/설계 자료}
- 선행: [{이전 문서 제목}]({이전_파일명}.md)   ← 후속 작업이면 링크
- 스크린샷: `Docs/shots/{파일}.png`             ← 있으면

---

## 1. 신규/변경 파일
| 파일 | 차수 | 내용 |

## 2. {로직/기능} 상세
- 핵심 로직, 알고리즘, 좌표/단위 규약 설명

## 3. JSON 스키마 / 파이프라인   ← 해당 시
```json
...
```

## 4. 영향도 / 검증 결과         ← impact-analyst, qa-verifier 산출물 반영
```

## 질문 답변 문서
사용자 질문에 답한 경우에도 같은 형식·경로로 저장한다. 제목을 `{질문주제}_답변` 등으로 명확히 한다.

## 표준 작업의 독립 주변 동작 사후점검

표준 구현 작업의 doc-writer는 최종 문서 작성 전에 호환 경로 `_workspace/{phase}_luna_behavior_impact_report.md`를 작성한다. 파일명의 `luna`는 기존 소비자 호환을 위해 유지하며 특정 플랫폼 모델을 강제하는 공통 계약이 아니다. 변경 지점의 인접 호출, UI/입력, JSON·저장/로드, 렌더·액터 상태 중 해당 경계면을 선택해 Automation/PIE 결과, 로그, 스크린샷, 참조 근거와 교차한다.

- 결과는 통과/실패/미검증과 근거를 함께 기록한다.
- 기능 코드를 직접 수정하지 않는다. 실패 또는 높은 위험은 오케스트레이터가 구현/QA 단계로 되돌리도록 즉시 보고한다.
- Goal/Loop에는 이 별도 점검을 적용하지 않는다. 설계·영향도·개발·QA 역할이 각 단계의 판단을 담당하며 doc-writer는 모든 조건 통과 뒤 최종 문서화만 한다.

## 작성 원칙
- 팀원(implementer/qa/impact) 산출물을 종합해 작성한다. 정보가 부족하면 추측하지 말고 해당 에이전트에 보강 요청.
- 검증 결과(통과/실패/미검증)와 영향도(위험도)를 사실대로 반영한다.
- 작성자·플랫폼·모델은 실제 실행 주체에서 주입하고 공유 템플릿 값을 그대로 복사하지 않는다.
- 최종 산출물은 `Docs/`에 저장하고, 경로를 오케스트레이터에 보고한다.
