## 1. 요구사항

1. 카메라 스트림 포트 대역(`min`/`max`)을 `DefaultGame.ini` 가 아니라 `config_pmaker.json` 에서 관리한다.
2. 포트 부여 방식(camId 1 = min, camId 2 = min+1 …)은 지금과 동일하게 유지한다.
3. 카메라 대수가 대역을 넘으면 **config 파일을 수정해서** 대역을 넓힌다.
4. 대수 확인 시점은 **카메라위치 파일 로딩 시**와 **저장 시**.

## 2. 설정 형식

`Park3D/Save/Config/config_pmaker.json`:

```json
{
    "rpc_port": 13510,
    "preset_file": "001_Preset_Seo_1.json",
    "carpos_file": "CarPos_Seoshin_2Cam.json",
    "camerapos_file": "CamPos_Seosin.json",
    "max_zoom": 36.0,
    "cam_port_min": 13601,
    "cam_port_max": 13610
}
```

`cam_port_min`/`cam_port_max` 는 **둘 다 있어야** 적용된다. 하나만 있으면 "미지정"으로 취급하고
`DefaultGame.ini` 값(`BasePort=13600`, `MaxCameras=10`, 즉 13601~13610)으로 폴백한다.
유효 조건은 `2 <= min <= max <= 65535`(`min=1` 은 내부 `BasePort` 가 0 이 되어 `ResolvePort` 가 거부하므로 막는다).

포트 계산은 기존 `ResolvePort(BasePort, CamId, MaxCameras)` 를 그대로 쓴다. `BasePort = min-1`,
`MaxCameras = max-min+1` 로 환산해 넣으므로, 기본 config(13601~13610)에서는 `BasePort=13600,
MaxCameras=10` 으로 지금과 완전히 같다.

## 4. 처리 흐름

### 4.1 기동 시 우선순위

```
DefaultGame.ini (BasePort=13600, MaxCameras=10)
  → config_pmaker.json 로드
  → cam_port_min/max 둘 다 유효하면 PortRangeToBase 로 환산해 덮어씀
  → 로그: [CamStream] 포트 대역 min~max (출처: config_pmaker.json|DefaultGame.ini, 최대 N대)
```

`config_pmaker.json > DefaultGame.ini` 순서로, 선행 기능의 `rpc_port` 우선순위 규약과 동일하다.

### 4.2 확장 시점

```
UCameraControlWidget::LoadFromJsonFile  (파일 열기 + 시작 자동 로딩 공용 경로)
UCameraControlWidget::HandleSave        (카메라위치 파일 저장)
    → EnsureCamStreamPortRange(카메라 대수)
        → CamCount <= MaxCameras 면 아무 것도 하지 않음
        → 아니면 ExtendedMaxPort 로 새 상한 계산(65535 클램프) → 메모리 즉시 반영
        → bDisabled(-NoCamStream 등)면 config 를 건드리지 않고 종료
        → UpdateCamPortRange(Path, MinPort, NewMaxPort) 로 min·max 둘 다 기록
```

채널 개설 자체는 기존대로 Tick 의 `SyncChannels` 가 담당한다. 이 함수는 **상한만** 올린다.
축소는 하지 않는다(카메라가 줄어도 `cam_port_max` 는 되돌리지 않음 — 설계 §4.3, 사용자가 넓혀둔
대역을 앱이 말없이 좁히지 않기 위함).

## 5. 결함 발견·수정 경위

**사후 영향도 분석(impact-analyst)에서 구현 결함 2건이 발견되어 되돌려 고쳤다.** 최초 구현·1차 유닛테스트·
1차 실행검증은 모두 이 결함을 잡지 못했고, 사후 영향도 단계에서 코드를 전수 대조하며 드러났다.

### H1 — `cam_port_min` 이 없는 config 에서 확장이 재기동에 사라짐

최초 구현의 `UpdateCamPortMax(Path, NewMax)` 는 `cam_port_max` **한 키만** 기록했다. 그런데
`FromJson` 은 `cam_port_min`/`cam_port_max` **두 키가 모두 있어야** 대역을 적용한다. 따라서
`cam_port_min` 이 아예 없는 config(패키지 배포본이 정확히 이 상태)에서 대역을 넓히면 `cam_port_max`
만 새로 생기고, 다음 기동에서 `HasValidCamPortRange()` 가 `CamPortMin==0` 으로 false 를 반환해
확장이 **조용히 사라진다**. 로그는 매번 "config 갱신 성공"으로 찍혀 사용자가 원인을 알 수 없는
무한 반복에 빠질 수 있었다.

1차 유닛테스트(T10)와 1차 실행검증은 둘 다 `cam_port_min` 이 **이미 있는** config 로만 확인해
이 경로를 덮지 못했다.

**수정**: `UpdateCamPortMax(Path, NewMax)` → `UpdateCamPortRange(Path, NewMin, NewMax)` 로 바꿔
두 키를 항상 함께 기록한다. `EnsurePortRangeForCameras` 는 이미 `MinPort = BasePort+1` 을 알고
있으므로 이를 함께 넘긴다.

### H3 — 인코딩 미지정으로 인한 UTF-16 오염

`SaveStringToFile(Out, *Path)` 에 인코딩 인자가 없어 기본값 `AutoDetect` 가 적용됐다. 엔진 구현상
비-ASCII 문자가 하나라도 있으면 파일 전체가 UTF-16LE+BOM 으로 바뀐다. `config_pmaker.json` 의
`camerapos_file` 에는 한글 파일명이 실제로 들어갈 수 있다(예: `CamPos_40Face_동대문.json`). 이는
저장소 관례(`Light/LightControlLibrary.cpp:118`, `Map/MapFloorLibrary.cpp:54` 가 이미
`ForceUTF8WithoutBOM` 을 명시)와도 어긋났다.

**수정**: `FFileHelper::EEncodingOptions::ForceUTF8WithoutBOM` 을 명시.

### 함께 처리한 항목

- **M2**: `bDisabled`(`-NoCamStream` 또는 `bEnabled=false`)일 때 `EnsurePortRangeForCameras` 가
  대역 확장·config 기록을 하지 않도록 조기 반환을 추가했다. 스트리밍을 진단·성능 목적으로 꺼둔
  상태에서까지 config 파일이 변조되던 것을 막았다.
- **M4**: `EnsurePortRangeForCameras` 가 성공 여부와 무관하게 항상 `true` 를 반환하던 구조는
  그대로지만, 호출부(`CameraControlWidget::EnsureCamStreamPortRange`)의 화면 알림 문구에서
  "(config 갱신)" 이라는 **단정적 표현을 제거**했다. config 기록 성공/실패는 여전히 `UE_LOG`
  레벨(Log/Warning)로만 구분되고, 화면 알림은 "대역을 넓혔습니다"까지만 말한다.

## 8. 남은 결정 사항 — H2 (사용자 결정 대기)

**앱이 git 추적 파일인 `config_pmaker.json` 을 자동으로 덮어쓴다.** 이는 요구사항 3("config 를 수정해서
쓴다")이 의도한 동작이지만, 부작용이 있다:

- 에디터/PIE 실행 중에는 카메라가 많은 파일을 **열기만 해도** config 가 바뀌어 `git diff` 에 뜬다.
  저장 버튼을 누를 필요조차 없다 — `LoadFromJsonFile` 호출만으로 트리거된다.
- 시작 자동 로딩(선행 기능)과 결합하면서 이 성질이 더 눈에 띄게 됐다 — **앱을 켜기만 해도** 추적
  파일이 바뀔 수 있다(`camerapos_file` 이 대역을 넘는 파일을 가리키면).
- 실제로 이번 사후 영향도 분석 도중 이 경로가 실증됐다 — 분석 시작 시점의 `git diff` 가 config
  전체가 변조된 상태였고(대역 확장 + 서식 변화), QA 가 백업본으로 수동 복원해야 했다.

이 문서 작성 시점까지 **사용자 결정은 아직 없다.** 해결된 것으로 간주하지 않는다. 검토가 필요한
선택지(참고용, 이번 작업에서 결정하지 않음):
- 현행 유지(요구사항대로, git 관리 대상에서 `config_pmaker.json` 을 제외하는 방향 검토)
- config 파일을 두 종류로 분리(배포용 읽기 전용 + 런타임 상태 파일)
- 확장 기록 시점을 명시적 사용자 조작(저장 버튼)으로만 제한(로딩 시 자동 기록은 하지 않음)

우선순위 순(영향도 §9 인용, 위험도 기준):
