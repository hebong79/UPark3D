# 질문: 언리얼 Park3D 실행파일(패키지 exe)이 MCP와 연결되나?

작성일: 2026-07-28
대상: `Package/Windows/Park3D.exe`, `park3d-rpc-mcp/server.py`, `.mcp.json`

---

## 결론

**연결된다. 에디터 없이 패키지 exe만 띄워도 MCP로 완전히 제어된다.** 실측으로 catalog 조회 79개, 읽기·쓰기 도메인 메서드, 카메라 캡처까지 모두 성공했다.

---

## 1. 연결 구조

Claude/Codex는 MCP만 말하고 Park3D는 JSON-RPC over HTTP만 말한다. 둘은 **다른 프로토콜**이라 직접 붙지 않고, 사이에 브리지가 있다.

```
Claude Code
   │  MCP (stdio)
   ▼
park3d-rpc-mcp/server.py          ← 브리지. 툴 2개만 노출
   │  HTTP POST /rpc , GET /rpc/catalog
   ▼
http://localhost:13120            ← PARK3D_RPC_URL (.mcp.json)
   │
   ▼
Park3D.exe 안의 URpcServerSubsystem
```

브리지가 노출하는 툴:

| MCP 툴 | 하는 일 |
|---|---|
| `park3d_catalog` | 등록된 메서드 이름 목록(GET `/rpc/catalog`) |
| `park3d_rpc(method, params)` | 메서드 1개 호출(POST `/rpc`) |

**핵심**: `URpcServerSubsystem`은 `GameInstanceSubsystem`이다. 즉 **에디터가 아니라 게임 인스턴스에 붙는다.** 그래서 PIE·`-game`·패키지 exe 어디서든 동일하게 뜨고, 반대로 **에디터를 그냥 열어놓기만 해서는 안 뜬다**(아래 3절).

## 2. 실측 검증

`Package/Windows/Park3D.exe`를 옵션 없이 실행(포트는 `DefaultGame.ini [RpcServer] Port=13120`).

| 검증 | 경로 | 결과 | 판정 |
|---|---|---|---|
| 포트 리슨 | `Get-NetTCPConnection 13120` | PID → `Package/Windows/Park3D/Binaries/Win64/Park3D.exe` | 통과 |
| 헬스체크 | HTTP `GET /health` | `{"ok": true}` | 통과 |
| 미등록 메서드 처리 | `app.ping` | `-32601 미등록 method: app.ping` | 통과(정상 거절) |
| **MCP catalog** | `park3d_catalog` | `ok:true`, 메서드 **79개** | 통과 |
| **MCP 읽기** | `park3d_rpc("map.get")` | `{sizeX:160, sizeZ:160}` | 통과 |
| **MCP 쓰기** | `park3d_rpc("preset.create", {offset:{x:0,y:0,z:0}, faceCount:6})` | `idx:1, presetName:"Preset_001", faceCount:6` | 통과 |
| **MCP 삭제** | `park3d_rpc("preset.delete", {idx:1})` → `preset.list` | `ok:true` → `[]` | 통과 |
| 카메라 생성 | `park3d_rpc("cam.create")` | `camId:1` | 통과 |
| **캡처(실 RHI)** | `cam.captureJPG {camId:1, width:320, height:180}` | `img_bytes` base64 59,932자 + width/height/format/camId | 통과 |

> 캡처는 base64가 커서 컨텍스트 오염을 피하려고 MCP가 아닌 HTTP로 직접 호출해 길이만 확인했다. 경로는 동일하다.

**캡처가 되는 게 중요한 이유**: `-nullrhi` 헤드리스에서는 캡처가 `-32000`으로 실패한다. 패키지 exe는 실제 RHI(DX12 SM6)로 뜨므로 캡처가 정상 동작한다. 즉 **화면을 눈으로 확인하는 시각 검증 루프를 패키지 exe로 돌릴 수 있다.**

## 3. 주의사항 (중요)

### 3-1. 에디터를 켜 놓은 것만으로는 13120이 안 열린다
확인 시점에 에디터(PID 9868)가 점유한 포트는 **8000(Unreal MCP 플러그인)** 뿐이었고 13120은 비어 있었다. `URpcServerSubsystem`은 GameInstance 소속이라 **PIE를 눌러 게임이 돌아야** 뜬다. 그래서 `park3d_rpc` 호출이 "연결 실패"로 나오면 대개 원인은 다음 둘 중 하나다.

1. 게임(PIE 또는 패키지 exe)이 안 떠 있음
2. 포트가 다름

### 3-2. 에디터 PIE와 패키지 exe는 같은 포트(13120)를 쓴다 — 동시 실행 시 충돌
둘 다 `DefaultGame.ini`의 같은 값을 읽는다. 먼저 뜬 쪽이 13120을 잡고, 나중 쪽은 바인드에 실패한다. **동시에 쓰려면 한쪽을 다른 포트로:**

```
Park3D.exe -RpcPort=13130
```

커맨드라인이 config보다 우선한다. 단, `.mcp.json`의 `PARK3D_RPC_URL`은 13120 고정이므로 **MCP가 붙는 쪽이 13120을 잡아야 한다.**

### 3-3. 도메인 메서드는 맵이 로드돼야 한다
`Game Default Map = /Game/Maps/PresetMaker1`이라 패키지 exe는 부팅 즉시 맵이 뜬다. 다만 갓 부팅한 상태는 **프리셋 0개·카메라 0개**의 빈 월드다. 작업하려면 `preset.load` / `car.load` / `map.load`로 데이터를 먼저 올려야 한다.

### 3-4. 부트스트랩 exe vs 실제 게임 프로세스
`Package/Windows/Park3D.exe`는 런처이고, 포트를 잡는 실제 프로세스는 `Package/Windows/Park3D/Binaries/Win64/Park3D.exe`다. 프로세스·창 핸들을 찾을 때 후자를 봐야 한다.

## 4. 사용 절차 (요약)

```
1) Package/Windows/Park3D.exe 실행           (창모드로 부팅 — 20260728_164900 문서 참조)
2) curl http://localhost:13120/health  →  {"ok":true}
3) Claude에서 park3d_catalog 로 메서드 확인
4) park3d_rpc(method, params) 로 제어
```

에디터 PIE로 하던 작업을 그대로 패키지 exe에서 할 수 있다. 차이는 **에디터·컴파일 환경이 필요 없다**는 것뿐이다.

## 5. 정리 사항

검증 중 생성한 프리셋 1개는 `preset.delete`로 제거해 `preset.list`가 `[]`임을 확인했다. 카메라 1대는 **마지막 1대라 삭제가 조용히 실패**하는 알려진 동작 때문에 남아 있으나, `preset.save`/`car.save`를 호출하지 않았으므로 **디스크에 기록된 것은 없고 exe 종료 시 함께 사라진다.**
