## 0. 요약 판정

**회귀 없음. 잔여 위험은 중간 4건 · 낮음 5건.** 코드 변경 자체는 사전 예측 범위 안에서 끝났고 기존 클램프 계약 9종이 코드 수준에서 전부 보존됐다. 남는 위험은 **코드 밖**에 있다 — 낡은 측정 기준선, 미갱신 패키지 빌드, 저장 파일의 의미 혼재, 그리고 영구히 확보 불가능해진 시각 전/후 대조.

사전 분석이 **놓친 것 1건, 틀린 것 1건**을 찾았다:
- **놓침**: 무관한 공백 변경이 diff에 섞였고, 구현 요약서가 이를 사실과 다르게 기술했다(§2-2).

## 2. 실제 변경 코드 재검토

### 2-1. 클램프 계약 9종 — 코드 수준 보존 확인

현행 구현(`CameraControlLibrary.cpp:66-85`):

```
ZoomToHFov: MaxZ = (MaxZoom<1)?1:MaxZoom → ZoomClamped = Clamp(Zoom,1,MaxZ) → RadToDeg(2·Atan(TanHalfFovDeg(DefaultHFov)/ZoomClamped))
HFovToZoom: MaxZ = (MaxZoom<1)?1:MaxZoom → if(HFov<=0) return MaxZ → Zoom = TanHalfFovDeg(DefaultHFov)/TanHalfFovDeg(HFov) → Clamp(Zoom,1,MaxZ)
```

| # | 계약 | 보존 근거(코드 경로 추적) | 판정 |
|---|---|---|---|
| 1 | `ZoomToHFov(0)` → 하한 | `Clamp(0,1,36)=1` → `2·atan(tan28.25/1)=56.5` | **보존** |
| 2 | `ZoomToHFov(-5)` → 하한 | `Clamp(-5,1,36)=1` → 56.5 | **보존** |
| 3 | `ZoomToHFov(100)` → MaxZoom 클램프 | `Clamp(100,1,36)=36` → 1.71021 | **보존** |
| 4 | `ZoomToHFov(z, MaxZoom<1)` → MaxZ=1 보정 | `MaxZ=1` → `Clamp(z,1,1)=1` → 56.5 | **보존** |
| 5 | `HFovToZoom(0)` → `MaxZ` | `if(HFov<=0) return MaxZ` **한 글자도 안 바뀜** | **보존** |
| 6 | `HFovToZoom(음수)` → `MaxZ` | 동일 조기 반환 | **보존** |
| 7 | `HFovToZoom(극소 양수)` → 상한 | `TanHalfFovDeg(0.0001)` → 0.001 클램프 → `tan=8.727e-6` → 비율 61573 → `Clamp(…,1,36)=36` | **보존** |
| 8 | `HFovToZoom(hfov > DefaultHFov)` → 하한 1 | `hfov=90` → `tan45=1` → 비율 0.537 → `Clamp=1` | **보존** |
| 9 | `HFovToZoom(h, MaxZoom<1)` → MaxZ=1 | `Clamp(…,1,1)=1` | **보존** |

**클램프의 순서도 그대로다.** `MaxZ` 계산·`Clamp` 호출·조기 반환은 diff 상 무변경 라인이며, 변경된 것은 **변환식 한 줄씩**뿐이다. 설계 §3.1 계약 9종 전부 이행.

> **파생 동작 변화 1건(무해, 설계 의도)**: 구 모델 `ZoomToHFov(1, 36, 0)` 은 `0/1 = 0` 을 **정확히 0** 으로 반환했다. 신 모델은 헬퍼 하한 클램프 때문에 `≈0.001°` 를 반환한다. 이는 "음수·NaN 화각을 만들지 않는다"는 W5 방어의 대가이며, `DefaultHFov=0` 자체가 비정상 상태이므로 실사용 영향 없다. 신규 단정 `DefaultHFov0→(0,1) 유한 양수` 가 이 성질을 명시적으로 고정한다.

| 그 상태의 `getPTZ.zoom` | `clamp(58/360, 1, 36) = 1` | `tan(28.25°)/tan(89.9995°) = 4.69e-6` → `clamp = 1` | **없음(둘 다 1)** |

**결론: 검은 화면은 `Capture->FOVAngle` 에 360 을 직접 넣은 결과이며 화각 모델과 무관하다. 구 코드에서도 똑같이 검게 나왔다. 회귀가 아니다.**

### 3-3. 다만 남는 사실

- `TanHalfFovDeg` 가드는 **라이브러리 함수 내부에만** 적용된다. `cam.setFOV` 는 라이브러리를 통과하지 않으므로 **가드가 닿지 않는다**(설계 §7.3이 명시적으로 인정한 설계 선택).
- 즉 "정의역 방어를 넣었다"는 이번 변경의 성과는 `SetZoom`/`GetZoom` 경로에만 유효하고, **`setFOV` 로는 여전히 임의의 `FOVAngle` 을 심을 수 있다.**
- 이번 범위 밖이다. 고치려면 `CamRpcModule.cpp:260` 에 입력 검증을 추가해야 하며 이는 **별도 설계 대상**이다(사용자 승인 필요).
- 실제 노출: `_workspace` 스크립트에 `setFOV` 호출 **0건**(§1-2 G-9). 사람이 수동 RPC 로 극단값을 넣을 때만 발생.

**위험 등급: 낮음(기존 동작 유지).**

## 4. 저장/로드 왕복 — UI 저장 시 기록되는 값과 파일 혼재 판정

### 4-1. UI 저장 시 기록되는 zoom — **코드로 재확인**

```
[저장] 버튼 → CameraControlWidget::CollectDirFromControls   (CameraControlWidget.cpp:755)
             → OutDir.zoom = GetControlCur(ECamCtrl::Zoom)  (:764)   ← UI 슬라이더/텍스트 배율값
             → UCameraControlLibrary::SaveToJson
```

- **`APTZCameraActor::GetZoom()`(= `FOVAngle` 역산)은 저장 경로에 존재하지 않는다.** `GetZoom()` 호출처는 여전히 RPC 응답 2곳(`CamRpcModule.cpp:211`, `RpcModuleSupport.cpp:168`)뿐이다.
- `ApplyControlToCamera`(`:470`)는 **UI → 카메라 단방향**이며 카메라 상태를 UI 로 되읽지 않는다 → **드리프트 경로 없음.**
- **답: 사용자가 UI 에 입력한 배율 숫자가 그대로 기록된다. 화각 모델을 통과하지 않는다.** 사전 §2-3 판정이 코드 수준에서 유효함을 재확인했고, QA 의 SHA-256 불변이 이를 실증했다.

### 4-2. 그런데 — **구/신 파일이 섞이면 문제가 되는가? → 스키마는 호환, 의도는 혼재한다**

**혼재가 문제되지 않는 경우 (설계 §5.3의 전제)**: `zoom` 이 **실기 PTZ 명령값**이라면, 구 파일도 신 파일도 "실기에 보낼 배율"을 담고 있으므로 의미가 동일하다. 시뮬의 화각 재현식만 고쳐진 것이므로 혼재 문제 자체가 성립하지 않는다.

**혼재가 문제되는 경우 (실제 데이터가 이쪽이다)**: `CamPos_office.json` 의 값은 **2.4 / 7.4 / 3.4 / 4.4 / 2.9** 로, 소수 첫째 자리에서 끊긴 라운드 값이다. 현장 카메라에서 읽어온 값이라면 `1.11843`, `1.35103`(→ `CamPos_40Face_동대문.json` 이 그런 형태다)처럼 임의의 소수가 나온다. **즉 `CamPos_office.json` 은 사람이 화면을 보며 다이얼로 맞춰 저장한 파일로 보인다.** 이런 파일의 숫자는 "구 모델에서 원하던 구도를 내던 값"이라는 정보를 담고 있고, 그 정보가 이번 변경으로 무효화된다.

같은 구도를 신 모델에서 재현하려면 다시 다이얼해야 하는 값:

| 기존 저장값 | 구 모델 화각 | 같은 화각을 내는 **신 모델 zoom** | 사용자가 다시 저장하면 |
|---|---|---|---|
| 2.4 | 24.167° | **2.510** | 파일에 `2.51` 이 기록됨 |
| 2.9 | 20.000° | **3.048** | `3.05` |
| 3.4 | 17.059° | **3.588** | `3.59` |
| 4.4 | 13.182° | **4.665** | `4.67` |
| 7.4 | 7.838° | **7.844** | `7.84` |

### 4-3. 판정

| 질문 | 답 |
|---|---|
| 로드가 깨지는가? | **아니다.** 스키마 무변경, 필드 추가/삭제 없음. QA 가 로드 정상·`cam.list` zoom 2.4 반영 확인 |

### 5-3. `unity/` 원본과의 의미 차이

| 출처 | 모델 | 기준 화각 | zoom=36 화각 |
|---|---|---|---|
| **Park3D (변경 후)** | 탄젠트 | **56.5°** | **1.710°** |
| `unity/CameraControl/CameraObj/CObjCamera.cs:27,235` (이 저장소 사본) | **선형** `DEFAULT_FOV / zoomClamped` | 58.0° | 1.611° |
| `unity/_MoveTmp/CPtzSpaceVehiclePlacer.cs:507-516` 이 호출하는 `CObjCamera.ZoomToHFov` | 탄젠트 `2·atan(tan(29°)/z)` | 58.0° | 1.764° |
| `unity/20260724_224837_RPC_전체_API_레퍼런스.md:424` | 탄젠트 | 58.0° | ≈1.76° |

**관찰 3건:**

1. **저장소의 `CObjCamera.cs` 사본에는 `ZoomToHFov` 메서드가 존재하지 않는다.** `CPtzSpaceVehiclePlacer.cs:516` 이 `CObjCamera.ZoomToHFov(dmaxZoom)` 를 호출하므로, **`_MoveTmp` 는 저장소에 없는 더 최신 `CObjCamera` 를 전제**한다. 즉 unity/ 사본 자체가 두 세대가 섞여 있다.
2. **모델은 이제 일치하고(둘 다 탄젠트), 상수만 어긋난다** — Park3D 56.5 vs Unity 58 = **2.65% 차**, zoom=36 에서 1.710 vs 1.764 = **3.1% 차**.
3. **메모리 [Unity 원본이 스키마 권위] 위반은 아니다.** 그 항목은 **JSON 스키마·id 진법**에 대한 것이고, `FCamDir::zoom` 의 스키마(배율 1~36)는 이번에 **바뀌지 않았다**. 바뀐 것은 렌더 파라미터이며, 이는 사양서(HNR-2036LA 광각 56.5°)라는 **더 상위 권위**를 따른 정정이다.

**남는 실질 위험**: `CPtzSpaceVehiclePlacer.cs:205` 가 `plateZoom = cam.ZoomFromFov(vFov)` 로 **VLM/데이터셋 manifest 산출식**을 갖고 있다. 그 manifest 를 Park3D 로 재현하려는 워크플로가 있다면 zoom=36 에서 **3.1% 구도 차**가 남는다. Park3D 측에 이 manifest 를 소비하는 코드는 **발견되지 않았다**(사전 §4-1 결론과 동일) → **미검증, 저장소 외부 확인 필요**.

## 8. 다음 작업자가 반드시 알아야 할 것

1. **`zoom` 은 여전히 배율(1~36)이고 저장 파일은 안 바뀌었다.** 바뀐 것은 *같은 숫자가 만드는 화각*이다. **z ≈ 1.23 에서 부호가 반전한다** — z<1.23 은 피사체가 커지고(zoom=1 에서 +3.16%), z>1.23 은 작아진다(zoom=7.4 에서 −5.65%). **단일 지점으로 판정하면 반드시 오판한다.**
2. **`_workspace/lightport/` 의 `cam` 프로파일 수치를 새 측정치와 직접 비교하지 마라.** 그리고 **사전 보고서 §4-2 의 보정 수치(+18px 바깥)는 틀렸다** — 운용 zoom 2.4 기준 실제는 **25px 안쪽**, `sky` ROI 세로 **15px**. `vp` 프로파일은 무관하다.
3. **`Package/Windows/` 는 구 규격이다**(exe 18:39 < DLL 21:27). 패키지로 검증하면 이번 변경을 **못 본다**. RPC 포트도 둘 다 13510 이므로 **PID 확인 선행**.
4. **`cam.setFOV` 는 라이브러리 가드를 우회한다**(`CamRpcModule.cpp:260`, 기존 동작). 극단값이 검은 화면을 내는 것은 **회귀가 아니고 이번 범위 밖**이다. 고치려면 별도 설계·승인이 필요하다.
5. **커밋 전에 `CameraControlLibrary.cpp:42` 의 후행 탭을 되돌려라**(`git checkout -p`). 기능 영향은 없지만 요청과 무관한 변경이다.
6. **최종 한글 문서가 아직 없다.** 소스 4개를 바꿨으므로 MCP 예외가 적용되지 않는다. 낡은 Docs 2건(§5-2)에 "정정 전 기준" 주석도 함께.
