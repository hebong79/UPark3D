# cam.captureJPG / capturePNG — width·height 로 1장만 고해상도 촬영 (보드 #991)

## 1. 요청

- 요청자: TourAgent(`claude/touragent-static-plate-1080`), 보드 #991.
- 객리단길 스태틱 카메라가 10~27 m 거리 면을 보는데 1280×720 에서는 번호판이 23~62 px 라 LPR 이 0건. 같은 장면을 1920×1080 으로 찍으면 8 m·10 m 에서 판독 성공(#990).
- 조건: **스트림은 1280×720 그대로**, 검출용 사진 한 장만 고해상도.
- 기존 동작: `cam.captureJPG {width,height}` 는 인자를 무시하고 1280×720 을 돌려줬다(`DoCapture` 가 스트림과 같은 `Cam->RenderTarget` 을 읽음).

## 2. 변경

### RPC 계약 (추가만, 기존 호출 불변)

| 파라미터 | 설명 |
|---|---|
| `width` (int, 선택) | 촬영 폭. 16..3840 으로 자름 |
| `height` (int, 선택) | 촬영 높이. 16..2160 으로 자름 |

- 둘 다 생략 → 스트림 타깃 크기(1280×720) 그대로 = 기존 동작.
- 한쪽만 주면 스트림 타깃 비율을 유지해 다른 쪽을 계산(`width:1920` → 1920×1080, `height:540` → 960×540).
- 결과가 스트림 타깃 크기와 같으면 기존 경로(`CaptureOnce` + `RenderTarget`)를 그대로 탄다.
- 응답 `width`/`height` 는 **실제 이미지 크기**. TourAgent 는 요청값과 비교해 지원 여부를 판단한다(버전 협상 없음).
- 응답에 `renderMs` 추가(렌더 + 리드백 시간, 인코딩 제외, 0.1 ms 단위). captureJPG·capturePNG 모두.

### 구현

- `APTZCameraActor::CaptureAtSize(W, H)` 신설.
  - 크기가 스트림 타깃과 같으면 `CaptureOnce()` 후 `RenderTarget` 반환.
  - 다르면 카메라별 캐시 타깃 `SizedCaptureTarget`(UPROPERTY Transient, GC 보호)을 쓴다. 포맷은 `RTF_RGBA8_SRGB` — `InitRenderTarget` 과 같은 감마 규약(선형 포맷이면 JPEG 이 어둡게 나온다).
  - 크기가 바뀔 때만 `InitAutoFormat`+`UpdateResourceImmediate`. 같은 크기를 반복 요청하면 재생성하지 않는다.
  - `Capture->TextureTarget` 을 캐시 타깃으로 바꾸고 `CaptureScene()` 후 **즉시** `RenderTarget` 으로 되돌린다. `CaptureScene` 은 호출 시점의 타깃으로 렌더 명령을 넣으므로 스트림 프레임에 섞이지 않는다. `RenderTarget` 은 재초기화하지 않는다.
- `CamRpcModule.cpp`: `ResolveCaptureSize` 로 크기 해석, `DoCapture` 가 `CaptureAtSize` 결과 타깃을 읽는다.
- `cam.captureStats` 는 손대지 않았다(요청 범위 밖).
- `APTZCameraActor` 를 부모로 하는 블루프린트는 Content 에 없다(grep 확인) → UPROPERTY 추가로 인한 쿠킹 WBP `Bad export index` 류 위험 없음.

### 메모리

- 캐시 타깃은 카메라당 하나, 요청된 크기만큼. 1920×1080 RGBA8 ≈ 8 MB, 최대 3840×2160 ≈ 33 MB. 고해상도를 한 번도 요청하지 않은 카메라는 만들지 않는다.

| 항목 | 결과 |

| 작업본 Work13540(포트 13540, LV_Park_01, camId 2) | 아래 |

RPC 실측(`hires_test.py`):

| 요청 | 응답 width×height | 실제 JPEG |
|---|---|---|
| `{}` | 1280×720 | 1280×720 |
| `{width:1920,height:1080}` | 1920×1080 | 1920×1080 |
| `{width:1920}` | 1920×1080 | 1920×1080 |
| `{height:540}` | 960×540 | 960×540 |
| `{width:5000,height:5}` | 3840×16 | 3840×16 |
| `{width:1280,height:720}` | 1280×720 | 1280×720 |
| capturePNG `{1920,1080}` | 1920×1080 png | 1920×1080 |
| 이후 `{}` | 1280×720 | 1280×720 (스트림 타깃 복원 확인) |

- **구도 동일성**: 1080 판을 1280×720 으로 줄여 720 판과 평균 절대차 12.4(0~255). 같은 설정 720 두 장을 시차를 두고 찍은 기준 차가 13.0 이라 시간 흐름 잡음 이하 → 구도·밝기 동일. 나란히 놓은 캡처로도 확인.
- **스트림**: MJPEG(13962) 을 받는 동안 1920×1080 을 20회 연속 촬영 — 스트림 프레임 크기는 전부 1280×720 한 종류, 스트림은 끊기지 않았다(촬영 중 1.56 fps, 직후 2.00 fps). `cam.streamStatus` 의 `channelFps` 30 불변.
- **renderMs**: 이 작업본은 정본과 함께 돌아 게임 fps 가 2.9(프레임 340 ms)였다. 그래서 기본 1280 촬영도 1300~1700 ms, 1920 연속 촬영은 610~720 ms 로 나왔다 — **요청서의 ~55 ms 와 비교할 수 없는 환경 값**이다. 같은 환경에서 1280 과 1920 이 같은 수준이라는 것까지만 확인했다.
